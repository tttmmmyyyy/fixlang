# 構造体の引数をフィールドごとの引数に割り、作った構造体をその場で読む

## 直すもの

`Iterator` の組み合わせ子は、渡された関数を自分の構造体のフィールドに置く。

```fix
type MapIterator i a b = unbox struct { iter : i, f : a -> b };
map = |f, iter| MapIterator { iter : iter, f : f };
```

`closure_specialization` が関数の値を追う道は「引数として渡された関数」と「持ち上げられたラムダの
キャプチャリストのフィールドに入った関数」の 2 つで、構造体のフィールドはどちらでもない。だから
`f` はクロージャの値のまま残り、`fold` は要素ごとに間接呼び出しをする (#450)。組み合わせ子を
重ねると、その間接呼び出しが段の数だけ並ぶ (#452)。

## 採る形

パスを 2 つ置く。1 つ目が `f` を引数の位置へ出し、2 つ目が引数へ渡る道を通す。

### 1. 構造体の引数をフィールドごとの引数に割る (`split_struct_args`)

グローバル関数 `f` の第 i 引数が非ボックス構造体 `T { g0 : A0, .., gn : An }` で、本体がそれを
分解しているとき、2 つに割る。

```
f#split_arg<i> : .. -> A0 -> .. -> An -> ..;
f#split_arg<i> = |p0, .., x0, .., xn, ..| <f の本体から分解を除いたもの>;

f = |p0, .., pi, ..| (
    let T { g0 : x0, .., gn : xn } = pi;
    f#split_arg<i>(p0, .., x0, .., xn, ..)
);
```

`f` は型も意味も変わらないので、**呼び出し側は 1 か所も書き換えない**。1 周につきグローバル 1 つに
つき引数 1 つを割り、プログラムが動かなくなるまで繰り返す。フィールドが構造体ならそれは twin の
引数になり、次の周がそれを割る。だから
`FilterIterator { MapIterator { ArrayIterator { arr, idx }, f }, pred }` は
`(arr, idx, f, pred)` へ 1 段ずつ平らになる。

割った後に残る wrapper は「構造体を分解してフィールドを渡す」形で、これは割る対象の形そのものである。
だから wrapper は割らない。割るべきものは twin の側に在る。

twin にも wrapper にも局所名を付け直す。フィールドはパターンが与えた名前を持ち、構造体に入れ子に
なった構造体は同じ名前でフィールドを取り出すパターンで分解されるので、2 周割ると 1 つの名前の
引数が 2 つ並ぶ。

### 2. 作った構造体を、それを分解する側で読む (`collapse_constructions`)

`inline` が wrapper を呼び出し側へ入れると、そこには「構造体を作る式」と「それを分解する
パターン」が並ぶ。作ってすぐ分解する値は、実行時に、プログラムがすでに言っていることを訊いている。
そこで次の 4 つを不動点まで回す。

- **構造体を作った所で読む。** `let T { g : a } = s` で `s` が `T { g : x }` として作られていれば、
  `a` は `x` である。
- **union を作った所で読む。** 作られた variant が分かっている値への `match` は、その variant が
  選ぶ腕そのものである。
- **場合分けの中へ `match` を入れる。** `match` の走査対象が場合分け (`match` または `if`) で、その
  腕がすべて variant を作るなら、読む側の `match` を各腕へ移す。移した先では各腕が「作った所」に
  なるので、上の規則が消す。腕どうしが読む側の相異なる腕を選ぶ形でだけ移す。そうすれば腕の本体は
  1 つも複製されず、1 周ごとにプログラムは小さくなる。
- **フィールドの式を名前に落とす。** 構造体のフィールドが式なら、先に名前へ束縛する。読む側へ渡せる
  のは名前であって、式を渡すとその式が 2 度評価される。

構造体とそれを読む側は 1 本の `let` の鎖に並んで初めて出会うので、周と周の間に `pull_let` で `let`
を外へ巻き上げ、`unique_local_names` で局所名を一意にする。

3 つ目の規則が要るのは、`Iterator` の `advance` が `Option (Self, Item)` を返すからである。組み合わせ子の
`advance` は、内側の `advance` の結果を `match` して、腕ごとに `Option` を作り直す。`fold` はそれを
`match` する。この往復を越えないと、再帰呼び出しで関数の同一性が失われ、1 要素目だけが特殊化される。

## なぜこの形か

**正しさが構成で決まる。** `split_struct_args` の wrapper は元の signature と元の意味を持ち、twin は
元の本体そのものである。`collapse_constructions` の 4 つはどれも、その場に見えているものだけを見て
書き換える。どれも「この本体に在るこの型の値はすべて〜」という全称の主張を必要としない。型検査が
呼び出し側の更新を強制するので、割り忘れはコンパイルエラーになる。

**組み合わせ子の重ね (#452) も解ける。** 割るのを繰り返せば、内側の `f` も外側の `pred` も引数に
なる。フィールドの道を 1 段から n 段へ広げる必要が無い。

## パス列のどこに置くか

```
.. -> defunctionalize_fix -> inline -> inline_local
    -> split_struct_args -> inline -> collapse_constructions -> closure_specialization -> ..
```

- `inline_local` の後にするのは、`fold` の本体が構造体の引数を分解するのは `advance` がそこへ
  入った後だからである。その前に置くと `advance` だけが割れる。
- `collapse_constructions` の前に `inline` を置くのは、wrapper が呼び出し側へ入って初めて構造体と
  それを読む側が出会うからである。
- `closure_specialization` の前に置くのは、そこが読む名前を作るのがこの 2 つだからである。

どちらも `Max` 以上で走る。

## 割る条件

正しさには要らない。引数が無闇に増えるのと、割っても損になる形を避けるための条件である。

- 引数の型が、プログラムが宣言した**非ボックス**の構造体で、穴の開いたフィールドを持たない。
- フィールドが 1 つ以上ある。
- 本体がその引数を分解している。分解しないなら、割っても中身は使われない。
- 割った後の引数の総数が 24 を超えない。
- **戻り値の型がその構造体の型構成子を含まない。** 渡された種類の値をそのまま返す関数は、呼び出し側で
  必ず組み立て直される。分解を呼び出し側へ移すだけになる。

最後の条件が効くのは `FilterIterator` の `advance` である。これは自分自身を再帰的に呼ぶので `inline`
が `fold` へ入れられず、グローバルとして残る。これを割ると `fold` が要素ごとに 3 段の構造体を分解し、
`advance` が同じものを組み立て直して返す。この条件を入れる前は `map+filter+fold` が 21% 遅くなっていた。

## 測ったもの

1 要素あたりの命令数。`(I(11) - I(1)) / 10 / 300000` を `perf stat -e instructions:u` で取る。

| chain | 前 | 後 |
|---|---|---|
| `map` | 14.00 | **0.84** |
| `map` + `map` | 22.00 | **0.97** |
| `map` + `to_array` | 20.01 | **12.01** |
| `filter` | 20.02 | 20.02 |
| `map` + `filter` + `fold` | 29.02 | 29.02 |
| `map` + `filter` + `to_array` | 33.04 | 33.04 |

`filter` を含む形が動かないのは、`FilterIterator` の `advance` が自分自身を再帰的に呼ぶために
`fold` へ入らないからである (#453)。

## 付録: 潰れた形

### `advance` を割る

`filter` だけの形は、この条件を入れる前は 20.02 から 15.00 になっていた。`advance` を割ると
`filter` 単体は速くなり、`map` を挟むと遅くなる。取ったのは、`filter` 単体の 25% よりも
2 本の 21% と 23% の退行を避けるほうである。

### 周と周の間に `inline` を走らせる

wrapper が呼び出し側へ入れば呼び出し側にも分解が現れるので、そこを次の周で割れる。そうすると
`filter` 単体が 15.00 から 20.02 へ戻り、`map+filter` の退行は消えなかった。
