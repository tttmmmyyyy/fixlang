# closure specialization の連鎖を延ばす (#166 / #131)

Fix の最適化パス `closure_specialization` を延ばして、`Array::sort` の実行命令を 13% 減らす。

実測の数字は本文から外し、付録 A にまとめてある。

---

## 1. 目標

`Array::sort` は、実行する命令の **13%** を「比較関数がクロージャのままであること」に払っている。

比較関数はユーザが渡すラムダである。それがクロージャ (捕まえた変数を抱えた値) のまま渡り歩くと、
比較のたびにその値の参照カウントを上げ下げする必要がある。`sort` の比較回数は約 420 万回で、
比較を実際に行う関数だけで `sort` の実行命令の 37% を占める。

13% は上限の推定ではなく実測値である (付録 A.1)。

そして、**参照カウント操作を減らす既存の最適化はここに原理的に届かない**。#122 で入った locality
推論は、呼び出し元で分かっている「この値は他から参照されていない」といった性質を呼び出し先へ
持ち込み、参照カウントの操作を省くものである。呼び出し地点ごとに違う版を作れることが前提になる。
ところがクロージャは間接的に呼ばれるので、呼び出し地点がその関数を名指ししない。名指しできない
以上、版を分けることも、呼び出し元の性質を持ち込むこともできない。

**名指しできるようにすること**、それがこのパスの仕事である。

---

## 2. パスがやっていること

`closure_specialization` は 2 つの技法を持つ。用語もここで決める。

### 2.1 技法 A: 持ち上げ (decapturing)

ラムダを、**捕まえた変数を詰めたもの**と、**それを引数に取るグローバル関数**の 2 つに分解する。

```fix
let n = 3;
let f = |x| x + n;      // n を捕まえたラムダ
```

これが次のようになる:

```fix
// 捕まえた変数を詰めたもの。以降これを「キャプチャリスト」と呼ぶ。
type Cap = unbox struct { n : I64 };

// キャプチャリストを第 1 引数に取るグローバル関数。以降これを「持ち上げ済みラムダ」と呼ぶ。
lam : Cap -> I64 -> I64;
lam = |{ n : n }, x| x + n;

let f = Cap { n : 3 };   // ラムダの値は、ただのキャプチャリストになる
```

`f(5)` という呼び出しは `lam(f, 5)` になる。**キャプチャリストそのものは関数ではない。** 呼ぶには持ち上げ済み
ラムダの名前が要る。

ラムダの正体が分からない場所へキャプチャリストを渡すときは、`lam` にそれだけを部分適用した `lam(f)` を渡す。
これは元どおりのクロージャなので、型も振る舞いも変わらない。**以降「正体の分かっているラムダを
渡している」とは、渡す式がこの `lam(キャプチャリスト)` の形、すなわち式の頭が持ち上げ済みラムダの名前である
ことを指す。**

キャプチャリストの型名には、捕まえた変数の名前と型の並びが埋め込まれる。以降のコード例で
`Cap<n : I64>` のように山括弧付きで書いてあるのは、この埋め込みを省略せずに書いたものである。

### 2.2 技法 B: 特殊化 (specialization)

クロージャを引数に取るグローバル関数を、**渡されるラムダごとに複製**する。

```fix
fold : S -> (A -> S -> S) -> Iter -> S;
fold = |s, op, iter| ( ... );      // 第 2 引数を op と呼ぶ
```

`fold` に上の `f` を渡す箇所があれば、`fold` の複製を作る。その複製の中では `op` を間接的に呼ぶ
代わりに `lam` を名前で直接呼ぶ。間接呼び出しが消え、`op` の参照カウント操作も消える。

複製を作れるのは、**渡すものの正体が分かっている呼び出し地点だけ**である。だから技法 B は技法 A
の上に乗っている。

### 2.3 連鎖が要る理由

`sort` の比較関数は、1 段では届かない。

```
sort
  |- _introsort_by_internal      <- 比較関数を受け取る
       |- 下請けのソート関数      <- 比較関数をそのまま下へ渡すだけ (中継役)
            |- 内側のループ       <- 比較関数を実際に呼ぶ
```

特殊化が `_introsort_by_internal` で止まると、その先はクロージャのまま渡り、比較のたびに参照
カウント操作が残る。比較回数は約 420 万回である。**連鎖を末端まで延ばして初めて 13% が取れる。**

実際にどの関数が「内側のループ」だったかは §9 に書く。§5 の設計は経路を名指ししないので、この
図の細部に寄りかかってはいない。

## 3. パスの骨格

この節は、**本ブランチの修正 (§4 の障壁 1 と 2) を入れた後**のパスを書く。修正の中身は §4 で
説明する。

以降の節が提案する変更のうち、条件 2・条件 3・条件 5 の削除と、表の解き方の変更は既に入っている
(§8 の 2 から 4 段目)。この節はそれらを入れる前の姿なので、§6 と §7 の議論の出発点として読む。

### 3.1 全体

```
run(プログラム):
    表 = 特殊化できる関数を計算する(プログラム)         // 3.3 で説明する
    安定集合 = {}

    変化がなくなるまで繰り返す:

        // 第 1 段: 全シンボルを 1 つずつ歩く
        要求 = []
        各シンボル s について:
            s が安定集合にあるなら飛ばす
            s の中のラムダを持ち上げ、グローバル関数として登録する
            s の中の呼び出しのうち、表に載っている関数へ
              正体の分かっているラムダを渡しているものを見つけたら:
                その呼び出しを、特殊化版の名前を呼ぶ形へ差し替える
                要求に「この関数を、この引数にこのラムダが来る形で作れ」を積む
            s が何も変わらなかったなら、s を安定集合に入れる

        // 第 2 段: 積んだ要求を実体化する
        要求が空になるまで:
            要求を 1 つ取り出す
            その名前の本体が既にあるなら、何もしない
            元の関数の本体をコピーし、
              「この引数はこのラムダだ」と分かった状態でコピーを歩く
            歩く途中で立った新しい要求を積む

        表 = 特殊化できる関数を計算する(プログラム)     // 増えた関数を含めて作り直す
```

### 3.2 呼び出しの差し替えと、本体を作ることは別々

第 1 段が積む「要求」は、この形をしている。

```rust
// 「この関数を、この引数にこのラムダが来る形で作れ」という要求。
struct SpecializationRequest {
    // 複製する元の関数。
    func: FullName,
    // 引数の位置 -> そこへ来る持ち上げ済みラムダの名前。
    args: Map<usize, FullName>,
}
```

以降、この `(func, args)` の組を、その特殊化の**キー**と呼ぶ。

第 1 段が呼び出しを差し替える時点で、差し替え先の本体はまだ存在しない。それでも成り立つのは、
**特殊化された関数の名前が、本体を作る前に決まる**からである。名前は

```
func + "#closure_spec_" + args のハッシュ
```

から機械的に作れる。本体が無くても呼び出しは書ける。

この決め方の帰結として、**同じキーの要求が何度立っても、本体は 1 つに共有される**。要求を実体化
するとき、その名前の本体が既にあれば作らない。以降この打ち切りを**同じキーは 1 度しか実体化
しない**と書く。

### 3.3 「特殊化できる関数」の表

第 1 段が引くこの表は、**どの関数のどのパラメータなら複製する価値があるか**を全プログラム分
まとめたものである。

```rust
// 関数 -> 特殊化できるパラメータの位置。
type Specializable = Map<FullName, Set<usize>>;
```

表に載っていない関数は、どんな呼び出し地点があっても複製されない。

```
特殊化できる関数を計算する(プログラム):
    表 = {}
    呼び出しグラフを、呼ばれる側が先に来る順に並べる
    その順に各関数 f について:

        f が自分の強連結成分の別の関数を呼ぶなら、f 全体を飛ばす      // 条件 3

        f の各パラメータ i について:
            i の型がクロージャでないなら飛ばす                        // 条件 1

            f が自分自身を呼んでいて、その呼び出しが位置 i まで引数を
              持っていて、かつ位置 i に渡しているのが i 自身でないなら飛ばす
                                                                      // 条件 2

            転送 = i が、表に載っている関数の
                        「特殊化できるパラメータ」へ渡されている
            届く = (i が f の中で呼ばれている) または 転送             // 条件 4
            価値 = f が自己再帰
                   または f が呼び出し地点に展開できるほど小さい
                   または 転送                                         // 条件 5

            届く かつ 価値 なら、表[f] に i を足す
    表
```

**関数 f が「特殊化できる関数」**とは、表に載っていること、すなわち上を満たすパラメータを 1 つ
以上持つことである。以降、条件 4 の後半を「**転送**」と呼ぶ。

条件 2 の書き方が回りくどいのは、実装がそうなっているからである。自己呼び出しが 1 つも無い関数
は条件 2 を満たす (中継役はこれで通る)。部分適用で位置 i まで引数が届いていない自己呼び出しも
条件 2 を満たす。弾かれるのは「位置 i に、i 以外の何かを渡している自己呼び出しがある」場合だけ
である。

条件には性質の違うものが混ざっている。条件 1 は型の話、条件 2 と条件 3 は無限ループを防ぐための
もの (§7 で扱う)、条件 4 と条件 5 は複製の見合いの話 (§6 で扱う) である。

**定義が自分を参照している。** 条件 4 と条件 5 の「転送」が、表そのものを参照する。地に足がつく
のは条件 4 の前半「f の中で呼ばれている」で、そこから呼ぶ側へ伝わる。`sort` の経路ではこうなる。

```
_heap_down_ranged       less_than を自分で呼ぶ              <- 条件 4 前半で成立 (基底)
  ^
_heap_sort_by_ranged    less_than を _heap_down_ranged の   <- 転送で成立 (伝播)
                        特殊化できるパラメータへ渡す
  ^
_introsort_by_internal  同上                                 <- さらに伝播
```

疑似コードが「呼ばれる側が先に来る順」に並べているのは、この伝播を 1 回舐めで解くためである。
f を処理する時点で、f が呼ぶ関数はすべて表に載っている。強連結成分の**中**には順序が無いが、
条件 3 が成分の他のメンバーを呼ぶ関数を丸ごと外すので、表を引く相手は必ず処理済みになる。
**条件 3 は無限ループを防ぐためだけでなく、この順序を成立させるためにも置かれている。**

### 3.4 外側のループの役目

第 1 段と第 2 段の全体を繰り返しているのは、**第 1 段が動いている最中にプログラムが増える**
からである。増えるのは持ち上げ済みラムダと特殊化の複製で、どちらもその周の第 1 段はまだ見て
いない。周 2 以降が歩いているのは、ほとんどが前の周で生まれたシンボルである (付録 A.5)。

繰り返しが要る理由は 2 つある。

1. **新しく生まれたシンボルを歩く。**
2. **表を作り直す。** 表は第 1 段の前に計算されるので、周 1 の表には周 1 が作る関数が載りようが
   ない。新しい関数が特殊化の対象になるには、作り直すしかない。

要らないのは、前の周で変化したシンボルの再走査である。安定の印が付くのは「歩いてみて何も変わら
なかった」ときなので、変化したシンボルは必ずもう 1 周歩かれ、そこで初めて安定と分かる。

**§5 の設計では、このループ自体が無くなる。** 持ち上げを先に完遂してしまえば、第 1 段が動いて
いる最中にプログラムが増えることも、表を作り直す必要も無くなるからである。

## 4. いま連鎖が切れている場所

障壁が 3 つある。1 と 2 は本ブランチで直した (§3 は修正後の姿である)。

### 4.1 障壁 1 (#131): 「誰に渡したか」を記録していなかった

パスは「ある名前がどう使われているか」を調べる補助関数を持つ。用途の 1 つは「**この引数は、
どの関数の何番目の引数として渡されたか**」を記録することである。

その記録が、渡された先の関数名ではなく、**調べている名前自身**を書き込んでいた。調べている名前
は必ずローカル変数なので、記録を読む側の「グローバル関数でなければ無視」という条件が毎回成立
し、**転送が一度も真にならなかった**。伝播の経路が塞がっていたので、条件 4 は前半だけで判定
されていた。

**修正済み**: 呼ばれた関数の名前を記録するようにした。

### 4.2 障壁 2: 中継するだけの関数が「複製する価値なし」と判定されていた

障壁 1 を直すと、中継役でも条件 4 が真になる。しかし**条件 5 が落としていた**。修正前の条件 5
は「自己再帰である」か「呼び出し地点に展開できるほど小さい」かの 2 択で、中継役はまさに自己
再帰でなく、中継するくらいなので小さくもない。`_heap_sort_by_ranged` がその形である。

**修正済み**: 条件 5 に「転送」を足した。中継役の複製にも価値がある — 複製の中では下流へ渡す
ものの正体が分かっているので、下流もまた特殊化できる。

この 2 つを直すと、中継役の複製 `_heap_sort_by_ranged#closure_spec` は**実際に生成されるように
なる**。しかし `sort` の命令数は改善しない (付録 A.2)。その先の `_heap_down_ranged` に複製が
無く、複製が 1 つ増えた分のコードだけが増えるからである。

### 4.3 障壁 3: 特殊化された引数が、呼び出しではなくキャプチャリストに入る

`_heap_sort_by_ranged` の中身はこう書かれている。

```fix
range_step(n/2-1, -1, -1).fold(arr, |i, arr| arr._heap_down_ranged(less_than, ...))
```

比較関数 `less_than` を下流へ渡す `_heap_down_ranged` の呼び出しは、**`fold` に渡すラムダの中に
ある**。

第 1 段でこのラムダが持ち上げられる。`less_than` はそのキャプチャリストに入る。

```fix
_heap_sort_by_ranged#closure_lam1 = (
    |#closure_cap| ( |i| ( |arr| (
        let Cap<#param : (I64, I64) -> Bool, ...> {#param, ...} = #closure_cap;  // 分解する
        ...
        _heap_down_ranged(#param, ...)      // <- 連鎖に必要な呼び出しはここにある
    ))))
);
```

第 2 段で `_heap_sort_by_ranged` の複製を作るとき、`less_than` の正体は分かっている。**しかし
そのときにはもう `_heap_down_ranged(less_than, ...)` という呼び出しが複製の本体に無い。** 第 1 段
で別のグローバル関数の中へ移動してしまっている。複製の本体には代わりに、
`Cap<#param : ..., ...>{...}` というキャプチャリストを組み、それを `fold` の複製へ渡す式が立っている。

**連鎖は「特殊化された引数が、呼び出しに渡されるのではなくキャプチャリストに詰められる」ところで切れている。**

紛らわしいので明示しておくと、`fold` の特殊化そのものは成功している。

```
_heap_sort_by_ranged の複製
  |- fold の複製            <- 直接呼び出しになっている
       |- closure_lam1      <- ここも名前で呼ばれている
            |- _heap_down_ranged(#param, ...)   <- #param の正体が分からない
```

`closure_lam1` に到達するまでの経路はすべて直接呼び出しである。切れているのは**その中身**で、キャプチャリスト
から取り出した `#param` が、比較関数の正体を持たないまま `_heap_down_ranged` へ渡される。だから
直すべきは「`closure_lam1` に届く経路」ではなく、「`closure_lam1` の中で `#param` の正体を知って
いる版を作ること」である。

issue #166 はこれを「持ち上げ先が空の表で始まる」と書いている。ここでの「表」は §3.3 の表では
なく、歩いている間だけ持つ「ローカル名 -> その正体であるラムダ」の対応のことである。現象として
は正しいが、**持ち上げのときに正体を引き継げば直る、というものではない**。第 1 段の時点で
`less_than` はまだただの引数であり、正体が分かるのは第 2 段だからである。順序の問題であって、
引き継ぎの問題ではない。

## 5. 設計: 正体を型に持たせ、包み直しをいつでも許す

### 5.1 追いかける境界と、諦める境界

「どのラムダか」という知識は、値が関数の境界を越えるたびに失われる。境界を 1 つずつ塞ぐときりが
ないので、**追いかける境界を先に決めて閉じる**。

持ち上げが終わった後、値が関数の中へ入ってくる経路は次の 2 つである。

1. **通常の引数**
2. **キャプチャリストのフィールド** — キャプチャリストは 1 個の引数で、本体の先頭で分解される

この 2 つを追いかける。以下は**追いかけない**と決める。

- **構造体 (タプルを含む) のフィールドに入れて取り出したラムダ**
- **`Array` に入れて取り出したラムダ** — 実行時に選ばれるので、どのラムダかは静的に決まらない
- **`Option` などの union に入れて取り出したラムダ** — 同じ理由
- **関数がクロージャを返す場合** — `f >> g` のような合成が該当するが、これはインライン展開で
  ラムダ式に潰れており、返り値としてクロージャが渡り歩く形はほぼ残らない
- **`defunctionalize_fix` が作ったキャプチャリストのフィールド** — 再帰を扱う別のパスが、この
  パスと同じ仕組みで自前のキャプチャリストを作り、このパスより前に走る。ユーザのクロージャが
  そちらのキャプチャリストに入って関数へ入ってくる経路がありうるが、作り手が別なので今回は対象にしない

追いかけない経路に入った値は、いまと同じくクロージャのまま扱われる。**正しさは失われず、最適化
が効かないだけ**である。

なお、構築地点が 1 つで途中に合流が無い場合は、前段の最適化が `S { f : L }.@f` を `L` に畳んで
しまうので、このパスが見る頃には構造体が消えていることがある。畳める範囲で得をするのは前段の
おかげであって、この設計の守備範囲ではない (付録 A.4)。

### 5.2 正体を型に持たせる

キャプチャリストのフィールドの型を、一般のクロージャ型から「そこに入る特定のラムダのキャプチャ
リスト型」へ差し替えることを、以下**狭める**と呼ぶ。狭めると

- そのフィールドは関数ポインタを持たなくなり、捕まえた環境だけになる
- そのフィールドを通る呼び出しは、ラムダを名前で直接呼ぶ形に書ける
- 参照カウントの操作が消える

`sort` の 13% はこの 1 点にある。

**狭めた結果を型で表す。** 正体の分かっているクロージャ値がどんなものかは、次の木で書ける。

```rust
// どのラムダのキャプチャリストで、どのフィールドがどう狭まっているか。
// 載るのは狭めたフィールドだけで、残りは元のまま。キャプチャリストの
// フィールドは大半が普通の値 (I64 や Array) で、狭めようがない。
struct Tree {
    lambda: FullName,
    fields: Map<usize, Tree>,
}
```

そして**不変条件を 1 つ置く**。

> キャプチャリストの型構成子は、木と 1 対 1 である。木が違えば型が違い、型が同じなら木も同じ。

いまの型構成子はフィールド名と型の並びから名前が作られるので、**捕まえる変数がたまたま一致する
別々のラムダが同じ型を共有する**。すると型を見てもどのラムダが消費するのか決まらない。名前
に持ち主のラムダを埋め込んで一意にすれば、この曖昧さは消える。**キャプチャリストの型が呼び先を決める**という
のが、この設計が寄りかかる土台である。

### 5.3 包み直しをいつでも許す

もう 1 つ不変条件を置く。これが設計の要である。

> 木 `t` を作ったら、その場で `t` に対応する「狭めた版のラムダ関数」も要求する。したがって木
> `t` のキャプチャリスト `b` は、どんな場所でも `unit_name(t)(b)` と包んで一般のクロージャに戻せる。

なぜこれが要るか。狭めていないキャプチャリストは、いつでも持ち上げ済みラムダに部分適用すれば一般のクロージャに戻る
(§2.1)。**狭めたものにはその戻り道がない** — 対応する狭めた版のラムダ関数が無ければ包めない。戻り
道が無いと、狭めるかどうかの判断が「**このキャプチャリストのすべての出現が狭めた型を受け付ける**」という
全数条件になる。全数条件は判断を非局所にし、判断どうしが噛み合わなくなる。

戻り道があれば、**どの地点も「駄目ならその場で包む」で完結する**。ある地点で狭めなかったことが、
別の地点で下した判断を無効にしない。これで「キャプチャリストを組む地点」「それを渡す地点」「表」「まだ本体の無い
複製」の 4 者が合意を取る必要そのものが無くなる。

#### 包みを剥がすときは、プログラムを書き換えない

包む規則と剥がす規則は同じ歩きの中で両方向に働くので、**剥がす側が式を書き換えると、包む側に
新しい仕事が生まれる**。これは実際に無限ループになった。

inline LLVM 式は変数しか読めないので、その中でキャプチャリストを使うときは包んだ形を別の名前に束縛して読ませ
る。その束縛を「包みが挟まっているだけ」と見て剥がすと、LLVM 式がまたキャプチャリストを読むことになり、また
包んで新しい名前を作る — 名前が伸び続けて、1 シンボルの処理が終わらなくなる。

したがって規則を 1 つ置く。

> 束縛から正体を読むときは、その束縛を書き換えない。束縛は自分の正体を、それが束縛する名前に
> 貸すだけである。裸のキャプチャリストが要る地点は、その束縛が正体を得た場所から直接読む。

使われなくなった束縛は死んだコードとして後段が落とす。剥がす側が何も書き換えないので、包む側に
新しい仕事が生まれず、循環が構造的に起きない。

### 5.4 パスの形

```
run(プログラム):
    第 L 相: 持ち上げだけを完遂する
    表 = 特殊化できるスロットを計算する(プログラム)
    第 S 相: ユニットの要求が尽きるまで実体化する
```

**第 L 相**は、全シンボルのラムダを持ち上げ、キャプチャリストの使用をすべて包み直した形にする。持ち上げで生ま
れたラムダ関数も対象に積み、新しいラムダが生まれなくなるまで回す。この相が終わった時点で

- **出どころの集合が確定し、以後増えない。** 出どころ = ソースに書かれた関数と、この相が作った
  ラムダ関数。§7.4 の「出どころは増えない」が、論証ではなくパスの形として成り立つ。
- 本体にラムダ式は残らない。正体の分かる値は「素のキャプチャリスト」と「それを包んだクロージャ」の 2 つの形で**構文と型に
  残る**。歩いている間だけの知識ではなくなる。

**呼び出しの引数として書かれたラムダも、この相で持ち上げる。** 持ち上げた結果は素のキャプチャリストではなく
包んだ形にする。これは §5.3 の「包み直しはいつでも合法」の系で、値としては元のクロージャと同じ
ものである。ここを第 S 相に残すと、複製ごとに新しいラムダ関数が生まれ、出どころが増える。増えた
出どころは固定表の見出しに載っていないので、§7.4 の停止規則が効かなくなる。第 S 相の終わりに
「この walk はラムダを 1 つも持ち上げなかった」ことを assert して、この不変条件を守る。

**表**は出どころだけを載せ、1 度だけ解いて以後更新しない。出どころが増えないので、「新しく生まれ
た関数について表をその場で足す」という要求が消える。

**第 S 相**は、次を単位にしたワークリストである。

```rust
// origin の本体を、スロットごとの木で置き換えて 1 度だけ実体化する単位。
struct UnitKey {
    origin: FullName,
    subst: Map<Slot, Tree>,   // 空なら origin そのもの
}
```

**「特殊化された関数」と「狭めた持ち上げ済みラムダ」の区別は無い。** 後者は `origin` がラムダで
`subst` の鍵がキャプチャスロットなだけの、同じ単位である。

外側のループは無い。安定の印も、周をまたぐ持ち回しも要らない。

### 5.5 表: 出どころの上の最小不動点

スロットが表に載る条件は、次の選言である。

```
スロット s に届く =
      s に来る値が本体で呼ばれている                                      (基底)
   or s に来る値が、表に載っている関数のスロットへ引数として渡されている  (転送)
   or s に来る値が、表に載っているラムダのキャプチャフィールドに捕まえられている
                                                                          (捕獲転送)
```

3 つ目が新しい。第 L 相の後は「ラムダに捕まえられて下流へ渡る」がキャプチャリストの構築として
現れるので、これを見ないと `sort` の連鎖が繋がらない。名前の使われ方を調べる補助関数に、この形
を報告させる。

```rust
enum UsageType {
    CalledAsFunction,
    FunctionArgument(FullName, usize),
    // キャプチャリストの構築で、フィールドに捕まえられた。
    CapturedInto(FullName /* ラムダ */, usize /* フィールド */),
}
```

型構成子が一意なので、構築式を見ればどのラムダのどのフィールドかが決まる (§5.2)。

### 5.6 書き換えは 4 つの規則で尽きる

**R1 構築** — キャプチャリストを組む地点。各クロージャ型フィールドについて、そこへ来る値の正体
が分かっているなら:

> 表がそのキャプチャスロットを載せていて、かつ §7 の停止規則が許すなら、フィールドを狭める。

通ったフィールドの集まりが木になる。木ができたら**その場でラムダの単位を要求する** (§5.3 の不変
条件)。拒否されたフィールドは包んだまま残す。それだけで完結する。

**R2 引数** — 呼び出しの地点。正体の分かっている引数について:

> 表がその引数スロットを載せていて、かつ停止規則が許すなら、狭めた形で渡す。

通った引数を集めて単位を要求し、呼び先をその名前に差し替える。拒否された引数は包んだまま渡す。

**R3 正体の分かった呼び出し** — キャプチャリストを通る呼び出しと、それを包んだクロージャへの呼び出しは、対応する単位の名前
へ差し替える。**ここに判定は無い。** キャプチャリストの型が木なので呼び先は型から決まり、その単位は木が生まれ
た時点で要求済みである。

**R4 既定** — 上のどれにも当たらないキャプチャリストの出現は、すべて包む。値として読まれる、配列や union に
入る、対象外の構造体に入る、inline LLVM が読む — 全部ここに落ちる。したがって**見落とした出現の
形は、健全性ではなく最適化の取りこぼしにしかならない**。

### 5.7 `sort` がどう解ける

```
_heap_sort_by_ranged を less_than = 木 t0 で実体化する
  |- 本体を歩く。less_than の正体は t0
       |- R1: Cap_L1{ #param : less_than, ... } を組む地点で #param を狭める
       |      -> 木 t1 = L1{ #param : t0 }。t1 のラムダ単位を要求する
       |- R2: それを fold へ渡す。木 t1 で fold の単位を要求する
            |- t1 のラムダ単位を歩く。#param の正体は t0
                 |- R2: _heap_down_ranged へ渡す。木 t0 で単位を要求する
                      |- _heap_down_ranged は自己再帰で同じ位置へ渡すので、以降は同じ規則で回る
```

**中継層を後から作り直す工程が無い。** `fold` の単位は最初から深い木 `t1` で要求されるので、
正しい型で 1 度だけ作られる。

これは規則の道すじを追った例であって、`sort` で実際に狭まった箇所ではない。実際の箇所は §9 に
書く。

### 5.8 型の波及はパスが自分で書く

このパスは型推論の後に走るので、式の型を変えたらプログラムへの波及はパスの仕事である。狭めた
キャプチャリストは当該フィールドの型が変わるので、

- 木から型構成子を作り、プログラムの型環境に登録する
- その型でキャプチャリストを組む側 (構築地点) を書き換える
- その型を分解する側 (単位の本体の先頭) を書き換える

を書く。機械的だが分量はある。

## 6. 複製する価値をどう判定するか

§3.3 の条件 5 は 3 択で、そのうち「呼び出し地点に展開できるほど小さい」だけが**関数の大きさ**を
見ている。他の条件はすべて「そのパラメータがどう使われるか」を見ている。この 1 つだけ性質が
違う。

特殊化で得られるものは「間接呼び出しが直接呼び出しになること」と「その先が解析可能になること」
であって、その大きさは**パラメータが呼ばれる回数**に比例する。関数自身の大きさとは関係がない。
むしろ**大きい関数の中でクロージャが熱く呼ばれている場合こそ特殊化が効く**のに、条件 5 は自己
再帰でない限りそれを外す。

Rust はクロージャの型でジェネリック関数を単相化する。渡されたクロージャごとに複製が作られ、
大きさは判定しない。それで実用になっている。**関数の大きさで複製の可否を決めるのは、特殊化と
インライン展開を取り違えている。**

ただし Fix と Rust には違いがある。Rust ではクロージャに統一表現が無いので、複製は**必須**で
ある (複製しない選択肢が無い)。Fix はクロージャを統一表現で持てるので、複製は**常に任意**で
あり、コード量と間接呼び出しの取引になる。したがって Rust をそのまま真似るのではなく、取引を
どこで管理するかを決める必要がある。

**提案**: 条件 5 を丸ごと落とし、条件 4 だけにする。条件 4 は「この複製が実際に何かを得る」を
言っているので、これだけが判定として意味を持つ。§4.2 で条件 5 に足したばかりの「転送」は、条件 4
の後半と同じものなので、条件 5 ごと落としても失われない。コード量は §8 の各段で測り、悪化する
ケースが出たらそのとき上限を置く根拠にする。

これで価値の判定は次の 1 行になる。

> そのパラメータを自分で呼ぶか、別の関数の「特殊化できるパラメータ」へ転送しているなら、
> 複製を作る。

## 7. 停止性

### 7.1 いまの 2 つの条件

§3.3 の条件のうち、無限ループを防ぐために置かれているのは次の 2 つである。

- **条件 2**: 自己呼び出しが、そのパラメータを同じ位置へそのまま渡していること。回るたびに引数
  が変わる形はここで弾かれる。
- **条件 3**: 同じ強連結成分の別の関数を呼ぶ関数は、特殊化対象から丸ごと外す。条件 2 は自己
  呼び出ししか見ないので、閉路が別の関数を経由する場合の代わりとして置かれている。

条件 3 は §3.3 のとおり表を作る順序も担っているので、落とすなら表を最小不動点で解き直す必要が
ある。

条件 3 が実際に効く場面は、見た目より狭い。このパスの前にインライン展開が走るので、小さな相互
再帰は片方が他方に取り込まれて自己再帰になっており、条件 3 の判定に届く前に相互再帰が消えて
いる。条件 3 が効くのは、インライン展開後も残る相互再帰だけである (付録 A.3)。

### 7.2 何が無限を生むのか

条件 2 が弾いているのは、この形である。

```fix
grow : I64 -> (I64 -> I64) -> I64;
grow = |n, op| (
    if n == 0 { op(0) };
    grow(n - 1, |x| op(x) + n)     // 受け取ったラムダを包んで次の周へ渡す
);
```

**いまのパスでは、この形でも無限にはならない。** 持ち上げが済むと、`grow` の本体にラムダ式は
残っていないからである。

```fix
type Cap = unbox struct { op : I64 -> I64, n : I64 };

L : Cap -> I64 -> I64;                        // |x| op(x) + n が持ち上げられた姿
L = |{ op : op, n : n }, x| op(x) + n;

grow = |n, op| (
    if n == 0 { op(0) };
    grow(n - 1, L(Cap { op : op, n : n }))    // 組んで L に部分適用しているだけ
);
```

再帰呼び出しが渡す式の頭は、何周しても `L` という同じ名前である。キャプチャリストの中身は周ごとに違うが、キー
は名前で決まるので、2 周目以降ずっと同じキーになる。§3.2 の「同じキーは 1 度しか実体化しない」
で打ち止めになる。

この「本体にラムダ式が残らない」は、パスの前段が**関数の引数に置かれたラムダをすべて `let` へ
括り出し**、`let` に束縛されたラムダは表と無関係に必ず持ち上げられる、という 2 つの性質から来て
いる。複製の本体は持ち上げ済みの本体をコピーしたものなので、複製の中で新しいラムダが持ち上がる
こともない。**この性質は §7.4 の停止性でも使う。**

**無限が現れるのは §5 を入れてからである。** §5 はキーをキャプチャスロットへ広げる。すると
`grow` は次のように回る。

| 周 | `grow` の複製 | その中で組むキャプチャリスト | `L` の複製 | 次の周へ渡るもの |
| ---: | --- | --- | --- | --- |
| 1 | `op = L` で特殊化 | スロット `op` に `L` が入る | `L1 = L[op:=L]` | `L1` |
| 2 | `op = L1` で特殊化 | スロット `op` に `L1` が入る | `L2 = L[op:=L1]` | `L2` |
| 3 | `op = L2` で特殊化 | ... | `L3 = L[op:=L2]` | `L3` |

キャプチャリストの型も同じ深さで入れ子になる (`Cap{op: Cap{op: ...}, n}`)。名前も型も止まら
ない。**条件 2 を落とすなら、代わりの止め方を §5 と同時に入れる必要がある。**

### 7.3 ハッシュコンスでは止まらない

持ち上げ済みラムダの名前を**内容のハッシュ**で決めれば、構造的に同じラムダは同じ名前になる。
これで名前の集合が閉じるかを上の表で確かめると、閉じない。

`L1` の内容は「`L` の本体、ただし `op` は `L`」、`L2` の内容は「`L` の本体、ただし `op` は
`L1`」である。**内容が実際に違う**ので、ハッシュも違う。何周しても同じにならない。

止まる形にするには、閉路を**まとめて**ハッシュする必要がある — 再帰的な定義の集まりを 1 つの形
として扱い、その形からハッシュを作る。しかしそれには「いま閉路の中にいる」ことを検出する仕組み
が先に要る。**閉路を検出できるなら、ハッシュを作らずにその場で結び目を閉じればよい。** した
がってハッシュコンスは停止性の答えにならない。

ハッシュコンスには別の値打ち (構造的に同じラムダが 1 つになる) があるが、それは重複の削減で
あって停止性ではない。

### 7.4 提案: 「どの関数のどのスロットに、どの系統のラムダ」ごとに 1 つへ固定する

魔法の数字を使わずに止める方法がある。先に言葉を 3 つ決める。

**出どころ.** §5.4 の第 L 相が終わった時点で確定する集合、すなわちソースに書かれた関数と、その
相が作ったラムダ関数である。単位 (§5.4) はどれも `origin` を陽に持つので、辿る必要はない。
**この集合は第 S 相の間ずっと増えない。**

**受け継ぎの道すじ.** 要求はかならず何かの単位を歩いている途中で立ち、要求から単位が作られ、
その単位を歩くとまた要求が立つ。この「単位 -> 要求 -> 単位 -> ...」の列を**受け継ぎの道すじ**と
呼ぶ。

**固定表.** 道すじに沿って持ち回る対応表である。**「どの関数のどのスロットに、どの系統のラムダを
入れるか」を見出しにして、「その道すじで実際に入れてよいラムダ 1 つ」を引く。**

```rust
// 固定表の見出し。
struct PinKey {
    // 特殊化される単位の出どころ。grow の単位はどれも "grow"。
    func: FullName,
    // その関数のどの入口か。
    slot: Slot,
    // そこへ入れようとしている木の根のラムダ。木が違っても根が同じなら同じ見出し。
    lambda: FullName,
}

// 見出し -> その道すじで入れてよい木。
type Pinned = Map<PinKey, Tree>;

// 要求は単位の鍵と、それを立てた道すじの固定表を運ぶ。
struct UnitRequest {
    key: UnitKey,
    pinned: Pinned,
}
```

`grow` の例で言えば、道すじの上に

```
PinKey { func: grow, slot: op, lambda: L }  ->  木 L{}
```

という行が立つ。読み方は「**この道すじでは、`grow` の単位の `op` スロットに根が `L` の木を入れ
るなら、入れてよいのは `L{}` だけ**」である。あとから `L{op: ...}` (根は同じ `L`) を入れようと
すると、見出しは同じで値が違うので通らない。

見出しにスロットが入っていることに意味がある。同じ関数の別々のスロットに、同じ系統の別々の
ラムダが入るのは正当な形なので、そこまで止めては効かせすぎになる。

持ち回り方を決める。

- 第 S 相の種となる単位 (置き換えの無いもの) の固定表は空である。
- 要求を立てるとき、歩いている単位の固定表を**複製**し、その要求の分を書き足したものを、その
  要求に持たせる。
- 要求から作られた単位は、その固定表を自分のものとして持つ。

複製して渡すので、同じ単位から立った 2 つの要求は互いに影響しない。

規則はこうである。判定するのは §5.6 の R1 と R2 の 2 箇所だけで、木が新しく生まれるのもこの
2 箇所だけである。

> 木 t をスロット s へ入れようとするとき、見出し
> `PinKey { func: 歩いている単位の出どころ, slot: s, lambda: t の根 }` を固定表に引く。
>
> - 載っていなければ、そこへ t を載せて通す。
> - 載っていて、値が **t と同じ木**なら通す。
> - 載っていて、値が **t と違う木**なら通さない。

通さなかった地点は、そこで**包む** (§5.3)。狭めないことは常に安全なので、正しさは失われない。
そして包める保証があるので、通さなかったことが他の地点の判断を壊さない。

#### 3 つの形に当てはめる

**(a) 自己再帰で素通しする形** — `fold` や `_heap_down_ranged`。

```fix
fold = |s, op, iter| ( ... iter.fold(op(a, s), op) ... )    // op をそのまま渡す
```

最初の要求で `{ fold, op, F } -> 木 F{}` が固定される。単位の中の再帰呼び出しは同じ木を同じ
スロットへ渡すので、見出しも値も一致して通る。そして単位の鍵が最初の要求と同じなので実体化は
打ち切られ、そこで終わる。**一番効かせたい形が、そのまま通る。**

**(b) 引数が 2 つあり、片方だけ違う形** — `h(F, G1)` と `h(F, G2)`。

固定表は要求ごとに複製されるので、同じ単位の中に並んだこの 2 つは互いに影響しない。仮に一方が
他方の単位の中にあったとしても、`G1` と `G2` はソース上の別のラムダなので根が違い、見出し
`{ h, 第 2 スロット, G1 }` と `{ h, 第 2 スロット, G2 }` は別の行になる。`F` のほうはどちらも
同じ木なので通る。**どちらの要求も通る。**

**(c) 回るたびに包む形** — §7.2 の `grow`。

`K` をユーザが書いた `|x| x`、`L` を `|x| op(x) + n` が持ち上げられた姿として、道すじを辿る。

| 段 | 規則 | 見出し | 固定表 | 判定 |
| ---: | --- | --- | --- | --- |
| 1 | R2: `grow` の `op` へ木 `K{}` | `{ grow, op, K }` | 空 -> `K{}` | 通す |
| 2 | R1: `L` の `op` フィールドへ `K{}` | `{ L, op, K }` | 空 -> `K{}` | 通す。木 `t1 = L{op:K}` |
| 2 | R2: `grow` の `op` へ `t1` | `{ grow, op, L }` | 空 -> `t1` | 通す |
| 3 | R1: `L` の `op` フィールドへ `t1` | `{ L, op, L }` | 空 -> `L{op:t1}` | 通す。木 `t2` |
| 3 | R2: `grow` の `op` へ `t2` | `{ grow, op, L }` | 値は `t1` | **通さない** (`t2` は違う木) |

最後の地点は包む (§5.3) — `t2` のキャプチャリストを一般のクロージャに戻して、一般の `grow` へ渡す。ここで
打ち止めになる。条件 2 が何も許さないのに比べれば、その分の直接呼び出しを得る。

#### 停止する論証

1 本の道すじを取る。その上で、出どころ O の単位がいくつ現れうるかを数える。

単位を決めるのは「どのスロットを置き換えたか」と「各スロットに何を入れたか」である。後者は固定表
が縛る — スロット s に入る木の根を P とすると、見出し `{ O, s, P }` に対して使える木は道すじの
上で 1 つに固定されている。したがってスロット s の取りうる値は「置き換えない」か「根 P ごとに
1 つずつ定まる木」のいずれかで、**根の個数だけの有限の選択肢**である。スロットの個数も有限なの
で、**出どころ O の単位は、1 本の道すじの上に有限個しか現れない。**

根になりうるのは第 L 相が確定させたラムダだけで、その集合は第 S 相の間ずっと増えない (§5.4)。
したがって道すじに現れる単位は全部で有限個である。同じ鍵は 1 度しか実体化しないので、道すじは
単位を作り尽くしたところで必ず終わる。

固定表を導入する前は、この論証が立たない。§7.2 の表のように、同じ根 `L` からいくらでも違う木が
作られ、`grow` の単位もそのたびに新しいものになるからである。

#### 同じキーを違う固定表で要求したとき

単位の本体は、実体化したときの固定表によって変わりうる (深い道すじでは内側の判定が通らず、包み
直しが残る)。一方 `UnitKey` は出どころと置き換えだけで決まり、固定表を含まない。したがって
**同じ鍵の要求が違う固定表で立つと、先に実体化したほうの本体が共有される。**

これは受け入れる。正しさも停止性も損なわれず、失うのは「浅い道すじから来た要求が、深い道すじの
都合で保守的に作られた本体を掴む」ことによる最適化の取りこぼしだけである。固定表をキーに含める
と、同じ本体が固定表の違いだけで何通りも作られ、コード量が跳ねる。**取りこぼしを引き受けて、
コード量を抑える**方を採る。

#### 条件 2 と条件 3 は要らなくなる

規則は自己呼び出しか相互再帰かを区別しない。固定表を受け継ぐだけなので、閉路が何段であっても
同じ判定になる。条件 3 が担っていたもう 1 つの役 (§3.3 の表を作る順序) は、表を最小不動点で解く
ことで既に置き換えてある。

#### 幅には予算を置く

上の論証は「単位は有限個」までしか言っていない。固定表が縛るのはスロット 1 つ 1 つで、単位を
決めるのは複数のスロットの**組**なので、独立に狭まるスロットを持つ関数は組み合わせだけ複製を
持つ。有限ではあるが現実的ではなく、クロージャを 6 個受け取って全部呼ぶ関数 1 つで、複製 800 個
とメモリ 1.8 GB になる。

そこで、**出どころあたり、ラムダを 2 つ以上名指す複製の個数に上限を置く**。判定は R1 と R2 の
2 箇所で、上限に達した出どころの新しい複製は要求せず、その地点は §5.3 のとおり包む。

**数えるのは、その複製が名指すラムダの個数が 2 以上のものだけである。** 積になって増えるのは
それで、ラムダを 1 つしか名指さない複製は「その入口に来る値 1 つにつき 1 個」なので、呼び出し
地点の個数に対して線形にしか増えない。置き換えた入口の**個数**で測ると足りない — 木は入れ子に
なるので、1 段につき 1 フィールドだけ狭める形が、どの階層でも入口 1 つのまま増えられる。

**上限は「基底 8 + 要求したソース位置の個数」で伸びる。** 出どころごとの固定枠だと、無関係な
呼び出し地点どうしが枠を取り合い、同じ関数を 17 箇所から別々のクロージャで呼ぶだけで特殊化が
黙って切れる。位置で伸ばすと、横に並んだ地点は自分の分を自分で持ち込み、同じ位置から何度も
要求する連鎖 (複製の本体は同じテキストの複製なので、そうなる) だけが上限に当たる。数えられる
複製の総数はプログラムテキストの大きさに線形になる。

コーパスには数えられる単位が 1 つも無いので、生成物は変わらない。

固定表は残る。予算だけにすると、§7.2 の `grow` のような深さの暴走が予算を丸ごと食い潰し、
16 個の複製がすべて「1 段深いだけの同じもの」に費やされる。**固定表は魔法の数字なしに深さを
止め、予算は幅を止める。**

問題の機構、退けた案、実測は `copy-budget.md` に書いた。

### 7.5 テストの主張が変わる

本ブランチで `changing_closure` というテストを足した。`grow` と、閉路を一周する間に 1 回だけ
ラムダが包まれる形の 2 つを持つ。主張は「複製は作られるが、**複製の複製は作られない**」で、
連鎖が尽きることを直接見ている。

この主張は**原理的に落ちない**ことが分かった。単位の名前は `origin` の名前から作られ、`origin`
は必ず第 L 相が残したシンボルなので、`#closure_spec` が 2 つ並ぶ名前は存在しえない。ケースの
値打ちは「この形でパスが暴走しないこと」なので、複製個数の上限に差し替えた。停止規則が壊れた
ときの実際の現れ方は**ビルドが終わらないこと**で、規則を外した版で 120 秒打ち切りを確認した
(§7.2 の無限の実測でもある)。

**連鎖が末端まで届いたことの回帰テスト**として `relayed_closure` を足した。`relay` は自分では
クロージャを呼ばず、`fold` に渡すラムダのキャプチャリスト経由でしか下流へ渡さない。末端の関数に
複製ができるのは狭めが働いたときだけなので、`narrow` を潰した版でこのテストが落ちることを確かめ
てある。これが無いと、連鎖が切れても答えが変わらないので誰も気づかない。

## 9. 前提の確認

設計の前提として挙げてあったものの結果を書く。

**比較関数がどの経路で末端へ届くか。** 実装後の `sort` を見ると、狭められたのは
`_insertion_sort_by_ranged` と `_introsort_by_internal` の中で組まれるキャプチャリストで、
`_heap_down_ranged` には複製が作られていない。それでも 13% を超える利得が出た。**§2.3 で書いた
`_heap_sort_by_ranged` 経由の経路は、実際に効く経路ではなかった**ということである。§5 の設計は
経路を名指ししないので、この読み違いに関係なく効いた。

狭めた後のラムダの本体はこうなる。比較関数は名前で直接呼ばれ、`#param` は関数ポインタを持たない
素のキャプチャリストである。

```
_insertion_sort_by_ranged#closure_lam0#closure_lam0#closure_spec = |#closure_cap, #v12| (
    let #CapList@..._spec<#param : #CapList@Main::main#closure_lam1<>, ...> {#param : #param, ...}
        = #closure_cap;
    ...
    if Main::main#closure_lam1(#param, #v17) { ... }
);
```

**この形がコーパスに何箇所あるか。** 46 ケースのうち動いたのは 3 つで、`sort` -43.88%、
`cp_lib_conv_zp` -5.23%、`cp_lib_bipartite` -0.26%。残る 43 ケースは 1 命令も動かない。

**型構成子が増えるコスト。** `sort` に生まれたキャプチャリストの型は 11 種、型構成子の名前は最長
113 文字だった。コンパイル時間は測定の揺れの内、実行ファイルは同じか小さくなる (付録 A.8)。

**§7.2 の無限を実測した。** §7.4 の規則を外した版で `changing_closure` をビルドすると、120 秒で
打ち切るまで終わらない。

**正体はフィールドの型が持つ。** 持ち上げ済みラムダのキャプチャリストが別のキャプチャリストを
持つとき、その正体は分解する `let` のところで失われていた。狭めた版を作る経路だけがフィールドの
木を持ち回っていたためである。フィールドの型がどの値かを言っている (§5.2 の不変条件) ので、分解の
地点でその型から正体を読んで、束縛する名前へ渡す。狭めた版かどうかを問わない 1 つの規則になった。

## 10. 一度書いて捨てた実装

§5 を「持ち上げ済みラムダの複製を、要求のたびに作る」形で一度実装した。狙いどおり狭めた
キャプチャリストが生成され、`sort` は基準比 -2.06% になったが、停止性のテストケースが落ちた。
そこから健全性の条件を足していくと、条件が互いに干渉して「片方が通るともう片方が止まる」状態に
なり、進まなくなった。

**原因は、狭めたキャプチャリストに包み直す手段が無かったことである。** 対応する狭めた版のラムダ関数は、特殊化
の要求が通ったときにしか作られなかった。戻り道が無いので、狭めるかどうかの判断が「このキャプチャリストの
**すべての**出現が狭めた型を受け付ける」という全数条件になる。全数条件は判断を非局所にし、
`fold` の自己再帰で自己参照を呼び込み、組む側と渡す側が別々の時点の表を見て食い違った。

§5.3 の不変条件はこの経験から来ている。**木を作った時点でその単位も要求する**ようにすれば、包み
直しが常に合法になり、各地点は「駄目ならその場で包む」で完結する。合意を取る必要そのものが
無くなる。

捨てた実装の差分は残していない。残す価値のある知見は上の 1 段落と §5.3 に写してある。

### A.3 条件 2 と条件 3 を外すとどうなるか

以下の 3 つの形を 1 つのプログラムに書いて測った。

```fix
// (1) 自己再帰。次の周へ渡すのは、受け取ったラムダを包んだ別のラムダ。
grow : I64 -> (I64 -> I64) -> I64;
grow = |n, op| (
    if n == 0 { op(0) };
    grow(n - 1, |x| op(x) + n)
);

// (2) 相互再帰。受け取ったラムダをそのまま渡し合う。
ping : I64 -> (I64 -> I64) -> I64;
ping = |n, op| (
    if n == 0 { op(1) };
    pong(n - 1, op)
);
pong : I64 -> (I64 -> I64) -> I64;
pong = |n, op| (
    if n == 0 { op(2) };
    ping(n - 1, op)
);

// (3) 相互再帰。閉路を一周する間に 1 回だけラムダが包まれる。
tick : I64 -> (I64 -> I64) -> I64;
tick = |n, op| (
    if n == 0 { op(3) };
    tock(n - 1, |x| op(x) + 1)
);
tock : I64 -> (I64 -> I64) -> I64;
tock = |n, op| (
    if n == 0 { op(4) };
    tick(n - 1, op)
);

main : IO () = (
    let a = grow(4, |x| x);            // 10
    let b = ping(4, |x| x * 10);       // 10
    let c = tick(4, |x| x * 100);      // 302
    println((a + b + c).to_string)     // 322
);
```

**条件 2 を外したコンパイラで (1) と (3) をビルドすると、ビルドは成功し、`grow` と `tock` の複製
はそれぞれ 2 個で止まった。** 答えも正しい。§7.2 の論証のとおりである。

**条件 3 は (2) を止めていなかった。** `pong` の複製が生成されている。生成物を読むと、`pong` が
呼んでいるのは `ping` ではなく `pong` 自身だった。インライン展開が `ping` の本体を `pong` に
取り込んで自己再帰にしてしまうので、条件 3 の判定に届く前に相互再帰が消えている (§7.1 に反映
済み)。

(1) と (3) は `src/tests/test_closure_specialization/cases/changing_closure` として本ブランチで
テストに入れた。

| 形 | `apply_many` の複製 | 結果 |
| --- | ---: | --- |
| 構築地点が 1 つで、そのまま `h.@op` を渡す | 2 個 | 構造体経由の呼び出しも特殊化された |

このパスの所要時間は `cp_lib_scc` で合計 0.011 秒、最適化全体が 0.078 秒だった。

### A.6 3 段目の中立性

表の作り方を 1 回舐めから最小不動点へ変えたとき、生成物が変わらないことを直接確かめた。
`cp_lib_bipartite` を新旧のコンパイラでビルドし、

- RC IR のダンプが完全一致
- 実行ファイルの `.text` セクションがバイト単位で一致 (差分はビルド ID とパス文字列だけ)

コーパスでは 7 ケースが数十命令だけ動いたが、いずれも `cp_lib_*` で、同じバイナリを測り直しても
同じ幅で揺れるケースである。

### A.7 R1 を入れたときの `sort`

| 版 | 実行命令数 | メモリ参照 |
| --- | ---: | ---: |
| 6 段目の組み替えまで | 64,091,751 | 87,023,828 |
| R1 と R3 まで | 35,921,169 | 45,565,240 |
| 差 | **-43.96%** | **-47.64%** |

目標の 13% (A.1) は「capture object の参照カウント操作だけを消す」計測用ビルドから来ている。
実測がそれを大きく超えたのは、狭めたキャプチャリストが参照カウントを消すだけでなく、比較関数の
呼び出しを直接呼び出しに変え、そこから先のインライン展開を開けるからである。

### A.8 コーパス全 46 ケース

命令数が動いたケースだけを挙げる。残る 43 ケースは 1 命令も動かない。

直前の版に対して:

| ケース | 実行命令数 | メモリ参照 |

| `cp_lib_conv_zp` | -5.23% | -6.64% |
