# closure specialization の連鎖を延ばす (#166 / #131)

対象コミット: `2b03bc28`。測定は `benchmark/speedtest/cases/sort`、cachegrind、`-O experimental`、
`--disable-cpu-feature 'avx512.*'`。

この文書はコンパイラのソースを開かずに読めるように書く。登場する用語はすべてここで定義する。

---

## 1. 取りに行くもの

`Array::sort` は、実行する命令の **13%** を「比較関数がクロージャのままであること」に払っている。

比較関数はユーザが渡すラムダである。それがクロージャ (捕まえた変数を抱えた値) のまま渡り歩くと、
比較のたびにその値の参照カウントを上げ下げする必要がある。`sort` の比較回数は約 420 万回。
比較を実際に行う関数だけで `sort` の実行命令の 37% を占める。

この 13% という数字は推測ではない。#122 の作業中に、**capture object の参照カウント操作だけを
消した計測用ビルド** (健全ではないが数字は取れる) で `sort` を測ると -13.04% で、参照カウントの
分岐を全部外した上限とちょうど一致した。つまり `sort` の伸びしろは全部この 1 経路にある。

そして **#122 の locality 推論はここに原理的に届かない**。クロージャは間接的に呼ばれるので、
呼び出し地点がその関数を名指ししない。名指しできない以上、呼び出し地点ごとに違う版を作ることも、
呼び出し元の性質を持ち込むこともできず、単一の版しか持てない。

---

## 2. このパスがやっていること

`closure_specialization` パスは 2 つの技法を持つ。用語もここで決める。

### 技法 A: decapturing (ラムダの持ち上げ)

ラムダを、**捕まえた変数を詰めた箱**と、**その箱を引数に取るグローバル関数**の 2 つに分解する。

```fix
let n = 3;
let f = |x| x + n;      // n を捕まえたラムダ
```

これが次のようになる:

```fix
// 捕まえた変数を詰めた箱。以降これを「キャプチャリスト」と呼ぶ。
type Cap = unbox struct { n : I64 };

// 箱を第 1 引数に取るグローバル関数。以降これを「持ち上げ済みラムダ」と呼ぶ。
lam : Cap -> I64 -> I64;
lam = |{ n : n }, x| x + n;

let f = Cap { n : 3 };   // ラムダの値は、ただの箱になる
```

`f(5)` という呼び出しは `lam(f, 5)` になる。**箱そのものは関数ではない**。呼ぶには持ち上げ済み
ラムダの名前が要る。

### 技法 B: specialization (関数の特殊化)

クロージャを引数に取るグローバル関数を、**渡されるラムダごとに複製**する。

```fix
fold : S -> (A -> S -> S) -> Iter -> S;
```

`fold` に上の `f` を渡す箇所があれば、`fold` の複製を作り、その複製の中では `op` を間接的に
呼ぶ代わりに `lam` を名前で直接呼ぶ。間接呼び出しが消え、`op` の参照カウント操作も消える。

### 2 つの技法の関係

技法 B が効くには、渡されるものが技法 A で分解済みである必要がある。**箱の正体が分かっている
呼び出し地点でしか、複製は作れない。**

## 3. 連鎖が要る理由

`sort` の比較関数は、1 段では届かない。

```
sort
  └─ _introsort_by_internal      <- 比較関数を受け取る
       └─ _heap_sort_by_ranged   <- 比較関数をそのまま下へ渡すだけ (中継役)
            └─ _heap_down_ranged <- 比較関数を実際に呼ぶ。ここが 37%
```

特殊化が `_introsort_by_internal` で止まると、その先はクロージャのまま渡り、`_heap_down_ranged`
の中で 420 万回の参照カウント操作が残る。**連鎖を末端まで延ばして初めて 13% が取れる。**

## 4. パスの動く順序

ここから先の説明に必要なので、パスが何をどの順でやるかを書く。

### 4.1 歩きながら持つ表

パスは関数の本体を上から歩く。歩く間、「**この名前は、持ち上げ済みのどのラムダを指しているか**」
という表を持っている。ラムダを持ち上げたときにその名前を表へ書き、以降その名前に出会ったら
正体が分かる、という使い方をする。以降この書き込みを「**表に載せる**」と書く。

表に載っている名前が、特殊化できる関数の引数として渡されているのを見つけた瞬間が、特殊化の
きっかけである。

### 4.2 特殊化は「呼び出しの差し替え」と「本体を作ること」に分かれる

特殊化のきっかけを見つけたとき、パスは 2 つのことをする。**この 2 つは同時ではない。**

- **呼び出し側の差し替えは、その場で即座に行う。** `fold(op, xs)` という式を、
  `fold#closure_spec_<ハッシュ>(box, xs)` に書き換える。
- **その名前の関数の本体を作ることは、後回しにする。** 「この関数を、この引数にこのラムダが
  来る形で作れ」という要求を控えておく。

順序が逆でも成り立つのは、**特殊化された関数の名前が、本体を作る前に決まる**からである。
名前は「元の関数名 + `#closure_spec_` + どの引数にどのラムダが来たかのハッシュ」から機械的に
作れるので、本体がまだ存在しなくても呼び出しは書ける。

名前がハッシュで決まることの帰結として、**同じ関数に同じラムダを渡す呼び出しが何箇所あっても、
本体は 1 つに共有される**。要求を実体化するとき、その名前の本体が既にあれば作らない。

### 4.3 2 段構え

上の分担があるので、パスは 2 段で動く。

**第 1 段: プログラムの全シンボルを 1 つずつ歩く。**
ラムダを持ち上げ、表に載せ、特殊化のきっかけを見つけたら呼び出しを差し替えて要求を控える。
この段が終わった時点で、**呼び出しは既に特殊化された名前を指しているが、その名前の本体はまだ
存在しない**。

**第 2 段: 控えた要求を実体化する。**
元の関数の本体をコピーし、「この引数はこのラムダだ」と**表に載せた状態で**そのコピーを歩く。
歩く途中で新しいきっかけが立てば、そこでも呼び出しが差し替わり、要求が積まれる。積まれた要求
がなくなるまで同じ段で繰り返す。**連鎖が伸びるのはここ**である。

さらにこの 2 段全体を、変化がなくなるまで繰り返す。持ち上げで生まれたグローバル関数は次の周回
で 1 つのシンボルとして歩かれる。**そのとき表は空から始まる** — 別のシンボルを歩いたときの表は
持ち越さない。

### 4.4 「特殊化できる関数」の定義

第 1 段が始まる前に、パスは**どの関数のどのパラメータなら複製する価値があるか**を全プログラム
分まとめて計算し、表にしておく。以降この表を引いて特殊化のきっかけを判定する。表に載っていない
関数は、どんな呼び出し地点があっても複製されない。

**関数 f の第 i パラメータが「特殊化できる」**とは、次の 5 つがすべて成り立つことである。

| | 条件 | 何のためか |
| --- | --- | --- |
| 条件 1 | 第 i パラメータの型が**クロージャ型**である | 複製する意味があるのはクロージャだけ |
| 条件 2 | f の**自己呼び出し**が、そのパラメータを**同じ位置へそのまま**渡している | 停止性 |
| 条件 3 | f が**自分の強連結成分の他の関数**を呼んでいない | 停止性 |
| 条件 4 | f の本体で、そのパラメータが**自分で呼ばれている**か、**別の関数の「特殊化できるパラメータ」へ渡されている** | 複製が何かを得るか |
| 条件 5 | f が**自己再帰**である、または**呼び出し地点に展開できるほど小さい**、または**別の関数の「特殊化できるパラメータ」へ渡している** | 複製する価値があるか |

**関数 f が「特殊化できる関数」**とは、上を満たすパラメータを 1 つ以上持つことである。

#### 定義が自分を参照している

条件 4 と条件 5 の後半が、**この定義自身を参照している**。地に足がつくのは条件 4 の前半
「自分で呼ばれている」で、そこから呼ぶ側へ伝わっていく。`sort` の経路で言えばこうなる。

```
_heap_down_ranged       less_than を自分で呼ぶ              <- 条件 4 前半で成立 (基底)
  ^
_heap_sort_by_ranged    less_than を _heap_down_ranged の   <- 条件 4 後半で成立 (伝播)
                        特殊化できるパラメータへ渡す
  ^
_introsort_by_internal  同上                                 <- さらに伝播
```

#### 計算の順序

この表は**呼ばれる側から呼ぶ側へ** 1 回舐めるだけで作る。呼び出しグラフを強連結成分ごとに
トポロジカル順に並べ、下流から順に登録していく。f を処理する時点で、f が呼ぶ関数は
すべて表に載っている。

強連結成分の**中**には順序が無いが、条件 3 が「成分の他のメンバーを呼ぶ関数は丸ごと外す」と
言っているので、表を引く相手は必ず処理済みである。**条件 3 は停止性のためだけでなく、この順序を
成立させるためにも置かれている** (§8.3)。

## 5. 連鎖がどこで切れるか

障壁が 3 つある。1 と 2 は本ブランチで直した。

### 障壁 1 (#131): 「誰に渡したか」を記録していなかった

パスは「ある名前がどう使われているか」を調べる補助関数を持つ。用途の 1 つは
「**この引数は、どの関数の何番目の引数として渡されたか**」を記録することである。

その記録が、渡された先の関数名ではなく、**調べている名前自身**を書き込んでいた。調べている
名前は必ずローカル変数なので、記録を読む側の「グローバル関数でなければ無視」という条件が毎回
成立し、**§4.4 の条件 4 の後半 (別の関数の特殊化できるパラメータへ渡している) が一度も真に
ならなかった**。伝播の経路が塞がっていたので、条件 4 は前半 (自分で呼ぶ) だけで判定されていた。

59 個のプログラムで数えた実測では、条件 4 の後半は全プログラムで 0 件だった。

**修正済み**: 呼ばれた関数の名前を記録するようにした。

### 障壁 2: 中継するだけの関数が「複製する価値なし」と判定される

障壁 1 を直すと、中継役でも条件 4 は真になる。しかし**条件 5 が落とす**。中継役はまさに自己
再帰でなく、中継するくらいなので呼び出し地点に展開できるほど小さくもない。
`_heap_sort_by_ranged` がその形である。

**修正済み**: 条件 5 に「別の関数の特殊化できるパラメータへ渡している」を足した。中継役の複製に
も価値がある (複製の中では、下流へ渡すものの正体が分かっているので、下流もまた特殊化できる)
からである。

### 障壁 1 と 2 を直した結果 (実測)

| | `sort` 命令数 | 差 |
| --- | ---: | ---: |
| `2b03bc28` (基準) | 64,037,014 | — |
| 障壁 1 + 2 | 64,106,502 | **+0.11%** |

中継役の複製 `_heap_sort_by_ranged#closure_spec` は**実際に生成されるようになった**。
一方、その先の `_heap_down_ranged` に複製は無く、わずかに悪化する。複製が 1 つ増えた分の
コードだけが増えて、狙った効果は出ていない。

### 障壁 3: 特殊化された引数が、呼び出しではなくキャプチャリストに入る

`_heap_sort_by_ranged` の中身はこう書かれている。

```fix
range_step(n/2-1, -1, -1).fold(arr, |i, arr| arr._heap_down_ranged(less_than, ...))
```

比較関数 `less_than` を下流へ渡す `_heap_down_ranged` の呼び出しは、**`fold` に渡すラムダの中に
ある**。

第 1 段でこのラムダが持ち上げられる。`less_than` はそのキャプチャリストに入る。生成物を読むと
こうなっている (実測):

```fix
_heap_sort_by_ranged#closure_lam1 = (
    |#closure_cap| ( |i| ( |arr| (
        let Cap<#param : (I64, I64) -> Bool, ...> {#param, ...} = #closure_cap;  // 箱を分解
        ...
        _heap_down_ranged(#param, ...)      // <- 連鎖に必要な呼び出しはここにある
    ))))
);
```

第 2 段で `_heap_sort_by_ranged` の複製を作るとき、`less_than` は表に載る。**しかしそのときには
もう `_heap_down_ranged(less_than, ...)` という呼び出しは複製の本体に無い。** 第 1 段で別の
グローバル関数の中へ移動してしまっている。

実測: 生成された複製の本体 60 行に `_heap_down_ranged` は 1 度も現れず、代わりに
`Cap<#param : (I64,I64) -> Bool, ...>{...}` という箱を組んで `closure_lam1` を呼んでいる。

**連鎖は「特殊化された引数が、呼び出しに渡されるのではなく箱に詰められる」ところで切れている。**

### 切れているのは `fold` ではない

紛らわしいので明示する。`fold` の特殊化そのものは**成功している**。実測すると、`fold` の複製が
`closure_lam1` を**名前で直接呼んでいる**。

```
_heap_sort_by_ranged の複製
  └─ fold の複製            <- 直接呼び出しになっている
       └─ closure_lam1      <- ここも名前で呼ばれている
            └─ _heap_down_ranged(#param, ...)   <- #param の正体が分からない
```

`closure_lam1` に到達するまでの経路はすべて直接呼び出しである。切れているのは**その中身**で、
箱から取り出した `#param` が、比較関数の正体を持たないまま `_heap_down_ranged` へ渡される。

だから直すべきは「`closure_lam1` に届く経路」ではなく、「`closure_lam1` の中で `#param` の正体を
知っている版を作ること」である。

なお、パスには似た状況への対処が既にある — 持ち上げようとしているラムダが**既に表に載っている**
ラムダを捕まえていたら、持ち上げる前にその中身を先に処理する。しかしこれは今回の形では発火
しない。第 1 段の時点で `less_than` はただの引数で、表に載るのは第 2 段だからである。**順序の
問題**である。

### issue #166 の記述との差

issue は障壁 3 を「持ち上げ先が空の表で始まる」と書いている。現象としては正しいが、**「表を
引き継ぐ」では直らない**。持ち上げ済みラムダは既に独立したグローバル関数になっており、その
キャプチャリストの**型**に「ここにはクロージャが入る」と焼き込まれているからである。

## 6. 設計: 特殊化のキーを「入口スロット」に一般化する

### 6.1 追いかける境界と、諦める境界

「どのラムダか」という知識は、値が関数の境界を越えるたびに失われる。境界を 1 つずつ塞ぐと
きりがないので、**追いかける境界を先に決めて閉じる**。

decapturing が終わった後、値が関数の中へ入ってくる経路は次の 2 つである。

1. **通常の引数**
2. **キャプチャリストのフィールド** — キャプチャリストは 1 個の引数で、本体の先頭で分解される

この 2 つを追いかける。以下は**追いかけない**と決める。

- **構造体 (タプルを含む) のフィールドに入れて取り出したラムダ**
- **`Array` に入れて取り出したラムダ** — 実行時に選ばれるので、どのラムダかは静的に決まらない
- **`Option` などの union に入れて取り出したラムダ** — 同じ理由
- **関数がクロージャを返す場合** — `f >> g` のような合成が該当するが、これはインライン展開で
  ラムダ式に潰れており、返り値としてクロージャが渡り歩く形はほぼ残らない

追いかけない経路に入った値は、いまと同じくクロージャのまま扱われる。**正しさは失われず、
最適化が効かないだけ**である。

これらを外すと、追う対象が「関数の入口」だけに閉じる。ここで効いているのは、
**ラムダが入口スロットに直接来たときだけ追う**という約束である。値の中に入れ子になったラムダを
追い始めると、キーが「スロットの中の、フィールドの中の、そのまた中」と深くなり、入口を数え上げた
意味が無くなる。

#### キャプチャリストも構造体なのに追うのはなぜか

キャプチャリストは構造体だが、**このパスが自分で作ったもの**である点が違う。持ち上げ済みラムダ
1 つにつき構築地点は 1 種類しかなく、分解されるのはそのラムダの本体の先頭だけである。**どの
フィールドに何が入っているかは、解析ではなく構成から分かる。** ユーザの書いた構造体は、どこでも
構築でき、どこへでも渡せ、どこでも分解できるので、同じことは言えない。

#### 実測: 構造体を通すと連鎖は切れる

構造体のフィールドに入れたラムダを取り出して関数へ渡すプログラムを 2 通り書いて測った。

| 形 | `apply_many` の複製 | 結果 |
| --- | ---: | --- |
| 構築地点が 1 つで、そのまま `h.@op` を渡す | 2 個 | 構造体経由の呼び出しも特殊化された |
| 構築地点が 2 つあり、分岐で合流してから `h.@op` を渡す | 1 個 | 構造体経由は間接呼び出しのまま |

上の行で特殊化されるのは、このパスが構造体を追ったからではない。**構築地点が 1 つで途中に合流が
無いとき、前段の最適化が `S { f : L }.@f` を `L` に畳んでしまう**ので、このパスが見る頃には構造体
が消えている。下の行のように畳めない形にすると、正体は失われ、一般の版が残る。

つまり構造体は「追いかけないと決める」対象であり、畳める範囲で得をするのは前段のおかげである。

### 6.2 スロット

いまの特殊化のキーは「**引数の何番目に、どのラムダが来たか**」である。これを

> **入口スロットに、どのラムダが来たか**

に広げる。入口スロットは次のどちらかとする。

- **引数スロット** `(関数, 引数の位置)`
- **キャプチャスロット** `(関数, キャプチャリストのフィールド名)`

§6.1 の結論から、この 2 種類で入口は尽きる。**穴を 1 つずつ塞ぐのではなく、入口の定義そのものを
閉じた集合にする**のがこの設計の要点である。

パスの変更はこうなる。

- **要求を立てる側**: いまは「表に載っている名前が、特殊化できる関数の引数として渡されている」
  のを見つけたときだけ要求が立つ。これに「**表に載っている名前が、キャプチャリストのフィールド
  に詰められ、そのキャプチャリストが持ち上げ済みラムダに渡されている**」を足す。
- **要求を実体化する側**: いまは複製を歩く前に引数スロットを表に載せる。これにキャプチャスロット
  を足す。すなわち、複製の先頭でキャプチャリストを分解して得られる名前を表に載せる。

### 6.3 今回のケースがどう解けるか

```
_heap_sort_by_ranged を less_than = L で特殊化する
  └─ 複製を歩く。表には less_than = L が載っている
       └─ 「Cap{ #param : less_than, ... } を組んで closure_lam1 を呼ぶ」を見つける
            └─ closure_lam1 を「キャプチャスロット #param = L」というキーで特殊化する要求を立てる
                 └─ その複製を歩く。表には #param = L が載っている
                      └─ _heap_down_ranged(#param, ...) を見つけ、引数スロットのキーで要求を立てる
                           └─ _heap_down_ranged は自己再帰で同じ位置へ渡すので、
                              以降は既存の仕組みで回る
```

### 6.4 キーはラムダの名前であって、型ではない

キャプチャリストの型名は「接頭辞 + フィールド名と型の並び」から作られるので、**同じ変数を捕まえた
別々のラムダは同じ型を共有する**。したがって型をキーにすると別のラムダを取り違える。

いまの特殊化名は既にラムダの**名前**をハッシュしているので、この点は現状のままで安全である。
キャプチャスロットを足すときも、キーに入れるのは名前であって型ではない。

### 6.5 型の波及はパスが自分で書く

このパスは型推論の後に走るので、式の型を変えたらプログラムへの波及はパスの仕事である。
特殊化版のキャプチャリストは当該フィールドの型が変わるので、

- 新しいキャプチャリスト型を作り、プログラムの型環境に登録する
- その型で箱を組む側 (構築地点) を書き換える
- その型を分解する側 (特殊化版の本体の先頭) を書き換える

を書く。機械的だが分量はある。

## 7. 複製する価値をどう判定するか

### 7.1 いまの判定

§4.4 の条件 4 と条件 5 が、それにあたる (障壁 2 の修正を入れた後の形)。

- **条件 4 (複製が何かを得るか)**: そのパラメータを自分で呼ぶ、または別の関数の特殊化できる
  パラメータへ渡している
- **条件 5 (複製する価値があるか)**: その関数が自己再帰である、**または呼び出し地点に展開できる
  ほど小さい**、または別の関数の特殊化できるパラメータへ渡している

### 7.2 インラインコストを見るのはやめる

条件 5 の「呼び出し地点に展開できるほど小さい」だけが、**関数の大きさ**を見ている。他はすべて
「そのパラメータがどう使われるか」を見ている。この 1 つだけ性質が違う。

特殊化で得られるものは「間接呼び出しが直接呼び出しになること」と「その先が解析可能になること」
であって、その大きさは**パラメータが呼ばれる回数**に比例する。関数自身の大きさとは関係がない。
むしろ**大きい関数の中でクロージャが熱く呼ばれている場合こそ特殊化が効く**のに、いまの条件は
自己再帰でない限りそれを外す。

Rust はクロージャの型でジェネリック関数を単相化する。渡されたクロージャごとに複製が作られ、
大きさは判定しない。それで実用になっている。**関数の大きさで複製の可否を決めるのは、特殊化と
インライン展開を取り違えている。**

ただし Fix と Rust には違いがある。Rust ではクロージャに統一表現が無いので、複製は
**必須**である (複製しない選択肢が無い)。Fix はクロージャを統一表現で持てるので、複製は
**常に任意**であり、コード量と間接呼び出しの取引になる。したがって Rust をそのまま真似るのでは
なく、「取引の管理をどこでやるか」を決める必要がある。

**提案**: 条件 5 を丸ごと落とし、条件 4 だけにする。条件 4 は「この複製が実際に何かを得る」を
言っているので、これだけが判定として意味を持つ。コード量は §9 の各段で測る。

これで §4.4 の定義は 4 つに減り、価値の判定は次の 1 行になる。

> そのパラメータを自分で呼ぶか、**別の関数の「特殊化できるパラメータ」へ渡している**なら、
> 複製を作る。

後半が定義自身を参照していることに変わりはない。基底は前半の「自分で呼ぶ」で、そこから呼ぶ側へ
伝わる (§4.4)。

### 7.3 測ること

コード量とコンパイル時間が増える方向の変更なので、コーパス 46 ケースで

- 実行命令数 (増える形が無いこと)
- コンパイル時間
- バイナリサイズ

の 3 つを見る。悪化するケースが出たら、そのときに上限を置く根拠として使う。

## 8. 停止性

### 8.1 いまの 2 つの条件

§4.4 の 5 条件のうち、停止性のために置かれているのは次の 2 つである。

- **条件 2**: 自己呼び出しが、そのパラメータを同じ位置へそのまま渡していること。回るたびに引数が
  変わる形はここで弾かれる。
- **条件 3**: 同じ強連結成分の別の関数を呼ぶ関数は、特殊化対象から丸ごと外す。条件 2 は自己
  呼び出ししか見ないので、閉路が別の関数を経由する場合の代わりとして置かれている。

### 8.2 測定に使ったプログラム

以下の 3 つの形を 1 つのプログラムに書いて測った。どれも「クロージャを受け取って再帰する」形で、
違いは**再帰が次の周へ何を渡すか**だけである。

```fix
// (1) 自己再帰。次の周へ渡すのは、受け取ったラムダを包んだ別のラムダ。
grow : I64 -> (I64 -> I64) -> I64;
grow = |n, op| (
    if n == 0 { op(0) };
    grow(n - 1, |x| op(x) + n)
);

// (2) 相互再帰。受け取ったラムダをそのまま渡し合う。
ping : I64 -> (I64 -> I64) -> I64;
ping = |n, op| (
    if n == 0 { op(1) };
    pong(n - 1, op)
);
pong : I64 -> (I64 -> I64) -> I64;
pong = |n, op| (
    if n == 0 { op(2) };
    ping(n - 1, op)
);

// (3) 相互再帰。閉路を一周する間に 1 回だけラムダが包まれる。
//     tick も tock も、自分の呼び出しだけを見ていては変化に気づけない。
tick : I64 -> (I64 -> I64) -> I64;
tick = |n, op| (
    if n == 0 { op(3) };
    tock(n - 1, |x| op(x) + 1)
);
tock : I64 -> (I64 -> I64) -> I64;
tock = |n, op| (
    if n == 0 { op(4) };
    tick(n - 1, op)
);

main : IO () = (
    let a = grow(4, |x| x);            // 10
    let b = ping(4, |x| x * 10);       // 10
    let c = tick(4, |x| x * 100);      // 302
    println((a + b + c).to_string)     // 322
);
```

(1) と (3) が「特殊化してはいけない」とされている形、(2) が「特殊化して安全」な形である。
(1) と (3) は `src/tests/test_closure_specialization/cases/changing_closure` としてテストにも
入れてある。

### 8.3 条件 3 には役が 2 つある

停止性のほかに、**「特殊化できる関数」の集合を 1 回舐めで解くための順序**を作る役がある。

§4.4 のとおり、この集合は再帰的に定義されており (条件 4 と条件 5 が定義自身を参照する)、
**下流から順に** 1 回舐めて表を作ることで解いている。

強連結成分の**中**には順序が無い。条件 3 が「成分の他のメンバーを呼ぶ関数は丸ごと外す」と言うので、
表を引く相手は必ず処理済みになる。**条件 3 を外すと 1 回舐めでは決まらず、この集合自体を不動点で
解くことになる。**

この不動点は**空から始めて増やす**方向である (種は「そのパラメータを自分で呼ぶ」)。停止性とは
別の話なので、§8.8 の規則とは独立に必要になる。

### 8.4 実測: いまのパスなら 条件 2 を外しても無限にならない

条件 2 を外したコンパイラを作り、§8.2 の (1) と (3) をビルドした。

| | 結果 |
| --- | --- |
| ビルド | 成功 (タイムアウト無し) |
| `grow` の複製 | **2 個** |
| `tock` の複製 | **2 個** |
| 答え | 正しい |

理由は持ち上げにある。第 1 段が終わった時点で `grow` の本体にラムダ式は**残っていない**。

```fix
// 第 1 段の後の grow (名前を短く書いたもの)

// |x| op(x) + n が捕まえる変数を詰めた箱
type Cap = unbox struct { op : I64 -> I64, n : I64 };

// そのラムダが持ち上げられた姿
L : Cap -> I64 -> I64;
L = |{ op : op, n : n }, x| op(x) + n;

grow = |n, op| (
    if n == 0 { op(0) };
    grow(n - 1, L(Cap { op : op, n : n }))   // 箱を組んで L に部分適用しているだけ
);
```

再帰呼び出しが渡す式の頭は、周を何回まわっても `L` という**同じ名前**である。箱の中身は周ごとに
違うが、キーは名前で決まるので、2 周目以降ずっと同じキーになり、そこで打ち止めになる。

### 8.5 実測: 条件 3 はインライン展開に先を越されている

§8.2 の (2) — 素通しの相互再帰 — をビルドすると、`pong#closure_spec` が**生成されていた**。
条件 3 は「成分の他のメンバーを呼ぶ関数は対象外」と言っているので、生成されないはずである。

生成物を読むと、`pong` が呼んでいるのは `ping` ではなく `pong` 自身だった。インライン展開が
`ping` の本体を `pong` に取り込んで**自己再帰にしてしまう**ので、条件 3 の判定に届く前に相互再帰が
消えている。条件 3 が効くのは**インライン展開後も残る相互再帰**だけである。

### 8.6 ただし §6 を入れると無限が復活する (論証)

§8.4 で無限にならなかったのは、キーが**引数の位置**に付いているからである。§6 はキーを
**キャプチャスロット**へ広げる。すると `grow` は次のように回る。

| 周 | `grow` の複製 | その中で組むキャプチャリスト | `L` の複製 | 次の周へ渡るもの |
| ---: | --- | --- | --- | --- |
| 1 | `op = L` で特殊化 | スロット `op` に `L` が入る | `L1 = L[op:=L]` | `L1` |
| 2 | `op = L1` で特殊化 | スロット `op` に `L1` が入る | `L2 = L[op:=L1]` | `L2` |
| 3 | `op = L2` で特殊化 | ... | `L3 = L[op:=L2]` | `L3` |

キャプチャリストの**型**も同じ深さで入れ子になる (`Cap{op: Cap{op: ...}, n}`)。名前も型も止まら
ない。

つまり **条件 2 は、いまのパスには要らないが、§6 を入れると要る**。§8.4 の結果を「条件 2 は不要」と
読んではいけない。

### 8.7 ハッシュコンスでは止まらない

持ち上げ済みラムダの名前を**内容のハッシュ**で決めれば、構造的に同じラムダは同じ名前になる。
これで名前の集合が閉じるかを §8.6 の表で確かめると、閉じない。

`L1` の内容は「`L` の本体、ただし `op` は `L`」、`L2` の内容は「`L` の本体、ただし `op` は `L1`」。
**内容が実際に違う**ので、ハッシュも違う。何周しても同じにならない。

止まる形にするには、閉路を**まとめて**ハッシュする必要がある (再帰的な定義の集まりを 1 つの形
として扱い、その形からハッシュを作る)。しかしそれには「いま閉路の中にいる」ことを検出する仕組み
が先に要る。**閉路を検出できるなら、ハッシュを作らずにその場で結び目を閉じればよい。**
したがってハッシュコンスは停止性の答えにならない。

ハッシュコンスには別の値打ち (構造的に同じラムダが 1 つになる) があるが、それは重複の削減で
あって停止性ではない。またコンパイラは既にアルファ同値な関数を多数出しており、インライン展開が
それを溶かすため、重複削減の効果は小さいと分かっている。

### 8.8 提案: 由来の閉路検査

魔法の数字を使わずに止める方法がある。**キーに使うラムダの「由来」を見て、閉路なら特殊化を
やめる。**

生成物はすべて「どのラムダから作られたか」を持てる (`L1`, `L2` の由来はどちらも `L`)。そこで
規則を 1 つ置く。

> ある原関数を特殊化する連鎖の上で、**既に使った原ラムダの子孫**をキーに使うことはできない。

§8.6 の表では、2 周目のキー `L1` の由来が `L` で、`L` は 1 周目で既に使っている。よって 2 周目は
特殊化せず、キャプチャスロットを一般のまま残す。**1 段だけ特殊化して止まる。**

この規則の性質:

- **停止する。** 1 本の連鎖で各原ラムダは高々 1 回しかキーになれず、原ラムダは有限個なので、
  連鎖の深さは有限である。
- **条件 2 より緩い。** 条件 2 は「引数が変わる形」を丸ごと拒否するが、この規則は 1 段は許す。
  `grow` は今日は何も得られないが、この規則なら 1 段分の直接呼び出しを得る。
- **`sort` の経路は素通しなので閉路にならない。** `_heap_down_ranged` は比較関数を同じ位置へ
  渡すだけなので、由来は最初のラムダのまま変わらず、連鎖は最後まで伸びる。
- **条件 3 も要らなくなる。** 相互再帰でも由来を見れば同じ判定ができる。ただし §8.3 の
  「表を作る順序」の役は残るので、そちらは最小不動点で解く必要がある。

理論上の上限は原ラムダの個数の階乗的な大きさになりうる。実際にそこまで伸びる形があるかは
コーパスで測る。膨らむ形が出たら、そのとき**測定値を根拠に**上限を決める。先に魔法の数字を
置くことはしない。

### 8.9 `changing_closure` のテストの主張が変わる

いまのテストは「複製が 1 つも作られない」を主張している。§8.8 の規則を入れると `grow` は 1 段
特殊化されるので、この主張は成り立たなくなる。

そのときテストの主張を「**複製の数が有限で、深さが 1 段で止まる**」に変える。ケースの値打ちは
「この形でパスが暴走しないこと」であって、「複製を作らないこと」ではない。

## 9. 段取りと各段での測定

1. **障壁 1 + 2** (済) — `sort` +0.11%。中継役の複製が生成されることを確認済み。
2. **判定の単純化** (§7.2) — 条件 5 を落とす。コーパスで実行命令数・コンパイル時間・バイナリ
   サイズを測る。
3. **「特殊化できる集合」を不動点で解く** (§8.3) — 1 回舐めをやめる。これ自体は結果を変えない
   はずなので、コーパスで**変化が無いこと**を確認する (中立性の検査)。
4. **由来の閉路検査を入れ、条件 2 と条件 3 を落とす** (§8.8) — `changing_closure` のテストを §8.9 の
   形に変える。相互再帰が特殊化対象に入るので、コーパスで効くケースがあるかを測る。
5. **キャプチャスロットの実装** (§6) — `_heap_down_ranged` の複製が生成されることを確認し、
   `sort` を測る。
6. **コーパス全 46 ケース** — 連鎖が伸びるとコード量が増えるので、`sort` 以外が悪化していない
   ことを確認する。コンパイル時間も測る。
7. **全テスト** — 4 つの最適化レベルすべて。

到達目標は `sort` **-13%**。

4 は 5 の前に必要である。5 を入れると §8.6 の無限が現れるので、その前に止める仕組みを置く。

## 10. まだ確かめていない前提

以下は設計の前提だが未実測である。実装前に潰す。

- `_heap_down_ranged` が自己再帰で比較関数を**同じ引数位置**へ渡していること。これが成り立たない
  と 5 段目が回らない。
- 13% のうち、`_heap_down_ranged` の特殊化だけで取れるのがどれだけか。比較関数が
  `_heap_sort_by_ranged` 以外の経路でも渡っている可能性がある。
- **この形 (クロージャを捕まえたクロージャが、そのクロージャを下流へ渡す) がコーパス全体で
  何箇所あるか。** 13% が `sort` 1 ケースの話なのか、他にも効くのかで、この設計の見合いが変わる。
- §8.6 の無限は論証であって実測ではない。§6 の実装が動いた時点で、由来の閉路検査を外した版で
  `changing_closure` が実際に暴走することを確かめる。
