# closure specialization の連鎖を延ばす (#166 / #131)

Fix の最適化パス `closure_specialization` を延ばして、`Array::sort` の実行命令を 13% 減らす。

実測の数字は本文から外し、付録 A にまとめてある。

---

## 1. 目標

`Array::sort` は、実行する命令の **13%** を「比較関数がクロージャのままであること」に払っている。

比較関数はユーザが渡すラムダである。それがクロージャ (捕まえた変数を抱えた値) のまま渡り歩くと、
比較のたびにその値の参照カウントを上げ下げする必要がある。`sort` の比較回数は約 420 万回で、
比較を実際に行う関数だけで `sort` の実行命令の 37% を占める。

13% は上限の推定ではなく実測値である (付録 A.1)。

そして、**参照カウント操作を減らす既存の最適化はここに原理的に届かない**。#122 で入った locality
推論は、呼び出し元で分かっている「この値は他から参照されていない」といった性質を呼び出し先へ
持ち込み、参照カウントの操作を省くものである。呼び出し地点ごとに違う版を作れることが前提になる。
ところがクロージャは間接的に呼ばれるので、呼び出し地点がその関数を名指ししない。名指しできない
以上、版を分けることも、呼び出し元の性質を持ち込むこともできない。

**名指しできるようにすること**、それがこのパスの仕事である。

---

## 2. パスがやっていること

`closure_specialization` は 2 つの技法を持つ。用語もここで決める。

### 2.1 技法 A: 持ち上げ (decapturing)

ラムダを、**捕まえた変数を詰めた箱**と、**その箱を引数に取るグローバル関数**の 2 つに分解する。

```fix
let n = 3;
let f = |x| x + n;      // n を捕まえたラムダ
```

これが次のようになる:

```fix
// 捕まえた変数を詰めた箱。以降これを「キャプチャリスト」と呼ぶ。
type Cap = unbox struct { n : I64 };

// 箱を第 1 引数に取るグローバル関数。以降これを「持ち上げ済みラムダ」と呼ぶ。
lam : Cap -> I64 -> I64;
lam = |{ n : n }, x| x + n;

let f = Cap { n : 3 };   // ラムダの値は、ただの箱になる
```

`f(5)` という呼び出しは `lam(f, 5)` になる。**箱そのものは関数ではない。** 呼ぶには持ち上げ済み
ラムダの名前が要る。

ラムダの正体が分からない場所へ箱を渡すときは、`lam` に箱だけを部分適用した `lam(f)` を渡す。
これは元どおりのクロージャなので、型も振る舞いも変わらない。**以降「正体の分かっているラムダを
渡している」とは、渡す式がこの `lam(箱)` の形、すなわち式の頭が持ち上げ済みラムダの名前である
ことを指す。**

キャプチャリストの型名には、捕まえた変数の名前と型の並びが埋め込まれる。以降のコード例で
`Cap<n : I64>` のように山括弧付きで書いてあるのは、この埋め込みを省略せずに書いたものである。

### 2.2 技法 B: 特殊化 (specialization)

クロージャを引数に取るグローバル関数を、**渡されるラムダごとに複製**する。

```fix
fold : S -> (A -> S -> S) -> Iter -> S;
fold = |s, op, iter| ( ... );      // 第 2 引数を op と呼ぶ
```

`fold` に上の `f` を渡す箇所があれば、`fold` の複製を作る。その複製の中では `op` を間接的に呼ぶ
代わりに `lam` を名前で直接呼ぶ。間接呼び出しが消え、`op` の参照カウント操作も消える。

複製を作れるのは、**渡すものの正体が分かっている呼び出し地点だけ**である。だから技法 B は技法 A
の上に乗っている。

### 2.3 連鎖が要る理由

`sort` の比較関数は、1 段では届かない。

```
sort
  |- _introsort_by_internal      <- 比較関数を受け取る
       |- _heap_sort_by_ranged   <- 比較関数をそのまま下へ渡すだけ (中継役)
            |- _heap_down_ranged <- 比較関数を実際に呼ぶ。ここが 37%
```

特殊化が `_introsort_by_internal` で止まると、その先はクロージャのまま渡り、`_heap_down_ranged`
の中で 420 万回の参照カウント操作が残る。**連鎖を末端まで延ばして初めて 13% が取れる。**

## 3. パスの骨格

この節は、**本ブランチの修正 (§4 の障壁 1 と 2) を入れた後**のパスを書く。修正の中身は §4 で
説明する。

### 3.1 全体

```
run(プログラム):
    表 = 特殊化できる関数を計算する(プログラム)         // 3.3 で説明する
    安定集合 = {}

    変化がなくなるまで繰り返す:

        // 第 1 段: 全シンボルを 1 つずつ歩く
        要求 = []
        各シンボル s について:
            s が安定集合にあるなら飛ばす
            s の中のラムダを持ち上げ、グローバル関数として登録する
            s の中の呼び出しのうち、表に載っている関数へ
              正体の分かっているラムダを渡しているものを見つけたら:
                その呼び出しを、特殊化版の名前を呼ぶ形へ差し替える
                要求に「この関数を、この引数にこのラムダが来る形で作れ」を積む
            s が何も変わらなかったなら、s を安定集合に入れる

        // 第 2 段: 積んだ要求を実体化する
        要求が空になるまで:
            要求を 1 つ取り出す
            その名前の本体が既にあるなら、何もしない
            元の関数の本体をコピーし、
              「この引数はこのラムダだ」と分かった状態でコピーを歩く
            歩く途中で立った新しい要求を積む

        表 = 特殊化できる関数を計算する(プログラム)     // 増えた関数を含めて作り直す
```

### 3.2 呼び出しの差し替えと、本体を作ることは別々

第 1 段が積む「要求」は、この形をしている。

```rust
// 「この関数を、この引数にこのラムダが来る形で作れ」という要求。
struct SpecializationRequest {
    // 複製する元の関数。
    func: FullName,
    // 引数の位置 -> そこへ来る持ち上げ済みラムダの名前。
    args: Map<usize, FullName>,
}
```

以降、この `(func, args)` の組を、その特殊化の**キー**と呼ぶ。

第 1 段が呼び出しを差し替える時点で、差し替え先の本体はまだ存在しない。それでも成り立つのは、
**特殊化された関数の名前が、本体を作る前に決まる**からである。名前は

```
func + "#closure_spec_" + args のハッシュ
```

から機械的に作れる。本体が無くても呼び出しは書ける。

この決め方の帰結として、**同じキーの要求が何度立っても、本体は 1 つに共有される**。要求を実体化
するとき、その名前の本体が既にあれば作らない。以降この打ち切りを**同じキーは 1 度しか実体化
しない**と書く。

### 3.3 「特殊化できる関数」の表

第 1 段が引くこの表は、**どの関数のどのパラメータなら複製する価値があるか**を全プログラム分
まとめたものである。

```rust
// 関数 -> 特殊化できるパラメータの位置。
type Specializable = Map<FullName, Set<usize>>;
```

表に載っていない関数は、どんな呼び出し地点があっても複製されない。

```
特殊化できる関数を計算する(プログラム):
    表 = {}
    呼び出しグラフを、呼ばれる側が先に来る順に並べる
    その順に各関数 f について:

        f が自分の強連結成分の別の関数を呼ぶなら、f 全体を飛ばす      // 条件 3

        f の各パラメータ i について:
            i の型がクロージャでないなら飛ばす                        // 条件 1

            f が自分自身を呼んでいて、その呼び出しが位置 i まで引数を
              持っていて、かつ位置 i に渡しているのが i 自身でないなら飛ばす
                                                                      // 条件 2

            転送 = i が、表に載っている関数の
                        「特殊化できるパラメータ」へ渡されている
            届く = (i が f の中で呼ばれている) または 転送             // 条件 4
            価値 = f が自己再帰
                   または f が呼び出し地点に展開できるほど小さい
                   または 転送                                         // 条件 5

            届く かつ 価値 なら、表[f] に i を足す
    表
```

**関数 f が「特殊化できる関数」**とは、表に載っていること、すなわち上を満たすパラメータを 1 つ
以上持つことである。以降、条件 4 の後半を「**転送**」と呼ぶ。

条件 2 の書き方が回りくどいのは、実装がそうなっているからである。自己呼び出しが 1 つも無い関数
は条件 2 を満たす (中継役はこれで通る)。部分適用で位置 i まで引数が届いていない自己呼び出しも
条件 2 を満たす。弾かれるのは「位置 i に、i 以外の何かを渡している自己呼び出しがある」場合だけ
である。

条件には性質の違うものが混ざっている。条件 1 は型の話、条件 2 と条件 3 は無限ループを防ぐための
もの (§7 で扱う)、条件 4 と条件 5 は複製の見合いの話 (§6 で扱う) である。

**定義が自分を参照している。** 条件 4 と条件 5 の「転送」が、表そのものを参照する。地に足がつく
のは条件 4 の前半「f の中で呼ばれている」で、そこから呼ぶ側へ伝わる。`sort` の経路ではこうなる。

```
_heap_down_ranged       less_than を自分で呼ぶ              <- 条件 4 前半で成立 (基底)
  ^
_heap_sort_by_ranged    less_than を _heap_down_ranged の   <- 転送で成立 (伝播)
                        特殊化できるパラメータへ渡す
  ^
_introsort_by_internal  同上                                 <- さらに伝播
```

疑似コードが「呼ばれる側が先に来る順」に並べているのは、この伝播を 1 回舐めで解くためである。
f を処理する時点で、f が呼ぶ関数はすべて表に載っている。強連結成分の**中**には順序が無いが、
条件 3 が成分の他のメンバーを呼ぶ関数を丸ごと外すので、表を引く相手は必ず処理済みになる。
**条件 3 は無限ループを防ぐためだけでなく、この順序を成立させるためにも置かれている。**

### 3.4 外側のループの役目

第 1 段と第 2 段の全体を繰り返しているのは、**第 1 段が動いている最中にプログラムが増える**
からである。増えるのは持ち上げ済みラムダと特殊化の複製で、どちらもその周の第 1 段はまだ見て
いない。周 2 以降が歩いているのは、ほとんどが前の周で生まれたシンボルである (付録 A.5)。

繰り返しが要る理由は 2 つある。

1. **新しく生まれたシンボルを歩く。**
2. **表を作り直す。** 表は第 1 段の前に計算されるので、周 1 の表には周 1 が作る関数が載りようが
   ない。新しい関数が特殊化の対象になるには、作り直すしかない。

要らないのは、前の周で変化したシンボルの再走査である。安定の印が付くのは「歩いてみて何も変わら
なかった」ときなので、変化したシンボルは必ずもう 1 周歩かれ、そこで初めて安定と分かる。素直に
書くなら、全走査ではなくワークリストにする — 新しいグローバル関数を作ったらキューに積み、表が
更新されたらその関数の呼び出し元を積み、キューが空になるまで回す。こうすれば第 1 段は「最初に
キューを全シンボルで満たす」だけになり、ループの本体から消える。ただし理由 2 は残るので、表を
増分で更新できないと全走査が戻ってくる。§8 の段取りで表の作り方を変えるときに一緒に扱う。

## 4. いま連鎖が切れている場所

障壁が 3 つある。1 と 2 は本ブランチで直した (§3 は修正後の姿である)。

### 4.1 障壁 1 (#131): 「誰に渡したか」を記録していなかった

パスは「ある名前がどう使われているか」を調べる補助関数を持つ。用途の 1 つは「**この引数は、
どの関数の何番目の引数として渡されたか**」を記録することである。

その記録が、渡された先の関数名ではなく、**調べている名前自身**を書き込んでいた。調べている名前
は必ずローカル変数なので、記録を読む側の「グローバル関数でなければ無視」という条件が毎回成立
し、**転送が一度も真にならなかった**。伝播の経路が塞がっていたので、条件 4 は前半だけで判定
されていた。

**修正済み**: 呼ばれた関数の名前を記録するようにした。

### 4.2 障壁 2: 中継するだけの関数が「複製する価値なし」と判定されていた

障壁 1 を直すと、中継役でも条件 4 が真になる。しかし**条件 5 が落としていた**。修正前の条件 5
は「自己再帰である」か「呼び出し地点に展開できるほど小さい」かの 2 択で、中継役はまさに自己
再帰でなく、中継するくらいなので小さくもない。`_heap_sort_by_ranged` がその形である。

**修正済み**: 条件 5 に「転送」を足した。中継役の複製にも価値がある — 複製の中では下流へ渡す
ものの正体が分かっているので、下流もまた特殊化できる。

この 2 つを直すと、中継役の複製 `_heap_sort_by_ranged#closure_spec` は**実際に生成されるように
なる**。しかし `sort` の命令数は改善しない (付録 A.2)。その先の `_heap_down_ranged` に複製が
無く、複製が 1 つ増えた分のコードだけが増えるからである。

### 4.3 障壁 3: 特殊化された引数が、呼び出しではなくキャプチャリストに入る

`_heap_sort_by_ranged` の中身はこう書かれている。

```fix
range_step(n/2-1, -1, -1).fold(arr, |i, arr| arr._heap_down_ranged(less_than, ...))
```

比較関数 `less_than` を下流へ渡す `_heap_down_ranged` の呼び出しは、**`fold` に渡すラムダの中に
ある**。

第 1 段でこのラムダが持ち上げられる。`less_than` はそのキャプチャリストに入る。

```fix
_heap_sort_by_ranged#closure_lam1 = (
    |#closure_cap| ( |i| ( |arr| (
        let Cap<#param : (I64, I64) -> Bool, ...> {#param, ...} = #closure_cap;  // 箱を分解
        ...
        _heap_down_ranged(#param, ...)      // <- 連鎖に必要な呼び出しはここにある
    ))))
);
```

第 2 段で `_heap_sort_by_ranged` の複製を作るとき、`less_than` の正体は分かっている。**しかし
そのときにはもう `_heap_down_ranged(less_than, ...)` という呼び出しが複製の本体に無い。** 第 1 段
で別のグローバル関数の中へ移動してしまっている。複製の本体には代わりに、
`Cap<#param : ..., ...>{...}` という箱を組み、それを `fold` の複製へ渡す式が立っている。

**連鎖は「特殊化された引数が、呼び出しに渡されるのではなく箱に詰められる」ところで切れている。**

紛らわしいので明示しておくと、`fold` の特殊化そのものは成功している。

```
_heap_sort_by_ranged の複製
  |- fold の複製            <- 直接呼び出しになっている
       |- closure_lam1      <- ここも名前で呼ばれている
            |- _heap_down_ranged(#param, ...)   <- #param の正体が分からない
```

`closure_lam1` に到達するまでの経路はすべて直接呼び出しである。切れているのは**その中身**で、箱
から取り出した `#param` が、比較関数の正体を持たないまま `_heap_down_ranged` へ渡される。だから
直すべきは「`closure_lam1` に届く経路」ではなく、「`closure_lam1` の中で `#param` の正体を知って
いる版を作ること」である。

issue #166 はこれを「持ち上げ先が空の表で始まる」と書いている。ここでの「表」は §3.3 の表では
なく、歩いている間だけ持つ「ローカル名 -> その正体であるラムダ」の対応のことである。現象として
は正しいが、**持ち上げのときに正体を引き継げば直る、というものではない**。第 1 段の時点で
`less_than` はまだただの引数であり、正体が分かるのは第 2 段だからである。順序の問題であって、
引き継ぎの問題ではない。

## 5. 設計: 特殊化のキーを「入口スロット」に広げる

### 5.1 追いかける境界と、諦める境界

「どのラムダか」という知識は、値が関数の境界を越えるたびに失われる。境界を 1 つずつ塞ぐときりが
ないので、**追いかける境界を先に決めて閉じる**。

持ち上げが終わった後、値が関数の中へ入ってくる経路は次の 2 つである。

1. **通常の引数**
2. **キャプチャリストのフィールド** — キャプチャリストは 1 個の引数で、本体の先頭で分解される

この 2 つを追いかける。以下は**追いかけない**と決める。

- **構造体 (タプルを含む) のフィールドに入れて取り出したラムダ**
- **`Array` に入れて取り出したラムダ** — 実行時に選ばれるので、どのラムダかは静的に決まらない
- **`Option` などの union に入れて取り出したラムダ** — 同じ理由
- **関数がクロージャを返す場合** — `f >> g` のような合成が該当するが、これはインライン展開で
  ラムダ式に潰れており、返り値としてクロージャが渡り歩く形はほぼ残らない
- **`defunctionalize_fix` が作ったキャプチャリストのフィールド** — 再帰を扱う別のパスが、この
  パスと同じ仕組みで自前のキャプチャリストを作り、このパスより前に走る。ユーザのクロージャが
  そちらの箱に入って関数へ入ってくる経路がありうるが、箱の作り手が別なので今回は対象にしない

追いかけない経路に入った値は、いまと同じくクロージャのまま扱われる。**正しさは失われず、最適化
が効かないだけ**である。

これらを外すと、追う対象が「関数の入口」だけに閉じる。ここで効いているのは、**ラムダが入口に
直接来たときだけ追う**という約束である。値の中に入れ子になったラムダを追い始めると、キーが
「引数の中の、フィールドの中の、そのまた中」と深くなり、入口を数え上げた意味が無くなる。

**このパスのキャプチャリストも構造体なのに追うのはなぜか。** それは、このパスが自分で作った
ものだからである。持ち上げ済みラムダ 1 つにつき構築地点は 1 種類しかなく、分解されるのはその
ラムダの本体の先頭だけである。**どのフィールドに何が入っているかは、解析ではなく構成から
分かる。** ユーザの書いた構造体は、どこでも構築でき、どこへでも渡せ、どこでも分解できるので、
同じことは言えない。

なお、構築地点が 1 つで途中に合流が無い場合は、前段の最適化が `S { f : L }.@f` を `L` に畳んで
しまうので、このパスが見る頃には構造体が消えていることがある。畳める範囲で得をするのは前段の
おかげであって、この設計の守備範囲ではない (付録 A.4)。

### 5.2 スロット

いまの特殊化のキーは「**引数の何番目に、どのラムダが来たか**」である。これを

> **入口スロットに、どのラムダが来たか**

に広げる。入口スロットは、**関数のパラメータ列への経路**とする。

```rust
// 関数の入口。
struct Slot {
    // 引数の位置。
    arg: usize,
    // `None` なら引数そのもの (引数スロット)。
    // `Some(j)` なら、その引数が受け取るキャプチャリストの第 j フィールド (キャプチャスロット)。
    field: Option<usize>,
}
```

§3.3 の表と §3.2 の要求は、引数の位置の代わりにこれを持つ形へ広がる。

```rust
type Specializable = Map<FullName, Set<Slot>>;

struct SpecializationRequest {
    func: FullName,
    args: Map<Slot, FullName>,
}
```

持ち上げ済みラムダはキャプチャリストを第 0 引数で受け取るので、`Slot { arg: 0, field: Some(1) }`
はそのキャプチャリストの第 1 フィールドを指す。

§5.1 の結論から、この 2 種類で入口は尽きる。**穴を 1 つずつ塞ぐのではなく、入口の定義そのものを
閉じた集合にする**のがこの設計の要点である。経路の長さを 2 で打ち切ってあることが、§5.1 の
「入れ子は追わない」をそのまま形にしている。

フィールドを名前ではなく位置で指すのは、キャプチャリストが「捕まえる名前と型の**並び**」から
作られるからである。型構成子の名前もその並びから作られ、構築する式も分解するパターンも同じ並び
を順に辿って作られるので、**フィールドの位置は持ち上げの時点で決まり、それ以降動かない**。名前
で指しても働きは同じだが、位置に揃えると 2 種類のスロットが 1 つの形になり、キャプチャスロット
を特殊化してフィールドの型が変わっても位置は変わらない。フィールド名のほうは、パス自身が複製の
本体でローカル名を振り直すので、複製をまたいだ同一性には使えない。

### 5.3 要求を立てる側と、実体化する側

- **要求を立てる側**: いまは「正体の分かっているラムダが、表に載っている関数の引数として渡されて
  いる」のを見つけたときだけ要求が立つ。これに「**正体の分かっているラムダが、キャプチャリストの
  フィールドに詰められている**」を足す。
- **要求を実体化する側**: いまは複製を歩く前に引数スロットの正体を控える。これにキャプチャ
  スロットを足す。すなわち、複製の先頭でキャプチャリストを分解して得られる名前も控える。

**要求を立てられる時刻に制約がある。** 正体の分かっているラムダをキャプチャリストのフィールドへ
詰める場面で、要求を立てそこねると、その値は §2.1 の `lam(箱)` の形に包まれて型を合わせられる。
**包んだ時点で正体は失われる**ので、次の周にやり直すことはできない。要求はその場で立てるしか
ない。

ところが、その場で相手 (持ち上げ済みラムダ) が §3.3 の表に載っているとは限らない。表はその周の
第 1 段の前に一度だけ計算されるのに、持ち上げ済みラムダはその周の第 1 段で生まれるからである。
したがって**表は、新しく生まれた関数についてその場で条件を評価して足せる形**でなければならない。
持ち上げ済みラムダの条件 4 を評価するのに要るのは、そのキャプチャスロットの中身が本体でどう
使われるかと、その渡し先が表に載っているかだけで、渡し先は元からある関数なので既に載っている。
これは §8 の 3 段目 (表を最小不動点で解く) と同じ工事である。

### 5.4 `sort` がどう解ける

```
_heap_sort_by_ranged を less_than = L で特殊化する
  |- 複製を歩く。less_than = L と分かっている
       |- 「Cap{ #param : less_than, ... } を組み、それを fold の複製へ渡す」を見つける
            |- 箱に L が入るので、closure_lam1 を
               「#param が入っているキャプチャスロット = L」というキーで特殊化する要求を立てる。
               その複製を closure_lam1' と呼ぶ
            |- 箱の型が closure_lam1' 用のものに変わるので、それを受け取る fold の複製も
               作り直す。すなわち fold を「第 1 引数 = closure_lam1'」というキーで
               特殊化する要求を立て、呼び出しをそちらへ差し替える
                 |- closure_lam1' の複製を歩く。#param = L と分かっている
                      |- _heap_down_ranged(#param, ...) を見つけ、引数スロットのキーで
                         要求を立てる
                           |- _heap_down_ranged は自己再帰で同じ位置へ渡すので、
                              以降は既存の仕組みで回る
```

3 段目が要ることに注意する。キャプチャリストを**素通しで運ぶだけの中継層** (ここでは `fold` の
複製) も、箱の型が変われば作り直しになる。連鎖はこの層を通らないと末端に届かない。

### 5.5 キーの値は、ラムダの名前で指す

キーは「どのスロットに、何が入っているか」の組である。スロットの側は位置で指す。入っている側は
**ラムダの名前**で指し、型では指さない。

キャプチャリストの型名は「接頭辞 + フィールド名と型の並び」から作られるので、**同じ変数を捕まえ
た別々のラムダは同じ型を共有する**。したがって型をキーにすると別のラムダを取り違える。いまの
特殊化名は既にラムダの名前をハッシュしているので、この点は現状のままで安全である。

### 5.6 型の波及はパスが自分で書く

このパスは型推論の後に走るので、式の型を変えたらプログラムへの波及はパスの仕事である。特殊化版
のキャプチャリストは当該フィールドの型が変わるので、

- 新しいキャプチャリスト型を作り、プログラムの型環境に登録する
- その型で箱を組む側 (構築地点) を書き換える
- その型を分解する側 (特殊化版の本体の先頭) を書き換える
- **その型を素通しで運ぶ中継層** (§5.4 の 3 段目) の引数の型を書き換える

を書く。機械的だが分量はある。

## 6. 複製する価値をどう判定するか

§3.3 の条件 5 は 3 択で、そのうち「呼び出し地点に展開できるほど小さい」だけが**関数の大きさ**を
見ている。他の条件はすべて「そのパラメータがどう使われるか」を見ている。この 1 つだけ性質が
違う。

特殊化で得られるものは「間接呼び出しが直接呼び出しになること」と「その先が解析可能になること」
であって、その大きさは**パラメータが呼ばれる回数**に比例する。関数自身の大きさとは関係がない。
むしろ**大きい関数の中でクロージャが熱く呼ばれている場合こそ特殊化が効く**のに、条件 5 は自己
再帰でない限りそれを外す。

Rust はクロージャの型でジェネリック関数を単相化する。渡されたクロージャごとに複製が作られ、
大きさは判定しない。それで実用になっている。**関数の大きさで複製の可否を決めるのは、特殊化と
インライン展開を取り違えている。**

ただし Fix と Rust には違いがある。Rust ではクロージャに統一表現が無いので、複製は**必須**で
ある (複製しない選択肢が無い)。Fix はクロージャを統一表現で持てるので、複製は**常に任意**で
あり、コード量と間接呼び出しの取引になる。したがって Rust をそのまま真似るのではなく、取引を
どこで管理するかを決める必要がある。

**提案**: 条件 5 を丸ごと落とし、条件 4 だけにする。条件 4 は「この複製が実際に何かを得る」を
言っているので、これだけが判定として意味を持つ。§4.2 で条件 5 に足したばかりの「転送」は、条件 4
の後半と同じものなので、条件 5 ごと落としても失われない。コード量は §8 の各段で測り、悪化する
ケースが出たらそのとき上限を置く根拠にする。

これで価値の判定は次の 1 行になる。

> そのパラメータを自分で呼ぶか、別の関数の「特殊化できるパラメータ」へ転送しているなら、
> 複製を作る。

## 7. 停止性

### 7.1 いまの 2 つの条件

§3.3 の条件のうち、無限ループを防ぐために置かれているのは次の 2 つである。

- **条件 2**: 自己呼び出しが、そのパラメータを同じ位置へそのまま渡していること。回るたびに引数
  が変わる形はここで弾かれる。
- **条件 3**: 同じ強連結成分の別の関数を呼ぶ関数は、特殊化対象から丸ごと外す。条件 2 は自己
  呼び出ししか見ないので、閉路が別の関数を経由する場合の代わりとして置かれている。

条件 3 は §3.3 のとおり表を作る順序も担っているので、落とすなら表を最小不動点で解き直す必要が
ある。

条件 3 が実際に効く場面は、見た目より狭い。このパスの前にインライン展開が走るので、小さな相互
再帰は片方が他方に取り込まれて自己再帰になっており、条件 3 の判定に届く前に相互再帰が消えて
いる。条件 3 が効くのは、インライン展開後も残る相互再帰だけである (付録 A.3)。

### 7.2 何が無限を生むのか

条件 2 が弾いているのは、この形である。

```fix
grow : I64 -> (I64 -> I64) -> I64;
grow = |n, op| (
    if n == 0 { op(0) };
    grow(n - 1, |x| op(x) + n)     // 受け取ったラムダを包んで次の周へ渡す
);
```

**いまのパスでは、この形でも無限にはならない。** 持ち上げが済むと、`grow` の本体にラムダ式は
残っていないからである。

```fix
type Cap = unbox struct { op : I64 -> I64, n : I64 };

L : Cap -> I64 -> I64;                        // |x| op(x) + n が持ち上げられた姿
L = |{ op : op, n : n }, x| op(x) + n;

grow = |n, op| (
    if n == 0 { op(0) };
    grow(n - 1, L(Cap { op : op, n : n }))    // 箱を組んで L に部分適用しているだけ
);
```

再帰呼び出しが渡す式の頭は、何周しても `L` という同じ名前である。箱の中身は周ごとに違うが、キー
は名前で決まるので、2 周目以降ずっと同じキーになる。§3.2 の「同じキーは 1 度しか実体化しない」
で打ち止めになる。

この「本体にラムダ式が残らない」は、パスの前段が**関数の引数に置かれたラムダをすべて `let` へ
括り出し**、`let` に束縛されたラムダは表と無関係に必ず持ち上げられる、という 2 つの性質から来て
いる。複製の本体は持ち上げ済みの本体をコピーしたものなので、複製の中で新しいラムダが持ち上がる
こともない。**この性質は §7.4 の停止性でも使う。**

**無限が現れるのは §5 を入れてからである。** §5 はキーをキャプチャスロットへ広げる。すると
`grow` は次のように回る。

| 周 | `grow` の複製 | その中で組む箱 | `L` の複製 | 次の周へ渡るもの |
| ---: | --- | --- | --- | --- |
| 1 | `op = L` で特殊化 | スロット `op` に `L` が入る | `L1 = L[op:=L]` | `L1` |
| 2 | `op = L1` で特殊化 | スロット `op` に `L1` が入る | `L2 = L[op:=L1]` | `L2` |
| 3 | `op = L2` で特殊化 | ... | `L3 = L[op:=L2]` | `L3` |

キャプチャリストの型も同じ深さで入れ子になる (`Cap{op: Cap{op: ...}, n}`)。名前も型も止まら
ない。**条件 2 を落とすなら、代わりの止め方を §5 と同時に入れる必要がある。**

### 7.3 ハッシュコンスでは止まらない

持ち上げ済みラムダの名前を**内容のハッシュ**で決めれば、構造的に同じラムダは同じ名前になる。
これで名前の集合が閉じるかを上の表で確かめると、閉じない。

`L1` の内容は「`L` の本体、ただし `op` は `L`」、`L2` の内容は「`L` の本体、ただし `op` は
`L1`」である。**内容が実際に違う**ので、ハッシュも違う。何周しても同じにならない。

止まる形にするには、閉路を**まとめて**ハッシュする必要がある — 再帰的な定義の集まりを 1 つの形
として扱い、その形からハッシュを作る。しかしそれには「いま閉路の中にいる」ことを検出する仕組み
が先に要る。**閉路を検出できるなら、ハッシュを作らずにその場で結び目を閉じればよい。** した
がってハッシュコンスは停止性の答えにならない。

ハッシュコンスには別の値打ち (構造的に同じラムダが 1 つになる) があるが、それは重複の削減で
あって停止性ではない。

### 7.4 提案: 出どころの組ごとに、ラムダを 1 つに固定する

魔法の数字を使わずに止める方法がある。先に言葉を 3 つ決める。

**出どころ.** 特殊化や持ち上げで作られた関数は、どれも「何の複製か」を覚えている。これを根まで
辿った先を**出どころ**と呼ぶ。`L1` は `L` の複製、`L2` も `L` の複製なので、どちらの出どころも
`L` である。`L1` をさらに特殊化したものの出どころも `L` である。複製ではない関数の出どころは
自分自身とする。**出どころの集合は、元のプログラムに書かれた関数とラムダの集合であり、パスが
何をしても増えない** (§7.2 の後半で見たとおり、複製の中で新しいラムダが持ち上がることはない)。

**受け継ぎの道すじ.** 要求はかならず何かの関数を歩いている途中で立ち、要求から関数が作られ、
その関数を歩くとまた要求が立つ。この「関数 -> 要求 -> 関数 -> ...」の列を**受け継ぎの道すじ**と
呼ぶ。

**固定表.** 道すじに沿って持ち回る、次の対応表である。

```rust
// (関数の出どころ, ラムダの出どころ) -> その組に対して既に使ったラムダ。
type Pinned = Map<(FullName, FullName), FullName>;

struct SpecializationRequest {
    func: FullName,
    args: Map<Slot, FullName>,
    pinned: Pinned,     // これを足す
}
```

持ち回り方を決める。

- ユーザが書いた関数の固定表は空である。
- 要求を立てるとき、歩いている関数の固定表を**複製**し、その要求の分を書き足したものを、その
  要求に持たせる。
- 要求から作られた関数は、その固定表を自分のものとして持つ。

複製して渡すので、同じ関数から立った 2 つの要求は互いに影響しない。作られた関数が固定表を持ち
続けるので、外側のループが次の周でその関数を歩き直しても、判定は同じところから続く。

規則はこうである。

> 要求のキーに現れる (要求の `func`, 各スロットに入っているラムダ) の組それぞれについて、
> その出どころの組を固定表に引く。
>
> - 載っていなければ、そのラムダを載せて要求を通す。
> - 載っていて、**同じラムダ**なら要求を通す。
> - 載っていて、**別のラムダ**なら要求を捨てる (特殊化せず、間接呼び出しのまま残す)。

要求を捨てても正しさは失われない。特殊化しないことは常に安全だからである。

#### 3 つの形に当てはめる

**(a) 自己再帰で素通しする形** — `fold` や `_heap_down_ranged`。

```fix
fold = |s, op, iter| ( ... iter.fold(op(a, s), op) ... )    // op をそのまま渡す
```

最初の要求で `(fold, F) -> F` が固定される。複製の中の再帰呼び出しは同じ `F` を渡すので、規則の
2 番目に当たり通る。そしてキーが最初の要求と同じなので §3.2 で実体化は打ち切られ、そこで終わる。
**一番効かせたい形が、そのまま通る。**

**(b) 引数が 2 つあり、片方だけ違う形** — `h(F, G1)` と `h(F, G2)`。

固定表は要求ごとに複製されるので、同じ関数の中に並んだこの 2 つは互いに影響しない。仮に一方が
他方の複製の中にあったとしても、`G1` と `G2` はソース上の別のラムダなので出どころが違い、固定表
では別の行になる。`F` のほうはどちらも同じラムダなので規則の 2 番目に当たる。**どちらの要求も
通る。**

**(c) 回るたびに包む形** — §7.2 の `grow`。

| 周 | 要求 | 出どころの組 | 固定表 | 判定 |
| ---: | --- | --- | --- | --- |
| 1 | `grow` を `op = L` で | (`grow`, `L`) | 空 -> `L` を載せる | 通す |
| 1 | `L` をスロット `op = L` で | (`L`, `L`) | 空 -> `L` を載せる | 通す |
| 2 | `grow` を `op = L1` で | (`grow`, `L`) | `L` が載っている | **捨てる** (`L1` は別のラムダ) |
| 2 | `L` をスロット `op = L1` で | (`L`, `L`) | `L` が載っている | **捨てる** |

`L1` の出どころが `L` であることが、ここで効いている。**1 段だけ特殊化して、そこで止まる。**
条件 2 が何も許さないのに比べれば、1 段分の直接呼び出しを得る。

周 2 で捨てられた呼び出しは、`L1` を包み直した一般のクロージャを一般の `grow` へ渡す形で残る。
外側のループの次の周は、その形をまた第 1 段で見ることになる。しかしそのとき歩いているのは
周 1 で作られた複製であり、固定表 `(grow, L) -> L` を持っている。判定は上の表の 3 行目と同じに
なり、**何周しても新しい複製は生まれない。**

#### 停止する論証

1 本の道すじを取る。その上で、出どころ O の関数がどんな複製になりうるかを数える。

複製を決めるのは「どのスロットを特殊化したか」と「各スロットに何を入れたか」である。後者は
固定表が縛る — スロットに入るラムダの出どころを P とすると、組 (O, P) に対して使えるラムダは
道すじの上で 1 つに固定されている。したがって各スロットの取りうる値は「特殊化しない」か
「出どころ P ごとに 1 つずつ定まるラムダ」のいずれかで、**出どころの個数だけの有限の選択肢**で
ある。スロットの個数も有限なので、**出どころ O の複製は、1 本の道すじの上に有限個しか現れない。**

出どころの集合自体が有限である (前述のとおり増えない) から、道すじに現れる複製は全部で有限個で
ある。同じキーは 1 度しか実体化しないので (§3.2)、道すじは複製を作り尽くしたところで必ず終わる。

固定表を導入する前は、この論証が立たない。§7.2 の表のように、同じ出どころ `L` から `L1`,
`L2`, ... といくらでも違うラムダが作られ、`grow` の複製もそのたびに新しいものになるからである。

#### 同じキーを違う固定表で要求したとき

複製の本体は、実体化したときの固定表によって変わりうる (深い道すじでは内側の要求が捨てられ、
包み直しが残る)。一方キーは `func` と `args` だけで決まり、固定表を含まない。したがって**同じ
キーの要求が違う固定表で立つと、先に実体化したほうの本体が共有される。**

これは受け入れる。正しさも停止性も損なわれず、失うのは「浅い道すじから来た要求が、深い道すじの
都合で保守的に作られた本体を掴む」ことによる最適化の取りこぼしだけである。固定表をキーに含める
と、同じ本体が固定表の違いだけで何通りも作られ、コード量が跳ねる。**取りこぼしを引き受けて、
コード量を抑える**方を採る。

#### 条件 2 と条件 3 は要らなくなる

規則は自己呼び出しか相互再帰かを区別しない。固定表を受け継ぐだけなので、閉路が何段であっても
同じ判定になる。ただし条件 3 が担っていたもう 1 つの役 (§3.3 の表を作る順序) は残るので、そちら
は表を最小不動点で解く形に変える必要がある。

#### 予算を先に置かない理由

このコンパイラには、参照カウントの最適化のために関数を複製する別のパスがあり、そちらは
「関数あたりの複製は 16 個まで」という上限を先に置いている。そのパスのキーは値の性質の組で
できていて、引数の個数に対して指数的に増えうるので、上限を置かないと現実に膨らむ。

このパスのキーは違う。スロットに入るのは**ソースに書かれたラムダ**であり、その個数はプログラム
が持つ呼び出し地点の数で頭打ちになる。上の論証のとおり、道すじの長さも有限で抑えられる。理論上
の上限はスロットの個数に対して大きくなりうるが、実際にそこまで伸びる形があるかは分からない。
まずコーパスで測り、膨らむ形が出たら**そのときの測定値を根拠に**上限を決める。先に魔法の数字を
置くことはしない。

### 7.5 テストの主張が変わる

本ブランチで `changing_closure` というテストを足した。`grow` と、閉路を一周する間に 1 回だけ
ラムダが包まれる形の 2 つを持ち、いまの振る舞い「複製が 1 つも作られない」ことを主張している。

§7.4 の規則を入れると 1 段は特殊化されるので、この主張は成り立たなくなる。そのとき主張を
「**複製の数が有限で、深さが 1 段で止まる**」に変える。ケースの値打ちは「この形でパスが暴走
しないこと」であって、「複製を作らないこと」ではない。

---

## 8. 段取りと各段での測定

1. **障壁 1 + 2** (済) — 中継役の複製が生成されることを確認済み。
2. **価値の判定を条件 4 だけにする** (§6) — コーパスで実行命令数・コンパイル時間・バイナリ
   サイズを測る。
3. **表を最小不動点で解き、新しい関数をその場で足せるようにする** (§3.3, §5.3) — 条件 3 がある
   間は 1 回舐めが既に不動点と一致するので、この段だけでは結果は変わらないはずである。コーパス
   で**変化が無いこと**を確認する (中立性の検査)。外側のループをワークリストに置き換えるなら
   (§3.4)、表の増分更新と一緒にこの段で行う。
4. **§7.4 の規則を入れ、条件 2 と条件 3 を落とす** — `changing_closure` のテストを §7.5 の形に
   変える。相互再帰が特殊化対象に入るので、コーパスで効くケースがあるかを測る。
5. **キャプチャスロットの実装** (§5) — `_heap_down_ranged` の複製が生成されることを確認し、
   `sort` を測る。
6. **コーパス全 46 ケース** — 連鎖が伸びるとコード量が増えるので、`sort` 以外が悪化していない
   ことを確認する。コンパイル時間も測る。
7. **全テスト** — 4 つの最適化レベルすべて。

到達目標は `sort` **-13%**。

3 は 5 の前に必要である。§5.3 のとおり、キャプチャスロットの要求はその場で立てるしかなく、その
とき相手が表に載っている必要がある。4 も 5 の前に必要である。5 を入れると §7.2 の無限が現れる
ので、その前に止める仕組みを置く。

## 9. まだ確かめていない前提

以下は設計の前提だが未確認である。実装前に潰す。

- **`_heap_down_ranged` が、インライン展開などを通った後も比較関数を同じ引数位置へ渡している
  こと。** ソースの上でそうなっていることは確かめた。最適化を通った後の姿は確かめていない。
- 13% のうち、`_heap_down_ranged` の特殊化だけで取れるのがどれだけか。比較関数が
  `_heap_sort_by_ranged` 以外の経路でも渡っている可能性がある。
- **この形 (クロージャを捕まえたクロージャが、そのクロージャを下流へ渡す) がコーパス全体で
  何箇所あるか。** 13% が `sort` 1 ケースの話なのか、他にも効くのかで、この設計の見合いが変わる。
- §5.4 の 3 段目 (キャプチャリストを素通しで運ぶ中継層の作り直し) が、機械的に書ける範囲に
  収まるか。中継層が何段も重なる形があると、書き換えの範囲が読めなくなる。
- §7.2 の無限は論証であって実測ではない。§5 の実装が動いた時点で、§7.4 の規則を外した版で
  `grow` が実際に暴走することを確かめる。
- §7.4 の「複製の中で新しいラムダが持ち上がることはない」が、前段の変換の詳細に依存している。
  前段が変わればこの前提も崩れるので、依存していることをコード側にも書き残す。

## 付録 A. 実測

測定条件: 対象コミット `2b03bc28`。命令数は `benchmark/speedtest/cases/sort` を cachegrind、
`-O experimental`、`--disable-cpu-feature 'avx512.*'` で測ったもの。

### A.1 目標の 13% の根拠

#122 の作業中に、**capture object の参照カウント操作だけを消した計測用ビルド** (健全ではないが
数字は取れる) で `sort` を測ると **-13.04%** だった。同じ作業で、参照カウントの分岐を全部外した
版も測っており、そちらの改善幅もほぼ同じだった。すなわち `sort` の伸びしろは、この 1 経路に
集中している。

### A.2 障壁 1 と 2 を直した結果

| | `sort` 命令数 | 差 |
| --- | ---: | ---: |
| `2b03bc28` (基準) | 64,037,014 | — |
| 障壁 1 + 2 | 64,106,502 | **+0.11%** |

障壁 1 の効きも数えた。転送が真になる箇所は、修正前は 59 個のプログラムすべてで 0 件だった。

### A.3 条件 2 と条件 3 を外すとどうなるか

以下の 3 つの形を 1 つのプログラムに書いて測った。

```fix
// (1) 自己再帰。次の周へ渡すのは、受け取ったラムダを包んだ別のラムダ。
grow : I64 -> (I64 -> I64) -> I64;
grow = |n, op| (
    if n == 0 { op(0) };
    grow(n - 1, |x| op(x) + n)
);

// (2) 相互再帰。受け取ったラムダをそのまま渡し合う。
ping : I64 -> (I64 -> I64) -> I64;
ping = |n, op| (
    if n == 0 { op(1) };
    pong(n - 1, op)
);
pong : I64 -> (I64 -> I64) -> I64;
pong = |n, op| (
    if n == 0 { op(2) };
    ping(n - 1, op)
);

// (3) 相互再帰。閉路を一周する間に 1 回だけラムダが包まれる。
tick : I64 -> (I64 -> I64) -> I64;
tick = |n, op| (
    if n == 0 { op(3) };
    tock(n - 1, |x| op(x) + 1)
);
tock : I64 -> (I64 -> I64) -> I64;
tock = |n, op| (
    if n == 0 { op(4) };
    tick(n - 1, op)
);

main : IO () = (
    let a = grow(4, |x| x);            // 10
    let b = ping(4, |x| x * 10);       // 10
    let c = tick(4, |x| x * 100);      // 302
    println((a + b + c).to_string)     // 322
);
```

**条件 2 を外したコンパイラで (1) と (3) をビルドすると、ビルドは成功し、`grow` と `tock` の複製
はそれぞれ 2 個で止まった。** 答えも正しい。§7.2 の論証のとおりである。

**条件 3 は (2) を止めていなかった。** `pong` の複製が生成されている。生成物を読むと、`pong` が
呼んでいるのは `ping` ではなく `pong` 自身だった。インライン展開が `ping` の本体を `pong` に
取り込んで自己再帰にしてしまうので、条件 3 の判定に届く前に相互再帰が消えている (§7.1 に反映
済み)。

(1) と (3) は `src/tests/test_closure_specialization/cases/changing_closure` として本ブランチで
テストに入れた。

### A.4 構造体を通した場合

構造体のフィールドに入れたラムダを取り出して関数へ渡すプログラムを 2 通り書いて測った。

| 形 | `apply_many` の複製 | 結果 |
| --- | ---: | --- |
| 構築地点が 1 つで、そのまま `h.@op` を渡す | 2 個 | 構造体経由の呼び出しも特殊化された |
| 構築地点が 2 つあり、分岐で合流してから `h.@op` を渡す | 1 個 | 構造体経由は間接呼び出しのまま |

上の行で特殊化されるのは、このパスが構造体を追ったからではなく、前段の最適化が
`S { f : L }.@f` を `L` に畳んだからである。

| ケース | 周 1 | 周 2 | 周 3 | 周 4 |
