# 複製の幅を止める

`closure_specialization` は、クロージャを引数に取る関数を「渡されるラムダごとに複製する」最適化
である。この文書は、その複製の個数が**関数の持つクロージャ引数の個数に対して指数的に増える**
ことと、その止め方を書く。

詳しい実測は付録にまとめ、本文には論の運びに要る数字だけを置く。

---

## 1. 症状

クロージャを k 個受け取る関数を 1 つ持つプログラムを、k を変えながらビルドする。プログラムの
行数は k に比例して増えるだけだが、コンパイルに要する時間とメモリは次のようになる。

| k | 時間 | 最大常駐メモリ |
| ---: | ---: | ---: |
| 4 | 3.3 秒 | 209 MB |
| 5 | 9.5 秒 | 539 MB |
| 6 | 37.4 秒 | 1836 MB |
| 7 | 368 秒 | 6849 MB |

スロットが 1 つ増えるごとに、時間もメモリも 3 倍前後になる。k = 8 は 20 GB を超える見込みで、
実際に測ることは諦めた。

**このパスが作った複製は、最終的な機械語に 1 つも残らない。** 同じプログラムの `.text` は
k = 1 で 3457 バイト、k = 6 で 3547 バイト、関数の個数はどちらも 20 である。指数的に増えるのは
パス自身の仕事と、それを受け取る LLVM の仕事だけで、成果物は増えない (付録 A.3)。

この形はブランチが作った退行である。ブランチに入る前のコンパイラは、この形の複製をどの k でも
1 つも作らない。停止性のために置かれていた古い条件が、「そのクロージャ引数に引数自身以外のものを
渡す自己呼び出しがあるなら、その引数は特殊化しない」というもので、いま問題にしている形がまさに
それに当たっていた。その条件を落としたのが本ブランチである。落としたこと自体は正しい —
落とすかわりに入れた停止規則は連鎖の**深さ**を止めており、深さを止める役目は果たしている。
止まっていないのは**幅**である。

## 2. 用語

この文書を読むのに要る範囲で、パスの語彙を定義する。

### 2.1 持ち上げとキャプチャリスト

ラムダは、**捕まえた変数を詰めた構造体**と、**それを第 1 引数に取るグローバル関数**の 2 つに
分解される。前者を**キャプチャリスト**、後者を**持ち上げ済みラムダ**と呼び、この分解を
**持ち上げ**と呼ぶ。

```fix
let n = 3;
let f = |x| x + n;
```

は、次のようになる。

```fix
type Cap = unbox struct { n : I64 };      // キャプチャリスト

lam : Cap -> I64 -> I64;                  // 持ち上げ済みラムダ
lam = |{ n : n }, x| x + n;

let f = lam(Cap { n : 3 });               // 部分適用すると元のクロージャに戻る
```

キャプチャリスト `Cap { n : 3 }` 自体は関数ではない。呼ぶには持ち上げ済みラムダの名前が要る。
逆に、キャプチャリストを持ち上げ済みラムダに部分適用すれば、いつでも元どおりのクロージャに
戻せる。以降この操作を**包む**と呼ぶ。

### 2.2 狭めること

キャプチャリストのフィールドが別のクロージャを持つとき、そのフィールドの型を、一般のクロージャ型
から「そこに入る特定のラムダのキャプチャリスト型」へ差し替えられる。これを**狭める**と呼ぶ。
狭めたフィールドは関数ポインタを持たなくなり、そこを通る呼び出しはラムダを名前で直接呼ぶ形に
書け、参照カウントの操作が消える。`sort` の実行命令が 43.9% 減ったのは、この 1 点と、そこで
開いた直接呼び出しの先のインライン展開による。

同じことが関数の通常の引数についても言える。引数の型をキャプチャリスト型に差し替えて、関数の
複製を作る。**キャプチャリストのフィールドも通常の引数も、値がその関数に入ってくる入口である**
ことに変わりはないので、両方まとめて**スロット**と呼ぶ。

```rust
// 値が関数へ入ってくる入口。
struct Slot {
    // 何番目の引数か。キャプチャリストのフィールドは第 0 引数を通るので 0。
    arg: usize,
    // キャプチャリストのフィールドなら、その位置。
    field: Option<usize>,
}
```

### 2.3 木と単位

「正体の分かっているクロージャ値」がどんなものかは、木で書ける。根がそのラムダで、子が狭めた
キャプチャフィールドである。

```rust
struct Tree {
    // この値を通る呼び出しが届くラムダ。
    lambda: FullName,
    // 正体の分かっているキャプチャフィールドを、位置の昇順で。
    fields: Vec<(usize, Tree)>,
}
```

そして、パスが作る複製 1 つを**単位**と呼ぶ。

```rust
// 1 つの複製: どの関数を複製したか、その各入口が何を受け取ると分かっているか。
// 置き換えが空なら、その関数自身を指す。
struct UnitKey {
    origin: FullName,
    subst: Vec<(Slot, Tree)>,
}
```

`origin` を**出どころ**と呼ぶ。単位の名前は `origin` の名前に `subst` のハッシュを付けたもの
なので、本体を作る前に決まる。**同じ鍵の単位は 1 度しか実体化しない。**

「特殊化された関数」と「狭めた持ち上げ済みラムダ」の区別は無い。後者は `origin` がラムダで
`subst` の鍵がキャプチャフィールドなだけの、同じ単位である。

### 2.4 パスの形と、4 つの書き換え規則

パスは 2 相からなる。

```
run(プログラム):
    第 L 相: 全シンボルのラムダを持ち上げきる
    表 = 特殊化する価値のあるスロットを計算する(プログラム)
    第 S 相: 単位の要求が尽きるまで実体化する
```

第 L 相が終わった時点で**出どころの集合が確定し、以後増えない**。表はそのスロットを複製する
価値があるかを一度だけ計算したもので、第 S 相の間ずっと変わらない。

第 S 相は単位のワークリストである。ある単位の本体を歩いていて、書き換えが起きるのは 4 箇所しか
ない。このうち**木が新しく生まれるのは R1 と R2 の 2 箇所だけ**で、判定もこの 2 箇所にある。

- **R1 構築** — キャプチャリストを組む地点。そこへ来る値の正体が分かっていて、表がそのスロット
  を載せていて、停止規則が許すなら、フィールドを狭める。狭めたフィールドの集まりが木になり、
  その木を受け取るラムダの単位をその場で要求する。
- **R2 引数** — 呼び出しの地点。正体の分かっている引数について、表がそのスロットを載せていて、
  停止規則が許すなら、狭めた形で渡す。通った引数を集めて単位を要求し、呼び先をその名前へ
  差し替える。
- **R3 呼び出し** — キャプチャリストを通る呼び出しは、対応する単位の名前へ差し替える。判定は無い。
- **R4 既定** — 上のどれにも当たらないキャプチャリストの出現は、すべて包む。

**R1 と R2 が「通さない」と決めた地点は、そこで包めば済む。** 木を作った時点でそれを受け取る
ラムダの単位も要求してあるので、狭めた値を一般のクロージャに戻す道は必ずある (design.md の
「包み直しをいつでも許す」)。したがって**通さないことは常に安全**で、失うのは最適化だけである。
この性質が、これから置く上限を「1 つの条件を足すだけ」で済ませる。

### 2.5 固定表

いま置かれている停止規則が**固定表**である。

```rust
// (関数, スロット, 木の根のラムダ) -> その道すじで入れてよい木。
type Pinned = Map<(FullName, Slot, FullName), Tree>;
```

読み方は「この道すじでは、この関数のこのスロットに、根がこのラムダの木を入れるなら、入れて
よいのはこの 1 つだけ」である。木は要求を伝って持ち回られ、要求ごとに複製されるので、別々の
要求は互いに影響しない。

```rust
// 木 t をスロット s へ入れてよいかを答え、通すならその約束を表に書く。
fn commit(pinned: &mut Pinned, func: &FullName, slot: Slot, tree: &Tree) -> bool;
```

これが止めるのは、**受け取ったクロージャを包んで次の周へ渡す再帰**である。周ごとに木が 1 段
深くなるが、根は同じラムダなので見出しが一致し、2 周目で値が食い違って通らなくなる。連鎖の
深さはここで尽きる。

## 3. 再現するプログラム

k = 3 のときの姿を書く。一般の k では、`g` の引数が k 個になり、再帰呼び出しが k 本になる。

```fix
module Main;

g : (I64 -> I64) -> (I64 -> I64) -> (I64 -> I64) -> I64 -> I64;
g = |p0, p1, p2, n| (
    if n <= 0 { (p0(0) + p1(0) + p2(0)) % 1000 };
    ( g(|x| (p0(x) + 1) % 97, p1, p2, n - 1)
    + g(p0, |x| (p1(x) + 2) % 97, p2, n - 1)
    + g(p0, p1, |x| (p2(x) + 3) % 97, n - 1) ) % 1000
);

main : IO () = ( let c = 3; println(g(|x| (x * c + 0) % 97, |x| (x * c + 1) % 97, |x| (x * c + 2) % 97, 2).to_string) );
```

要点は 3 つである。

1. `g` は k 個のクロージャを受け取り、**そのすべてを基底で呼ぶ**。だから k 個のスロットすべてが
   「複製する価値がある」と表に載る。
2. 再帰呼び出しは k 本あり、**それぞれ違う 1 つのスロットだけを包み直す**。残りは素通しする。
3. `main` は k 個とも別々のラムダを渡す。

第 L 相の後、`g` の本体にラムダ式は残らない。j 番目の再帰呼び出しに書かれていたラムダは持ち上げ
られて、キャプチャリストに `p_j` 1 つを持つ持ち上げ済みラムダ `L_j` になっている。`main` の k 個の
ラムダも同様に `K_0 .. K_{k-1}` になっている。

---

## 4. なぜ増えるのか

k = 2 で、単位が生まれる順を追う。`K_i{}` は「`K_i` そのもの、狭めたフィールドは無い」木、
`L_j{K_j}` は「`L_j` の第 0 フィールドを `K_j` に狭めた」木である。

**1. `main` の単位を歩く。** R2 が `g(K_0, K_1, 2)` を見る。

| スロット | 入れる木 | 見出し | 固定表 | 判定 |
| --- | --- | --- | --- | --- |
| `arg0` | `K_0{}` | `(g, arg0, K_0)` | 空 -> `K_0{}` | 通す |
| `arg1` | `K_1{}` | `(g, arg1, K_1)` | 空 -> `K_1{}` | 通す |

単位 `U_a = g[arg0 := K_0{}, arg1 := K_1{}]` を要求する。

**2. `U_a` を歩く。** この本体では `p0` の正体が `K_0{}`、`p1` が `K_1{}` と分かっている。
再帰呼び出しは 2 本ある。

- **1 本目** — R1 が `L_0` のキャプチャリストを組み、フィールドに来る `p0` を狭める
  (`(L_0, field0, K_0)` は空なので通る)。木 `t_0 = L_0{K_0}` ができる。続く R2 は
  `arg0` に `t_0`、`arg1` に `K_1{}` を渡す。見出し `(g, arg0, L_0)` は**空である** —
  固定表に載っているのは `(g, arg0, K_0)` であって、根が違うので別の行になる。通る。
  単位 `U_b = g[arg0 := t_0, arg1 := K_1{}]`。
- **2 本目** — 同じことが `arg1` 側で起きる。単位 `U_c = g[arg0 := K_0{}, arg1 := t_1]`。

**3. `U_b` を歩く。** 固定表には `(g, arg0, L_0) -> t_0` が載っている。

- **1 本目** — 木は `L_0{t_0}` になる。根は `L_0` のままなので見出しは一致し、値が違うので
  **通らない**。ここで包む。`arg0` は特殊化されず、`arg1` だけが通って、単位
  `U_d = g[arg1 := K_1{}]` になる。**深さはここで止まっている。**
- **2 本目** — `arg1` 側は初めてなので通る。`arg0` は `t_0` のまま一致して通る。単位
  `U_e = g[arg0 := t_0, arg1 := t_1]`。

以降も同じである。**固定表が縛るのはスロット 1 つ 1 つで、単位を決めるのは k 個のスロットの
組である。** スロット 1 つが取りうる状態は 3 つ — 「元のまま (`K_i{}`)」「1 回包んだ
(`L_i{K_i}`)」「通らなかったので載っていない」 — で、それが k 個独立に動くので、単位は
おおよそ `3^k` 個になる。実測もそうなっている (付録 A.2: k = 6 で `g` の複製 791 個、
`3^6 = 729`)。

同じ本体からラムダの単位も要求されるが、そちらはスロット j ごとに 3 個で、**k に対して線形**
である。指数的に増えるのは `g` の複製だけである。

**一言でいえば、固定表はスロットごとの規則であり、スロットごとの規則はどれも組み合わせの積を
残す。** 深さを止めても幅は止まらない。

### 4.1 コーパスがこの形に当たらない理由

計測に使っている 46 ケースで最も複製される出どころは `Std::Iterator::fold` と `Std::loop` で、
どちらもクロージャを 1 つしか取らない。1 つのキャプチャリストが正体の分かるクロージャを 2 つ
持つ形も、46 ケースにもテストにも現れない (本ブランチで `two_narrowed_fields` を書き足したのは
そのためである)。スロットが 1 つなら組み合わせが無いので、問題は姿を見せない (付録 A.4)。

## 5. 固定表を強くしても止まらない

固定表の見出しから木の根を落として `(関数, スロット)` にすれば、「1 つのスロットは、1 本の
道すじで 1 つのラムダにしか特殊化されない」という、より強い規則になる。これを実際に作って
測った (付録 A.5)。

複製の個数は k = 6 で 809 個から 138 個に減るが、**指数であることは変わらない** — スロット
1 つあたりの倍率が約 2.7 から約 1.9 になるだけで、k = 6 のメモリは依然 566 MB である。理由は
4 節の状態の数え上げから分かる。この案は「1 回包んだ」状態を消すが、「通らなかったので載って
いない」状態は消せない。スロットごとに 2 状態が残り、`2^k` になる。

そしてこの案には代償がある。1 本の道すじの上で、同じ関数の同じスロットに違うラムダが正当に
来る形 — たとえば中継役の関数を、経路の途中で 2 つの異なる比較関数に対して使う形 — が
特殊化されなくなる。

**どのようにスロットごとの規則を強くしても、単位はスロットの組で決まるので積が残る。**
個数を抑えるには、スロットではなく**単位の個数そのもの**を数える必要がある。

## 6. 修正案: 出どころあたりの複製数に上限を置く

### 6.1 置くもの

```rust
// 出どころごとに、このパスが作ると約束した単位と、それを要求したソース位置。
//
// 固定表は連鎖の深さを止める。こちらは幅を止める。固定表はスロット 1 つについての規則で、
// スロット 1 つについての規則は組み合わせの積を残すからである。
struct CopyBudget {
    units: Map<FullName, Set<UnitKey>>,
    sites: Map<FullName, Set<(PathBuf, usize, usize)>>,
}

// どのソース位置も要求していないときに許される、組み合わせた複製の個数と、
// 要求したソース位置 1 つが持ち込む追加分。
const BASE_COMBINING_COPIES: usize = 8;
const COMBINING_COPIES_PER_SITE: usize = 1;

impl CopyBudget {
    // 位置 site から要求された単位 unit を作ると約束し、作ってよいかを答える。
    //
    // 既に約束した単位はいつでも通る。新しい単位は、要求したソース位置が稼いだ許容量に
    // 出どころがまだ届いていなければ通る。通さなかった地点は値を包むので、許容量をどう
    // 決めても正しさを損なうことはない。
    fn admit(&mut self, unit: &UnitKey, site: Option<&Span>) -> bool {
        if unit.lambdas() < 2 {
            return true;
        }
        if self.units.entry(unit.origin.clone()).or_default().contains(unit) {
            return true;
        }
        let sites = self.sites.entry(unit.origin.clone()).or_default();
        if let Some(site) = site {
            sites.insert((site.input.file_path.clone(), site.start, site.end));
        }
        let allowance = BASE_COMBINING_COPIES + COMBINING_COPIES_PER_SITE * sites.len();
        let committed = self.units.entry(unit.origin.clone()).or_default();
        if committed.len() >= allowance {
            return false;
        }
        committed.insert(unit.clone());
        true
    }
}
```

この表は第 S 相の全体で 1 つ持つ。固定表が道すじごとに複製されるのと対照的で、**予算は
プログラム全体で共有する資源**である。

### 6.2 何を数えるか: 単位が名指すラムダの個数

数えるのは、**ラムダを 2 つ以上名指す複製**である。積になって増えるのはそれで、ラムダを
1 つしか名指さない複製は「その入口に来る値 1 つにつき 1 個」なので、呼び出し地点の個数に
対して線形にしか増えない。

置き換えたスロットの**個数**では足りない。木は入れ子になるので、「1 段につき 1 フィールド
だけ狭める」形は、どの階層でも置き換えスロットが 1 つのまま増えられる。実測 (付録 A.8):
クロージャ引数を 1 つしか持たない 10 行のプログラムで、再帰のたびに別のラムダで包み直す
だけで、複製は k=6 で 3913 個・312 秒・4.09 GB になる。増えているのは「どのラッパーを
どの順で通ったか」の場合の数で、固定表は 1 本の道すじを止めるが、道すじの本数は止めない。

木は共有されるので、名指すラムダの個数は木を作るときに数えて `TreeData` に持つ。歩いて
数えると、共有された木では経路の本数だけの費用がかかる。

### 6.3 許容量をソース位置でスケールさせる理由

出どころごとに固定の上限を置くと、**無関係な呼び出し地点どうしが枠を取り合う**。クロージャを
2 つ取る単純な関数を、N 個の独立した 1 行関数からそれぞれ別のラムダ対で呼ぶプログラム
(組み合わせはどこにも無い) で、上限 16 の固定枠は 17 箇所目から特殊化を落とす。実行ファイルの
`.text` は N=40 で 16514 バイト、上限を外したときの 10930 バイトに対して 51% 増える (付録 A.7)。
どの地点が落ちるかは走査順で決まり、熱さとは無関係である。

要求したソース位置の個数で許容量が伸びるようにすると、この母集団は**自分の分を自分で持ち込む**。
N 個の地点は N 個の位置なので許容量も N だけ伸び、上の `.text` はどの N でも上限なしと完全に
一致する。一方、増え続ける連鎖は**同じソース位置から何度も要求する** — 複製の本体は同じテキストの
複製だから — ので、許容量は伸びずに要求だけが増え、そこで止まる。

したがって、数えられる複製の総数は

```
sum over 出どころ O of (BASE + C * |O を要求した位置|) <= (BASE + C) * |プログラムの位置|
```

で、**プログラムテキストの大きさに線形**である。

### 6.4 どこで引くか

木が新しく生まれる 2 箇所、すなわち判定が既にある 2 箇所で引く。

- **R1** (`narrow`) — 狭めるフィールドが決まり、木ができたところ。その木を受け取るラムダの
  単位を `admit` に掛け、通らなければ**狭めを 1 つも行わずに** `known` をそのまま返す。
- **R2** (`start_visit_app`) — 狭めて渡す引数が決まったところ。`UnitKey::new(func_name,
  specialized_args)` を `admit` に掛け、通らなければ**この呼び出しでは 1 つも狭めず**、
  すべて包んだ引数で元の関数を呼ぶ。

どちらも「通らなければ包む」で、これは 2.4 節のとおり常に安全である。単位が実体化される時点
ではなく、**呼び出しを書き換えるかどうかを決める時点**で引くのが要点で、呼び出しを差し替えて
から予算切れに気づいても、その名前の本体を作らずに済ませる道は無い。

判定の粒度は呼び出し 1 つ分である。1 つのスロットだけ諦めて残りを通す、という中間の
振る舞いは取らない。予算に達した出どころは既に 16 個の複製を持っており、そこから先の
取りこぼしを細かく減らすことに意味は薄い。

実装上の注意が 1 つある。`narrow` は現在、フィールドを 1 つ通すたびに呼び出し側の固定表へ
書き込む。予算で取り消しうるようになるので、**書き込みは局所の複製に対して行い、`admit` が
通ったときだけ呼び出し側へ書き戻す**必要がある。そうしないと、実際には起きなかった狭めの
約束が道すじに残る。

### 6.5 なぜ 8 と 1 か

コーパス 46 ケースの全ビルドで、**1 つの関数が持つ複製の最大は 4 個**である (付録 A.4)。
最も複製されるのは `Std::Iterator::fold` と `Std::loop` で、`sort` と `cp_lib_conv_zp` で
4 個、それ以外のケースでは 1 個か 2 個である。基底の 8 は、その最大に対して 2 倍の余裕を、
どの位置も要求していない時点で与える。

位置あたりの追加分は 1 で足りる。位置 1 つは自分の分を 1 つ要求するので、要求の前に位置を
数えれば、新しい位置からの最初の要求は必ず通る。2 にしても良性の形は変わらず、病的な形の
費用だけが増えることを実測した (付録 A.9): スロット 16 個の形で、複製 350 個 / 7.73 GB が、
1 にすると 206 個 / 4.39 GB になる。良性の形はどちらでも上限なしと完全に一致する。

このコンパイラには先例がある。参照カウントの最適化のために関数を複製するパス
(`rc_ir/specialization.rs`) が、`MAX_CLONES_PER_FUNCTION = 16` を同じ理屈で置いている —
鍵の空間が積になるので上限を置き、超えた分は何も証明しない版に落とす。そちらは固定枠なので、
無関係な呼び出し地点が取り合う問題を同じ形で抱えている。

### 6.6 何が抑えられるか

出どころの集合は第 L 相で確定し、第 S 相の間ずっと増えない。**ラムダを 2 つ以上名指す複製は、
出どころ 1 つにつき「基底 + 要求した位置の個数」で頭打ちになる**ので、その総数は 6.3 節の
とおりプログラムテキストの大きさに線形である。残るラムダ 1 つの複製は「その入口に来る値
1 つにつき 1 個」なので、これもプログラムが持つ値の個数で頭打ちになる。したがってスロットの
個数に対する指数も、包み直しの順序に対する指数も消える。

固定表を残す理由も、これで言える。予算だけにすると、深さの暴走 (受け取ったクロージャを
包んで次の周へ渡す再帰) が予算を丸ごと食い潰し、許された複製がすべて「1 段深いだけの同じ
もの」に費やされる。**固定表は魔法の数字なしに深さを止め、予算は幅を止める。** 役目が違う
ので両方置く。

## 7. 退けた案

**置換の大きさに上限を置く (同時に狭めるスロットは m 個まで)。** 単位の個数は `k` の m 次
多項式に落ちる。しかし失う最適化を決めるのが「何番目のスロットまで見たか」という、得られる
利得と無関係な順番になる。本ブランチには、1 つのキャプチャリストが正体の分かるクロージャを
2 つ持つ形のテスト (`two_narrowed_fields`) が既にあり、m = 1 はそれを落とす。どの m を選んでも
「クロージャを m+1 個熱く呼ぶ関数」で理由なく効かなくなる。採用したのは、置換の大きさで
**断る**のではなく、置換が 2 つ以上のものだけを**数える**形である (6.2 節)。どの組み合わせを
作るかは予算が尽きるまで自由で、尽きた地点だけが包まれる。

**プログラム全体の複製の総数に上限を置く。** 大きなプログラムほど最適化が効かなくなる。
`cp_lib_bipartite` が 32 個作っている一方で 25 ケースは 2 個以下なので、全体の総数はプログラム
の大きさに強く依存し、上限として意味のある値を選べない。

**予算を超えた単位を、ラッパー関数として実体化する。** 呼び出しの差し替えは行い、その単位の
本体は「受け取った狭めたキャプチャリストを包み直して、元の関数を呼ぶ」だけにする。判定が
実体化の 1 箇所に集まる利点はあるが、間接呼び出しが 1 段増えたうえに、拒否した地点を包む道が
既にある以上、遠回りである。呼び出しの地点で断るほうが、生成物も判定も素直になる。

## 8. 入れたあとに確かめたこと

**コーパスの生成物が 1 バイトも変わらない。** 46 ケースを予算導入前のコンパイラと突き合わせ、
パスを出た直後のシンボルダンプが 46/46 完全一致した。**比較が働くことも確かめてある**:
入口の個数で数える形に戻して上限を 3 に下げると、1 関数あたりの複製が 4 個ある 4 ケース
(`sort`、`cp_lib_conv_zp`、`nbody`、`nbody_fold`) だけが食い違い、そこに届かない 2 ケースは
一致する。

**良性の 3 つの形は上限に触れない**。(a) 違うラムダで同じ `fold` を呼ぶ地点を 40 箇所 —
複製 40 個、拒否ゼロ。(b) クロージャを 2 つ取る 1 つの関数を 40 箇所から別々のラムダ対で
呼ぶ — `.text` は N = 16/20/30/40 で 6462/7189/9090/10930 バイト、**上限を外したときと完全に
一致**する。(c) そういう関数が 40 個あってそれぞれ 1 箇所から呼ばれる — 同じく完全に一致。

**病的な 3 つの形が収まる** (付録 A.6, A.8)。スロット k 個の形は k = 7 が 368 秒 / 6849 MB
から収まり、前は測ることを諦めた k = 16 が 48 秒 / 4.39 GB でビルドできる。包み直しの順序が
増える形は k = 6 で 3913 複製 / 312 秒 / 4.09 GB が 27 複製 / 1.4 秒 / 134 MB になり、k に
線形になる。別々の関数の連鎖を 2 通りに包む形は k = 10 で 27567 複製 / 67 秒 / 2.17 GB が
293 複製 / 3.8 秒 / 185 MB になる。答えはどれも 4 つの最適化レベルで一致する。

**ビルドは決定的である。** 予算は先に来た要求が取るので、走査の順序が変われば生成物が変わり
うる。`Map` と `Set` が使うハッシュは乱数種を持たないので順序は決まっており、同じソースを
2 回ビルドしたシンボルダンプは一致する。

**テストは 1342 件が `experimental` と `max` の両方で通る。** 回帰テストは 2 つで、
`independent_slots` が入口の組み合わせを (複製 24 個以下)、`wrapped_chain` が包み直しの順序を
(複製 17 個以下) 見る。既存の `changing_closure` が連鎖の深さの尽きることを見ているので、
深さ・幅・順序の 3 つが揃う。上限を外したコンパイラで、前者は 95 個、後者は 129 個を数えて
落ちる。

### A.8 包み直しの順序が増える形

クロージャ引数を 1 つしか持たない 10 行のプログラム。再帰のたびに、受け取ったクロージャを
k 通りの別のラムダで包み直して次の周へ渡す。どの単位も入口を 1 つしか置き換えず、どの
キャプチャリストもクロージャを 1 つしか持たない。

| k | 3 | 4 | 5 | 6 |
| --- | ---: | ---: | ---: | ---: |
| `g` の複製 (入口の個数で数える) | 31 | 129 | 651 | 3913 |
| 時間 / メモリ | 3.4 秒 / 118 MB | 8.1 秒 / 184 MB | 41 秒 / 626 MB | 312 秒 / 4.09 GB |
| `g` の複製 (名指すラムダで数える) | 18 | 21 | 24 | 27 |
| 時間 / メモリ | 0.6 秒 / 117 MB | 0.7 秒 / 120 MB | 1.0 秒 / 127 MB | 1.4 秒 / 134 MB |

再帰の深さには依存しない (k = 4 では深さ 2/3/4/5 のどれでも 129)。固定表は 1 本の道すじで
同じラッパーを 2 度使うことを止めるが、**ラッパーを使う順序の個数**は止めない。

別々の関数の連鎖でも同じことが起きる。k 個の関数が順に並び、各関数が次の関数を 2 通りの
包み方で呼ぶ形では、複製は厳密に `2^(k+1) - 3` になる。

| k | 8 | 10 |
| --- | ---: | ---: |
| 入口の個数で数える | 6843 複製 / 6.8 秒 / 605 MB | 27567 複製 / 67 秒 / 2.17 GB |
| 名指すラムダで数える | 225 複製 / 2.1 秒 / 140 MB | 293 複製 / 3.8 秒 / 185 MB |
