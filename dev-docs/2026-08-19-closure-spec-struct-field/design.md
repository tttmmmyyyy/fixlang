# 引数の構造体のフィールドを特殊化の入り口にする (#450)

## 直すもの

`Iterator` の組み合わせ子は、渡された関数を**自分の構造体のフィールド**に置く。

```fix
type MapIterator i a b = unbox struct { iter : i, f : a -> b };
map = |f, iter| MapIterator { iter : iter, f : f };
```

`closure_specialization` は関数の値を 2 通りの道で追う。引数として渡された関数と、持ち上げられた
ラムダが受け取るキャプチャリストのフィールドに入った関数である。構造体のフィールドはどちらでも
ないので、`f` はクロージャの値のまま残り、要素ごとに間接呼び出しになる。

`arr.to_iter.map(f).fold(0, op)` を最適化し切った後の本体では、同じ関数の中に 2 つの呼び出しが並ぶ。

```
destructure #v2 { .0 -> iter, .1 -> f : U8 -> I64 }
retain f.1 @deeplocal                       // 要素ごとに参照カウント
let struct#58 = struct_make(struct#48, f)   // 要素ごとに作り直し
let app#59 = f(v#45)                        // 間接。map の関数はフィールドに入っている
let app#67 = Main::...closure_lam1#funptr3(#v1, app#59, #v0)   // 直接。fold の演算子は引数
```

## 効き目 (実測)

変換が作る形を Fix で手書きして測った。300,000 要素の `Array U8`、`-O max`、1 要素あたりの命令数。

| 連鎖 | 今 | 変換後 | 手書きループ |
| --- | --- | --- | --- |
| `map` -> `fold` | 14.00 | **0.84** | - |
| `filter` -> `fold` | 20.02 | **12.02** | - |
| `map` -> `filter` -> `fold` | 29.02 | **13.02** | 1.44 |
| `map` -> `filter` -> `to_array` | 33.04 | **15.54** | 11.52 |

`fold` に `advance` を展開した形だけを取り出して 3 通りに手書きすると、複製がキャプチャリストを
どう受け取るかは速さに効かない。

| 受け取り方 | 命令数 |
| --- | --- |
| 今の形。構造体がクロージャを持ち、間接呼び出し | 29.00 |
| キャプチャリストを余分の引数で受け取る | **0.72** |
| 構造体のフィールドの型をキャプチャリストに絞る | 0.84 |

構造体に残ったクロージャは、フィールドからフィールドへ移されるだけで読まれないので、要素ごとの
参照カウントは残らず、作り直しは LLVM がレジスタに落とす。

`map` は完全に融合して消える。`filter` に 12 命令が残るのは、`FilterIterator::advance` が
条件に合わない要素を飛ばすために**自分自身を呼ぶ**からで、これは関数の置き場とは別の問題である。

## 今の仕組みのうち、この変更が使うもの

**decapturing** は各ラムダをグローバル関数に持ち上げ、捕まえた環境を運ぶ非ボックスの構造体
(キャプチャリスト) を鋳造する。ラムダの値はそのキャプチャリストの値になり、クロージャが要る場所
では持ち上げた関数を部分適用して包み直す。

**特殊化**は、そういう値を受け取るグローバル関数を、受け取る値ごとに複製する。複製の中では
その値を名前で呼べる。どの入り口を複製する価値があるかは `find_specializable_slots` が
プログラム全体で 1 度解き、`Slot { arg, field }` の集合として持つ。

**絞り込み (narrowing)** は、キャプチャリストのフィールドがまた別のキャプチャリストを持つとき、
そのフィールドの型をクロージャからキャプチャリストへ変える。型が変わるので、それを消費する
ラムダも複製される。これがあるので、受け取ったクロージャをそのまま渡すだけのラムダを越えて
複製の鎖が続く。

## パスが見ている本体

`arr.to_iter.map(f).fold(0, op)` に対して、`closure_specialization` の入力は次の形をしている
(`--emit-symbols` の `6.inline_local`)。`advance` は既にインライン展開されている。

```
fold : I64 -> (I64 -> I64 -> I64) -> MapIterator (ArrayIterator U8) U8 I64 -> I64;
fold = |#param| |#v0| |#v1| (
    match (
        let MapIterator {iter: #v2, f: f} = #v1;           // 引数を分解する
        match ( ...ArrayIterator の advance... ) {
            none() => union_make_0(none),
            some((#v3, a)) =>
                let some = Tuple2{0 : MapIterator{iter : #v3, f : f}, 1 : f(a)};   // 組み立てと呼び出し
                union_make_1(some)
        }
    ) {
        none() => #param,
        some((iter, a)) => fold(#v0(a, #param), #v0, iter),                        // 再帰。引数 2
    }
);
```

`MapIterator` の値が本体の中で通る場所は、引数、分解のパターン、組み立て、`Tuple2` のフィールド、
`Option` の payload、`match` が束縛する名前、再帰呼び出しの引数 2 の 7 か所である。

## 設計

### 複製はキャプチャリストを余分の引数で受け取る

`fold` の引数 2 が持つ `MapIterator` の `f` に、持ち上げられたラムダ `lam_f` が入っていると分かった
とき、`fold` の複製は**そのラムダのキャプチャリストを余分の引数で受け取る**。構造体の型も、その
フィールドの型も、値も、何一つ変わらない。

```
fold#spec : I64 -> (I64 -> I64 -> I64) -> MapIterator ... -> #CapList@lam_f -> I64
```

複製の中では、引数 2 を分解して得た名前 `f` の**呼び出しだけ**が `lam_f(fcap, ...)` に置き換わる。
`f` を構造体へ入れ直す箇所はそのまま `f` を置く。クロージャを作り直すと要素ごとに確保が起きる
ので、置き換えるのは呼び出しの位置に限る。

余分の引数は、それが属する引数の**直後**に挿し込む。引数の数は元の関数の型が決めているので、
末尾に足すと部分適用の形が崩れる。

### `Slot` の 2 つの読み

`Slot { arg, field: Some(j) }` は「第 `arg` 引数として届く構造体の j 番目のフィールド」を指す。
複製がその値を受け取る道は 2 通りあり、その関数が持ち上げられたラムダかどうかで決まる。

- 持ち上げられたラムダの第 0 引数はそのキャプチャリストなので、フィールドの**型を絞る**。
  これは既にある仕組みで、複製の鎖がクロージャを中継するだけのラムダを越えて続くのを支えている。
- それ以外の引数の構造体では、**余分の引数**で受け取る。

### 型を変えないことが何を買うか

複製の中で構造体の型が変わらないので、次のどれも壊れない。

- 取得関数 `.@f`、`mod_` / `act_`、穴の開いた形。フィールドはクロージャのままで、punched 形も
  鋳造しなくてよい。
- 構造体が本体の外へ出ること。返り値でも、配列の要素でも、union の payload でも、届く先が
  受け取るのは今までどおりの `MapIterator` である。
- 予算が複製を断ること。断られた呼び出しは元の関数を呼ぶだけで、渡す値は同じである。

### 断る条件

直接呼びが正しいのは、**その複製に入るどの経路でも、フィールド j が同じラムダを持つ**ときに限る。
呼び出し 1 つ 1 つについては、引数の入り口と同じく `commit` が鎖に沿って 1 つの値へ縛る。
複製の**中**で作り直される値については、本体を見て次を全部確かめる。

- 引数 i の型が構造体で、フィールド j の型がクロージャである
- 本体が引数 i を `Pattern::Struct` で分解し、フィールド j に束縛した名前が
  `reaches_a_direct_call` を満たす
- 本体にあるその型構築子の `MakeStruct` が、フィールド j に、その型の値を分解して得た名前を置く
  （フィールドが素通りする、ということ）
- 引数 i 以外の引数の型が、その型構築子に触れない
- 本体が呼ぶグローバルの**返り値**の型が、その型構築子に触れない

後ろ 3 つが揃うと、本体の中のその型の値は、引数 i そのものか、引数 i から素通りで作られたものに
限られる。`advance` がインライン展開されていない形は最後の条件で落ちる。このパスは `-O max` から
しか走らないので、そこでは展開されている。

### 入り口は、複製自身が分解する引数に限る

構造体を別の関数の入り口へ渡しているだけの引数も入り口として数える（転送）ことは、できる。
`Slot::arg` について表が解いている不動点と同じ形で書ける。だが**測ると 1 つ退行する**ので採らない。

| 連鎖 | 転送なし | 転送あり |
| --- | --- | --- |
| `map` -> `fold` | **0.84** | 0.84 |
| `filter` -> `fold` | 20.02 | **12.02** |
| `map` -> `filter` -> `fold` | 29.02 | **21.02** |
| `map` -> `filter` -> `to_array` | 34.16 | **69.78** |

退行の中身は LLVM のインライン化である。転送があると
`FilterIterator::advance` の複製ができ、その複製は `pred` を名前で呼ぶぶん本体が大きくなる。
`to_array` の畳み込みは演算子が `push_back` で元から大きいので、そこへ `advance` を入れる判断が
閾値を割り、`advance` がループの外の関数として残る。すると `advance` の中に残っている
`map` の関数の間接呼び出しも、定数に落ちる機会を失って要素ごとの間接呼び出しのまま残る。
`perf` で見ると、転送なしでは 1 つの関数が 97% を占め、転送ありでは `advance` が 58%、
`map` の関数が 27% を占める。

パスの後にもう一度インライン展開を走らせても、`FilterIterator::advance` は自分自身を呼ぶので
展開されず、変わらない (69.83)。複製に `alwaysinline` を付けても同じ理由で変わらない。

### 届かない形

ラムダを構造体リテラルの中に直接書いた `Stepper { n : 4, f : |x| x * k }` は、そのラムダが持ち上げ
られない。decapturing が拾うのは呼び出しの引数に書かれたラムダと `let` が束縛したラムダで、
構造体のフィールドに書かれたものはどちらでもない。`map(f)` のように組み合わせ子へ渡す形は
引数なので拾われる。

## 段階

1. `Slot` の意味を「第 `arg` 引数の構造体の j 番目のフィールド」に広げる。振る舞いは変わらない。
2. 値の木の頭を 2 種類にする。振る舞いは変わらない。
3. `find_specializable_slots` に構造体フィールドの入り口と断る条件を足す。入り口は複製自身が
   分解する引数に限る。
4. 複製の型と本体に余分の引数を足し、呼び出し側でキャプチャリストを渡す。
5. 複製の中で、分解して得た名前の呼び出しを名前での呼び出しに替える。

## 測り方

コンパイラは worktree の `target/release/fix`。1 周の費用は
`(I(11) - I(1)) / 10` を `perf stat -e instructions:u` で取る。実装ごとに別のバイナリで測る。

比較の相手は `~/.cache/fixlang-iter-spec/bench-itertest/` の
`a_map_only` / `a_filter_only` / `a_map_filter_fold` / `a_map_filter_toarray2` と、
変換後の形を手書きした `n_map_only` / `n_filter_only` / `n_narrowed_struct` /
`n_map_filter_toarray`。

`ofold_closure` / `ofold_extra` / `ofold_narrow` は、`fold` に `advance` を展開した形を 3 通りに
手書きしたもので、上の 2 つの受け取り方が同じ速さであることを示す。
