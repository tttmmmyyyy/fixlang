# 型引数が伸びるプログラムを、最適化の前に落とす

## 0. この文書が決めること

**判定の中身**を決める。issue #245 で確定した方針 — 最適化の前に走るバリデーションで落とす — は
動かさない。動かすのは「何を判定するか」である。

#245 は判定として **expansive recursion** (Kennedy と Pierce の判定、.NET がジェネリクスに課して
いるもの) を挙げていた。**これは Fix では成り立たない。** 2 節で反例を挙げ、3 節で代わりに採る判定を
述べる。

## 1. 何が起きているか

`-O max` で終わらず、メモリを食い尽くすプログラムがある。同じプログラムが `-O none` と `-O basic`
では正しい答えを出す。

```fix
type [f : *->*] H f = unbox struct { d : f I64 };
type Ph a = unbox struct { z : I64 };
type Y a = unbox struct { p : Ph (Y (Array a)), h : H Array };
```

型変数はふつう型そのものを表すが、Fix では**型を取る型変数**も書ける。`H` の `f` は `Array` や
`Option` のような、型を 1 つ取って型になるものを表す。コード生成はこの形を直接は扱えないので、
`remove_hktvs` パスが、`H Array` のような型引数の組ごとに専用の 0 パラメータ型構築子
`#RHKTV<H Array>` を作り直し、そのフィールド型を `f I64` に `f := Array` を代入した `Array I64` と
して登録し、元の `H` を型環境から取り除く。取り除く型構築子を名指す宣言も同じく作り直すので、
`H Array` を名指す `Y` も対象になる。

`Y I64` を処理すると、そのフィールド `Ph (Y (Array I64))` に降り、そこから `Y (Array I64)` へ、
さらに `Y (Array (Array I64))` へ降りる。型引数は段ごとに 1 つ大きくなり、同じ型に戻らないので、
この再帰は止まらない。

`Ph` は引数を捨てるので、**値のレイアウトは有限**である。`Y I64` の値は `I64` 1 つ分の `Ph` と
`H Array` だけを持つ。だから大きさの検査 (`Program::validate_layouts`) はこのプログラムを正しく
受理する。検査が有限性を保証するのはレイアウトの関係であって、パスが辿る「宣言のフィールド型に
現れる型」の関係ではない。

同じ形が、フィールドを関数型にしても、高階の引数位置を使っても作れる (5 節の一覧)。

## 2. expansive recursion は Fix では成り立たない

### 2.1 判定の定義

宣言のパラメータの位置 `(C, i)` を節点とするグラフを引く。宣言 `C a₁..a_n` の本体に現れる適用
`D τ₁..τ_k` ごとに、引数 `τ_j` と各パラメータ `a_i` について、

- `τ_j` が `a_i` そのものなら、**非増大**の辺 `(C,i) -> (D,j)`。
- `τ_j` が `a_i` を真に含むなら、**増大**の辺 `(C,i) -> (D,j)`。

**増大の辺を含む閉路が無い**ことを要求する。閉路を回るたびに引数が真に大きくなる、という事態を
これが禁じる。

### 2.2 反証: 辺の引けない増大

判定が見られるのは、**適用の頭が型構築子である**場合だけである。頭が高階のパラメータなら、
どの宣言のどの位置へ引数が流れるかは、そのパラメータに何が代入されるかで決まり、宣言だけを見ても
決まらない。

```fix
type Ph a = unbox struct { z : I64 };
type [f : *->*] B f b = unbox struct { x : Ph (f b), n : I64 };
type A a = unbox struct { y : B A (a, a), n : I64 };
```

`B` の本体の `f b` は、頭が `f` なので辺を引けない。`A` の本体の `B A (a, a)` は増大の辺
`(A,1) -> (B,2)` を引くが、`(B,2)` から出る辺が無いので閉路にならない。**この宣言の組は判定を
通る。** ところが `f := A` が代入されるので、展開は

`A I64` -> `B A (I64,I64)` -> `Ph (A (I64,I64))` -> `A (I64,I64)` -> `B A ((I64,I64),(I64,I64))` -> ...

と止まらない。実測でも、このプログラムは `-O none` と `-O basic` で `2` を出し、`-O max` で
終わらない。

#245 はこの形について「深さ上限が既に捕まえているので取りこぼしても穴にならない」と書いていた。
それは `f b` を**フィールドに直接置いた**場合の話である。上のように `Ph` の後ろに隠すと、`f b` は
レイアウトの関係に現れないので、深さ上限は当たらない。**判定の穴と検査の穴が重なる。**

### 2.3 保守側に倒すと minilib が落ちる

頭が分からないなら、あらゆる位置へ流れうると見なすしかない。すると `f τ̄` の `τ_j` がその宣言の
パラメータを真に含む場合、増大の辺がその宣言自身の位置へも引かれ、自己閉路になって拒否される。

この形は、モナド変換子そのものである。

```fix
type [m: *->*] StateT s m a = unbox struct { data: s -> m (s, a) };
```

`m (s, a)` の引数 `(s, a)` はパラメータ `s` と `a` を真に含む。よって `StateT` は拒否される。
minilib で同じ理由で拒否される宣言は次のとおり。

| 宣言 | 高階パラメータの適用 |
|---|---|
| `StateT s m a` | `m (s, a)` |
| `WriterT e m a` | `m (e, a)` |
| `ResultT e m a` | `m (Result e a)` |
| `OptionT m a` | `m (Option a)` |
| `Free f a` | `f (Free f a)` |
| `Cofree f a` | `f (Cofree f a)` |
| `StoreT p w a` | `w (p -> a)` |
| `TracedT e w a` | `w (e -> a)` |
| `PairLT r f l` / `PairRT l f r` | `f (l, r)` |
| `JmpBuf cm a b` | `cm (a b -> cm b)` |

これらはいずれも有限であり、いま動いていて、minilib のテストも通っている。**判定が保守側に倒れる
先が、ライブラリの中心にある。**

流れ解析で頭を絞り込んでも救われない。`StateT s1 (StateT s2 Iden) a` を書けば `StateT` 自身が
`m` に流れ込み、同じ自己閉路が引かれる。変換子を積むことは変換子の目的そのものである。

### 2.4 なぜこうなるか

expansive recursion は、パラメータが型を表す言語のための判定である。Fix のパラメータは**型構築子**
も表せる。`StateT s (StateT s2 Iden) a` の展開が止まるのは、`a` の位置の引数が伸びる一方で
`m` の位置の引数が 1 段浅くなるからで、この「別の引数が減る」を宣言のグラフは表せない。#245 の
付録 B が「文献の決定可能な断片は高階カインドの型パラメータを含まない」と書いているのは、
この意味である。

## 3. 採る判定: 展開して届く型の深さを抑える

### 3.1 定義

判定が扱う型は、**実体化された後の ground な型** — 型変数を含まない型 — である。実体化が済んだ
時点で、プログラムに現れる型に自由な型変数は残っていない。

歩きの**根**は、既存の大きさの検査が歩く根と同じものを使う
(`Program::validate_instantiated_types`)。次の 2 つである。

- 実体化された各シンボルについて、**その型**と、**その式の各節点に付いた型**。
- 実体化されたエントリの IO 値と、各 `FFI_EXPORT` 文の値の式の、各節点に付いた型。これらの式は
  実体化されたシンボルを名指す `Var` 節点 1 つなので、その型は上のシンボルの型でもある。覆う範囲
  としては冗長で、**報告の順序**のために先に置かれている。歩きは型ごとに 1 度しか答えないので、
  最初に到達した根が報告の主語になる。プログラム自身の値を先に歩けば、標準ライブラリの関数が
  プログラムの型で実体化されている場合に、報告がライブラリではなくプログラム側の型を名指す。

根が関数型のときだけ、それ自身ではなく**取る型と返す型**を根とする。関数の値がそこに在るという
ことは、その関数がコンパイルされるということなので、引数と返り値の型は実際に要る型である。

その ground な型 `τ` が**名指す**型を、次の 2 つとする。どちらも ground である。

- `τ` が適用されている**型引数**。
- `τ` の型構築子が飽和しているとき、その宣言が与える**フィールドの型**に `τ` の型引数を代入した
  もの (`TypeNode::field_types`)。宣言に書かれたフィールド型はパラメータを自由変数として含むが、
  代入した後の型は含まない。`Y I64` が名指すのは `Ph (Y (Array a))` ではなく
  `Ph (Y (Array I64))` である。

根から、この関係で届く型がすべて、**項としての深さ `D` = 500 以下**であることを要求する。ただし
関数型はこの上限から除く (3.2 の末尾)。

**ground であることが、2 節で破れたものを直している。** 宣言だけを見ると `f b` の頭は定まらない。
ground な型の上では適用の頭は必ず型構築子であり、`B A (I64,I64)` を展開する時点で `f := A` は
済んでいるので、`Ph (A (I64,I64))` が実際に現れ、そこから先も辿れる。判定を宣言から実体化後の型へ
移すこと自体が、高階パラメータの問題を消している。

ground であることと**飽和している**ことは別である。`H Array` の引数 `Array` は型変数を含まないが、
パラメータ 1 つに引数 0 個である。この出現には**展開すべきものが無い**: フィールドの型は宣言の
パラメータに引数を代入したものなので、引数が揃っていなければ計算できない (`field_types` は飽和を
表明する)。その型構築子のフィールドが問われるのは、代入が作った飽和した適用のところ — `H Array`
を展開して出てくる `Array I64` — であり、歩きはそこへ届く。

パスの側も同じである。`run_on_type` は入口で飽和を表明しており、飽和していない型に対して呼ばれる
ことはない。取り除かない型構築子は高階パラメータを持てない (持てば取り除く対象になる) ので、その
型引数の kind は必ず `*` である。**パスが展開する型は常に飽和している。**

高階の引数の中で伸びる分も取りこぼさない。飽和していない出現は展開しないだけで、**見てはいる**:
深さの検査に掛からないのは関数型だけで、飽和しているかどうかは関係ない。さらにその引数は飽和した
型の部分項なので、そちらの深さにも数えられる。5.1 の最後の形がこれを踏んでいる。

### 3.2 これは既存の検査と同じ道具である

大きさの検査 (#193) は、コード生成が実際にレイアウトする関係 `held` の上で、同じ `D` = 500 の上限を
当てている。上限を「型 1 つの項の深さ」に置く理由も同じで、
`dev-docs/2026-08-06-circular-unbox-layout/correctness.md` の 4 節が論じている。

> 単純な型をプロジェクトに足しただけでコンパイルできなくなってはいけない。`Needed` の個数や
> 降下の長さに上限を置くとこれを破るが、**型 1 つの項の深さ**は単純な型をいくつ足しても増えない。

変わるのは**歩く関係**だけである。レイアウトの関係は、捨てられる引数にも、関数型の先にも進まない。
展開の関係はどちらにも進む。パスが辿るのがそちらだからである。

**関数型を上限から除くのも同じである。** Fix の関数型はカリー化されているので、引数 600 個の関数の
型は 600 段の入れ子になる。この深さが測っているのは引数の数であって、族の増大ではない。上限を
当てると、そのような関数が拒否される (#193 で実際に起きた。実測: 引数 600 個の関数を宣言した
プログラムは、この判定の下で通る)。

除いても取りこぼさない。**無限の族は、必ず関数型でない型の側で深さが伸びる**からである。段が伸びる
のは宣言のフィールド型 `σ` に型引数 `t̄` を代入するときだけで、その結果の深さは
`depth(σ) + max_i depth(t_i)` 以下である。`σ` は宣言に書かれた有限個の項の 1 つであり、`t_i` は
`C t̄` という**関数型でない**型の部分項である (フィールドを与えるのは宣言された型構築子だけ)。
つまり関数型の深さは、上限に当たる型の深さで抑えられている。3.4 がこの議論である。

そして関数型の中身は歩く。取る型・返す型は名指す型なので、増大はそれが住んでいる関数型でない型の
ところで捕まる。#245 の 2 つ目の再現がこれで、`Y (Array a) -> I64` という矢印は上限から除かれるが、
その引数の `Y (Array I64)` は除かれない。

### 3.3 停止性

判定自身は必ず停止する。型構築子は有限個なので、深さ `D` 以下の ground な型は有限個である
(correctness.md の補題 1)。歩きは到達した型を記録して 2 度目を切るので、訪れる型は「深さ `D` 以下の
型」と「最初に `D` を超えた 1 つ」に限られる。

### 3.4 完全性: 終わらないプログラムは必ず落ちる

> **主張.** 展開の関係で根から届く型の集合が無限なら、この判定は必ず報告する。

*論証.* 報告しなかったとする。関数型でない型はすべて深さ `D` 以下である。関数型の深さも抑えられる:
関数型が集合に入るのは、根の部分項としてか、`C t̄` のフィールド型 `σ[ā := t̄]` の部分項としてで
ある。後者の深さは `depth(σ) + max_i depth(t_i)` 以下であり、`σ` は宣言に書かれた有限個の項の
1 つ、`t_i` は関数型でない型 `C t̄` の部分項なので深さ `D` 未満である。よって集合のどの型も深さが
抑えられ、型構築子は有限個なので集合は有限。矛盾。∎

型構築子が有限個で深さが有限なら型は有限個、というだけの議論である。**個数を数える必要も、増大の
形を分類する必要もない。**

### 3.5 パスの停止性が系として出る

`remove_hktvs` が辿る関係は、上の「名指す」関係の部分である。`run_on_type` は、取り除かない型
構築子に対してはその型引数へ、取り除く型構築子に対してはそのフィールド型へ進む。`unwrap_newtype`
が置き換え先に採るフィールド型も同じ関係の中にある。したがって、受理されたプログラムでは、これらの
パスが作る型の集合は有限である。**パスの側に証明義務は残らない。**

パスの前に走る `skip_eval` / `optimize_act` / `simplify_symbol_names` / `remove_tyanno` は、検査
済みの型を組み合わせた型しか作らない。有限個の型を組み合わせて作る型の展開の集合は、もとの集合の
和に自分自身を足したものなので、やはり有限である。

### 3.6 代償

有限なのに拒否されるプログラムがある。**深さ `D` を超える型を展開が必要とするもの**である。これは
既存の検査が持つ代償 (correctness.md の定理 4) と同じ形であり、`D` の位置がその大きさを決める。

具体的には、#245 が挙げた次の形がこれに当たる。いま 4 レベルすべてで動き、レベル依存も無い。

```fix
type Phantom a = unbox struct { x : I64 };
type C a = unbox struct { p : Phantom (C (a, a)), n : I64 };
```

`C I64` の値のレイアウトは有限だが、宣言を展開すると `C (I64,I64)`、`C ((I64,I64),(I64,I64))` と
型引数が伸び続ける。correctness.md の受理表がこの形を意図した受理として載せているので、その判断を
覆すことになる。この代償が現存する Fix コードで発生しないことは 5 節で実測する。

## 4. 実装

`src/type_size.rs` に、レイアウトの歩きと並べて 2 つ目の歩きを置く。

```rust
/// Why the compiler needs endlessly many types to compile a value of `ty`, and `None` where
/// unfolding the declarations `ty` names reaches finitely many.
pub fn endless_types_reason(ty, type_env, walk) -> Option<String>;

/// The types unfolding `ty` names: the type arguments it is applied to, and the types its
/// declaration gives its fields at those arguments.
fn named_types(ty, type_env) -> Vec<Arc<TypeNode>>;
```

`Program::validate_layouts` が根ごとに呼ぶ。2 つの歩きは記憶 (`LayoutWalk`) を共有し、根の列挙を
共有する。

**2 つの歩きを別にする理由。** 展開の関係はレイアウトの関係を含むので、深さの上限は 1 つに畳めそう
に見える。畳まない。レイアウトの歩きが決めるもう 1 つのこと — 値が自分自身を含むか — は、
**レイアウトする型についてだけ問うべき**だからである。捨てられる引数の位置に現れるだけの型は、
値を持たないので、そこに循環があってもプログラムは動く。歩きを 1 つにすると、この型にも循環の判定が
当たる。

報告の文面は 2 つの歩きで共有する。どちらも言うことは同じ — 型が際限なく大きくなっているので、
再帰する出現に同じ型引数を与えよ — であり、どちらの関係で見つけたかは利用者の関心ではない。

```
`Main::Y Std::I64` needs endlessly many types: it reaches types nested more than 500 deep
(`Main::Y Std::I64` -> `Main::Ph (Main::Y (Std::Array Std::I64))` -> `Main::Y (Std::Array Std::I64)`
 -> ...). A type reached from itself at a larger type argument does this; give the recursive
occurrence the same type arguments.
```

## 5. 実測

試作を当てた `fix` で測った。

### 5.1 落ちるべきものが落ちる

6 つの病的なプログラムが、`-O none` と `-O max` で**同じ**診断を出す。試作前は、いずれも
`-O none` / `-O basic` で答えを出し、`-O max` で終わらなかった。

| プログラム | 増大の経路 |
|---|---|
| `Y a = { p : Ph (Y (Array a)), h : H Array }` | phantom な引数位置 |
| `Y a = { step : Y (Array a) -> I64, ... }` | 関数型のフィールド |
| `Grow f = { g : Ph (Grow (Wrap (f I64))), ... }` | 高階の引数位置 |
| `A a = { y : B A (a,a) }` + `B f b = { x : Ph (f b) }` | 高階パラメータ経由 (2.2 の反例) |
| `C g = { y : Ph (C (Wrap g)), n : I64 }` | 増大が高階の引数位置だけに閉じている |
| `C a = { p : Phantom (C (a,a)), n : I64 }` | 有限だが伸びる (3.6 の代償) |

### 5.2 通るべきものが通る

| 対象 | 結果 |
|---|---|
| minilib 16 サブモジュール (`fix test`) | **16/16 通過** |
| cp-library + project_euler 100 個 (`fix build`) | **新しい診断は 0 件** |
| `StateT I64 (StateT I64 Iden) I64` を組んで走らせる | 通過 (`-O none` / `-O max`) |
| 同じ型引数で自己参照する `C a = { p : Phantom (C a), n : a }` | 通過 (`-O none` / `-O max`) |

コーパスで失敗するプロジェクトはあるが、原因は 3 つとも古い依存が現在の標準ライブラリと合わない
ことである — 削除済みの `Std::Array::_unsafe_set_size` の呼び出し、`Array` が `Boxed` を実装
しなくなったこと、`Std::unsafe_is_unique` が `Boxed` を要求するようになったこと。**この検査が出す
診断は 1 件も無く、コンパイラの panic も 0 件**である。minilib の `_depgraph` と `_publisher` も
同じ理由で失敗し、main のコンパイラでもエラーの数は同じ (1 件 / 13 件) である。

### 5.3 スイート

全件 (`cargo test --release`) が通る。挙動が変わったテストは 1 件で、3.6 の代償
(`C a = { p : Phantom (C (a,a)) }` が受理から拒否へ) を主張していたものである。これを拒否の主張に
書き直し、5.1 と 5.2 の各形にテストを足した。

|---|---|---|
| 判定する対象 | 型宣言 | 実体化されたプログラムの型 |
| 高階パラメータ | 頭が定まらず、辺が引けない (2.2) | 引数も頭も ground なので問題にならない |
| 保守側に倒したときの代償 | minilib の中心が落ちる (2.3) | 深さ 501 以上を必要とする有限のプログラム |
| 完全性 (終わらないものを必ず落とす) | 高階パラメータがあると成り立たない | 成り立つ (3.4) |
| 既存の検査との関係 | 別の道具を足す | 同じ道具を別の関係に当てる |

## 付録 B: `-O none` で動くのに `-O max` で終わらない、を残さないこと

判定を最適化の**前**に置くと、受理・拒否が最適化レベルに依らないことが構成から従う。パスの変換規則を
狭める案は、狭めた規則の停止性を証明する義務を残し、その証明は #245 の 3 節で反例により潰れている。
