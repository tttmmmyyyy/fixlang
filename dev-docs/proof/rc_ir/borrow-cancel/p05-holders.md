2. `b` (とそれが返す `IO` の動作の活性化) が返す参照が、`o` の `_value` の leaf に入る。

P28 が (F) の段で偽になることを示す。

## 1. 記法

プログラム `P` の 1 つの実行 `X` を固定する。`X` は段の列 `s_1, s_2, ...` である (D24)。

- **時点** -- `t_0` を `s_1` の前、`t_i` を `s_i` の後 (`i ≥ 1`) の時点とする。段は不可分なので、段の
  内部に時点は無い (D24)。(F) の解放と、(F) が作る活性化の内側にも時点は無い (D24)。
- **`Liv(t)`** -- 時点 `t` に生きている活性化 (D23) の集合。
- **`Obj(t)`** -- 時点 `t` に生きているオブジェクト (D25: 割り当てた段より後、解放する段より前) の集合。
- **`Cnt(t)`** -- 時点 `t` に計数下 (D26) のオブジェクトの集合。
- 計数下オブジェクト `O` について:
  - `H_t(O)` -- `O` の参照カウント (D7)。
  - `A_t(O) := Σ_{a ∈ Liv(t)} (Obl(a) が持つ O への参照の個数)`。
  - `B_t(O) :=` 対 `(o', λ)` の個数。ここで `o' ∈ Obj(t)`、`λ` は `o'` が保持する値の boxed leaf (D4)
    であって、`t` において inhabited (D16) であり、null ポインタでなく、`obj(o', λ) = O` である。
  - `C_t(O) :=` `E` が持つ `O` への参照の個数 (D22)。
- **`INV(t)`** -- すべての `O ∈ Cnt(t)` について `H_t(O) = A_t(O) + B_t(O) + C_t(O)`。

`A`、`B`、`C` は D25 の 3 種の持ち手に 1 対 1 に対応する。`B` が対を数えるのは A5 による -- 生きている
オブジェクトの inhabited で非 null で計数下を指す leaf が、参照をちょうど 1 つ持つ。

`<1>4.` 次の 6 種を**素動作**と呼ぶ。素動作は、その直前に `H = A + B + C` が成り立っていれば、
その直後にも成り立たせる。

  DEFINE 素動作 ==
  - **(α) 受け渡し**: 1 つの参照が 1 つの持ち手を離れ、別の 1 つの持ち手に入る。`H` は変わらない。
  - **(β) 生成**: 既にあるオブジェクト `O` への参照が 1 つ新しく作られ、1 つの持ち手に入る。`H(O)` が
    1 上がる。
  - **(γ) 割り当て**: 新しいオブジェクト `O` が在るオブジェクトの集合に入る。その値は、inhabited で
    非 null で計数下を指す boxed leaf を 1 つも持たない。`O` への参照が 1 つでき (`H(O) = 1`)、1 つの
    持ち手に入る。
  - **(δ) 処分**: 1 つの持ち手が持つ `O` への参照が 1 つ無くなる。`H(O)` が 1 下がる。
  - **(ε) 解放**: `H(o) = 0` である計数下のオブジェクト `o` について、`o` が持つ参照 (D25) を (δ) で
    すべて処分し、`o` を在るオブジェクトの集合から取り除く。
  - **(ζ) グローバル化**: 計数下のオブジェクト `O` が `Cnt` を出て、グローバル状態になる (D26)。

  段の中で素動作を数えるときの「在るオブジェクトの集合」とは、その (γ) が済んで、その (ε) が済んで

**A18 は使わない。**(a) の非巡回性は (F) の連鎖の停止に要らない -- D24 が停止をオブジェクトの個数で
述べている。(b) のグローバル状態のオブジェクトが計数下を指さないことも要らない -- `<1>4` の `<2>6` は
`B` の定義が計数下かどうかを問わないことだけを使う。

**2 つの実行の対応 (D30) も、観測 (D18、D19) も現れない。**P28 は 1 つの実行についての主張である。

## 4. README について

### 4.1 (H-D12) -- P28 には仮定が要る

README の P28 の言明は「実行 (D24) の各時点において、処分されていない各参照は、D25 が挙げる 3 種の
持ち手のちょうど 1 つに属する」であり、`P` についての仮定を持たない。この形は偽である。

**(S-a) が無いと偽である。**所有するパラメータ `y` を 1 つ持ち、本体が `Release(y, [], s, Release(y, [],
s, Ret(u)))` である関数を考える。初期の `Obl` は `y` の leaf の参照 1 つであり、1 つ目の `Release` が
それを取り除いて `H` を 1 下げる。2 つ目の `Release` は D10 に従ってもう一度 `H` を下げるが、取り除く
参照は `Obl` に無い。`H` が 1 減って `A + B + C` が減らないので、その時点で `A + B + C > H` となる。
すなわち 1 つの参照を 2 つの持ち手が持っている。

**(S-b) が無いと偽である。**所有するパラメータ `y` を 1 つ持ち、本体が `Ret(u)` (`u` は `y` を含まない)
である関数を考える。終端の `Ret` の消費の後も `Obl` に `y` の参照が残り、その活性化は終わる。以後その
参照はどの持ち手にも属さないので `A + B + C < H` となる。

**要る形**: P28 の言明に「`P` が D12 を満たすとき」を足す。読む者にとって足枷にはならない -- README の
第 7 節が挙げる P28 の読み手は A19 (i) であり、A19 の量化の範囲は「`borrow_ify` の入力の各本体と、
`borrow_ify` がそれを写した各本体」であって、そのどちらも A1 と P14 が D12 を与える。

### 4.2 (H-F) -- (F) が `_value` の参照を動かすことを述べていない

D24 の (F) は「解放とは、`o` が持つ参照 (D25) をすべて処分し、それから `o` の記憶域を返すことである」と
書き、`Destructor` について「`o` の参照を処分する**前に**、`o` が `_dtor` の欄に持つ関数が `_value` の
欄の値に適用され、返った `IO` の動作が走る」、「**この段は参照も作る。** `_dtor` の欄の関数に適用の分の
参照を与える retain がそれである ... 作られた参照の持ち手は、この解放を含む段を実行している活性化で
ある」と書く。

**`_dtor` の側は閉じた。**`_dtor` の欄の参照は `o` に残り、新しく作られた参照が適用に渡る。

**`_value` の側は閉じない。**適用は D9 の `App` の行の消費を行い、所有する引数の leaf の参照を消費する。
その参照を持っているのは `o` の `_value` の leaf だけである (`INV`、D25)。ところが (F) は「`o` が持つ参照
をすべて処分し」とも書くので、同じ参照が 2 度処分される -- 1 度は適用の消費として、1 度は解放として。
`H` が 2 減って持ち手の側は 1 しか減らないので、**その段の切れ目で `A + B + C > H` となり、P28 が偽に
なる。**

**動く参照はこれである。**解放される `Destructor` のオブジェクト `o` の `_value` の欄が指すオブジェクト
への参照。持ち手は `o` (D25 の 2 番目の持ち手) であり、行き先は解放が作る活性化 `b` の `Obl(b)` である。
D24 はこの移動を挙げていない。

**コードはこの移動をしている** (`CODE src/generator.rs: Generator::build_run_destructor`)。

- `ObjectFieldType::move_out_struct_field` は欄を読むだけで参照カウントに触れない。`_value` の参照は
  `apply_lambda(dtor, vec![value], false)` が消費する。この関数は引数をそのまま渡し、参照カウントに
  触れない (`CODE src/generator.rs: Generator::apply_lambda`)。`build_run_destructor` は適用の後に
  `value` を release しない。
- 走った結果は `ObjectFieldType::move_into_struct_field` で `_value` の欄へ戻る (「taking over the
  caller's reference to `field`」)。
- その後に走る `traverse_refs` が処分するのは、`_value` に入ったその結果と、もとの `_dtor` である
  (`CODE src/generator.rs: Generator::build_traverser_work_nonnull_boxed_with` --
  `build_run_destructor` を `traverse_refs` の**前**に置く)。

**要る形**: 第 0 節の (H-F) の 3 つ。すなわち (1) `_value` の参照が `o` を離れて `Obl(b)` に入ること、
(2) 返る参照が `o` の `_value` の leaf に入ること、(3) 「`o` が持つ参照をすべて処分し」が指すのは
その後に `o` が持つ参照であること。

### 4.3 (H-A) -- (E2) の行き先の欄が 2 つ足りない

D24 の (E2) の行き先の表は `Llvm` の行の行き先を

> その op が書き込む先 (この段が割り当てるオブジェクト、または環境)、あるいは処分

と書く。**この欄に無い行き先が 2 つある。**

**(1) この段が作る活性化の `Obl`。** 同じ (E2) の後段は「(E3) と違うのは 3 点である ... `Obl(a)` の
動きは D9 の `Llvm` の行と A3 の宣言が決めるので、この表の行はそのままである」と書く。この 2 つの文は
行き先について食い違う。

- 「この表の行はそのままである」と読むと、適用された関数へ渡る参照の行き先が欄に無い。
  `Option::mod_some` の modifier がその参照である。この op は `applies_a_function_operand` を真と宣言し、
  `result_prov` を override しないので既定の `Unknown` を取る。よって modifier の boxed leaf (クロージャの
  capture) は D9 の `Llvm` の行が消費し、生成コードはそれを `apply_lambda(modifier.clone(),
  vec![value], false)` へ渡す。行き先は作られた活性化の `Obl` である
  (`CODE src/fixstd/builtin.rs: InlineLLVMUnionModBody`,
  `CODE src/ast/inline_llvm.rs: LLVMGen::result_prov` の既定 --
  `Provenance::uniform(result_ty, type_env, LeafOrigin::Unknown)`)。
- 「(E3) と違うのは 3 点である」を、挙げられた 3 点のほかは (E3) と同じと読むと、D9 の `Llvm` の行が
  消費する参照が**すべて** `Obl(b)` の初期値になる。同じ op がこれを破る -- union のオペランド `obj` も
  同じ行が消費するが、適用に渡るのは payload であって union ではなく、タグが合わない腕では modifier が
  `gc.release(modifier, RcState::Unknown)` で処分される
  (`CODE src/fixstd/builtin.rs: InlineLLVMUnionModBody`)。

**(2) 既に在るオブジェクトの leaf。** 一意性検査で分岐する op は、一意の腕でオペランドのオブジェクトを
そのまま使う (A3)。`struct_set` の一意の腕は、消費したオペランド `value` の参照を、この段が割り当てた
のではないオブジェクトへ書き込む
(`CODE src/fixstd/builtin.rs: InlineLLVMStructSetBody` -- `force_unique_or_assert` の後に
`ObjectFieldType::move_into_struct_field(gc, struct_obj, self.field_idx as u32, &value)`)。欄の括弧書きは
「この段が割り当てるオブジェクト」しか挙げていない。

**要る形**: 第 0 節の (H-A) の 3 つ。3 番目 (作る活性化の初期 `Obl` の出どころ) が要るのは、この段が
作る活性化に渡る値がオペランドとは限らないからである。`InlineLLVMFixBody` の 1 回目の適用に渡る
`fix(f)` がそれで、これはこの段が組み立てた値である。`fix(f)` 自身は unbox のクロージャ集約なので
新しいオブジェクトではなく、その capture の欄が持つのはオペランド `cap` の参照なので、この op について
は 3 番目の前半 (移ったもの) で足りる (`<2>3` の `<3>5`)。3 番目の後半 (新しく作った参照) を書いて
おくのは、D24 が op ごとの内訳を宣言に委ねていて (A3)、A3 に「適用された関数へ何を渡すか」を述べる欄が
無いからである。

### 4.4 実行の最初の状態が定まっていない

D24 は「プログラム `P` の**実行**とは、**段**の有限または無限の列である」とだけ書き、第 1 段の前の状態に
ついて何も述べない。`<1>3` はそこを、参照を作るのが D10 の生成 (D8) と (F) の retain (D24) の 2 つで
あり、どちらも段の中で起きることから埋めている。

この読みには帰結が 1 つある。**第 1 段が (E1) であるとき、その活性化の初期 `Obl` は空でなければならない。**
A17 (i) は「環境が活性化を作るとき、D10 の初期値が要求する参照を渡し」と書くが、渡す参照はまだ 1 つも
存在しないからである。C のエントリ点はこれを満たす -- 読むグローバル `main` の値が到達するオブジェクトは
(E5) を経てグローバル状態であり、渡す `IOState` は `is_unbox: true` の primitive で `fields` が空なので
boxed leaf を持たない (`CODE src/build/build_object_files.rs: build_main_function`,
`CODE src/fixstd/builtin.rs: run_ios_runner`, `CODE src/fixstd/builtin.rs: bulitin_tycons`)。
`FFI_EXPORT` のエントリ点が boxed な引数を取るときは、その参照は C の呼び出し元が持っている。実行の中で
それを C の側へ渡した段があれば (E4) か (E2) の環境行き先がそれを説明するが、実行の外から来る場合は
説明が無い (`CODE src/ast/export_statement.rs: ExportStatement::implement` -- `Object::from_parts` が
C の引数から Fix の値を作る)。

### 4.5 (E7) が環境からのグローバル読みを覆っていない

D24 の (E7) は「**生きている活性化** `a` が、まだ初期化されていないグローバル `g` を読む節点の位置に
あるとき」と書く。環境がグローバルを読む場合が抜けている。C のエントリ点は、活性化が 1 つも無い時点で
グローバル `main` を読む (`CODE src/build/build_object_files.rs: build_main_function` --
`gc.get_scoped_obj(&main_name)`)。`FFI_EXPORT` のエントリ点も、書き出された値のグローバルを同じように
読む (`CODE src/ast/export_statement.rs: ExportStatement::implement` --
`gc.get_scoped_obj(&fix_name)`)。どちらもアクセサを通るので、初期化されていなければ初期化子の活性化が
作られる (`CODE src/rc_ir/codegen.rs: Generator::implement_rc_global`)。

P28 はこの穴に触れない -- `Obl(b)` は空で始まり、`b` が返す参照は `E` に入って (E5) でグローバル状態に
なる。すなわち `<2>8` の議論は読み手が環境でも活性化でも同じである。

### 4.6 (E2) の `H` の表の `Unknown` の行が 1 つの op に当たらない

D24 の (E2) の `H` の表は、`result_prov` が単一の `Unknown` を宣言する結果の leaf を「既存の
オブジェクトで +1」とする。`InlineLLVMBoxedFromRetainedPtrIOS` はこの行に当たらない。この op は
`result_prov` を override せず既定の `Unknown` を取る (A3 がそう述べる) が、生成コードは retain を
1 つも出さない -- オペランドの `Ptr` から番地を取り出して結果の欄へ入れるだけである
(`CODE src/fixstd/builtin.rs: InlineLLVMBoxedFromRetainedPtrIOS`)。その参照は C の側 (環境) が持って
いたものであり、この段で `E` から `Obl(a)` へ渡る。D24 の (E2) の 2 つの表は、`Obl(a)` を**離れる**参照と
**作られる**参照しか挙げず、`E` から `Obl(a)` へ**入る**参照を挙げていない。

P28 はこの行を字義どおりに読んでも閉じる -- (β) として `H` が 1 上がり、`E` は自分の参照を持ち続ける
ので、`H = A + B + C` は保たれる。食い違うのはモデルとコードの間であって、モデルの中ではない。

### 4.7 (E5) の位置が D22 と食い違う

D24 の (E5) は「グローバル初期化子の活性化が終わり、その参照が `E` に入った後 (E4)、環境が `mark_global`
で ... 印を付ける」と書く。D22 は「`mark_global` で印を付けるのは `InitValue#<symbol>` の側であり、
本体を評価した直後、値を返す前に行う」と書く。コードは D22 の側である
(`CODE src/rc_ir/codegen.rs: Generator::implement_rc_global` -- `eval_rc_expr` の直後に
`self.mark_global(obj.clone())` を置き、その後に `build_return`)。

P28 はどちらの順でも閉じる。`<2>6` が使うのは (ζ) が参照を作らず渡さず処分しないことだけであり、
消える参照を持っていたのが `E` でも `Obl(b)` でも議論は同じである。
