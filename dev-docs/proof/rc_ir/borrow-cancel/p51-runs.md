## 0. 結論

| 主張 | 結果 |
|---|---|
| (R1) 解放されたオブジェクトの読みが起きない | 証明した |
| (R2) どのオブジェクトも高々 1 回しか解放されない | 証明した。ただし A16 が要る |

この文書が見つけたことは 3 つある。

1. **P27 の言明は、書かれたままでは偽である。** グローバル状態のオブジェクト (D26) は決して解放されず、
   発散する実行と中断する実行では生きたままのオブジェクトが残り、C のエントリ点は自分が作った `IOState` を

2. **D11 だけからは (R2) が出ない。** D11 を満たしながら 1 つのオブジェクトを 2 回解放する本体が書ける

   (S-a) にも掛からない。A16 がその穴を塞ぐ。
3. **D10 の義務集合と D11 の (S-a)/(S-b) は、グローバル状態でないオブジェクトへの参照だけを数えるものとして
   読まなければならない。** 制限しないと、グローバル値を所有位置の引数として渡す呼び出しが (S-a) を破る
   (反例 R2)。A8 が「規律の外」と言っているのはこのことだが、D10 と D11 の本文はオブジェクトの状態で
   場合分けしていない。

## 1. 実行のモデル (README への追加提案)

**語の使い分け。** README の D21 は、**1 つの本体の 1 回の計算**を「実行」と呼ぶ。この文書ではその概念を
**活性化** (D23) と呼び、「実行」はプログラム全体の 1 回の実行 (D24) だけに使う。1 つの活性化は 1 つの本体の
D21 の意味の実行を含み、それに加えて義務集合と、実行の中での位置づけ (誰が作ったか、いつ終わるか) を持つ。
README へ移すときは、D21 の語を「本体の実行」へ改めるか、活性化に吸収するかの判断が要る。

### D22 (環境)

RC IR プログラムの外側にあって、その本体を起動するコードを**環境**と呼ぶ。環境は次の 3 つからなる。

- **C のエントリ点**。`argc` と `argv` をグローバル変数へ格納し、グローバル `main` を読み、その `IO` の
  runner に `apply_lambda` で `IOState` を渡す (`CODE src/build/build_object_files.rs: build_main_function`,
  `CODE src/fixstd/builtin.rs: run_io_or_ios_runner`, `run_ios_runner`)。
- **`FFI_EXPORT` のエントリ点**。C の呼び出し元から引数を受け取り、書き出された Fix の値に `apply_lambda` で
  渡す (`CODE src/ast/export_statement.rs: ExportStatement::implement`)。
- **グローバルのアクセサ**。初期化済みの旗を見て、まだならグローバル初期化子の本体を持つ関数
  `InitValue#<symbol>` を呼び、返った値に `mark_global` で印を付けてから記憶域へ格納する。以後の読みは
  記憶域を読むだけである (`CODE src/rc_ir/codegen.rs: Generator::implement_rc_global`)。

環境は参照を持つ (D25)。環境が持つ参照の多重集合を `E` と書く。

### D23 (活性化)

**活性化**とは、1 つの本体 -- ある関数の `body` か、あるグローバル初期化子の `init` -- の D21 の意味の
1 回の実行である。活性化 `a` は次の 4 つを持つ。

- **本体** `B(a)`。
- **入力の束縛**。`B(a)` が関数の本体なら、その関数の各パラメータと capture に 1 つずつの値
  (`CODE src/rc_ir/codegen.rs: Generator::implement_rc_function` -- `func.params` と `func.capture` を
  `scope_push` する)。`B(a)` がグローバル初期化子の `init` なら無い (D1 より `init` はパラメータも
  capture も持たない)。
- **位置**。`B(a)` の 1 つの実行路 (D3) の上の位置。活性化が始まった時点では `B(a)` の根であり、段 (D24)
  ごとにその路に沿って 1 つ進む。D21 より、活性化が節点を訪れる順序は `B(a)` の実行路の 1 つであり、それを
  `a` が**辿る実行路**と呼ぶ。
- **義務集合** `Obl(a)`。D10 が定める参照の多重集合。始まった時点での値は D10 の初期値であり、以後は D24 の
  段が動かす。

活性化 `a` が**終わる**とは、`a` の位置が `B(a)` の終端の `Ret` に着き、その `Ret` の消費 (D9) を行うことを
いう。終わった活性化はそれ以後の段を持たない。**生きている活性化**とは、始まって終わっていない活性化である。

`Let(x, App(callee, args), k)` の**呼び出し先**は、その段で `callee` の値が指す関数である。`callee` の値が
クロージャならその funptr の指す関数、funptr ならそれ自身である
(`CODE src/generator.rs: Generator::apply_lambda` -- `get_lambda_func_ptr` が返す関数ポインタを
`build_indirect_call` で呼ぶ)。**D9 の `App` の行と D10 の生成の `App` の行が「呼び出し先」と言うのは、この
実行時の関数である。**すなわち D10 の義務集合、したがって D11 は、実行時に決まる呼び出し先を読む。L0 が、
`cancel` と `borrow_ify` が静的に決める呼び出し先がこれと食い違わないことを述べる。

### D24 (実行)

プログラム `P` の**実行**とは、**段**の有限または無限の列である。段は不可分であり、複数の制御の流れ
(`FFI_EXPORT` を通じて外から入るスレッド) がある実行では、それらの段が 1 つの列に並ぶ。段は次の 6 種で
ある。このほかに (F) の**解放**があるが、これは段ではなく、参照を処分するどの段の中でも起きる動作である。

**(E1) 環境が活性化を作る段。** 環境が本体 `B` の活性化 `a` を作る。`B` が関数の本体なら、環境は `a` の
初期 `Obl` (D10 の初期値) の各参照を `E` から渡す。`B` がグローバル初期化子の `init` なら `Obl(a)` は空で
始まる。

**(E2) 節点の段。** 生きている活性化 `a` が、自分の位置の節点を実行し、D3 に従って次の位置へ進む。`Obl(a)`
と参照カウント `H` の動きは D10 が定めるとおりである。`Obl(a)` を離れる参照の**行き先**は次の表による。

| 節点 | `Obl(a)` を離れる参照 | 行き先 |
|---|---|---|
| `Let(x, Closure(f, caps), k)` | 各 capture の inhabited な全 boxed leaf (D9) | この段が割り当てる capture object |
| `Let(x, Llvm(gen, args), k)` | D9 の `Llvm` の行 | その op が書き込む先 (この段が割り当てるオブジェクト、または環境)、あるいは処分 |
| boxed 容器の `Destructure(c, fs, s, k)` | `c` の参照 (D9) | 処分 |
| unbox 容器の `Destructure(c, fs, s, k)` | 名前の付いていないフィールドの leaf (D9) | 処分 |
| `Release(v, π, s, k)` | `π` の下の inhabited な各 leaf (D10) | 処分 |

**処分**された参照は以後存在せず、`H` が 1 下がる。行き先のある参照は存在し続け、`H` は変わらない。
D9 の消費の表の残る 2 行 -- `App(callee, args)` と関数本体の終端の `Ret(x)` -- は、それぞれ (E3) と (E4) が
述べる。

新しい参照を作る節点は D10 の生成の表のとおりであり、作られた参照の持ち手は `Obl(a)` である。`H` の動きは
次のとおりで、D10 の生成の表を段の水準に書き直したものである。

| 生成 | `H` |
|---|---|
| `Retain(v, π, s, k)` の各 leaf | +1 |
| `Llvm` の結果の leaf のうち、`result_prov` の宣言が単一の `Arg(j, σ)` でないもの | A3 の表による。単一の `Fresh` ならこの段が新しく割り当てるオブジェクトで `H` = 1、単一の `Unknown` なら既存のオブジェクトで +1、空集合ならその leaf は inhabited にならず参照は生じない |
| boxed 容器の `Destructure` の名前付きフィールドの各 leaf | +1 |
| boxed union の変位アームの payload の各 leaf | +1 |
| `Closure(f, caps)` の結果 | この段が新しく割り当てる capture object、`H` = 1。ただし `caps` が空のときは capture ポインタが null であり、オブジェクトも参照も無い (`CODE src/rc_ir/codegen.rs: Generator::build_rc_closure`) |
| `App(callee, args)` の結果の各 boxed leaf | **変わらない**。(E4) が呼び出し先から受け取る参照である |

最後の行は D10 の生成の表の括弧書き (「`H` はその場で上がる」) と違う。呼び出しの結果の leaf が持つ参照は、
呼び出し先の中で作られて (E4) で渡ってくるものであり、返りの段で新しく作られるのではない。1 つの本体だけを
見る証明ではこの差は現れないが、実行の水準では `H` の収支が合わなくなるので、ここで正す。

**(E3) 呼び出しの段。** 生きている活性化 `a` が `Let(x, App(callee, args), k)` の位置にあるとき、D9 の
`App` の行が消費する各参照が `Obl(a)` を離れ、呼び出し先 (D23) の本体の新しい活性化 `b` が作られて、それらの
参照が `Obl(b)` の初期値になる。`a` は `b` が終わるまで**中断中**であり、その間 `a` は段を持たない。

**(E4) 返りの段。** 活性化 `b` が終端の `Ret(x)` に着く。D9 の終端の `Ret` の行が消費する参照 -- `x` の
inhabited な全 boxed leaf の参照 -- が `Obl(b)` を離れ、`b` を作った (E3) の呼び出し元 `a` の `Obl(a)` に
入る。`a` は `k` の位置で再開する。`b` を作ったのが環境 (E1) であれば、それらの参照は `E` に入る。

**(F) 解放。** ある段が参照を処分して計数下のオブジェクト (D26) `o` の `H(o)` が 0 になったとき、`o` は
**その同じ段の中で解放される**。解放とは、`o` が持つ参照 (D25) をすべて処分し、それから `o` の記憶域を
返すことである (`CODE src/generator.rs: Generator::build_release_boxed_with` -- `destruction_bb` が
`traverse_refs` を走らせてから `build_free_boxed` を呼ぶ、`CODE src/object.rs: build_free_boxed`)。その
処分で `H` が 0 になったオブジェクトも、同じ段の中で同じように解放される。この連鎖はオブジェクトの個数で
抑えられるので有限で終わり、段の終わりには `H = 0` の計数下のオブジェクトはすべて解放されている。

解放が段ではなく段の一部であるのは、そうしないと「`H` が 0 になったが解放されていない」時点ができてしまう
からである。コードもそうなっている -- `Release` が呼ぶ `build_release_boxed_with` は、`destruction_bb` の
中で子の release を呼び、その入れ子の呼び出しが終わってから戻る。

解放の中では `o` はまだ解放されておらず、走査は `o` を読む。

**(E5) グローバル化の段。** グローバル初期化子の活性化が終わり、その参照が `E` に入った後 (E4)、環境が
`mark_global` でその値が到達するオブジェクトのグラフ全体に印を付ける
(`CODE src/generator.rs: Generator::mark_global`, `CODE src/rc_ir/codegen.rs: Generator::implement_rc_global`)。
印の付いたオブジェクトはこの段からグローバル状態 (D26) になる。

**(E6) 中断の段。** ある `Llvm` の op がプロセスを終える。`undefined` が実行時検査つきでビルドされている
とき、この op はメッセージを書いて `abort` を呼ぶ (`CODE src/fixstd/builtin.rs:
InlineLLVMUndefinedInternalBody::generate`)。`FFI_CALL` が呼ぶ C の関数がプロセスを終えるときも同じで
ある。この段の後に段は無い。

実行時検査を切ってビルドしたとき、`undefined` は `unreachable` を出す。そこへ制御が届くプログラムの
振る舞いは LLVM の定めるところで未定義であり、この文書のモデルの外にある。

### D25 (参照の持ち手)

処分されていない各参照は、ちょうど 1 つの**持ち手**を持つ。持ち手は次の 3 つのいずれかである。

- **生きている活性化** `a`。`Obl(a)` の元がそれである。
- **生きているオブジェクト** `o'`。A5 より、`o'` が保持する値の inhabited な各 boxed leaf が 1 つずつ持つ。
  ただしその leaf が null ポインタのときは、そこにオブジェクトも参照も無い
  (`CODE src/generator.rs: Generator::build_traverser_work` -- boxed の腕は `build_if_nonnull` で包む
  ので、null の leaf には何の操作も届かない)。
- **環境**。`E` の元がそれである。

D8 の `H(o)` は `o` への処分されていない参照の総数である。**オブジェクト `o` から `o''` へ到達できる**とは、
`o` が持つ参照が指すオブジェクトを辿って `o''` に着けることをいう。

### D26 (計数下のオブジェクトとグローバル状態のオブジェクト)

オブジェクトは**計数下**か**グローバル状態**かのどちらかである。割り当てられたオブジェクトは計数下であり、
(E5) の段が印を付けた時点でグローバル状態になる。逆向きの遷移は無い。A8 より、グローバル状態のオブジェクトへの
`Retain`/`Release` は `H` を変えず、それが解放されることは無い
(`CODE src/generator.rs: Generator::build_release_boxed_with` -- `global_bb` はカウントを下げず
`destruction_bb` へも行かず `end_bb` へ跳ぶ)。

**D10 の義務集合、D11 の (S-a) と (S-b)、D25 が数える参照、`H` の勘定は、どれも計数下のオブジェクトへの参照
だけを対象とする。**グローバル状態のオブジェクトを指す leaf は、D25 の意味の参照を持たない。持ち手の側には
制限が無い -- グローバル状態のオブジェクトも、計数下のオブジェクトを指す leaf を持てば持ち手である。第 3 節が
この制限が要る理由を述べる。

### D27 (実行の終わり方)

実行は次の 3 つのいずれかである。

- **正常終了**: 段の列が有限で、(E6) の段を含まず、最後の段の後に生きている活性化が 1 つも無い。
- **中断**: 段の列が有限で、(E6) の段で終わる。
- **発散**: 段の列が無限であるか、ある段が終わらない (返らない `Llvm` の op、または返らない `FFI_CALL`)。

この 3 つは実行を尽くす。段の列が無限なら発散である。有限なら、最後の段が終わっていなければ発散、終わって
いて (E6) ならば中断、終わっていて (E6) でなければ、生きている活性化は次の段を持つはずなので生きている
活性化は無く、正常終了である。

D2 より本体は有限の木で、D3 の実行路は有限なので、1 つの活性化が終わるまでに持つ段は有限であり、
1 つの活性化が作る活性化も有限個である。よって発散する実行では、活性化の入れ子が無限に深くなるか、ある段が
終わらないかのどちらかが起きている。

### D28 (実行の読み)

実行における**オブジェクトの読み** (D7 の意味の読み) は、次の 3 つですべてである。

- **(読み-1)** D7 の読む構文の実行。名指された値の inhabited な各 boxed leaf が指すオブジェクトを読みうる。
- **(読み-2)** 走査。3 つある。**(F) の解放の走査**は、解放されるオブジェクト `o` の中の参照を読んで
  それらを処分する。読むのは `o` そのものである -- 子への `Release` が触るのは子の参照カウントと状態バイト
  だけであり、子の中身が読まれるのは子自身が解放されるときである
  (`CODE src/generator.rs: Generator::build_release_boxed_with`)。**(E5) の `mark_global` の走査**と
  **`Std::mark_threaded` の走査**は、起点のオブジェクトと、そこから到達できる (D25) オブジェクトを読む
  (`CODE src/generator.rs: Generator::mark_global`, `Generator::mark_threaded`)。
- **(読み-3)** 環境の読み。

D7 が読みから除いているもの -- 参照カウントと状態バイト -- はここでも読みではない。`Retain` と `Release` が
触るのはそれだけである。

## 2. 提案する仮定

### A16 (`Retain` は解放されたオブジェクトに触れない)

果たす者: 誰も。検査: valgrind の下で走るテスト。

実行のどの `Retain(v, π, s, k)` の段でも、`π` の下の inhabited な各 leaf が指すオブジェクトは、その段の
時点で解放されていない。

**この仮定が要る理由 (反例 R1)。** 次の本体は D11 を満たし、1 つのオブジェクトを 2 回解放する。パラメータ
`y` は boxed で、その unit は所有されているとする。

```
Let(x, Var(y),
Release(y, [],
Retain(x, [],
Release(x, [],
Ret(u)))))
```

- 初期 `Obl` は `y` の leaf `[]` の参照 1 つ (D10 の初期値)。
- `Let(x, Var(y), ..)` は移動なので `Obl` は変わらない (D9)。
- `Release(y, [])` はその参照を取り除く。取り除かれる参照は `Obl` に在るので (S-a) は成り立つ。`H` は
  1 から 0 になり、オブジェクトは解放される。
- `Retain(x, [])` は参照を 1 つ作って `Obl` に入れる。(S-a) は参照を**取り除く**操作についての条件なので、
  この段には掛からない。`H` は 0 から 1 になる -- 解放された記憶域への書き込みである。
- `Release(x, [])` はその参照を取り除く。取り除かれる参照は `Obl` に在るので (S-a) は成り立つ。`H` は
  再び 0 になり、オブジェクトは**2 度目に**解放される。
- 終端の `Ret(u)` の時点で `Obl` は空なので (S-b) も成り立つ。読む構文は 1 つも無いので (S-c) も成り立つ。

## 3. グローバル状態のオブジェクトの上での D10 と D11 の読み

D26 が置いた制限 -- 義務集合と (S-a)/(S-b) は計数下のオブジェクトへの参照だけを数える -- は、無いと矛盾する。

**反例 R2。** グローバル値 `g` は boxed で、本体が `g` を所有位置の引数として関数 `f` に渡すとする。RC IR
では `g` は本体の中の 1 つの `RcVar` として現れ、束縛を持たない (`CODE src/rc_ir/lower.rs: Lowerer::lower_var`
の `None` の腕 -- グローバルは名前を運ぶ atom になる)。

- D10 の初期値はパラメータと capture だけを入れるので、`g` の leaf の参照は `Obl` に入らない。
- `g` の leaf を生成する構文も無い。D10 の生成の表にグローバルの行は無く、`origin_inner` は表に無い名前に
  `here()` -- すなわち `Exactly((g, π))` -- を返す (`CODE src/rc_ir/ownership.rs: origin_inner` の
  `None | Some(Binding::Param) | Some(Binding::Producer)` の腕)。
- ところが `App(f, [g])` は D9 の `App` の行によって `g` の leaf を消費する。消費は `Obl` から参照を
  1 つ取り除くので、(S-a) が破れる。

コード生成もこれと合っている。boxed なグローバルの読みは retain を伴わない
(`CODE src/generator.rs: Generator::add_global_object` -- `retain_on_read = !ty.is_box(..)`、
`CODE src/generator.rs: Generator::get_scoped_obj`)。呼び出し先はその引数を所有するので `Release` するが、
その `Release` はグローバル状態のオブジェクトに対しては何もしない (D26)。すなわち**カウントの上でも
義務の上でも、グローバル状態のオブジェクトは勘定の外に居る**。A8 が言っているのはこのことであり、D26 は
それを D10 と D11 の本文に届く形に書き直したものである。

制限した後、グローバル状態のオブジェクトについて P27 が主張することは次の 2 つに尽きる。どちらも A8 から
直ちに従う。

- 解放されないので、解放後の読みは起きない。
- 解放されないので、「ちょうど 1 回解放される」は成り立たない。第 7 節。

**DEF 勘定が合っている時点**
実行 `ρ` の 1 つの時点 (段と段の間) が**勘定が合っている**とは、次の 3 つが成り立つことをいう。

- **(i)** 処分されていない各参照はちょうど 1 つの持ち手 (D25) を持つ。

## 7. P27 の言明との差

P27 の言明は「そのプログラムのどの実行においても、解放されたオブジェクトの読みは起きず、どのオブジェクトも
ちょうど 1 回解放される」である。前半は (R1) がそのまま与える。後半は、書かれたままでは**偽**である。
反例が 3 つあり、どれもコードの欠陥ではなく言明の側の不足である。

1. **グローバル状態のオブジェクトは 1 度も解放されない。** A8 がそう述べており、コードもそうである
   (`CODE src/generator.rs: Generator::build_release_boxed_with` の `global_bb`)。「ちょうど 1 回」は
   計数下のオブジェクト (D26) に限らなければならない。
2. **発散する実行と中断する実行では、生きたままのオブジェクトが残る。** 発散する実行では終端の `Ret` に
   着かない活性化があり、(S-b) は何も言わない。中断する実行は (E6) の段で終わり、その後に段は無い。
   「ちょうど 1 回」は正常終了する実行に限らなければならない。
3. **正常終了する実行でも、環境が持つ参照から到達できるオブジェクトは残る。** C のエントリ点は
   `run_ios_runner` が作る `IOState` を処分せず、`main` の runner が返した値も処分せずに 0 を返す
   (`CODE src/build/build_object_files.rs: build_main_function`,
   `CODE src/fixstd/builtin.rs: run_ios_runner`)。プロセスが終わるので実害は無いが、「ちょうど 1 回解放
   される」はこの `IOState` について偽である。

したがって P27 の言明は、たとえば次のように書き直す必要がある。

> **P27** (実行の合成)。プログラムのすべての本体が D11 を満たし、A16、A17、A18 が成り立つならば、その
> プログラムのどの実行においても、解放されたオブジェクトの読みは起きず、どのオブジェクトも高々 1 回しか
> 解放されない。さらに正常終了する実行では、最後まで解放されずに残る計数下のオブジェクトは、環境が持つ参照が
> 指すオブジェクトから到達できるものに限る。

この形なら、主定理 T の 2 が依頼者の言葉で述べていること -- 「この 2 つのパスが原因の segv と二重解放は
起きない」-- はそのまま届く。segv は (R1) が、二重解放は (R2) が閉じる。届かないのは「漏れが無い」の側で
あり、そこは (R3) が「漏れるとすれば環境が持っているものだけである」という形で答える。
