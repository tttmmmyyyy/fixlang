# `borrow_ify` と `cancel` の保存の証明 -- 較正、発見、記録

**この文書は証明の一部ではない。** 証明は `README.md` の定義・仮定・命題と、`p*.md` の証明である。ここに在るのは、その性質を選んだ理由 (較正)、証明を書く作業が対象のコードに見つけた欠陥、そして測って外した設計である。

## 6. 較正

RC 規律の定義 (D11) が弱すぎないことを、このコードが実際に持っていたバグで確かめる。

**較正に使うバグ**: issue #519 (修正は `853f9756`、マージは `b81cc2c8`)。構造体のフィールドに入った unbox
union (`Option` や `Result`) の payload を 2 回読むと、`-O max` で読んでいる最中に解放されていた。原因は
`origin_from_leaves_under` が、leaf の辿り着いた origin を、読み出した値自身の名前で組み直していたことである。
1 つのオブジェクトが道ごとに 3 つの名前を持ち、`release` が括弧を閉じず、最初の `Retain` が最後の `Release` と
対になり、その対を消した結果、最初の `Release` が読んでいる最中の payload を解放した。

**この定義がそれを弾くこと**: 修正前のコードは D11 の (S-c) に違反する。payload のオブジェクトが解放された後に
読まれるからである。よって P23 (`cancel` は RC 規律を保存する) は修正前のコードについては偽であり、証明は閉じない。
定義は #519 を弾く。

**この定義が弾く先**: 同じ形の誤りは (S-a) にも現れる。参照が 2 度処分されれば (S-a) が破れる。#519 の症状に
二重解放が含まれていたのはこのためである。

**実行できる形**: この違反を捕まえるテストが `src/tests/test_union_rc_shapes.rs` にある。
`test_field_read_twice_memory_safety` (valgrind の下で走る) と `test_field_read_twice_correctness` である。
`853f9756` の `src/rc_ir/ownership.rs` への変更を戻すと、この 2 つが落ちる。

**節ごとの較正。** 性質は 4 つの節を持つ -- (S-a)(S-b)(S-c) と P26 の観測。節ごとに、その節**だけ**を破る
バグで較正しなければ、較正されていない節が残る。現状は次のとおりである。

| 節 | 較正するバグ | 較正するテスト | 状態 |
|---|---|---|---|
| (S-c) 解放後の読み | #519、#529、#545 | `test_field_read_twice_*`、`test_join_payload_*`、`test_union_payload_two_units_*` | 較正済み |
| (S-a) 過剰処分 | #519 (二重解放の症状) | 同上 | 較正済み。ただし #519 は (S-c) も破るので、この節だけを破る例ではない |
| (S-b) 漏れ | #530、#530 の残穴 | `test_split_ownership_unit_memory_safety`、`test_one_variant_owned_memory_safety` | 較正済み |

**P26 の節は #551 で較正された。** この節は critic が「D11 を満たす間違ったパス」を挙げたことで足された
もので、長らく実在のバグを持たなかった。P26 を証明しようとして見つかった #551 -- 借用化が値を一意から共有へ
倒し、`-O max` でだけ `Debug::assert_unique` が止まる -- がその例である。**その入力は D11 を満たす**
(valgrind でエラー 0、漏れ 0 バイト) のに P26 だけを破るので、この節だけを破る例として要件を満たす。

### (S-c) を強めた記録

**(S-c) はもとは「読む構文が読みうるオブジェクト」だけを扱っていた。** その形では、3 つの節をすべて満たし
ながら 1 つのオブジェクトを 2 回解放する本体が書ける。P27 を証明する作業がこれを見つけた。

```
Let(x, Var(y), Release(y, [], Retain(x, [], Release(x, [], Ret(u)))))
```

`y` は所有するパラメータであり、`x` は `y` の move-bind なので同じオブジェクトを指す。追うと:
初期の `Obl` は `y` の参照 1 つ。`Release(y)` がそれを取り除き、`H` は 0 になってオブジェクトが解放される。
`Retain(x)` は解放されたオブジェクトのカウントを 1 に上げ、`Obl` に参照を 1 つ**加える**。`Release(x)` が
それを取り除き、`H` は再び 0 になってオブジェクトが 2 度目の解放を受ける。

3 つの節はどれも破れない。(S-a) は `Obl` から**取り除く**操作しか見ないので、`Retain` が解放済みの
オブジェクトに触れることを見ない。(S-b) は終端で `Obl` が空なので満たされる。(S-c) は、もとの形では
`Retain` と `Release` を読む構文に数えていなかったので、何も言わない。

**穴は 1 か所であり、直したのは (S-c) の側である。** `Retain` と `Release` が触れる先を (S-c) に入れた。
仮定を足す道 -- 「`Retain` は解放されたオブジェクトに触れない」を A16 として置く -- は採らなかった。それを
果たす者が居らず、穴を動かすだけだからである。(S-c) に入れれば、`borrow_ify` と `cancel` がそれを保つことが
証明の義務になる。

この強化は較正をやり直させない。強めた性質は、弱い形が弾いていたものを弾き続ける。#519、#529、#530、#545 は
どれも強めた (S-c) の下でも規律を破る。

較正をやり直す条件: D11 または P26 を**弱めた**とき。弱めた定義の下で修正前のコードが規律を満たすなら、その
変更は却下する。

(i) は仮定ではなく D21 が活性化に課す制限であり (README の第 4 節)、実行が作る活性化がそれを満たすことを

**(ii-b) を読むのは P18a、P18c、P19、P21 -- `cancel` の健全性の鎖の全体である。**

**「名前は別名類を決める」の否定は「1 つの名前が 2 つの別名類にまたがる」ことである。** 1 つの
オブジェクトが道ごとに 2 つ以上の名前を持つことではない -- そちらはこの性質と両立し、そのとき
`un_bump` は `shares_an_object` が偽になって `NoBracket` を返し、対を見つけずに諦める。すなわち保守的な
側に倒れる。

**この性質は `p13-disposals-and-pending.md` の `L14` の後半が与える** -- 「`obj(x, λ)` が計数下であるとき、
`o = origin(x, λ).identity()` は `ρ` の上のスロットであって `C_ρ(o) = C_ρ(x, λ)` である」。
`p60-insert-rc.md` の `L5b` が 3 段でそれを引く。**前提として置く者は居ない。**

**この性質が偽になりうるのは A3 の 1 節を落としたときだけである。** 「複数の元を宣言する op は存在
しない」を落とすと 1 つの名前が 2 つの類にまたがりうる。そのとき `un_bump` は `VarPath` の鍵で対を
選ぶので、`O1` の `Retain` と `O2` の `Release` を対にして両方を削除する -- `O1` の二重解放と `O2` の
漏れである。**A19 (ii-b) の下でこの節が load-bearing なのはこの経路による。**

**A19 (i) が制限であることの重み。** (a) と (b) は循環するので、P28 は `p05-holders.md` の 1 つの帰納で <!--#4610062-->
示す -- 実行の点 `p` までの接頭で D11 が当たることから `p` の許容性が出て、それが `p+1` の D11 を当てる。
`p60-insert-rc.md` が持っていた活性化ごとの勘定は、そこへ移った。

**(i) を制限に置いたことが、T の 1 と 2 の範囲を守っている。** (i) を仮定のまま置くと `H` が活性化から
計算できず、実行が作る活性化に絞るしかなくなる。ところが D29 が P21 のために構成する入力の活性化 `α` は
実行に実現するとは限らないので、絞ると P21 (b) が覆えず、P23 と T の 1・2 がその差だけ閉じない。
狭めた先は「出力の実際の実行」ですらない -- `cancel` が計数を動かして分岐を変えた時点で `α` を実現する
入力の実行が無くなるので、根の活性化が覆われず P27 が起動できない。


## 8. 発見

証明を書く作業が、対象のコードに 6 件の欠陥を見つけた。3 件は miscompile、2 件は漏れ、1 件は一意な値が
共有として観測されることであり、いずれもバグハントでは見つかっていなかった。5 件は修正済みで、#552 は
「A19 を示す」に置き換わった (この節の末尾)。

**#529 (miscompile、修正 `be26b396`、PR #531)。** P3/P4 の証明が閉じない原因はコードにあった。
`origin_from_leaves_under` と `origin_inner` の `Binding::Join` の腕が、内側の `Origin` を `candidates()` で
平坦化するとき、その `identity` を落とす。落ちた名前は消費の側の名前に現れず、`cancel` の `Release` の腕が
その名前の pending な `Retain` に印を付けないので、対でない retain と release が消える。`-O max` で解放後の
メモリを読む Fix プログラムを作って確かめた (`-O none` と `-O basic` は正しい)。

**#530 (漏れ、修正 `211b2d3c`、PR #544)。** P14 の証明が閉じない原因もコードにあった。`owns_unit` は unit
ごとに真偽値を 1 つ答えるが、所有は leaf ごとの性質である。1 つの unit の下の leaf が別々の root に由来して
所有が分かれると、`rewrite_rc` は `Release` を丸ごと落とすか、借りている参照まで処分するかの二択になり、
どちらも誤りである。leaf を 2 つ以上持つ unit は unbox union だけであり、`-O max` で 32 バイトが漏れる Fix
プログラムを作って確かめた (`-O basic` は漏れない)。修正は `level_ownership`: 割れた候補を所有の側へ倒す。

**#530 の残穴 (漏れ、修正 `50e7712d`、PR #546)。** `level_ownership` の発火判定は leaf 粒度で所有を読み、
書き換えが読む `owns_object` は unit 粒度で読む。パラメータの unbox union の一方の変位の leaf だけが所有
されているときに食い違い、`Release` が落ちて参照が漏れる。修正は `owns_object_yet`: 発火判定を
`owns_object` と同じ粒度で書き、`level_ownership` がそれを読む。

**#545 (miscompile、修正 `a924f115`、PR #546)。** `origin_from_leaves_under` は、unit の path の下の leaf が
別々のオペランド unit に辿り着くとき、答えを「読み出した値自身の名前」を identity とする `Join` にする。
すると union 自身のキーはその値の名前になり、payload の leaf を消費する構文のキーは payload の元の名前に
なる。1 つのオブジェクトが 2 つのキーを持ち、`Retain` と消費が別のキーに分かれるので、`cancel` が消費を
またいで対を消す。`Std::Option (a, b)` と `Std::Result e (a, b)` がこの形である。

**同じ族の 3 件目が設計をやり直させた。** #519、#529、#545 はどれも「1 つのオブジェクトが道ごとに 2 つ以上の
名前を持ち、`Retain` と `Release` が別のキーに分かれる」形である。3 件目の応急処置は、`Etc::Works` を
+6.40% 遅くした。根は、キー -- `origin` の identity を unit へ丸めた名前 -- が何を名指す量なのか定まって
いなかったことである。`a924f115` はキーを取り除いた。`cancel` は `Retain` を 1 本の `Vec<PendingRetain>` に
積み、`Release` はオブジェクトを共有する最内の要素と対になる。**対にするのに要る情報は最初から
`outstanding` にあり、キーがそれを潰していた。** LangArena のコーパスで RC 操作は 28 減り、速度は雑音の中で
ある。

**この設計変更で言明が変わった命題。** P5、P7c、P16、P17、P18a、P19。いずれもキーを主語にしていた。
新しい言明は、`identity` が名指す位置 (`VarPath`) ごとに数えた参照の多重集合 (`References`) を主語に
する。**`VarPath` はオブジェクトではない** -- D6 の位置であり、`obj(・)` で写した先が D25 のオブジェクト
である。2 つを同一視すると P5 (a) (「identity が等しい 2 つの leaf のスロットは同じオブジェクトを指す」)
が空虚になる。

**#551 (一意性が倒れる、修正済み)。** P26 の証明が閉じない原因はコードにあった。借用化は、本体のどこでも
消費されないパラメータ leaf を借用に倒す。借用版はその leaf の `Release` を落とすので、呼び出し元がその
参照を呼び出しの後まで持つ。その結果、借用版の中の一意性の観測点でカウントが入力より 1 大きくなり、
一意だった値が共有として観測される。`Debug::assert_unique` を持つプログラムが `-O max` でだけ止まる
(`-O none` と `-O basic` は止まらない)。`unsafe_is_unique` の doc が認めているのは共有から一意への向き
だけなので、この向きは認められていない。

振り分けの判定 `routing_saves_retain` が引数についての `any` であることが、この欠陥を目立たなくしている。
条件を満たす引数は、`Release` が落ちる引数とも観測される引数とも別でよい。

修正は「一意性の観測点に到達する関数の借用版を作らない」である。代償は実測でゼロだった -- LangArena と
speedtest のどちらでも借用版を 1 つも止めず、命令数はベースラインと一致する。

**この修正には穴が 5 度あり、いずれも証明が見つけた。** 5 度とも症状は同じ「`-O max` でだけ
`Debug::assert_unique` が止まる」であり、テストは 1 度も見つけていない。

1. 到達を**直接呼び出しのグラフだけ**で取っていたので、局所変数が持つクロージャを経た間接呼び出しの先に
   ある観測点に届かなかった。直したのは、間接呼び出しを持つ関数にクロージャが運びうる全関数への辺を張る
   ことである (A7 が呼び出し先の解決を放棄している以上、これが健全な近似)。
2. その「クロージャが運びうる全関数」を `prog.funcs` の本体からしか集めておらず、**グローバル初期化子の
   中で作られるクロージャ**が落ちた。走査を 1 つの閉包に括り出し、プログラムが持つ本体を全部そこへ通す
   形にした (`prog.funcs` の各本体と `prog.globals` の各初期化子)。
3. 関数を適用する仕組みを `App` だけだと数えていた。**`Llvm` の op が、生成するコードでオペランドを適用
   する**経路が落ちていた -- `Option::mod_some` を 1 つ使うだけで届く。同じ形の op は `Std::fix`、どの
   union の `mod_{変位}`、`with_retained`、`Array::borrow_elements`、`mutate_boxed` 系と
   `Array::mutate_elements` 系の 8 つである。

4 件目の直し方は前の 3 件と違う。**op 自身に宣言させ、宣言し忘れたら開発モードで落ちるようにした。**
`LLVMGen::applies_a_function_operand` を足し (既定は偽)、`Generator::apply_lambda` が、いま生成中の op が
それを宣言しているかを検査する。宣言を落とした op が関数を適用した瞬間にテストが落ちるので、次の op が
同じ穴を作れない。

5. **解放が `Std::FFI::Destructor` のデストラクタを走らせる経路**が落ちていた。解放はどの本体にも在り、
   デストラクタ関数も、それが返す `IO` の動作も、オブジェクトの欄から来るのでどの構文も名指さない。
   `Destructor::make(o, |v| ...)` の `o` を借用位置にも渡す 20 行のプログラムで届く。

5 件目の直し方は**辺を条件付きで張る**ことである。プログラムが `Destructor` を作らなければ、この解放は
起こりえないので辺を 1 本も張らない (`builds_a_destructor`)。作るプログラムでは、到達しうる先に境界が
無い -- デストラクタ関数が返す `IO` の動作がまた別の動作を返しうる -- ので、クロージャが運びうる全関数へ
張る。**代償を払うのを、その形を実際に使うプログラムだけに限った。**

広げた分の代償はゼロだった (クロージャを多用する 10 ケースで命令数が一致)。回帰テストは 5 本あり、いずれも
対応する辺を外すと落ちる。

**この 5 件は「列挙を手で並べると落とす」という族である。** 同じ族が、キャッシュの鍵が手書きの列挙で
4 つ漏れていた件にある。落とした列挙が安全側に倒れるなら気付かないが、この門は落とすと**借用版を通して
しまう**向きなので、落とした分だけ穴が開く。手は 3 つ出た -- 3 件目までの「在りかを 1 か所に集める」、
4 件目の「集められないときは、落としたことが検出できる形にする」、5 件目の「境界が引けないときは、その形を
使うプログラムだけに代償を寄せる」。

**#552 (`cancel` の対の判定の非対称、修正しない)。** P18a の証明が閉じない原因はコードにあった。`Release` の
訪問は `other_objects` -- その節点が触れうる、identity 以外の候補 -- を `consume_objects` へ渡すのに、
`Retain` の訪問はそれを記録しない。よって `Join` の値の `Retain` は identity (`Match` の束縛変数の名前) だけを
名指し、アームが作った値を名指す消費がその `Retain` を素通りする。括弧の中で消費が起きたまま対が消え、
消費先が解放したオブジェクトを束縛変数が読む形になる。反例 `C1` は `p13-disposals-and-pending.md` の
P18a の証明にある。

**実在の入力にこの形が現れることは測った。** `cancel` が消した retain のうち、pending の間に候補を消費された
ものは、LangArena で 11 件ある (`HashMap::insert` の 5 つの特殊化、`Std::loop` のクロージャ特殊化、
`CompressArith::_code`)。**ただし観測可能な障害は再現できていない。** `insert_rc` はアーム本体の値が
`Match` の後で live なら、そのアームの中に `Retain` を置く。その参照が P18a の `+1` を与えるので、
`C1` の形をそのまま Fix のソースから作ることはできなかった (2 通り試した)。

**修正を書いて測り、外した。** `PendingRetain` に候補を持たせて `consume_objects` に見せると、
`cp_lib_dijkstra` の命令数が **+9.73%**、`cp_lib_bipartite` が +1.93%、`cp_lib_lsegtree` が +1.05% 増えた
(`-O experimental`、変更を 1 つずつ入れて属性を取った)。出どころは増える参照カウント操作 (静的に +0.85%)
ではなく、消せなかった retain が値を Unique のまま残さないので `unique_check_elim` が特殊化を諦めることで
ある。

**その後、この修正では P18a が閉じないことが分かった。** ずれを作る本体は `Match` を 1 つも含まず、
`origin` はどの leaf についても `Exactly` を返すので `other_objects` はどこでも空である。ずれを作るのは `Join` ではなく `App` -- 所有する引数を取って返す関数が、参照を別の
別名類へ移すこと -- であり、候補を記録しても届かない。**すなわち外した修正は、代償を払ったうえで問題を
閉じもしなかった。**

P18a が要る前提は A19 として書いた。**(ii-a) と (ii-b) は `insert_rc`・`split_rc_units`・`borrow_ify` の
3 人が果たし、(i) は仮定ではなく D21 が活性化に課す制限で、実行が作る活性化がそれを満たすことは P28 (b) が
示す。** この issue は「コードを直す」ではなく「A19 を示す」に置き換わり、それは済んだ。

**定義の側の欠陥も 3 件出た。** 最初の 2 件はどちらも P27 を証明する作業が見つけた。1 つは (S-c) が
`Retain` の触れる先を見ておらず、3 つの節をすべて満たしながら二重解放する本体が書けたこと (第 6 節)。
もう 1 つは D10 と D11 がグローバル状態のオブジェクトで場合分けしておらず、**グローバル値を所有位置の引数に

**この周回で定義の側の欠陥がさらに 9 件出た。** 内訳を族ごとに述べる。

## 9. 測って外した設計 -- 呼び出し側の局所条件

門 (`funcs_observing_uniqueness`) は全プログラムの到達可能性を計算し、5 度にわたって列挙を落とした
(第 8 節)。**列挙の要らない設計を測り、外した。**ここに残すのは、同じ案が再提案されたときに測り直さなくて
済むようにするためである。

### 案

借用版へ振り替えた呼び出しで、借用される unit は 3 通りしかない。

| | 入力の呼び出し中 | 出力の呼び出し中 | |
|---|---|---|---|
| A: 呼び出し元も借用している | base + 1 (所有する呼び出し先のために retain が要る) | base | 出力が低い |
| B: 所有していて、呼び出しの後も使う | base + 1 | base | 出力が低い |
| C: 所有していて、呼び出しで死ぬ | 1 -> 呼び出し先が最後の使用で解放 -> 0 | 1 のまま (解放は `call_rc` の after) | **出力が高い** |

カウントが上がるのは C だけであり、**C は借用しても retain が消えない** -- `routing_saves_retain` の doc が
「An owned value whose object ends at the call is moved either way, so borrowing it removes no retain
and only delays its release」と述べているのがこの場合である。ところが判定は引数についての `any` なので、
別の unit が得をすれば C の unit も一緒に借用に倒れる。

**判定を「1 つでも得をする unit が在る、かつ C の unit が 1 つも無い」に変えると、振り替えた呼び出しの
どの計数下オブジェクトについても出力のカウントが入力以下になる。** `unsafe_is_unique` が認めるのは
共有から一意への向き、すなわちカウントが下がる向きなので、これで観測値が悪化しない。呼び出し 1 か所しか
見ないので、到達可能性の列挙が要らない。門も、`observes_uniqueness` と `applies_a_function_operand` の
宣言も、`apply_lambda` の検査も、`builds_a_destructor` の走査も消える。

### 効いたことは確かめた

門を切った状態で、第 8 節の 5 件の回帰テストが 5 本とも緑になった。すなわちこの 1 条件が 5 つの穴を
すべて塞ぐ。加えて、門の証明が閉じられない場合 -- `FFI_EXPORT` から入る第 2 の制御の流れが、こちらの
借用版の窓の中で観測する場合 (`p50-observation.md` の「オーケストレータへ報告する定義と仮定の穴」の項目 1) -- も、カウントがそもそも上がらない
ので閉じる。

### 外した理由 -- `levenshtein` が 1.5 倍になる

コーパス 56 ケースを測った (`benchmark/speedtest/log.csv` の `deb3b0ea` と `0ec1a398`)。

| ケース | 命令数 | cycles:u |
|---|---|---|
| `levenshtein` | **+49.97%** (746,743,934 -> 1,119,858,074) | **+38.12%** |
| `cp_lib_scc` | -0.83% | 雑音内 |
| 残り 54 件 | 動かず | 雑音内 |

`levenshtein` は振り替えが 2 件から 1 件に減っただけである。熱い内側ループの呼び出しが 1 つ、C の unit を
1 つ持つために借用版を失い、それだけで命令数が 1.5 倍になる。コーパス全体では振り替えが 57 件から 44 件へ
減る。

**門の側の代償はゼロである。**門を切っても借用版の数はコーパスのどのケースでも変わらない -- すなわち
門はこのコーパスでは 1 つも止めていない。

### 詰めるとすれば

`levenshtein` が落ちるのは、借用版が**すべての**借用可能な unit を借用し、呼び出しがそのうち 1 つでも C を
持つと丸ごと断られるからである。**借用版が borrow する unit を、どの呼び出し位置でも C にならないものだけに
絞れば**、この呼び出しは振り替えられたまま残る。unit を減らすと断られる呼び出しが減るので、単調減少の
不動点で決まる。測っていない。

## 10. 検証が骨格に出した欠陥

検証は、証明の段の誤りだけでなく、**定義と仮定の側の欠陥**を 5 件出した。どれも「証明済み」と記録した後の
取り消しにつながっている。ここに置くのは、この枠のどの項目がどう直ったかの記録であり、
そこから出た一般の規則は `code-proof` スキルが持つ。

### A19 (ii) が、どのプログラムも満たさない形で使われていた

`p13-disposals-and-pending.md` の P18a の証明も `p40-cancel-soundness.md` の `L42` も、A19 (ii) を **各時点に
ついて `held ≥ 1 + bumps`** の形で置き、その上に P18a と P18c を建てていた。この形は病的な本体ではなく
**正しい本体すべて**で破れる。`p13` 自身の例 `f` (`Let(z, Llvm(zero,[]), Release(b,[],s,Ret(z)))`) で、
`Release(b,[])` の直後に `held = 0`、`bumps = 0` となり `0 ≥ 1` を要求する。前提が空虚なので、導出の各段が
妥当でも結論は何も言っていなかった。

**直したのは仮定の側である。** A19 (ii-b) は `bumps ≥ 1` を条件に付けた形になった。弱い `held ≥ bumps` に
してから `1 +` を導く道は塞がっている -- `held = bumps` かつ `bumps ≥ 1` の時点を弱い形は許し、
`p13-disposals-and-pending.md` の `C1` の類 `C` が `Let(w, App(f, [q]), ・)` の入口でその時点だからである。台帳で測ると弱い形と強い形はちょうど 1 単位違う。

**証明者 2 人が互いに独立に、同じ誤読をした。** README の A19 の脇に「字義どおりには偽である」と書いて
あっても防げていない。引用の突き合わせを課した検証者だけがこれを見つけた。
