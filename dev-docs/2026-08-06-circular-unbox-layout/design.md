# 循環した unbox 型でコンパイラがスタックを使い切る (#193)

## 1. 症状

次の 2 行を含むプログラムをビルドすると、コンパイラが自分のスタックを使い切って core dump する。

```fix
type A = unbox struct { b : B, n : I64 };
type B = unbox struct { a : A, m : I64 };
```

```
thread '<unknown>' has overflowed its stack
fatal runtime error: stack overflow, aborting
Aborted (core dumped)
```

`A` の値のレイアウトは「`B` の値 + `I64`」で、`B` の値のレイアウトは「`A` の値 + `I64`」なので、
どちらも有限のバイト数を持たない。コンパイラはこれを診断して拒否すべきところで、答えを求めて
無限に再帰する。

診断の文面自体はコンパイラの中にある。`ObjectType::to_struct_type`（LLVM の構造体型を組み立てる
関数）が、自分がいま何の型のレイアウトを求めている最中かを経路として持ち回り、同じ型が再び現れたら

```
Cannot determine the layout of type `A`. There are circular definitions by unboxed types.
Please change some types to boxed.
```

を出す。**この診断にはどのプログラムからも到達できない。** レイアウトを組み立てるより前に、
コンパイラの別の場所が同じ循環を無防備に辿ってスタックを使い切るからである。

その別の場所は `TypeNode::is_fully_unboxed`（「この型は boxed な部分を一切含まないか」を答える
述語）である。この述語は各フィールドの型に再帰し、boxed / クロージャ / 配列 / 関数ポインタの
いずれかに当たったところで止まる。unbox struct だけの循環はそのどれにも当たらないので、止まらない。
呼び出し元は参照カウント IR (`src/rc_ir/`) の各パスで、いずれもコード生成より前に走る。

## 2. 止まらない形は 2 つある

同じ「レイアウトの展開が終わらない」でも、形が 2 つある。両方を扱う必要がある。

**循環**: 展開の途中で**まったく同じ型**が再び現れる。上の `A` -> `B` -> `A` がこれ。

**増大**: 同じ型は二度と現れないが、型が段ごとに大きくなり続ける。

```fix
type P a = unbox struct { x : P (a, a), n : I64 };
```

`P I64` のレイアウトは `P (I64, I64)` を含み、それは `P ((I64,I64), (I64,I64))` を含む。
型は毎段 2 倍に育ち、二度と同じにならない。既存の診断は「まったく同じ型の再出現」だけを見るので、
仮に到達可能になっても**この形は捕まえられず、やはり止まらない**。

## 3. 判定基準

誤りは 2 つあり、決め方が違う。

**(a) 値が自分自身を含む。** その場に置かれるフィールドだけを降り、いま降下中の型に再び出会ったら
報告する。ポインタは指す先によらずポインタなので、boxed なフィールドで降下は止まる。
**これは厳密に決まる**（有限グラフ上の深さ優先探索）。降下中の型と降り終わった型を区別するのが
要点で、混ぜると `type A = unbox struct { xs : Array B, b : B }` のような、ポインタ側の辺が先に
届く循環を取りこぼす。

**(b) 自分自身をより大きな型引数で再び要求する。** `P a = unbox struct { x : P (a, a) }` を
`P I64` で使うと、`P (I64,I64)`、`P ((I64,I64),(I64,I64))`… と型が毎段育ち、二度と同じにならない。
コード生成は型ごとにオブジェクトを作るので終わらない。ポインタを挟んでも同じである
（`type P a = box struct { x : P (a, a) }` も終わらない）。**これは上限で止める。**

### 上限は「到達した型 1 つの項の深さ」

厳密に決める基準は使えない。この問いは一般には決定不能で、文献にある決定可能な断片
（Kennedy と Pierce の expansive recursion、.NET がジェネリクスに課しているもの）は、Fix が持つ
**高階カインドの型パラメータを含まない**。実際、宣言のグラフで決める案は反例 2 つで潰れた
（`correctness.md` 7 節）。

上限を何に置くかは、次の原則が決める。

> 単純な型をプロジェクトに足しただけでコンパイルできなくなってはいけない。複雑な型を足して
> 落ちるのは許容できるが、単純なソースファイルは、時間が伸びるだけで通るべきである。

- **型の個数**の上限はこの原則を破る。モジュールを足せば増えるので、閾値に近いプロジェクトが
  無関係なファイル 1 つで落ちる。
- **降下の長さ**の上限も破る。`A` が `B` を、`B` が `C` を…と単純な型が 1000 個繋がるだけで深くなる。
- **1 つの型の項としての深さ**は破らない。`A` も `B` も項としては深さ 1 で、いくつ繋げても
  深くならない。(b) の族だけが 1 段ずつ育つ。

したがって上限は `MAX_TYPE_DEPTH`（500）1 つである。実測: コーパスと examples で到達する型の
最大の深さは **10**、手で 25 段ネストしたタプルで **27**。

**この上限は停止性も与える。** 有限個の型構築子の上で深さが抑えられた項は有限個しかないので、
記憶と合わせて歩きは必ず尽きる。個数の予算も降下の深さの上限も要らない。

### 型を辿る処理が線形でなければならない

`substitute_type` は束縛変数に置換先の `Arc` をそのまま返すので、**型は共有 DAG** になる。ところが
`Hash`・`PartialEq`・`free_vars` は共有を辿らず木として展開していた（深さ k で 2^k）。上限 500 を
現実的にするために、`TypeNode` にハッシュ・groundness・深さのキャッシュを持たせ、等価性に
`Arc::ptr_eq` の近道を入れた。`ty_to_object_ty` の `assert!(ty.free_vars().is_empty())` は
キャッシュ付きの `is_ground` に置き換えた（これだけで倍々型が 200 秒かかっていた）。

## 4. 検査を置く場所

**バリデーションで拒否する。** 型検査とインスタンス化が終わった時点、コード生成が始まる前に、
`Program::validate_layouts` がインスタンス化された式の木を歩き、各ノードの型のレイアウトが定まる
ことを確かめる。当たったら、コンパイラの他のエラーと同じ `Errors` で、その値が現れる式を指して
報告する。

```
error: `Main::A` has no size: its unboxed fields reach `Main::A` itself (`Main::A` -> `Main::B` ->
`Main::A`). Make one of these types boxed.

7:6-7:7 in "main.fix",
  |
7 | f = |x| x.@n;
  |      ^
```

直し方は判定した誤りで変わる。(a) は経路のどこかをボックスにすれば終わるが、(b) はボックスに
しても終わらないので、引数を育てるのをやめることを言う。

```
error: `Main::P Std::I64` has no size: laying it out reaches types nested more than 500 deep, so it
needs endlessly many. A type reached from itself at a larger type argument does this; give the
recursive occurrence the same type arguments.
```

報告は標準ライブラリの外に出す。シンボルを名前順に歩くと、ユーザの型で実体化された
`Std::Array::empty` のような関数が先に当たり、報告がライブラリの中に出てしまうので、`Std` の
シンボルは最後に歩く。

ノードの型を型ごとに 1 回だけ調べるので、大きなプログラムでも 1 ミリ秒に収まる（付録 B）。

見る順は 3 段。**ソース位置を持つノードの型**、次に**位置を持たないノードの型**、最後に
**インスタンス化されたシンボルの型そのもの**である。報告はいちばん先に型を掴んだところに出るので、
この順がそのまま「できるだけユーザのコードを指す」ことになる。シンボルの型が最後なのは、
コンパイラが作ったアクセサにはソース位置が無いからで、これを先に見ると位置の無い診断になる。
ノードを見る順も、エントリポイントと export した値が先、シンボルの本体が名前順で後になっている。
ライブラリの関数がユーザの型でインスタンス化されているとき、報告をライブラリの中ではなくユーザの
コードに出すためである。

**コード生成の側では調べない。** ユーザのプログラムの誤りは、コード生成が答えを求めて自滅する形では
なく、その前のバリデーションで拒否されるべきものである。したがって、型のフィールドを降りる歩き
（`is_fully_unboxed`、`ObjectType::to_struct_type`、`rc_ir` の 3 つ）は、レイアウトが定まる型しか
渡されないことを前提に、判定を持たない。`to_struct_type` が持っていた「circular definitions by
unboxed types」の検査と、それを支えるために配られていた `unboxed_path` 引数も外した。

歩きは、コード生成がオブジェクトを組み立てる関係（`ty_to_object_ty`）そのものを辿るので、両者が
食い違う余地が構成上ない。それでも数え漏らせば、その型はコード生成に届き、以前と同じ形で（スタックを
使い切るか、確保が止まらずに）落ちる。**そのときに直すのはバリデーションの側**である。付録 D。

**型宣言の検証時に置くことはできない。** レイアウトが定まるかどうかは、宣言だけでは決まらず、
型引数に何を渡したかで決まるからである。次の 2 つのプログラムは、型宣言が同一で、片方だけが正しい。

```fix
type [f : *->*] C f = unbox struct { x : f (C f), n : I64 };

type U  b = unbox struct { y : b, m : I64 };  // unbox
type Bx b =   box struct { y : b, m : I64 };  // box
```

`C U` は `U (C U)` を含み、それは `C U` を含む。無限である。`C Bx` は `Bx (C Bx)` を含み、
そこはポインタなので有限である。`C` の宣言も `U` の宣言も `Bx` の宣言も、それぞれ単独では
何も間違っていない。したがって、この誤りは**型が組み上がったところ**でしか判定できない。
インスタンス化より前に判定できないということは、`fix check` と言語サーバには届かないということでもある。

## 5. コード生成スレッドの panic がプロセスを壊す

この作業の途中で見つけた、これとは独立の既存欠陥である。コード生成は翻訳単位ごとにスレッドを立てて
並行に走り、そのうちの 1 つが panic すると、**5 回に 1 回ほどの割合でプロセスが SIGSEGV や SIGABRT
で落ちる**。panic のメッセージは表示されるが、その後にクラッシュが続く。

原因は、スレッドを待ち合わせる側にある。`build_object_files` は、最初に panic したスレッドを
見つけた時点で自分も panic して抜けていた。残りのスレッドは LLVM のコード生成の途中で走ったまま
であり、プロセスはその下で終了処理に入る。アロケータがヒープを解放するのと、まだ走っている
スレッドが LLVM を実行しているのが同時に起きて落ちる（`mi_process_done` と
`SelectionDAGISel::runOnMachineFunction` が並んだスタックが取れている）。

直し方は、**全スレッドを待ってから** panic を運び直すこと。運び直しは `resume_unwind` で行う。
`panic_any` で新しい panic を起こすと、panic hook が 2 度目の報告を試み、join から受け取った
payload は文字列ではないので `(unknown error)` という行が後ろに付く。

コード生成スレッドの panic は、RC IR の各パスが持つ内部アサーションが今も出しうる。

## 6. 見落としやすい形

型そのもののフィールドだけを見ていると、次の 3 つが見えない。いずれもコード生成はレイアウトを
要求するので、見落とすとスタックを使い切る。テストで固定してある。

```fix
type T = unbox struct { p : Box I64, y : T, n : I64 };   // boxed フィールドが先にある循環
type Tree = unbox union { leaf : (), node : (Tree, Tree) };  // これを `Array Tree` に入れる
type P a = box struct { x : P (a, a), n : I64 };         // ポインタ越しの増大
```

1 つ目は `is_fully_unboxed` の目に入らない。この述語はフィールドを順に見て、最初の boxed フィールドで
答えが false に決まり、そこで打ち切るので、`y : T` を見ない。2 つ目の要素の型は `Array` のフィールド
ではなく `#ArrayStorage Tree` の側に現れる。3 つ目はポインタの先なので、その場に置かれるフィールドを
辿るだけでは届かない。オブジェクトの中身（付録 D）を辿ると 3 つとも通り道に乗る。

## 7. このプログラムは今後どうなるか

今日コンパイルが通り、今後も通るもの:

- 型構築子が経路に再び現れるが展開が終わるもの（`W (W (W I64))`）。
- 循環が boxed / 配列 / クロージャを通るもの（`type T = box struct { x : T }`、
  既存のテスト `test_circular_type_definition`）。
- コンテナを自分の型引数で再帰させる普通の書き方。隣接リスト
  `type Node = box struct { edges : Array (I64, Node) };` を `Array Node` で使う形がこれで、
  レイアウトは 6 個の型で閉じる。
- 循環した unbox 型を**宣言だけして使わない**プログラム。レイアウトを誰も要求しないので、
  検査も走らない。

今日 core dump し、今後はエラーになるもの: 循環・増大する unbox 型のレイアウトを要求するプログラム。

## 8. テスト

`src/tests/test_basic.rs` に 21 本。エラーを主張する 13 本は `test_source_fail` で、コンパイルが
`Errors` で失敗すること、すなわち報告がバリデーションから来ていることまで見る。

1. 2 型の循環 `A -> B -> A`（誤り a）。文面の**経路** `` `Main::A` -> `Main::B` -> `Main::A` `` まで見る。
2. 増大 `P a = unbox struct { x : P (a, a) }`（誤り b）。
3. 型引数によってのみ循環する `C U`（宣言では判定できない形）。
4. boxed フィールドが先にある循環 `T = unbox struct { p : Box I64, y : T, n : I64 }`（6 節）。
5. union を通る循環 `Tree = unbox union { leaf : (), node : (Tree, Tree) }`。マニュアルが
   「`box` で書くべき例」として載せている宣言そのもの。
6. `C Bx` がコンパイルでき、実行できる。3 と宣言が同一なので、宣言だけを見て拒否する実装を弾く。
7. `W (W (W I64))` がコンパイルでき、実行できる。型構築子の再出現だけで拒否する実装を弾く。
8. 5 の `box` 版がコンパイルでき、値を作って読める。
9. 循環した unbox 型を宣言するだけのプログラムがコンパイルできる（7 節の「今後も通るもの」）。
10. 大きさの定まらない型の `Array`（要素は `#ArrayStorage` の中に置かれる）。
11. boxed フィールドの先にある循環（プログラムが名前を出すのは、そのフィールドを持つ型だけ）。
12. ポインタ越しの増大（ポインタを挟んでも (b) に当たること）。
13. フィールドアクセサの値だけが型を名指す形（関数が取る型を辿ること）。
14. `Array E`（`E` は `Array (I64,I64)` を持つ）がコンパイルでき、実行できる。増大を引数の
    大きさや埋め込みで見る実装を弾く。
15. 関数を持つ union の variant があっても、その関数を作らないプログラムは通る。関数が取る型を
    オブジェクトの中からも辿ると、これが落ちる。
16. 自分自身を取るコールバックを持つ struct が通る。
17. 報告がユーザのコードの行を指す（文面にその行が入る）。3 段の順を崩すと落ちる。
18. 関数の**戻り値**の型が大きさを持たない形。
19. 引数 2 つの型構築子の増大（引数を 1 つずつ突き合わせること）。
20. 引数 2 つの型構築子で、片方の引数だけが無関係なもの（受理側）。
21. 関数を作る側の union variant（拒否側。15 と対）。

6 と 7 は、値を作れない型を扱うので、実行時の引数の個数で分岐を選び、その片方でだけ当該の型の
関数を呼ぶ形にしてある。定数条件だと最適化で分岐ごと消え、レイアウトが要求されなくなる。

`src/tests/test_build_exit_status.rs` に 1 本。`fix build` を別プロセスで走らせ、診断が標準エラーに
出ること、その後ろに何も続かないこと、そして**シグナルではなく終了ステータスで**終わることを見る。

5 節の直し（全スレッドを待ってから運び直す）を主張するテストは無い。コード生成スレッドの panic は
内部アサーションからしか出ないので、それを起こすプログラムを書けないためである。

## 付録 B: コンパイル時間

`perf stat -e instructions:u` で、バリデーションの呼び出しだけを外したビルドと比べた（`-O max`）。

| | バリデーションあり | なし | 差 |
|---|---|---|---|
| hello world | 3.654 G | 3.650 G | +0.1% |
| nbody | 5.181 G | 5.168 G | +0.3% |
| binary_trees | 3.593 G | 3.590 G | +0.1% |
| fannkuch | 5.174 G | 5.161 G | +0.3% |
| 幅 8 を 5 段入れ子にした unbox struct | 7.87 G | 7.87 G | +0.0% |

差は最大で 0.3%。パスの中で時間を測ると、hello world で 0.58 ms、
最後の入れ子プログラム（issue #182 で測った病的なプログラム、葉が 32768 個）で 1.0 ms。型ごとに
1 回しか歩かないので、型の種類の数でしか伸びない。同じプログラムの `-O none` は 72.68 G 対
72.65 G。

**コード生成の側に判定を置いた場合の値段（不採用）。** 型のフィールドを降りる歩き 4 つすべてに
判定を持たせた版では、上の入れ子プログラムが `-O max` で 8.01 G（+1.8%）になった。さらに、
`is_fully_unboxed` の打ち切りをやめて 1 箇所にまとめる案では、fannkuch のビルドが 5.16 G から
5.31 G（**+3.0%**）になった。どちらも採らず、バリデーションだけにしてある。

## 付録 C: 同じ族の issue が 2 つある

### #171 自己参照する associated type

外から見た症状が同じ（宣言の循環でスタックを使い切る）ため、同じ検査で両方落ちるかを最初に確かめた。
**落ちない。別の機構である。**

- #193 は**レイアウトの展開**（unbox フィールドを辿る）が終わらない。コード生成の前段で起きる。
- #171 は**型の簡約**（associated type を実装の右辺で置き換える）が終わらない。型検査で起きる。

さらに、**#171 の本文が挙げている修正案は採れない**ことが分かった。案は「実装が与える
associated type の値に associated type が含まれないことを要求する」だが、これは標準ライブラリを
拒否する。`src/fixstd/std.fix` のイテレータの実装がまさにその形である。

```fix
type Item (FilterIterator i a) = Item i;
type Item (ZipIterator i1 i2) = (Item i1, Item i2);
type Item (EnumerateIterator it) = (I64, Item it);
```

`examples/type_level_nums.fix` の型レベル加算も同じ形である。

```fix
impl [n : Nat] Succ n : Nat { type Add (Succ n) m = Succ (Add n m); }
```

代わりに使えるのが、GHC が type family に課している Paterson 条件である。右辺に現れる各
associated type の適用 `G s1..sm` について、(1) `s1..sm` が associated type を含まない、
(2) `s1..sm` に現れる記号（型構築子と型変数）の総数が左辺の引数のそれより真に少ない、
(3) どの型変数も、左辺より多くは現れない、を要求する。上の 4 つはすべてこれを満たし、#171 の
2 つの再現例はどちらも (2) で落ちる（`Elem (Array a) = Elem (Array a)` は 2 対 2、
`El I64 = Array (El I64)` は 1 対 1）。

### #68 無限個の型を必要とするプログラム

```fix
func  : I64 -> a -> a = |level, a| ( if level <= 0 { a }; func2(level - 1, a) );
func2 : I64 -> a -> a = |level, a| func(level, Wrap { data: a }).@data;
```

`func` を `a` で使うと `func2` を `a` で使い、それが `func` を `Wrap a` で使う。必要な
インスタンスが型ごとに増え続ける。今日の挙動は core dump ではなく**無限ループ**（90 秒で
打ち切り、診断なし）。

機構は #193 とは別（レイアウトの展開ではなく、シンボルのインスタンス化）だが、**判定基準は
同じもの**が使える。「同じ鍵（#193 は型構築子、#68 はシンボル）が経路に再び現れ、しかも型が
真に大きい」なら終わらない。

## 付録 D: バリデーションが辿るもの、辿らないもの

歩きは、`ty_to_object_ty` が組み立てるオブジェクトの中身をそのまま辿る。struct のフィールド、
union のペイロード、配列ストレージが持つ要素は、その場に置かれるので降りる。boxed 型のフィールドは
ポインタなので、その先は**別のオブジェクトとして**、ポインタを挟まない経路を仕切り直して辿る。

関数の値は 2 つのポインタだが、**その関数が取る型と返す型**は、関数が生成される場所でレイアウトが
要る。そこで、これも別のオブジェクトとして辿る。これが無いと、プログラムがその型を名指す場所が
フィールドアクセサしか無い形（`let g = A::@n;`）を素通りする。逆に、関数の型どうしを大きさで
比べてはいけない。関数型はすべて 1 つの型構築子 `->` を共有するので、無関係な関数の型が
「同じ型構築子で真に大きい」に当たってしまう（hello world が拒否される）。

**辿る関係は、コード生成がレイアウトを要求する関係と一致していなければならない。** 型そのものの
フィールド（`TypeNode::field_types`）を辿る形では 3 箇所で食い違い、いずれもコンパイラがスタックを
使い切った。`Array Tree` の要素は `Array` のフィールドではなく `#ArrayStorage Tree` の側に現れる。
boxed フィールドの先はポインタの向こうにある。関数が取る型と返す型は、どのオブジェクトの中にも無い。

型引数は辿らない。`type Phantom a = unbox struct { x : I64 };` の `a` はオブジェクトに現れないので、
`Phantom Bad` を拒否するのは誤りである。オブジェクトに現れるものだけを辿る形には、その危険がない。

型ごとに 1 回しか歩かない（`checked`）。経路との比較は記憶より先に行うので、既に検査した型を
指す循環も見つかる。

## 付録 E: 判定の作り直し

最初に入れた判定は、経路上の祖先との**準同相埋め込み**で増大を見て、型ごとの記憶で循環を刈って
いた。バグハント wave 20 と Fable の査読が、その両方に反例を出した。

- 隣接リスト `type Node = box struct { edges : Array (I64, Node) };` を `Array Node` で使うと
  拒否された（回帰。ベースラインは通す）。
- `type A = unbox struct { xs : Array B, b : B, n : I64 };` の循環を取りこぼした（記憶が
  「降下中」と「降り終わった」を混ぜていた）。

代わりに試した「増大は宣言のグラフで決まる」案も、高階カインドのパラメータと phantom な引数位置で
両方向とも偽であることが示された。経緯と反例は `correctness.md` にある。
