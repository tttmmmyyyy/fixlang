# 循環した unbox 型でコンパイラがスタックを使い切る (#193)

## 1. 症状

次の 2 行を含むプログラムをビルドすると、コンパイラが自分のスタックを使い切って core dump する。

```fix
type A = unbox struct { b : B, n : I64 };
type B = unbox struct { a : A, m : I64 };
```

```
thread '<unknown>' has overflowed its stack
fatal runtime error: stack overflow, aborting
Aborted (core dumped)
```

`A` の値のレイアウトは「`B` の値 + `I64`」で、`B` の値のレイアウトは「`A` の値 + `I64`」なので、
どちらも有限のバイト数を持たない。コンパイラはこれを診断して拒否すべきところで、答えを求めて
無限に再帰する。

診断の文面自体はコンパイラの中にある。`ObjectType::to_struct_type`（LLVM の構造体型を組み立てる
関数）が、自分がいま何の型のレイアウトを求めている最中かを経路として持ち回り、同じ型が再び現れたら

```
Cannot determine the layout of type `A`. There are circular definitions by unboxed types.
Please change some types to boxed.
```

を出す。**この診断にはどのプログラムからも到達できない。** レイアウトを組み立てるより前に、
コンパイラの別の場所が同じ循環を無防備に辿ってスタックを使い切るからである。

その別の場所は `TypeNode::is_fully_unboxed`（「この型は boxed な部分を一切含まないか」を答える
述語）である。この述語は各フィールドの型に再帰し、boxed / クロージャ / 配列 / 関数ポインタの
いずれかに当たったところで止まる。unbox struct だけの循環はそのどれにも当たらないので、止まらない。
呼び出し元は参照カウント IR (`src/rc_ir/`) の各パスで、いずれもコード生成より前に走る。

## 2. 止まらない形は 2 つある

同じ「レイアウトの展開が終わらない」でも、形が 2 つある。両方を扱う必要がある。

**循環**: 展開の途中で**まったく同じ型**が再び現れる。上の `A` -> `B` -> `A` がこれ。

**増大**: 同じ型は二度と現れないが、型が段ごとに大きくなり続ける。

```fix
type P a = unbox struct { x : P (a, a), n : I64 };
```

`P I64` のレイアウトは `P (I64, I64)` を含み、それは `P ((I64,I64), (I64,I64))` を含む。
型は毎段 2 倍に育ち、二度と同じにならない。既存の診断は「まったく同じ型の再出現」だけを見るので、
仮に到達可能になっても**この形は捕まえられず、やはり止まらない**。

## 3. 判定基準

展開の経路（いま自分が内側にいる型を外側から順に並べたもの）に対して、次のどちらかが成り立った
ときに「レイアウトが定まらない」と判定する。

1. いま見ている型が、経路上の型と**完全に一致する**。
2. いま見ている型が、経路上の型と**同じ型構築子**を持ち、かつ**型として真に大きい**
   （型に現れる型構築子と型変数の個数で測る）。

**この基準は漏らさない。** 展開が終わらないなら、経路は無限に長い。型構築子は有限個しかないので、
ある型構築子 `C` が無限回現れる。それらがすべて相異なるなら（同じならすなわち条件 1）、
ある大きさ以下の型は有限個しかないので、大きさは限りなく増える。よって後の方に、前より真に大きい
`C` の型が必ずある。すなわち条件 2 に当たる。

**この基準は正しいプログラムを拒否しない。** 条件 1 は明らかに無限。条件 2 は、経路上で
`C t` から `C s`（`s` の方が大きい）に至ったなら、その間に辿ったフィールドの選び方は `C` の宣言
だけで決まるので、`C s` からも同じ選び方が使える。それは `C t -> C s` と同じ「引数の作り替え」を
`s` に適用した `C s'` に至り、`s'` は `s` より大きい。これが限りなく続く。

大きさの比較を省いて「同じ型構築子が経路に現れたら誤り」としてはいけない。`W (W (W I64))` の
展開は `W (W I64)`、`W I64` を経て `I64` で終わる有限のレイアウトで、これは今日コンパイルできる
正しいプログラムである。

## 4. 検査を置く場所

**バリデーションで拒否する。** 型検査とインスタンス化が終わった時点、コード生成が型のフィールドを
1 つも降りないうちに、`Program::validate_layouts` がインスタンス化された式の木を歩き、各ノードの型の
レイアウトが定まることを確かめる。当たったら、コンパイラの他のエラーと同じ `Errors` で、その値が
現れる式を指して報告する。

```
error: `Main::A` has no size: its unboxed fields reach `Main::A` itself (`Main::A` -> `Main::B` ->
`Main::A`). Make one of these types boxed.

7:6-7:7 in "main.fix",
  |
7 | f = |x| x.@n;
  |      ^
```

ノードの型を型ごとに 1 回だけ調べるので、大きなプログラムでも 1 ミリ秒に収まる（付録 B）。歩く順は
エントリポイントと export した値が先で、次にシンボルを名前順に見る。ライブラリの関数がユーザの型で
インスタンス化されているとき、報告をライブラリの中ではなくユーザのコードに出すためである。

**型のフィールドを降りる歩き 4 つも、それぞれ判定を持つ。** これはバリデーションが取りこぼした型に
対する網である。取りこぼしても止まらないだけで済み、無限再帰にも 52 GB の確保にもならない。

| 歩き | 何のために降りるか |
|---|---|
| `TypeNode::is_fully_unboxed` | boxed な部分を含むかを答える |
| `ObjectType::to_struct_type` | LLVM の構造体型を組み立てる |
| `rc_ir::leaf_map::boxed_leaf_paths` | 値の boxed leaf の位置を列挙する |
| `rc_ir::ownership::rc_units` / `param_ownership_shape` | 参照カウントの単位と、その所有・借用を決める |

判定の本体は `TypeNode::no_layout_message` の 1 つで、バリデーションはその結果を `Errors` にし、
歩きは `TypeNode::panic_if_no_layout` 経由で `panic_with_msg` にする。歩きの側の作法（降りる前に
判定し、降りているあいだだけ経路に載せ、戻ったら降ろす）は `TypeNode::descend_layout` が持つ。

網が 4 つとも要るのは、**どれか 1 つを直しても他が止まらない**からである。`is_fully_unboxed` は
フィールドを順に見て、最初に boxed のものが来たところで答えが false に決まり、そこで打ち切る。
`type T = unbox struct { p : Box I64, y : T, n : I64 };` のように boxed フィールドが先にあると、
循環しているフィールドは見られない。この形は、`rc_units` の再帰が経路を積み続けて
**30 秒で 52 GB を確保する**（診断も出ず、終わらない）。打ち切りをやめて全フィールドを歩かせる案は、
fannkuch のビルドが +3.0% になったので採らない（付録 B）。

**型宣言の検証時に置くことはできない。** レイアウトが定まるかどうかは、宣言だけでは決まらず、
型引数に何を渡したかで決まるからである。次の 2 つのプログラムは、型宣言が同一で、片方だけが正しい。

```fix
type [f : *->*] C f = unbox struct { x : f (C f), n : I64 };

type U  b = unbox struct { y : b, m : I64 };  // unbox
type Bx b =   box struct { y : b, m : I64 };  // box
```

`C U` は `U (C U)` を含み、それは `C U` を含む。無限である。`C Bx` は `Bx (C Bx)` を含み、
そこはポインタなので有限である。`C` の宣言も `U` の宣言も `Bx` の宣言も、それぞれ単独では
何も間違っていない。したがって、この誤りは**型が組み上がったところ**でしか判定できない。
インスタンス化より前に判定できないということは、`fix check` と言語サーバには届かないということでもある。

## 5. 網が発火したときにプロセスが死ぬ

4 節の網（コード生成の途中で panic して報告する経路）には、それだけでは足りない問題があった。
コード生成は翻訳単位ごとにスレッドを立てて並行に走り、そのうちの 1 つが報告して panic すると、
**5 回に 1 回ほどの割合でプロセスが SIGSEGV や SIGABRT で落ちる**。診断は表示されるが、その後に
クラッシュが続く。

原因は、スレッドを待ち合わせる側にある。`build_object_files` は、最初に panic したスレッドを
見つけた時点で自分も panic して抜けていた。残りのスレッドは LLVM のコード生成の途中で走ったまま
であり、プロセスはその下で終了処理に入る。アロケータがヒープを解放するのと、まだ走っている
スレッドが LLVM を実行しているのが同時に起きて落ちる（`mi_process_done` と
`SelectionDAGISel::runOnMachineFunction` が並んだスタックが取れている）。

直し方は、**全スレッドを待ってから** panic を運び直すこと。運び直しは `resume_unwind` で行う。
`panic_any` で新しい panic を起こすと、panic hook が 2 度目の報告を試み、join から受け取った
payload は文字列ではないので `(unknown error)` という行が診断の後ろに付く。

これはこの変更で作った欠陥ではなく、**コード生成スレッドの panic すべてに元からあったもの**
である（RC IR の各パスが持つ内部アサーションも同じ経路を通る）。今日まで表に出なかったのは、
そこに届くユーザ向けの診断が 1 つも無かったからである。

## 6. 診断が届かない形が 1 つ残っていた

`is_fully_unboxed` だけに判定を置いた最初の実装では、boxed フィールドが先にある循環

```fix
type T = unbox struct { p : Box I64, y : T, n : I64 };
```

が捕まらなかった。この述語は最初の boxed フィールドで答えが決まって打ち切るので、`y : T` を見ない。
そして参照カウントの歩き (`rc_units`) は、この述語が false を返したあと**自分でフィールドを降りる**。
その再帰が経路を積み続け、30 秒で 52 GB を確保して終わらない（診断も出ない）。この挙動は変更前の
コンパイラでも同じで、この変更が作ったものではない。

これが 4 節で歩き 4 つすべてに判定を置いている理由である。

## 7. このプログラムは今後どうなるか

今日コンパイルが通り、今後も通るもの:

- 型構築子が経路に再び現れるが展開が終わるもの（`W (W (W I64))`）。
- 循環が boxed / 配列 / クロージャを通るもの（`type T = box struct { x : T }`、
  既存のテスト `test_circular_type_definition`）。
- 循環した unbox 型を**宣言だけして使わない**プログラム。レイアウトを誰も要求しないので、
  検査も走らない。

今日 core dump し、今後はエラーになるもの: 循環・増大する unbox 型のレイアウトを要求するプログラム。

## 8. テスト

`src/tests/test_basic.rs` に 9 本。エラーを主張する 5 本は `test_source_fail` で、コンパイルが
`Errors` で失敗すること、すなわち報告がバリデーションから来ていることまで見る。

1. 2 型の循環 `A -> B -> A`（判定 1）。文面の**経路** `` `Main::A` -> `Main::B` -> `Main::A` `` まで見る。
2. 増大 `P a = unbox struct { x : P (a, a) }`（判定 2）。
3. 型引数によってのみ循環する `C U`（宣言では判定できない形）。
4. boxed フィールドが先にある循環 `T = unbox struct { p : Box I64, y : T, n : I64 }`
   （`is_fully_unboxed` では見えず、参照カウントの歩きが報告する形）。
5. union を通る循環 `Tree = unbox union { leaf : (), node : (Tree, Tree) }`。マニュアルが
   「`box` で書くべき例」として載せている宣言そのもの。
6. `C Bx` がコンパイルでき、実行できる。3 と宣言が同一なので、宣言だけを見て拒否する実装を弾く。
7. `W (W (W I64))` がコンパイルでき、実行できる。判定 2 の大きさの比較を省くと、これが落ちる
   （実際に比較を外して落ちることを確認済み）。
8. 5 の `box` 版がコンパイルでき、値を作って読める。
9. 循環した unbox 型を宣言するだけのプログラムがコンパイルできる（7 節の「今後も通るもの」）。

6 と 7 は、値を作れない型を扱うので、実行時の引数の個数で分岐を選び、その片方でだけ当該の型の
関数を呼ぶ形にしてある。定数条件だと最適化で分岐ごと消え、レイアウトが要求されなくなる。

`src/tests/test_build_exit_status.rs` に 1 本。`fix build` を別プロセスで走らせ、診断が標準エラーに
出ること、その後ろに何も続かないこと、そして**シグナルではなく終了ステータスで**終わることを見る。

5 節の直し（全スレッドを待ってから運び直す）を主張するテストは無い。バリデーションが先に拒否する
ので、網が発火するプログラムを書けないためである。

## 付録 B: コンパイル時間

判定は unbox フィールドを降りるたびに、経路上の型と型構築子を比べる。`perf stat -e instructions:u`
で、判定の呼び出しだけを外したビルドと比べた（`-O max`）。

| | 判定あり | 判定なし | 差 |
|---|---|---|---|
| hello world | 3.645 G | 3.650 G | -0.1% |
| nbody | 5.173 G | 5.168 G | +0.1% |
| binary_trees | 3.591 G | 3.590 G | +0.0% |
| fannkuch | 5.166 G | 5.161 G | +0.1% |
| 幅 8 を 5 段入れ子にした unbox struct | 8.01 G | 7.87 G | +1.8% |

実際のコードでは差が出ない（測定間のばらつきが 0.1% ほどある）。最後の 1 つは、issue #182 で
測った病的なプログラムで、葉が 32768 個ある。同じプログラムの `-O none` は 72.82 G 対 72.65 G
で +0.2%。

バリデーション自体は、この表に見えない大きさである。パスの中で時間を測ると、hello world で
0.58 ms、上の入れ子プログラムで 1.0 ms。型ごとに 1 回しか歩かないので、型の種類の数でしか伸びない。

**打ち切りをやめる案の値段。** `is_fully_unboxed` が最初の boxed フィールドで打ち切るのをやめれば、
歩き 1 つの修正で 4 つ全部が守られる（他の 3 つはこの述語を先に呼ぶ）。fannkuch のビルドを
3 回ずつ測ると、打ち切りありが 5.158 / 5.160 / 5.161 G、打ち切りなしが 5.310 / 5.313 / 5.316 G で、
**+3.0%**。fannkuch の状態は配列を持つ struct で、今日は最初の配列フィールドで打ち切れている。
この値段を毎回のビルドで払うより、歩き 4 つに判定を置く方を採った。

## 付録 C: 同じ族の issue が 2 つある

### #171 自己参照する associated type

外から見た症状が同じ（宣言の循環でスタックを使い切る）ため、同じ検査で両方落ちるかを最初に確かめた。
**落ちない。別の機構である。**

- #193 は**レイアウトの展開**（unbox フィールドを辿る）が終わらない。コード生成の前段で起きる。
- #171 は**型の簡約**（associated type を実装の右辺で置き換える）が終わらない。型検査で起きる。

さらに、**#171 の本文が挙げている修正案は採れない**ことが分かった。案は「実装が与える
associated type の値に associated type が含まれないことを要求する」だが、これは標準ライブラリを
拒否する。`src/fixstd/std.fix` のイテレータの実装がまさにその形である。

```fix
type Item (FilterIterator i a) = Item i;
type Item (ZipIterator i1 i2) = (Item i1, Item i2);
type Item (EnumerateIterator it) = (I64, Item it);
```

`examples/type_level_nums.fix` の型レベル加算も同じ形である。

```fix
impl [n : Nat] Succ n : Nat { type Add (Succ n) m = Succ (Add n m); }
```

代わりに使えるのが、GHC が type family に課している Paterson 条件である。右辺に現れる各
associated type の適用 `G s1..sm` について、(1) `s1..sm` が associated type を含まない、
(2) `s1..sm` に現れる記号（型構築子と型変数）の総数が左辺の引数のそれより真に少ない、
(3) どの型変数も、左辺より多くは現れない、を要求する。上の 4 つはすべてこれを満たし、#171 の
2 つの再現例はどちらも (2) で落ちる（`Elem (Array a) = Elem (Array a)` は 2 対 2、
`El I64 = Array (El I64)` は 1 対 1）。

### #68 無限個の型を必要とするプログラム

```fix
func  : I64 -> a -> a = |level, a| ( if level <= 0 { a }; func2(level - 1, a) );
func2 : I64 -> a -> a = |level, a| func(level, Wrap { data: a }).@data;
```

`func` を `a` で使うと `func2` を `a` で使い、それが `func` を `Wrap a` で使う。必要な
インスタンスが型ごとに増え続ける。今日の挙動は core dump ではなく**無限ループ**（90 秒で
打ち切り、診断なし）。

機構は #193 とは別（レイアウトの展開ではなく、シンボルのインスタンス化）だが、**判定基準は
同じもの**が使える。「同じ鍵（#193 は型構築子、#68 はシンボル）が経路に再び現れ、しかも型が
真に大きい」なら終わらない。

## 付録 D: バリデーションが辿るもの、辿らないもの

バリデーションの歩きは、**コード生成がレイアウトをその場に埋め込む関係**をそのまま辿る。struct と
union のフィールドを降り、boxed / クロージャ / 配列 / 関数ポインタのフィールドではポインタが大きさを
抑えるので止まる。止まった先の型は、それ自身がノードの型として現れたときに、改めて根から調べる。

型引数は辿らない。`type Phantom a = unbox struct { x : I64 };` の `a` はレイアウトに現れないので、
`Phantom Bad` を辿って拒否するのは誤りである。配列の要素型も、`Array a` の値は `{ポインタ, 長さ,
容量}` なので辿らない（要素のレイアウトが要るのは `#ArrayStorage a` の側で、そちらは別の根として
現れる）。この 2 つを辿ると、今日コンパイルできるプログラムを拒否する。
