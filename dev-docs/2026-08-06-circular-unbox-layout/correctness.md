# 大きさの定まらない型の検査 — 正しさ

`design.md` が述べた判定には、正しいプログラムを拒否する誤りと、止まらないプログラムを見逃す
誤りが 1 つずつある。どちらも実測で再現した (付録 A)。この文書は、何を証明すべきかを定め、
そのために判定をどう組み直すかを述べ、組み直した判定について証明を与える。

## 0. なぜ証明が要るか

この検査は 2 方向に失敗しうる。

- **見逃す**と、コード生成が答えを求めて無限に再帰する。今日の症状はスタックの使い切りか、
  メモリの食い潰しである。診断は出ない。コード生成の側の検査は取り払ってあるので、網はこれ 1 枚
  しかない。
- **過剰に拒否する**と、書けるはずのプログラムが書けなくなる。しかも拒否の理由は型の宣言では
  なく展開の途中経過なので、ユーザには理由が見えない。

どちらも「たいてい正しく動く」では済まない種類の失敗である。

## 1. モデル

### 1.1 宣言と型

型構築子 `C` は、パラメータの列 `ā = a₁..a_k` と、フィールドの型の列 `σ₁..σ_n` を宣言する。
`C` は `box` か `unbox` のいずれかである。型 `τ` は、型構築子に引数を全て与えたもの
(`TypeNode`、`free_vars` が空) とする。バリデーションが走る時点で、プログラムに現れる型は
すべてこの形である。

型 `τ = C t̄` の**フィールドの型**は、宣言のフィールドの型に引数を代入したものである
(`TypeNode::field_types`)。

```
fields(C t̄) = [ σ₁[ā := t̄], …, σ_n[ā := t̄] ]
```

組み込みの型構築子もこの形に収まる。`Array a` のフィールドは `[a]` (要素の型)、
`#ArrayStorage a` も `[a]` である。

### 1.2 展開関係 R

コード生成は型ごとに 1 つの LLVM 型を組み立て、答えを型で記憶する
(`Generator::struct_type_of` / `embedded_type_of`)。ある型の LLVM 型を組み立てるために別の型の
LLVM 型が要る、という関係が `ObjectType::field_types`、すなわち `ty_to_object_ty` の出力である。
そこから読み取れる関係を `R` と書く。`τ R υ` を「`τ` のレイアウトを決めるには `υ` のレイアウトが
要る」と読む。

`ty_to_object_ty` の場合分けをそのまま写すと、`R` の辺は次で尽きる。

| `τ` の形 | `τ R υ` となる `υ` | その場か、ポインタ越しか |
|---|---|---|
| struct `C t̄` | `fields(C t̄)` の各要素 | その場 |
| union `C t̄` | `fields(C t̄)` の各要素 (ペイロード) | その場 |
| `Array t` | `#ArrayStorage t` | ポインタ越し |
| `#ArrayStorage t` | `t` (要素) | その場 |
| クロージャ `s -> t` | `#DynamicObject` | ポインタ越し |
| 関数ポインタ | なし | — |
| primitive | なし | — |
| `#DynamicObject` | (捕獲した値の型。歩きは捕獲を渡さないので辺なし) | その場 |

`box` の型構築子が作る値はポインタなので、その中身は**別のオブジェクト**である。したがって
`R` の辺は 2 種類に分かれる。

- **その場の辺** (`τ →ᵢ υ`): `υ` の値が `τ` の値の中に埋め込まれる。`υ` が `unbox` の場合。
- **ポインタ越しの辺** (`τ →ₚ υ`): `υ` の値は別のオブジェクトで、`τ` はそこへのポインタを持つ。
  `υ` が `box` の場合、および `Array t → #ArrayStorage t`、クロージャ → `#DynamicObject`。

**根**は、プログラムの式に付いた型と、実体化されたシンボルの型、および関数型が取る型・返す型
である (`Program::validate_layouts` と `no_size_reason` の入口)。

### 1.3 何を判定したいのか

**補題 0.** コード生成が型 `τ` のレイアウトを求めて停止する ⟺ 次の 2 つがともに成り立つ。

1. `τ` から**その場の辺だけ**を辿って `τ` 自身に戻る道が無い (どの `υ ∈ R*(τ)` についても同様)。
2. `R*(τ)` が有限である。

*証明の筋。* (⇐) `R*(τ)` が有限なら、記憶があるので型ごとの組み立ては高々 `|R*(τ)|` 回しか
起きない。その場の循環が無ければ、1 つの型の LLVM struct を組み立てる再帰も停止する。
(⇒) その場の循環があれば、その型の値のバイト数が自分自身より真に大きいという要求になり、
`to_struct_type` の再帰は停止しない。`R*(τ)` が無限なら、記憶があっても新しい型が尽きない。∎

条件 1 は**インスタンスで決まる** (`C U` は無限、`C Bx` は有限。宣言は同一)。
条件 2 は**宣言で決まる** (次節)。この 2 つを別の層で判定するのが、この文書の主張である。

### 1.4 根が足りない (実測された穴)

上の「根」は、検査が走る時点、すなわち**最適化の前**のプログラムから取ったものである。しかし
コード生成がレイアウトを求める型は、最適化が作り替えた後のプログラムから来る。実測すると、
`examples/*.fix` だけで**154 個の型が、検査を一度も通らずにコード生成でレイアウトされている**。

- `#CapList<…>` (`capture_struct` が最適化中に作る捕獲リストの型)
- `#FixCap<>` (`defunctionalize_fix` が作る型)
- `Quantity#PunchedAt1` (フィールドを抜いた型)
- `unwrap_newtype` が `IO a` を `IOState -> (IOState, a)` に開いた後に現れる組

したがって、`ObjectType::to_struct_type` に書いた

> such a type is rejected before code generation begins

は、これらの型については成り立っていない。証明を完成させるには次のどちらかが要る。

- **補題 R (未証明)**: 最適化の各パスは、大きさを持つ型だけから大きさを持つ型を作る。
  すなわち検査を通った型集合から出発する限り、後で作られる型も大きさを持つ。
- あるいは、検査を最適化の後にも走らせる (コンパイル時間の実測が要る)。

大きさを失う型を作る最適化パスの例は構成できなかったが、**それは証明ではない**。

### 1.5 未解決: associated type

`fields` は宣言のフィールド型に代入するだけで、associated type の簡約は行わない。
フィールド型が associated type の適用を含むとき、代入後に簡約されない `AssocTy` が `R` の辺に
現れうるか。現れるなら `R` は型レベルの計算を含み、以下の議論は成り立たなくなる。実体化の時点で
すべての associated type が簡約済みであることを確かめる必要がある (未確認)。

## 2. いまの判定と、その誤り

いまの `no_size_cause` は、歩きが持つ 2 本の経路に対して次を見る。

1. 現在の型が、**その場の経路**上の祖先と一致する (循環)。
2. 現在の型が、**ポインタ越しを含む経路**上の祖先と同じ型構築子を持ち、各引数がその祖先の
   対応する引数を**準同相埋め込み**として含む (増大)。

### 2.1 条件 2 は正しいプログラムを拒否する

反例 (実測、付録 A の R1):

```fix
type Node = box struct { edges : Array (I64, Node) };   // 隣接リスト
```

`Array Node` を使うと拒否される。経路は
`Array Node → #ArrayStorage Node → Node → Array (I64, Node)` で、祖先 `Array Node` と現在の
`Array (I64, Node)` は頭が同じ `Array`、引数 `Node` は `(I64, Node)` に埋め込まれている。

`design.md` の健全性の論証はこうだった。

> 経路上で `C t̄` から `C s̄` に至ったなら、その間に辿ったフィールドの選び方は `C` の宣言だけで
> 決まるので、`C s̄` からも同じ選び方が使える。それは同じ引数の作り替えを `s̄` に適用した
> `C s̄'` に至り、各 `sᵢ` は `s'ᵢ` に埋め込まれている。

**この文には書かれていない前提がある**: 降下の各ステップが、祖先の引数を運んでいること。
`Node → Array (I64, Node)` は `Node` の宣言そのもので、`Node` は引数を持たない。ここから先の型は
`Node` だけで決まる定数であり、`Array (I64, Node)` から同じ選び方を再適用しても
`(I64, Node) → Node → Array (I64, Node)` と同じ型に戻る。育たない。

`Node ⊑ (I64, Node)` という埋め込みは、`Node` が自分のフィールドの型の中に字面として現れることの
帰結であって、成長の証拠ではなかった。

さらに、条件 2 は**歩く順に依存する**。同じ宣言でも `Node` を先に歩くプログラムは通る
(`checked` に入るため)。無関係な 1 行で受理と拒否が入れ替わる。

### 2.2 記憶が循環を隠す

反例 (実測、付録 A の R2):

```fix
type A = unbox struct { xs : Array B, b : B, n : I64 };
type B = unbox struct { a : A, m : I64 };
```

診断なしでメモリを食い潰す。フィールドの順を `b : B, xs : Array B` にすると正しく報告される。

`no_size_reason` の `checked` は、型を 1 度歩いたら 2 度目を飛ばす。その根拠として

> 型に大きさがあるかはその型の性質なので、既に歩いた型は飛ばしてよい

と書いたが、**これは証明していない主張であり、偽である**。条件 1 は `in_place` に対する判定で、
`in_place` はポインタ越しの辺でリセットされる。したがって「`A` に大きさがあるか」の答えは、
`A` にどの経路で入ったかに依存する形で計算されている。上の例では `Array B` を先に見た結果
`A` が `in_place = [B]` の文脈で再訪され、記憶に切られて `A → B → A` が誰にも見えない。

### 2.3 2 つの誤りは同じ形をしている

条件 2 は**宣言で決まる性質**をインスタンスの上で判定している。条件 1 は**インスタンスで決まる
性質**を型ごとの記憶で刈っている。どちらも層を取り違えている。

## 3. 組み直した判定

### 3.1 増大は宣言のグラフで決める

**パラメータ流れグラフ** `G` を次で定める。節点は対 `(C, i)` (型構築子 `C` の第 `i` パラメータ)。
`C` のフィールド型 `σ` の中に `D` の適用 `D u₁..u_m` が現れ、`u_j` が `aᵢ` を含むとき、
`(C, i) → (D, j)` の辺を引く。この辺に印を付ける。

- **等辺**: `u_j = aᵢ` (パラメータがそのまま渡る)。
- **拡大辺**: `u_j ≠ aᵢ` かつ `u_j` が `aᵢ` を真部分項として含む (`(aᵢ, aᵢ)` や `F aᵢ` など)。

**定義.** 宣言の集合が**非正則**であるとは、`G` に拡大辺を含む閉路があることをいう。

例: `P a = unbox struct { x : P (a,a), n : I64 }` は `(P,1) → (P,1)` が拡大辺なので非正則。
`Node = box struct { edges : Array (I64, Node) }` はパラメータを持たないので `G` に節点が無く、
正則。`W a = unbox struct { x : a }` は `(W,1)` から出る辺が無く (フィールドがパラメータそのもの
で、型構築子の適用ではない)、正則。

**定理 A (増大の厳密な判定).** 型 `τ` に対し `R*(τ)` が無限である ⟺ `τ` から到達する宣言の
中に、拡大辺を含む閉路があり、かつ `τ` の展開がその閉路を通る。

証明は 5 節で与える。要点は、正則な宣言だけを通る展開は、現れる引数が元の引数の部分項に限られる
ので、型の集合が「到達する型構築子 × 元の引数の部分項の組」で抑えられ有限になること。逆向きは、
拡大辺を含む閉路を回るたびに引数が真に大きくなるので、型が二度と一致しないこと。

この判定は**埋め込みを使わない**。誤検知が原理的に出ない (定理 A が同値だから)。
2.1 の反例は、`Node` にパラメータが無いので `G` に閉路が作れず、通る。

### 3.2 その場の循環はインスタンスのグラフで決める

**定義.** 型 `τ` が**その場で自分に戻る**とは、`τ →ᵢ⁺ τ` (その場の辺だけで 1 歩以上) が
成り立つことをいう。

増大が無いと分かっていれば `R*(τ)` は有限なので、`R*(τ)` を節点、その場の辺を辺とする有限グラフ
の上で、白/灰/黒の深さ優先探索により厳密に決まる。**灰 (降下中) と黒 (降り終わった) を区別する
のが要点で、いまの `checked` はこれを混ぜている。**

この判定はインスタンスに依る。`C U` は `C U →ᵢ U (C U) →ᵢ C U` で自分に戻り、`C Bx` は
`C Bx →ₚ Bx (C Bx)` でポインタを挟むので戻らない。

### 3.3 走る順番

1. 根の型から `R` を辿る。辿りながら、通った宣言に拡大辺を含む閉路が無いかを見る (定理 A)。
   当たったら報告して終わり。**この段が、次の段の有限性を保証する。**
2. 有限と分かった `R*(根)` の上で、その場の辺だけの DFS で循環を探す。当たったら報告する。

段 1 が「使っていない非正則な型は拒否しない」を満たす: 展開がその閉路を通らなければ報告しない。

## 4. 証明すべきこと

以下を証明する。定理 A と補題 0 は上に述べた。

- **定理 1 (停止性).** 検査そのものが停止する。段 1 は宣言の有限グラフ上の閉路検出なので停止する。
  段 2 は段 1 が保証する有限グラフ上の DFS なので停止する。段 1 と段 2 を交互に行う実装では、
  「拡大辺の閉路を通った瞬間に打ち切る」ことが停止性の根拠になる。
- **定理 2 (完全性).** `R*(τ)` が無限、またはその場の循環があるなら、検査は必ず報告する。
  前者は定理 A の (⇒)、後者は有限グラフ上の DFS の完全性による。
- **定理 3 (健全性).** `R*(τ)` が有限で、その場の循環が無いなら、検査は報告しない。
  前者は定理 A の (⇐)、後者は DFS の健全性による。
- **補題 (記憶).** 段 2 の DFS が型ごとに 1 度しか降りないことは、灰と黒を区別する限り循環の
  検出を落とさない (標準的な議論)。段 1 の記憶は宣言の上なのでインスタンスに依存しない。

**いまの実装との差**: 定理 3 が今日は成り立たない (2.1)。補題が今日は成り立たない (2.2)。

## 5. 定理 A の証明

準備。型 `τ` の**部分項**を通常どおり定める。`Sub(τ)` を `τ` の部分項の集合とする (有限)。

**(⇐) 正則なら有限.** `τ` の展開が拡大辺を含む閉路を通らないとする。展開の各ステップは
`C t̄ → σ[ā := t̄]` である。`σ` に現れる型構築子の適用 `D u₁..u_m` について、代入後の引数
`u_j[ā := t̄]` は次のいずれかである。

- `u_j` が `aᵢ` なら `tᵢ` — `t̄` の要素。
- `u_j` が `aᵢ` を含まないなら、`σ` に書かれた閉じた型 — 宣言だけで決まる有限個のうちの 1 つ。
- `u_j` が `aᵢ` を真部分項として含むなら、それは拡大辺であり、仮定よりその辺は閉路上に無い。

拡大辺が閉路上に無いということは、展開のどの経路も拡大辺を高々 (グラフの節点数) 回しか通れない。
したがって、現れる引数はすべて「元の引数の部分項」か「宣言に現れる閉じた型」に、有限回の拡大を
施したものに限られる。型構築子は有限個、引数の候補は有限個なので、`R*(τ)` は有限である。

**(⇒) 非正則な閉路を通るなら無限.** 展開が拡大辺 `(C,i) → (D,j)` を含む閉路を通るとする。
閉路を 1 周する間に、第 `i` パラメータの引数 `t` は `u_j[…]` に置き換わり、`u_j` は `aᵢ` を真部分項
として含むので、置き換わった引数は `t` を真部分項として含む。すなわち項として真に大きい。
閉路を回るたびに真に大きくなるので、2 度と同じ型にならない。無限。∎

**注意**: (⇐) の議論は「拡大辺が閉路上に無い」ことしか使っていない。閉路の外にある拡大辺は
有限回しか通れないので害がない。これが 2.1 の反例を通す根拠である。

## 6. いまのテストがどの主張を固定しているか

`design.md` 8 節の 21 本のうち、拒否側の 13 本は「報告が出ること」だけを見ている。組み直した後は、
主張を分けて固定する必要がある。

- 定理 2 (完全性) の証拠: 循環 5 本、増大 3 本。
- 定理 3 (健全性) の証拠: 受理側 8 本 + **付録 A の反例 2 本**。とくに R1 は、宣言のグラフで
  判定していることを discriminate する (埋め込み監視に戻すと落ちる)。
- 補題 (記憶) の証拠: R2 は、灰と黒を区別していることを discriminate する。

## 付録 A: 実測した反例

いずれも `fix build -O none` / `-O max` で確認。ベースラインは `92e567b6` (この変更の分岐点)。

**R1 — 正しいプログラムの拒否 (回帰)**

```fix
module Main;
type Node = box struct { edges : Array (I64, Node) };
first_weight : Array Node -> I64;
first_weight = |nodes| nodes.@(0).@edges.@(0).@0;
make_nodes : () -> Array Node;
make_nodes = |_| (
    let leaf = Node { edges : [] };
    [Node { edges : [(7, leaf)] }]
);
main : IO ();
main = println(first_weight(make_nodes(())).to_string);
```

`ffc2a779`: ``error: `Std::Array Main::Node` has no size: its fields reach ever larger types``。
`92e567b6`: ビルドでき、`7` を出力。

`Array` 固有ではない。`type Node = box struct { next : Option (I64, Node) };` を `Option Node`
経由で使っても同じ。

同じ宣言でも `Node` を先に歩くプログラムは通る (順序依存):

```fix
main = (
    let leaf = Node { edges : [] };
    let ns = [Node { edges : [(7, leaf)] }];
    println(ns.@(0).@edges.@(0).@0.to_string)
);   // コンパイルでき、7 を出力
```

**R2 — 循環の見逃し**

```fix
module Main;
type A = unbox struct { xs : Array B, b : B, n : I64 };
type B = unbox struct { a : A, m : I64 };
depth : A -> I64;
depth = |x| x.@n;
main : IO ();
main = println(depth(undefined("no value")).to_string);
```

`ffc2a779`: 診断なしで `memory allocation of 328264 bytes failed` + core dump
(仮想メモリ 6 GB 制限下)。フィールドの順を `b : B, xs : Array B` にすると正しく報告される。
`92e567b6` も同じプログラムで死ぬので、これは回帰ではなく、新しい網の穴である。

## 付録 B: 退けた案

**閾値 (証人 2 つ).** 条件 2 を「経路上に埋め込みの対が 2 つ揃ってから撃つ」に変える probe を
当てると、R1 は通り、増大は拒否されたまま、大きさ関連のテスト 22 本も通った。しかし**壊れた
補題をそのままに閾値を動かしただけ**で、証人が 3 つ必要な正しいプログラムがあれば同じことが
起きる。証明にならないので採らない。

**予算 (到達型数の上限).** 「到達した型が N 個を超えたら報告する」は健全 (有限なら N まで通る)
かつ完全 (無限なら必ず止まる) だが、N が恣意的で、診断が「どの宣言が悪いか」を言えない。
定理 A が使えるなら要らない。

**単相化の文献にならって埋め込み監視を使う.** 単相化器が埋め込みや深さ制限を使うのは、型レベルの
計算 (関数、associated type) を含む一般の設定では有限性が決定できないためである。この検査が見て
いるのは**データ型の宣言だけ**なので、その一般性は要らない。ただし 1.3 の未解決点
(associated type が展開に現れうるか) の答えが「現れる」なら、この判断は見直しが要る。
