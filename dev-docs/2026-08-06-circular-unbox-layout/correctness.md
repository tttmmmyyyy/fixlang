# 大きさの定まらない型の検査 — 正しさ

## 0. 何を保証し、何を保証しないか

検査が受理するプログラムの集合は、次で**きっかり**定まる。

> 根から到達する型がすべて、(a) その場のフィールドだけを辿って自分自身に戻らず、
> (b) 項としての深さが `D`（`MAX_TYPE_DEPTH` = 500）以下である。

- **(a) は厳密**である。その場の循環を持つプログラムは必ず拒否され、持たないプログラムが
  循環を理由に拒否されることはない（定理 2）。
- **(b) は上限**である。レイアウトが終わらないプログラムは必ず拒否される（定理 3）が、
  **深さ `D` を超える型を必要とする有限のプログラムも拒否される**（定理 4）。これが唯一の
  「正しいのに拒否される」形であり、上限をどこに置くかがその大きさを決める。
- 検査自身は必ず停止する（定理 1）。

上限が「型 1 つの項の深さ」であることが、その犠牲を実用上ゼロに保つ。**単純な型をプロジェクトに
いくつ足しても、この量は増えない**（4 節）。

保証の外にあるものは 5 節にまとめた。

## 1. モデル

### 1.1 宣言と型

型構築子 `C` は、パラメータの列 `ā` とフィールドの型の列 `σ₁..σ_n` を宣言する。`C` は `box` か
`unbox` である。型 `τ` は型構築子に引数を全て与えたもので、型変数を含まない（`TypeNode`、
`is_ground`）。バリデーションが走る時点でプログラムに現れる型はすべてこの形である。

```
fields(C t̄) = [ σ₁[ā := t̄], …, σ_n[ā := t̄] ]        (TypeNode::field_types)
```

**項としての深さ** `depth(τ)` を、名前は 1、適用と associated type は「部分の最大 + 1」で定める
（`TypeNode::depth`）。

### 1.2 展開関係

コード生成は型ごとに 1 つの LLVM 型を組み立て、答えを型で記憶する。ある型のレイアウトを決めるのに
別の型のレイアウトが要る、という関係が `ty_to_object_ty` の出力である。`held(τ)` を、その出力の
`SubObject` / `UnionBuf` / `ArrayStorageBuf` が持つ型の列とする（`type_size::held_types`）。

```
held(struct C t̄)      = fields(C t̄)
held(union C t̄)       = fields(C t̄)              （ペイロード）
held(Array t)         = [#ArrayStorage t]
held(#ArrayStorage t) = [t]
held(closure)         = [#DynamicObject]
held(funptr) = held(primitive) = []
```

2 種類に分ける。

- **その場の辺** `τ →ᵢ υ`: `υ ∈ held(τ)` かつ `υ` が unbox。`υ` の値は `τ` の値の中に埋め込まれる。
- **ポインタ越しの辺** `τ →ₚ υ`: `υ ∈ held(τ)` かつ `υ` が box。

`R = →ᵢ ∪ →ₚ`。**根**は、式に付いた型、実体化されたシンボルの型、および関数型が取る型・返す型
（`Program::validate_layouts` と `no_size_reason` の入口）。`Needed` を根からの `R` の反射推移閉包と
する。

### 1.3 判定したいこと

**補題 0.** コード生成が停止する ⟺ (a) どの `τ ∈ Needed` も `τ →ᵢ⁺ τ` を持たない、かつ
(b) `Needed` が有限。

*論証.* (⇐) コード生成は型ごとに 1 回だけ組み立て、答えを記憶する。`Needed` が有限なら組み立ての
回数は有限。その場の循環が無ければ、1 つの型の struct を組み立てる再帰も止まる。
(⇒) その場の循環があれば、その型の大きさが自分自身より真に大きいという要求になり止まらない。
`Needed` が無限なら、記憶があっても新しい型が尽きない。∎

## 2. 検査

`src/type_size.rs`。2 つの記憶と 2 つの歩きからなる。

```
reached : Set<Type>     到達した型。到着時に記録する。
settled : Set<Type>     その場の降下が報告なしで終わった型。降り終わってから記録する。

reach(root, τ):
    if τ ∈ reached:                       return None
    reached ← reached ∪ {τ}
    if depth(τ) > D:                      return 深さの報告(root)
    if size_of(root, τ, [], ∅) = Some(m): return Some(m)
    for υ ∈ held(τ): if reach(root, υ) = Some(m): return Some(m)
    return None

size_of(root, τ, path, on_path):
    if τ ∈ on_path:  return 循環の報告(τ, path)
    if τ ∈ settled:  return None
    if depth(τ) > D: return 深さの報告(root)
    push τ を path と on_path に
    r ← 最初に報告を返す size_of(root, υ, …)    for υ ∈ held(τ) のうち υ が unbox
    pop
    if r = None: settled ← settled ∪ {τ}
    return r
```

`no_size_reason` は根ごとにこれを呼び、`reached` と `settled` は根をまたいで持ち回る。

## 3. 定理

`T_D` を「プログラムの型構築子の上で、深さ `D` 以下の ground な型」の集合とする。

**補題 1（`T_D` は有限）.** 型構築子は宣言から来るので有限個である。深さ `D` 以下の項は、有限個の
葉と 2 引数の適用（`TyApp`）と有限アリティの associated type からなる高さ `D` 以下の木であり、その
個数は記号数と `D` の関数で抑えられる。∎

### 定理 1（停止性）

検査は必ず停止する。

*証明.* `reach` は入口で `reached` に入れ、既にあれば即座に返すので、**相異なる型ごとに高々 1 回**
本体を実行する。本体で降下を続ける型は、深さ `D` を超えていれば直ちに報告して返るので `T_D` に
属する。補題 1 より `T_D` は有限。したがって `reach` の呼び出し回数は有限である。

`size_of` は、`on_path`・`settled`・深さのいずれかで即座に返るか、`τ` を `on_path` に入れて降りる。
1 回の呼び出しの中である型が `on_path` に入るのは高々 1 回である（既に入っていれば即座に返る）。
したがって降下の深さは `|T_D|` で抑えられ、降下する型も `T_D` に属する。呼び出しは `reach` から
相異なる型ごとに 1 回なので、全体も有限。∎

### 定理 2（その場の循環は厳密）

`size_of` が「自分自身を含む」と報告する ⟺ ある `τ ∈ Needed`（深さ `D` 以下）が `τ →ᵢ⁺ τ` を持つ。

*健全性（⇒）.* 報告は `τ ∈ on_path` のときだけ出る。`on_path` はいま降下中の各段で押した型の集合で
あり、段から段へは `→ᵢ` の辺で進む（`held` のうち unbox のものだけを降りる）。したがって `on_path`
に `τ` があるとは `τ →ᵢ⁺ τ` があるということである。∎

*完全性（⇐）.* `C = τ0 →ᵢ τ1 →ᵢ … →ᵢ τk = τ0` を循環とし、`τ0 ∈ Needed` とする。

まず**`C` のどの型も `settled` に入らない**。`settled` に入るのは降下が報告なしで完了した型だけで
ある。`τi ∈ C` の降下が完了したとすると、その降下は `τi →ᵢ … →ᵢ τi` を辿るので、最後の段で
`τi ∈ on_path` に当たって報告を返し、完了しない。矛盾。

次に `reach` は、報告を返すまで `Needed` の型を漏れなく訪れる（`held` の全要素に再帰する）。途中で
報告を返したならその時点で主張は成り立つ。返さないなら `τ0` に到達し、`size_of(root, τ0, [], ∅)` を
呼ぶ。`τ0 ∉ settled` であり深さも `D` 以下なので降下が始まる。降下は `held` の unbox な要素すべてに
再帰するので `τ1` に進む。`τ1 ∉ settled`、`τ1 ∉ on_path`（`on_path = {τ0}`）なので更に進む。以下
同様に `τk = τ0` に至り、`τ0 ∈ on_path` なので報告する。∎

### 定理 3（レイアウトが終わらないなら必ず報告する）

`Needed` が無限、または `Needed` に `→ᵢ` の循環があるなら、検査は報告を返す。

*証明.* 循環の場合は定理 2 の完全性による。`Needed` が無限の場合、補題 1 より `T_D` は有限なので、
深さが `D` を超える型 `υ ∈ Needed` が存在する。検査が何も報告しなかったと仮定すると、`reach` は
`Needed` の全要素を訪れる。`υ` を訪れた時点で深さの判定に当たり報告する。矛盾。∎

補題 0 と合わせて、**コード生成が停止しないプログラムは必ず拒否される**。

### 定理 4（受理する集合）

検査が何も報告しない ⟺ `Needed` のどの型も深さ `D` 以下であり、`→ᵢ` の循環が無い。

*証明.* (⇐) `reach` と `size_of` が見る型はすべて `Needed` の要素である（`reach` は根と `held` の
推移閉包しか見ず、`size_of` は `held` の unbox な要素しか降りない）。よって深さの判定は当たらない。
循環の報告も定理 2 の健全性より出ない。
(⇒) 対偶。深さが `D` を超える型があれば定理 3 の議論で報告し、循環があれば定理 2 で報告する。∎

**この定理が保証の全体である。** 「レイアウトが有限に決まる」ことと「受理される」ことは一致
**しない**。深さ `D` を超える型を必要とする有限のプログラムは拒否される。それが唯一のずれである。

### 補題 2（2 つの記憶）

- **`settled` は出口で記録する。** 「`τ` の大きさが定まるか」は `τ` の `→ᵢ` 到達集合だけで決まる
  性質なので、一度答えたら再利用してよい。**入口で記録してはいけない**: 降下中の型を「答え済み」と
  扱うと、その型に戻る循環が見えなくなる（実際に起きた欠陥。付録 B）。定理 2 の完全性の証明は、
  この違いにだけ依存している。
- **`reached` は入口で記録する。** ここで答える問いは「`τ` の深さ」と「`τ` の大きさが定まるか」で、
  どちらも `τ` だけの性質である。2 度目の到来は `Needed` に何も足さないので切ってよい。

## 4. 上限を「型 1 つの項の深さ」に置く理由

原則: **単純な型をプロジェクトに足しただけでコンパイルできなくなってはいけない。** 複雑な型を
足して落ちるのは許容できるが、単純なソースファイルは、時間が伸びるだけで通るべきである。

この原則が、上限を置ける量を選ぶ。

| 量 | 単純な型を足すと | 原則 |
|---|---|---|
| `Needed` の個数 | 増える | 破る |
| 降下の長さ | 増える（`A`→`B`→`C` と繋げるだけで） | 破る |
| **型 1 つの項の深さ** | **増えない**（`A` も `B` も項としては深さ 1） | 保つ |

そして深さの上限は、補題 1 を通じて停止性そのものを与える（定理 1）。したがって上限はこれ 1 つで
よく、個数の予算も降下の深さの上限も要らない。

実測: コーパス（speedtest 46 件）と examples で到達する型の最大の深さは **10**、手で 25 段ネスト
したタプルを書いた型で **27**。`D = 500`。

### 上限を実用的な値に取るための前提

型は共有 DAG である（`substitute_type` は束縛変数に置換先の `Arc` をそのまま返す）。ところが
`Hash`・`PartialEq`・`free_vars` は共有を辿らず木として展開していたので、深さ k の型で 2^k かかった。
`TypeNode` にハッシュ・groundness・深さのキャッシュを持たせ、等価性に `Arc::ptr_eq` の近道を入れ、
`ty_to_object_ty` の `assert!(ty.free_vars().is_empty())` を `is_ground` に置き換えてある。これが
無いと `D` は 20 程度しか取れない（付録 A）。

## 5. 保証の外にあるもの

1. **最適化が作る型。** 検査は最適化の**前**に走る。`capture_struct` の `#CapList<…>`、
   `defunctionalize_fix` の `#FixCap<>`、punched 型、`unwrap_newtype` が `IO a` から作る組は、検査を
   通らずにコード生成へ届く（`examples` だけで 154 個）。それらが大きさを持つことは**証明して
   いない**。最小の直しは、検査を最適化の後にもう一度走らせること（1 回 0.6〜1 ms）。
2. **`R` がコード生成の要求と一致すること。** `held` は `ty_to_object_ty` の出力を写したものだが、
   一致は構成によるものであって証明ではない。両者がずれた実績が 3 回ある（付録 B）。
3. **`D` を超える有限のプログラム。** 定理 4 のとおり拒否される。
4. **associated type** は `Program::validate_type_defns` が struct / union のフィールド型と型
   エイリアスの右辺で既に拒否しているので `σ` に現れない。根が assoc-free であることを実体化の
   不変条件として表明で固定するのが望ましい（未実施）。

## 付録 A: 実測

倍々型 `type P a = unbox struct { x : P (a,a), n : I64 };` に、判定を外して深さだけで止める probe を
当てたときの費用。**RSS はどの場合も平ら**（型は共有 DAG なので深さに線形）で、死ぬのは時間の側。

| 深さ上限 | キャッシュ前 | キャッシュ後 |
|---|---|---|
| 20 | 0.37 s | — |
| 25 | 4.39 s | — |
| 30 | 115.9 s | — |
| 1000 | 測れない | 0.25 s |

最終形の全ケース（`-O none`、負荷 25 の下、いずれも 2 秒以内）:

| プログラム | 期待 | 結果 |
|---|---|---|
| 隣接リスト `Array Node` + `Array (I64, Node)` | 受理 | 受理 |
| `Option Node` + `Option (I64, Node)` | 受理 | 受理 |
| `Phantom a = unbox struct { x : I64 }` + `C a = unbox struct { x : Phantom (C (a,a)) }` | 受理 | 受理 |
| 25 段ネストのタプル | 受理 | 受理 |
| `A/B` 相互循環 | 拒否 | 拒否 |
| `A = unbox struct { xs : Array B, b : B }` の循環 | 拒否 | 拒否 |
| unbox の増大 `P a` | 拒否 | 拒否 |
| 高階カインドの増大 `B f b` + `A a` | 拒否 | 拒否 |
| box 越しの増大 `Q a` | 拒否 | 拒否 |

スイート 1241 件が `-O none` で通る。hello world のコンパイルは +0.4%（負荷の下での測定）。

## 付録 B: 潰れた案と、その反例

**案 1: 経路上の祖先との準同相埋め込みで増大を見る（最初に入れた版）。**
隣接リスト `type Node = box struct { edges : Array (I64, Node) };` を `Array Node` で使うと拒否する
（回帰。ベースラインは通して `7` を出力）。健全性の論証に「降下の各ステップが祖先の引数を運んで
いる」という書かなかった前提があり、引数を持たない型（`Node`）を通ると破れる。歩く順にも依存した。
同じ版は記憶を入口で記録していたため、`type A = unbox struct { xs : Array B, b : B, n : I64 };` の
循環を取りこぼした（診断なしでメモリを食い潰す。フィールド順を入れ替えると報告する）。

**案 2: 宣言のグラフ（パラメータ流れの拡大閉路）で増大を決める。** Kennedy と Pierce の
expansive recursion と同じ装置で、.NET がジェネリクスに課しているもの。査読が両方向とも反証した。

```fix
type [f : *->*] B f b = unbox struct { x : f b, n : I64 };
type A a = unbox struct { x : B A (a, a), n : I64 };          // グラフに辺が引けないのに無限
type Phantom a = unbox struct { x : I64 };
type C a = unbox struct { x : Phantom (C (a, a)), n : I64 };  // 拡大閉路があるのに有限
```

前者はパラメータが頭の適用（`f b`）が代入で初めて構築子の適用になるため、宣言のグラフに写らない。
後者は落とされる引数位置が偽の辺を作る。保守側に倒すと今度は `C Bx` を拒否する。**この案が
成り立たないのは Fix が高階カインドの型パラメータを持つためで、文献の決定可能な断片はそれを
含まない。**

**歩きが辿る関係がコード生成と食い違った 3 回**: `Array Tree` の要素は `Array` のフィールドでは
なく `#ArrayStorage Tree` の側に現れる。boxed フィールドの先はポインタの向こうにある。関数が取る型と
返す型はどのオブジェクトの中にも無い。いずれもコンパイラがスタックを使い切った。
