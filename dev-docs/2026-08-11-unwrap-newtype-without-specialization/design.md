# `unwrap_newtype` を代入の後に置き、`remove_hktvs` を消す

## 1. 直す対象

次の Fix プログラムは、`-O none` と `-O basic` ではコンパイルできて正しい答えを出すが、
`-O max` と `-O experimental` では終わらず、メモリを無制限に消費する (issue #245)。

```fix
module Main;

type [f : *->*] H f = unbox struct { d : f I64 };
type Ph a = unbox struct { z : I64 };
type Y a = unbox struct { p : Ph (Y (Array a)), h : H Array };

main : IO ();
main = (
    let y : Y I64 = Y { p : Ph { z : 0 }, h : H { d : [1] } };
    println(y.@p.@z.to_string)
);
```

RSS は毎秒約 15 MB 増え続け、上限が無い。既存の欠陥であり、`7a0ecb76` からビルドした
コンパイラでも同じである。

このプログラムの**値のレイアウトは有限**である。`Y I64` の中身は `Ph` (`I64` 1 つ) と
`H Array` だけで、そこから先へは広がらない。`Ph a` は引数 `a` を捨てるからである。
一方で**名前の上に現れる型の族は無限**で、`Y I64` のフィールド型 `Ph (Y (Array I64))` は
`Y (Array I64)` を名指し、その先は `Y (Array (Array I64))` を名指す。大きさを持たない型を
拒否する検査 (#193) が辿るのはレイアウトの関係なので、このプログラムを受理するのは正しい。

直った後に残ってはならない性質が 1 つある。**最適化レベルによって結果が変わらないこと**である。
いまの状態そのもの (低いレベルで動き、高いレベルで終わらない) が直すべき対象なので、
直し方がその性質を壊してはならない。

## 2. 関係する 2 つのパス

`-O max` でだけ走るパスが 2 つ関わる。どちらも最適化の初期、型検査とインスタンス化が
終わった後に走る。

### 2.1 newtype の畳み込み (`unwrap_newtype`)

**newtype** とは、フィールドがちょうど 1 つの unbox 構造体である。標準ライブラリの `IO` が
その形をしている。

```fix
type IO a = unbox struct { runner : IOState -> (IOState, a) };
```

このパスは、newtype の値をその 1 フィールドの値で置き換える。プログラム中の `IO ()` という型は
`IOState -> (IOState, ())` になり、`IO { runner : f }` という構造体リテラルは `f` そのものになり、
`x.@runner` という読み出しは `x` そのものになる。

**このパスの価値は、`IO`・State モナド・イテレータを関数にすることにある。** 型が関数
(クロージャ) になって初めて、その後に走るインライン展開とクロージャ特殊化がそれらを掴める。
値の表現が変わらない改名ではなく、**式に付く型がクロージャになる**ことが目的である。

置き換えは instance ごとに行われ、フィールド型はその instance で読まれる。
`type Foo a = unbox struct { data : () -> a };` に対して `Foo Bool` は `() -> Bool` になる。

このパスが要求することが 1 つある。**畳む型構築子が、飽和しない出現を持たないこと**である。
いまの実装は畳んだ型構築子の宣言を型環境から取り除くので、飽和しない出現が残ると、
宣言されていない型構築子を名指すことになって壊れる。飽和しない出現が現れうるのは、
高階の型変数の引数位置だけである。

```fix
type [f : *->*] Foo f = box struct { data : f () };
```

`Foo IO` という型の中で、`IO` は引数を伴わずに現れる。`Foo` は box なので畳まれず、
裸の `IO` はそこに残る。しかし `IO ()` や `IO I64` は畳まれて `IO` は消える。

### 2.2 高階型変数の除去 (`remove_hktvs`)

このパスは、2.1 の要求を先回りして満たすためだけに存在する。高階の型変数を持つ宣言を、
**型引数の組ごとの 0 パラメータの型構築子**に作り直す。`Foo IO` に対して `#RHKTV<Foo IO>` を
作り、そのフィールド型を `f ()` に `f := IO` を代入した `IO ()` として登録し、元の `Foo` を
型環境から取り除く。作り直しの対象は 2 つの規則で決まる。

1. 高階の型変数を持つ struct または union の宣言。
2. 取り除く型構築子を名指す struct または union の宣言 (推移的、最小不動点)。

作り直した後は、すべての型構築子がパラメータを持たないか kind が `*` のパラメータしか
持たないので、飽和しない出現は現れない。

## 3. 止まらない機構

`remove_hktvs` の中心は `run_on_type` で、型を 1 つ受け取り、作り直した型を返す。
1 節のプログラムに対して、状態を追う。

まず対象の集合が決まる。`H` は規則 1 で対象になる (`f : *->*` を持つ)。`Y` は規則 2 で
対象になる (フィールド型 `H Array` が `H` を名指す)。`Ph` はどちらでもない。

`main` の中の `y : Y I64` に対して `run_on_type(Y I64)` が呼ばれる。

1. `Y` は対象なので、`#RHKTV<Y I64>` を作り、型環境に登録する。
2. そのフィールド型を `Y` の宣言から読み、`a := I64` を代入する。
   `[Ph (Y (Array I64)), H Array]` が得られる。
3. 各フィールド型に `run_on_type` を再帰する。
   `run_on_type(Ph (Y (Array I64)))` — `Ph` は対象ではない。**この場合は型引数へ再帰する。**
4. `run_on_type(Y (Array I64))` — `Y` は対象なので `#RHKTV<Y (Array I64)>` を作る。
5. そのフィールド型は `[Ph (Y (Array (Array I64))), H Array]`。3 へ戻る。

型引数は段ごとに 1 つ大きくなり、同じ型に戻らない。よってこの再帰は止まらず、段ごとに
新しい型構築子が型環境に積まれるので、メモリも増え続ける。

止まらない原因は 2 つの合わせ技である。**フィールド型へ降りること**と、**型引数へ降りること**である。
`Ph` は引数を捨てるので、レイアウトを求める walk なら `Y (Array I64)` に触れない。
このパスは名前の上に現れる型をすべて実体化するので、触れてしまう。

対して `unwrap_newtype` の畳み込み `unwrap_type` は止まる。畳む対象の newtype のフィールド型に
しか降りず、しかも「フィールド型に自分の名前が出る newtype は畳まない」(`is_acyclic_newtype`) が
効いているので、降りる関係が非巡回だからである。型引数へも降りるが、それは受け取った型の
構文的な深さで抑えられている。

**実測でも、止まらないのは `remove_hktvs` の歩きだけである** (付録 A)。病的なプログラム 5 本を
`remove_hktvs` を止めた構成で `-O max` でコンパイルすると、すべて通って正しく走る。

## 4. 方針

### 4.1 代入が特殊化そのものである

`remove_hktvs` がしていることは、**代入の結果を新しい型構築子として前もって実体化すること**である。
`#RHKTV<Foo IO>` のフィールド型 `IO ()` は、`Foo` の宣言のフィールド型 `f ()` に `f := IO` を
代入したものにほかならない。

その代入は、型環境に問い合わせれば必ず行われる。`field_types(Foo IO)` は `Foo` の宣言を読み、
`f := IO` を代入して `IO ()` を返す。**畳み込みをこの代入の後に置けば、前もっての実体化は要らない。**

したがって:

- 畳んだ型構築子の**宣言を型環境に残す**。飽和しない `IO` が名指す先が在り続ける。
- **フィールド型を答える出口で畳み込みを通す**。`field_types(Foo IO)` は `IO ()` ではなく
  `IOState -> (IOState, ())` を返す。これは今日 `#RHKTV<Foo IO>` が答えるものと同じである。
- **式の型を畳む部分は今日のまま**。各式の型に畳み込みを当てる走査が、2.1 の価値を作っている。

`x : Foo IO` は今日 `#RHKTV<Foo IO>` という名前になり、改修後は `Foo IO` のままになる。
レイアウトも、フィールドが裸のクロージャであることも同じである。`Foo` が unbox 1 フィールドなら、
`x` 自身がクロージャ型まで畳まれる。これも今日と同じである。

### 4.2 型環境が畳み込みを持つ

畳む型構築子の集合を型環境が持ち、フィールド型を答える 2 つの入口がその集合を通る。
2 つの入口 (`field_types` / `unpunched_field_types`) はすでに 1 つの漏斗を共有しているので、
置く場所はそこ 1 か所である。

以下の例はすべて、次の 2 つの宣言のもとでのものである。`IO` は unbox 1 フィールドなので畳まれ、
`Foo` は box なので残る。`Foo` の唯一のフィールドの名前は `data` である。

```fix
type IO a = unbox struct { runner : IOState -> (IOState, a) };
type [f : *->*] Foo f = box struct { data : f () };
```

```rust
pub struct TypeEnv {
    /// 型構築子ごとの宣言。private。この環境に入る宣言はすべて畳まれた形になる (4.3)。
    tycons: Arc<Map<TyCon, TyConInfo>>,
    pub aliases: Arc<Map<TyCon, TyAliasInfo>>,
    /// 1 フィールドの値そのものになった newtype。この環境が答えるフィールド型には、
    /// ここに載った型構築子が飽和して現れることはない。
    unwrapped_newtypes: Arc<Set<TyCon>>,
}

impl TypeEnv {
    /// `newtypes` の各 newtype の値が、その 1 フィールドの値になったことを記録し、
    /// 保存されている全宣言のフィールド型を畳む。`unwrap_newtype` パスが `{IO}` を渡して呼ぶ。
    pub fn unwrap_newtypes(&mut self, newtypes: Set<TyCon>);

    /// `new_tycons` の宣言を、フィールド型を畳んでから加える。パスの後に宣言を作るパスの受け口。
    pub fn add_tycons(&mut self, new_tycons: Map<TyCon, TyConInfo>);

    /// `tycon` の値がその 1 フィールドの値になっているなら、その宣言。`IO` に対して `Some`、
    /// `Foo` に対して `None` を返す。
    pub fn unwrapped_newtype_info(&self, tycon: &TyCon) -> Option<&TyConInfo>;
}

impl TypeNode {
    /// `self` の中で飽和して現れる各 unwrapped newtype を、その instance における 1 フィールドの
    /// 型で置き換えた型。
    ///
    ///     IO ()             -> IOState -> (IOState, ())   飽和しているので畳む
    ///     Array (IO ())     -> Array (IOState -> (IOState, ()))   型引数の中も畳む
    ///     Foo IO            -> Foo IO   `IO` は引数を伴わないので畳めない
    ///     IO#PunchedAt0 ()  -> ()   唯一のフィールドが穴なら、その値は何も持たない
    pub fn unwrap_newtypes(self: &Arc<TypeNode>, type_env: &TypeEnv) -> Arc<TypeNode>;

    /// `tycon_info` の各フィールドが宣言されている型に、`self` の型引数を代入したもの。
    ///
    ///     Foo IO  -> [IO ()]
    ///     IO ()   -> [IOState -> (IOState, ())]
    fn declared_field_types(&self, tycon_info: &TyConInfo) -> Vec<Arc<TypeNode>>;

    /// `tycon_info` の各フィールドを、この instance で値が持つ型。代入で飽和した newtype は
    /// 畳まれているので、返る型はコード生成がそのままレイアウトできるものである。
    ///
    ///     Foo IO  -> [IOState -> (IOState, ())]
    ///     IO ()   -> [IOState -> (IOState, ())]
    fn instance_field_types(&self, tycon_info: &TyConInfo, type_env: &TypeEnv) -> Vec<Arc<TypeNode>>;
}
```

畳み込みそのものをするのは `unwrap_newtypes` で、フィールドを答える 2 つの違いは `Foo IO` の行
だけに出る。`Foo` の宣言のフィールド型 `f ()` に `f := IO` を代入すると `IO ()` になり、
そこで初めて `IO` が飽和する。畳み込みが代入の後に要るのはこの 1 か所である。

層は 2 段になる。下が代入だけを行う `declared_field_types` で、`unwrap_newtypes` はこれを使う。
上が代入に畳み込みを重ねた `instance_field_types` で、公開されている入口はこれを使う。
畳み込みが自分の中で下の層だけを見るので、2 つの関数が互いを呼び合うことはない。

擬似コードで書くと次のようになる。

```
unwrap_newtypes(T, env):
    tc := T の先頭の型構築子
    if tc が飽和していて env.unwrapped_newtype_info(tc) が宣言を返す:
        if tc の唯一のフィールドが穴:      return ()
        f := declared_field_types(T, tc の宣言)[0]
        return unwrap_newtypes(f, env)     # 畳んだ先も畳む
    T の型適用の各部分に再帰する

instance_field_types(T, tycon_info, env):
    field_types := declared_field_types(T, tycon_info)
    if tycon_info が高階のパラメータを持たない: return field_types    # 4.3
    field_types の各型に unwrap_newtypes を当てて返す
```

`unwrap_newtype` パスは、畳む集合を計算して型環境に載せ、式の型と構造体操作を今日どおり
書き換えるだけになる。**型環境の宣言そのものには手を触れない。**

### 4.3 代入の後に畳み込みが要るのはどこか

漏斗を通るたびに型を歩き直すのは、コード生成が `field_types` を呼ぶ回数を考えると無駄が大きい。
歩き直しが本当に要る場合は限られており、それは静的に判る。

型 `T` (kind `*`、型変数を含まない) が **畳み済み** であるとは、`T` のどの部分項にも、
畳む対象の型構築子が飽和して現れないことをいう。

**補題.** 宣言 `D v1 .. vn` のフィールド型を `τ` (自由変数は `v1 .. vn` のみ)、`T = D a1 .. an` の
各引数 `ai` を畳み済みとし、`σ = [vi := ai]` とする。`τ` が畳み済みで、かつ `v1 .. vn` の kind が
すべて `*` ならば、`σ(τ)` は畳み済みである。

*証明.* `σ(τ)` に現れる「先頭が型構築子である部分項」は次の 3 通りに尽きる。
(a) ある `ai` の内部にそっくり収まるもの。`ai` は畳み済みなので、飽和した対象は無い。
(b) `τ` の部分項 `u` (先頭が型構築子) に `σ` を施したもの。`vi` の kind が `*` なので `vi` は
何かに適用されることがなく、`u` の適用の骨組みは `σ` で変わらない。よって先頭の型構築子も
引数の個数も `τ` のときと同じであり、`τ` が畳み済みだから飽和した対象は無い。
(c) `τ` の部分項 `vi τ1 .. τk` (k >= 1) に `σ` を施したもの。`vi` の kind が `*` ならこの形は
存在しない。(証明終)

補題が言うのは、**新しい飽和を作れるのは高階のパラメータへの代入だけ**ということである。
これは `remove_hktvs` が発火する条件そのものでもある。

この補題を使うには、宣言に書かれたフィールド型 `τ` の側が畳み済みでなければならない。
`τ` には `IO a` のように対象が飽和して直に書かれていることがあるからである。これは今日の
実装がすでに行っていることで (畳み込み後の型環境は、残す宣言のフィールド型を畳んだ形で持つ)、
`f := a` のような自由変数を引数に取る代入でも問題なく行える。改修後も同じく、パスの最後に
**すべての宣言のフィールド型を畳んでおく**。畳む対象の宣言も残すので、その宣言のフィールド型も
同じく畳んでおく。

以上から漏斗の規則は次になる。

- 宣言のパラメータの kind がすべて `*` — 代入の結果をそのまま返す。
- 高階のパラメータを持つ — 代入の結果に `unwrap_newtypes` を当てて返す。

標準ライブラリには高階のパラメータを持つ struct/union の宣言が 1 つも無い (検査済み)。
したがって高階の宣言を自分で書かないプログラムでは、漏斗の追加コストは
`tyvars` を 1 回なめる分だけになる。

この近道が買うものは測ってある。近道を外して**常に畳む**版 (付録 B.3) と比べると、型環境の大きな
プログラム (minilib の monad) で **2.8% のコンパイル時間**である (付録 A.5)。

近道は「保存された宣言のフィールド型が畳み済みである」ことに寄りかかる。これは宣言が型環境に入る
口をすべて畳ませることで、構成から従わせる。

| 宣言が入る口 | 畳み済みである理由 |
|---|---|
| `TypeEnv::new` | パスより前。畳む集合が空なので畳み込みは恒等 |
| `TypeEnv::unwrap_newtypes` | 全宣言のフィールド型を畳む |
| `TypeEnv::add_tycons` | 受け取った宣言のフィールド型を畳む |
| `program.rs` の中の書き換え | `tycons` は private なので、外から宣言を入れる道が無い |

`add_tycons` は、パスの後に宣言を作るパス (`defunctionalize_fix`、`closure_specialization`) の
受け口である。それらが渡す capture struct のフィールド型は式の型から来るので今日はすでに畳み済み
だが (付録 A.5 で実測)、それは**出所の性質**であって、口の側の保証ではない。宣言の側から型を組む
将来のパスは畳み込まれていない型を持ち込むので、口の側で畳む。

### 4.4 停止性

`unwrap_newtypes` の再帰は 2 方向ある。

- **型適用の中への再帰。** 受け取った型の構文的な深さで抑えられる。
- **畳んだ先への再帰。** 畳む対象は「フィールド型に自分の名前が出ない newtype」に限られており
  (`is_acyclic_newtype`)、この判定は改修で変えない。よって「newtype をそのフィールド型で
  置き換える」関係は非巡回で、有限回で底に着く。

底に着いたフィールド型は、`declared_field_types` すなわち**代入だけ**で得たものである。
型引数へ降りて新しい型を作ることはしない。3 節で見た止まらない再帰は、ここに無い。

### 4.5 型の共有を壊さないこと

型は木ではなく**有向非巡回グラフ**である。宣言が 2 度名指す引数を代入すると、2 つの出現は同じ節点に
なる。`P (a, a)` を木として歩くと、展開した木の大きさ、すなわち段ごとに倍になる量を歩くことになる。
`TypeNode` がハッシュ・接地性・深さを節点に持っているのは、どれもこの理由による。

畳み込みも同じ規律に従う必要がある。漏斗は代入した型に対して呼ばれ、代入した型は共有を持つからである。

- **歩いた節点の答えを覚える。** 木ではなくグラフを歩く。
- **子が両方とも変わらなければ、元の節点をそのまま返す。** `Substitution::substitute_type` が
  同じことをしている。
- 覚える表は**型で引く**。`TypeNode` はハッシュを節点に持ち、`Arc` の等価はポインタ一致で短絡する
  ので、この鍵は安い。プロジェクトが型の表に使っている鍵もこれである。

型で引く表は、**構造の等しい別の節点を 1 つに束ねる**。2 つ目の出現は 1 つ目に与えた答えを受け取る
ので、答えの節点は入力の節点と同一とは限らない。値は同じであり、型はどこでも構造で比較されるので
差は出ない。出てくるグラフの共有はむしろ増える。

節点のアドレスで引く表も考えられるが、それには「表に入れた節点を手放さない」という規律が要る。
畳み込みは途中で型を作るので、持たずに捨てた節点はそのアドレスを後から作られる節点に譲り、その節点が
別の型の答えを受け取る。この規律を守らないと何が起きるかは実測してある (付録 A.4)。

### 4.6 詰め直しの処理が要らないこと

畳んだ型構築子の宣言が型環境に残るなら、`Foo IO` に入れるときに runner を `IO` に詰め、
出すときに取り出す処理を式に挿入しなければならないのではないか。要らない。理由は 2 つあり、
どちらも `IO` に限った話ではない。

1. **畳むかどうかは型構築子ごとに決まる。** 出現ごとではない。型構築子 `N` が畳む集合に
   入っていれば、`N` の構築・読み出し・書き込み・punch・plug-in は、プログラムのどこに
   現れても畳まれる。「`Foo N` の中に入る値だから畳まない」は起きない。
2. **残る `N` に値は住まない。** 宣言から決まる `N` の kind を `k1 -> .. -> kn -> *` とすると、
   `N a1 .. aj` の kind が `*` になるのは `j = n` のとき、すなわち飽和しているときに限る。
   値が住むのは kind `*` の型だけなので、値の型に現れる `N` は必ず飽和しており、
   飽和した出現はすべて畳まれる。詰める相手も取り出す相手も存在しない。

`Foo N` の中に残る `N` は kind が `*` でないので、それ自身は値の型ではない。値になるのは
フィールドの型 `N τ` のほうで、それは漏斗が畳む。

したがって挿入が要るのは、畳むかどうかを**出現ごと**に決める設計を採った場合だけである。
その設計は採らない。

この性質は今日の実装がすでに持っており、実測でも畳んだ newtype の構造体の姿は 1 つも
残らない (付録 A.3)。改修はこの性質を変えない。

### 4.7 抜けたときに黙らないための表明

今日は、畳んだ型構築子の宣言を型環境から取り除くこと自体が安全網になっている。畳み損ねた型が
残れば、宣言の引き当てに失敗して即座に落ちる。宣言を残す改修はこの網を失う。畳み損ねた
unbox 1 フィールド構造体は、たまたまフィールドと同じレイアウトを持つので、黙ってコード生成まで
進んでしまう。

代わりの網を、Fix の型から object のレイアウトを作る唯一の入口 `ty_to_object_ty` に置く。

```rust
assert!(
    !type_env.is_unwrapped_newtype(&tc),
    "A value of `{}` is laid out, though it has become a value of its one field.",
    ty.to_string()
);
```

集合の引き当て 1 回なので、develop mode に限らず常に走らせる。この表明が見るのは先頭の
型構築子だけだが、それで足りる。畳み損ねた部分項は、それ自体がレイアウトされる番になった
ときに捕まる。レイアウトされることが無い部分項 (`Ph` が捨てる引数など) は、畳み損ねても
コード生成に影響しない。

バリデーションを足さないので、「最適化レベルで挙動が変わらない」ことの保証は**いまの実装に

その道は測って退けた (付録 B)。

# 付録 A: 実測

## A.1 病的なプログラム 5 本 x 3 構成

いずれも `-O max`。表の数字はプログラムが出した答えで、いずれも期待どおりである。

| プログラム | 増大の経路 | 今日 | 両パス停止 | `remove_hktvs` のみ停止 |
|---|---|---|---|---|
| `Y a = { p : Ph (Y (Array a)), h : H Array }` | phantom な引数 | 止まらない | `0` | `0` |
| `Y a = { step : Y (Array a) -> I64, ... }` | 関数型フィールド | 止まらない | `3` | `3` |
| `Grow f = { g : Ph (Grow (Wrap (f I64))), n }` | 高階の引数位置 | 止まらない | `7` | `7` |
| `A a = { y : B A (a,a) }` + `B f b = { x : Ph (f b) }` | 高階パラメータ経由 | 止まらない | `2` | `2` |
| `C g = { y : Ph (C (Wrap g)), n }` | 高階引数だけで増大 | 止まらない | `9` | `9` |

対照として、高階の型変数をどこにも使わない増大する型族
(`C a = { p : Phantom (C (a,a)), n }`) は今日も通る。`remove_hktvs` の対象になる宣言が
1 つも無いためである。

## A.2 スイート

- `remove_hktvs` だけ止める: 1344/1348。失敗 4 件は
  `test_unwrap_newtype_partial_application` / `test_unwrap_newtype_cont` /
  `test_regression_issue_64_boxed` / `test_regression_issue_64_more_complex_boxed`。
  いずれも `unwrap_newtype` が飽和しない出現に当たって落ちるものである。
- 両方止める: 1341/1348。失敗 7 件はすべて `test_provenance` の RC IR ダンプ比較で、
  `IO` が畳まれないことによる。

**`remove_hktvs` を必要としているのは `unwrap_newtype` だけである。**

## A.3 畳んだ newtype の構造体の姿は残らない

4.6 の主張を、今日のコンパイラで測ったもの。6 つの型を使うプログラムを `-O max --emit-symbols`
でビルドし、`unwrap_newtype` の直後の出力を読んだ。

| 宣言 | 形 | `@field` の型と本体 |
|---|---|---|
| `M a = unbox struct { r : I64 -> (I64, a) }` | kind `*->*` の newtype | `(I64 -> (I64, I64)) -> I64 -> (I64, I64)`, `\|x\| x` |
| `Name = unbox struct { data : Array U8 }` | kind `*` の newtype | `Array U8 -> Array U8`, `\|x\| x` |
| `NN a = unbox struct { inner : M a }` | newtype の newtype | `(I64 -> (I64, I64)) -> ...`, `\|x\| x` |
| `[f : *->*] W f = unbox struct { x : f I64 }` | 高階パラメータを持つ newtype | `(I64 -> (I64, I64)) -> ...`, `\|x\| x` |
| `[f : *->*] Foo f = box struct { data : f I64 }` | 残る箱。`M` を飽和せずに持つ | `#RHKTV<Foo M> -> I64 -> (I64, I64)` |
| `Holder = box struct { m : M I64, k : I64 }` | 残る箱。宣言が `M I64` を直に名指す | `Holder -> I64 -> (I64, I64)` |

- 畳んだ 4 つの型の構造体リテラルは 1 個ずつあったものが 0 個になる。
- 残る 2 つの箱のフィールドの型は、どちらも畳んだ後の関数型である。`Foo M` は代入で飽和した
  場合、`Holder` は宣言に直に書かれていた場合で、経路が違っても同じ答えになる。
- `mod_r` (穴を開けて差し戻す操作) を通しても、穴の開いた型は残らない。
- 畳んだ型構築子の名前が出力に残るのは、シンボル名の名前空間 (`Main::M::@r#...`) と、
  `let` パターンに書かれた利用者の型注釈だけである。後者は 2 つのパスがどちらも意図して
  書き換えない (`Pattern::Var` の注釈)。この注釈は `Symbol::hash` が
  `Expr::stringify` 経由で印字するので、最適化の後にオブジェクトキャッシュの鍵へ入る。
  鍵に余分な情報が入るだけで、区別を失う方向には働かない。

## A.4 共有を壊すと何が起きるか

4.5 の 3 つの規律は、どれも破ったときに何が起きるかを見てある。

**歩いた節点を覚えず、木として歩いた場合。** 大きさを持たない型を拒否するテスト
(`type [f : *->*] B f b = unbox struct { x : f b, n : I64 };` と
`type A a = unbox struct { x : B A (a, a), n : I64 };`) が、0.2 秒 / RSS 124 MB から
**RSS 50 GB で終わらない**に変わった。`A a` は段ごとに `(a, a)` を作るので、グラフとしては段の数
だけ、木としては 2 の段数乗の大きさになる。`-O none` でも起きる。畳む型が 1 つも無くても、
歩くこと自体が代償だからである。

**覚える表を節点のアドレスで引き、節点を持たなかった場合。** 高階の宣言を持つテスト 2 件
(`test_regression_issue_64_more_complex` と `test_unwrap_newtype_cont`) が、型の食い違いで落ちた。
落ち方が原因を名指していた。

```
Std::Option (Std::I64 -> Std::I64 Std::I64)               I64 に I64 を適用した型
... IOState -> (IOState, IOState -> (IOState, Result ...))  IO が 2 回はがれた型
```

畳み込みは newtype のフィールド型を instance で代入した型をその場で作る。その型は答えを返した
直後に解放されるので、番地が空く。後から作られた別の節点がその番地を取ると、表がその節点に
**別の型の答え**を返す。落ちたのが高階の宣言を持つ 2 件だけだったのは、漏斗が畳み込みを呼ぶ
経路がそこにしか無く、一時的な型もそこでしか作られないからである。

## A.5 近道の値段と、その前提が成り立っている理由

**近道 (4.3) を外すといくら払うか。** 漏斗が常に畳む版 (付録 B.3) をビルドし、同じワークツリーから
同じ引数で測った。直列、CPU 時間 (user + sys)。

| | 近道あり (4.3) | 常に畳む (B.3) | 差 |
|---|---|---|---|
| speedtest コーパス 43 件 x 3 往復 | 59.75 / 60.54 / 61.05 秒 | 60.30 / 60.53 / 61.37 秒 | +0.5% (往復の順位が入れ替わる) |
| minilib の monad x 2 往復 | 66.98 / 67.38 秒 | 68.80 / 69.29 秒 | **+2.8%** |

コーパスは高階の宣言を持たないので、近道が**最も得をする条件**である。そこで差が出ないことは、
近道の節約が小さいことを言う。型環境が大きく宣言の多い minilib では 2 往復とも同方向に出た。
両者が同じ機械語を出すことは、コーパス 8 件の `--emit-llvm` と `--emit-rc-ir` のバイト一致で
確かめてある。

**近道の前提が今日は成り立っている理由。** `add_tycons` に渡される宣言のフィールド型が畳み込みで
変化したら止まる表明を置き、スイート全件を流した。**1 度も鳴らない** (1379 + 139 passed)。
`defunctionalize_fix` と `closure_specialization` が渡す capture struct のフィールド型は
`state.scope` と式の型から来るので、パスが畳んだ後の型だからである。したがって `add_tycons` の
畳み込みは今日のふるまいを変えず、口の側の保証としてだけ働く。

## A.6 畳んだ型は共有を持つので、型を文字列で比べる所が指数になる

畳み込みは共有を持つ型を作る (4.5)。`unwrap(F X) = I64 -> (X, X)` のような newtype を k 段
重ねると、畳んだ型は節点数 O(k) のグラフだが、木として展開すると 2^k である。値のレイアウトは
O(k) のままなので、プログラムそのものは小さい。

型の等価判定を `TypeNode::to_string` の文字列比較で行っている箇所がある
(`expr_let_typed`、`expr_match_typed`、`closure_specialization` の 4 か所)。`to_string` は
節点ごとのメモを持たない木の走査なので、この 2^k を毎回払う。

| k | `-O none` | `-O max` (この改修) | `-O max` (改修前) |
|---|---|---|---|
| 14 | 1.77 秒 / 112 MB | 4.90 秒 / 117 MB | 3.16 秒 / 834 MB |
| 16 | 1.40 秒 / 117 MB | 8.32 秒 / 126 MB | 11.78 秒 / 3.05 GB |
| 18 | 1.09 秒 / 115 MB | 27.86 秒 / 180 MB | 47.87 秒 / 11.9 GB |
| 20 | 1.24 秒 / 119 MB | 59.38 秒 / 359 MB | 160.95 秒 / **47.0 GB** |

改修前の畳み込みは節点をすべて作り直していたので、木を実体化していた。共有を保つようにした
改修は、k=20 で**メモリを 130 分の 1**にし、2.7 倍速くする。残る指数は時間だけで、その出所は
畳み込みではなく文字列比較である。`expr_let_typed` の表明 1 つを外すと k=20 が 59.4 秒から
38.0 秒になる。

根本は「型の等価判定を文字列で行っていること」で、この改修の範囲外である。`TypeNode` は節点ごとに
ハッシュを持ち、それはグラフ走査 1 回で求まる。

# 付録 B: 退けた案

## B.1 最適化の前に走る検査で増大する型族を落とす

宣言を展開する関係の上で型の深さに上限 (500) を置き、超えたらコンパイルエラーにする案。
判定が最適化より前にあるので、レベル非依存が構成から従う。作りきってあり、ブランチ
`reject-growing-types` (コミット `42eac869`、push していない) に一式が残っている。
その設計文書 `dev-docs/2026-08-11-growing-type-arguments/design.md` に、判定の健全性・完全性の
論証と、スイート・minilib・コーパス 100 プロジェクトの実測がある。

退けた理由は、**言語が受け付けるプログラムの集合を狭めるのに、狭める理由がコンパイラの
実装の都合しか無くなったから**である。`remove_hktvs` を消せば増大する型族はそのまま
コンパイルできる。

同文書に残しておく価値のあるものが 2 つある。

- **expansive recursion (Kennedy と Pierce の判定、.NET がジェネリクスに課しているもの) が
  Fix では成り立たない論証。** 高階パラメータの適用に辺が引けないこと、保守側に倒すと
  minilib の 11 宣言 (`StateT` `WriterT` `ResultT` `OptionT` `Free` `Cofree` `StoreT`
  `TracedT` `PairLT` `PairRT` `JmpBuf`) が落ちること。#245 の本文はこの判定を採る前提で
  書かれているので、閉じるときに訂正が要る。
- 病的なプログラム 5 本と対照 3 本のテスト。改修版では**これらが通ることを主張する**テストに
  書き直す。

## B.2 `remove_hktvs` を需要駆動にする

`#RHKTV<...>` を作るのをやめず、レイアウトが実際に要求した型に限って作る案。1 節の
プログラムでは `Ph` が引数を捨てるので `Y (Array I64)` がレイアウトを要求されず、止まる。

退けた理由は、4.1 が示すとおり**実体化そのものが要らない**からである。代入が特殊化を
やっているので、パスを 1 つ残す理由が無い。

## B.3 宣言のフィールド型を畳まず、漏斗だけで畳む

型環境は宣言を書かれたまま持ち、フィールド型を答えるたびに畳む案。「宣言は書かれたまま、
答えるフィールド型は畳み済み」という規則は 4.3 の規則より単純である。

退けた理由はコストである。この形では 4.3 の補題が使えず、`field_types` の呼び出しごとに
型を歩き直すことになる。実装して測った結果は付録 A.5 にある。型環境の大きなプログラムで 2.8%。

単純さの差は、4.3 の前提を口の側で守らせることで無くなった (4.3 の表を見よ)。残るのはこの
2.8% だけなので、近道を採る。
