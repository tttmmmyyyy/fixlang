# どのラムダかを型に持たせるクロージャ特殊化

## 目的

クロージャの呼び出しを、どのラムダを呼ぶかがコンパイル時に分かる場所では、直接呼び出しにする。
それを、クロージャが構造体のフィールドに入るときも、関数の結果として返るときも、`if` の分岐で
合流するときも、ループの状態に乗るときも、同じ一つの仕組みで行う。

仕組みは、型検査と単相化の終わったプログラムの関数の型に、「そこに届きうるラムダの集合」を
付けて推論し直すことである。Rust や C++ はラムダごとに固有の型を与えるので、`DSegtree<F>` の
`F` が何であるかを型が運ぶ。この設計は、それを言語仕様ではなく最適化として行う。手法は
Brandon らの lambda set specialization（以下 LSS。PLDI 2023、「付録 A」に要約）に拠る。

## 今のやり方と、その限界

main の `closure_specialization` は、ラムダを大域関数に持ち上げ（decapture）、既知のラムダを
受け取る関数の写しを作る（specialization）。「既知」は変数に付く知識で、ラムダに束縛された変数、
そのラムダを受け取った引数、捕捉リストのフィールド（1 段まで、narrowing）を追う。

クロージャが値として運ばれる経路は、ほかにもある。

- 利用者の構造体や union のフィールド
- 関数の結果
- `if` や `match` の合流
- `Std::loop` や `fold` が運ぶループの状態

変数に付く知識でこれらを追うには、経路ごとに変換が要る。試作（ブランチ
`struct-field-closure-spec`）は、構造体の引数の分割（`split_struct_args`）、引数をそのまま返す
部分の削除、case-of-case、合流の読み取りを足して、繰り返し回した。iterator の連鎖や遅延
セグメント木の一部では効いたが、getter と setter でクロージャを運ぶ構造体（cp-library の
`DSegtree`）では経路が 4 つ続き、4 つ目の「ループの状態の `if` での合流」で止まった。詳細は
「付録 B」にある。

もう一つの限界は停止性である。写しを作るたびに既知の値が育つ再帰（毎回クロージャを包み直す
関数）があるので、今のやり方は「写しの数の予算」で止めている。予算はテストの多くが数を固定する
ほど振る舞いに効いており、どの写しが作られるかが予算の消費順で決まる。

## 手法の要点

LSS は、関数の型の矢印ごとに lambda set を付ける。lambda set は、その型の値として実行時に
現れうるラムダの集合である。

```
twice : (I64 -α-> I64) -> I64 -> I64        // α は lambda set の変数
twice(|x| x + 2, 5)                          // α := { λ1 }
twice(if b { |x| x } else { |x| x + 2 }, 5)  // α := { λ2, λ1 }
```

- **推論。** 単相化の済んだプログラムに、矢印ごとに新しい変数を置き、型検査と同じ単一化で
  変数どうしを等しくする。部分型は使わないので、合流では二つの集合が一つになる。
- **多相性。** 大域関数の型に現れる変数は全称化する。`twice` は α について多相になり、呼び出し
  ごとに α の具体値が決まる。型に現れない変数は、そこへ流れ込むラムダの最小の集合に決める。
- **再帰。** 集合が自分を含むとき（ラムダが同じ集合のクロージャを捕捉するとき）は、再帰型と同じ
  `μ` で表す。大域関数の再帰は単相にし、多相再帰を作らない。
- **特殊化。** 大域関数を、呼び出しで決まった lambda set の具体値ごとに写す。多相再帰がない
  ので、写しの数は有限で、手続きは必ず停止する。予算は要らない。
- **下ろし方。** 関数の型は「各ラムダの捕捉の直和」になり、ラムダを作る式は直和への注入に、
  呼び出しは直和の `match` と直接呼び出しになる。集合が一つのラムダだけなら、値は捕捉そのもので、
  呼び出しは分岐のない直接呼び出しになる。

経路ごとの変換は要らない。構造体のフィールドも関数の結果も合流もループの状態も、どれも型の
単一化の中で扱われる。`DSegtree` の `set` が返す値の型は、`_op` の lambda set を含む
`DSegtree` の型なので、`if` で合流しても同じ型どうしの単一化になり、ループの次の周にも
同じ lambda set が届く。

## Fix への当てはめ

### 置き場所

新しいパスは、AST の最適化の中の、今の `closure_specialization` の位置に置く。`defunctionalize_fix`、
`inline`、`inline_local` の後で、`decapture_scope_functions` と `uncurry` の前である。

- **入力がそろっている。** 単相化が済み、すべての記号（`Program::symbols`）が具体的な型を持ち、すべての
  式のノードに型が付いている。`unwrap_newtype` の後なので、`IO a` は `IOState -> (IOState, a)` という
  関数の型になっており、IO のコードもこのパスの対象になる。この位置の式はカリー化された形で、`Lam` の
  引数と `App` の引数は一つずつである。
- **前のパスの前提を崩さない。** `defunctionalize_fix` は、`Std::fix` に渡したラムダをそのままの形で
  受け取る。
- **ラムダが少ない。** `inline` が combinator を利用者のコードに展開した後なので、ラムダの数が少なく、
  集合も小さい。
- **後段がそのまま使える。** 出力は「捕捉の構造体を受け取る大域関数と、その呼び出し」で、今の
  `closure_specialization` の出力と同じ種類の形である。

RC IR では、クロージャはすでに関数ポインタと `#DynamicObject` の組に下ろされ、構造体の型の配置も
決まっている。型の写しを作るには遅い。

推論に、型検査の単一化は使わない。この位置のプログラムは型検査を通っているので、注釈を付ける前の Fix の
型は、等しくあるべき二か所でもう等しい。二つの注釈付きの型の単一化は、同じ位置にある lambda set の
変数どうしを一つにすることに尽き、union-find で書ける。

### パスの組み立て

パスは四段からなる。

1. **注釈。** 各記号の本体を写した木を作り、ノードごとに、型の中の置き場所の数だけ新しい変数を置く。
2. **推論。** 記号の呼び出しグラフの強連結成分ごとに、依存の順に、変数を union-find で一つにし、
   ラムダの包含の制約を集める。成分の記号の型に現れる変数を全称化する。
3. **特殊化。** エントリの IO 値と export された値から、呼び出しをたどり、全称化した変数の具体値ごとに
   記号の写しを作る。名前の付いた型の写しも作る。
4. **下ろし。** 写しごとに、式と型を Fix の式と型に書き戻す。

推論で使う型を Rust で書くと次のようになる。

```rust
/// lambda set の変数。union-find の要素。
struct SetVar(u32);

/// 注釈付きの型: Fix の型と、その型の置き場所ごとの変数。
/// `slots` の並びは「型の中の置き場所」の節が決める。
struct AType {
    ty: Arc<TypeNode>,
    slots: Vec<SetVar>,
}

/// プログラムの中の一つのラムダ: それを書いた記号と、その本体の中での順番。
struct LamId {
    symbol: FullName,
    index: u32,
}

/// 具体的な lambda set の要素。
enum Elem {
    /// ラムダ。捕捉の型は、そのラムダを持つ記号の写しで決まるので、写しと組にする。
    Lam { lam: LamId, owner: Instance },
    /// 実行時のクロージャでしか表せない値（「消去済み」の節）。
    Erased,
}

/// 記号の写し: 元の記号と、全称化した変数の具体値。
struct Instance {
    symbol: FullName,
    args: Vec<ConcreteSet>,
}
```

`ConcreteSet` は `Elem` の集合で、共有した表現で持つ。自分を含む集合（`μ`）は、その表現の中の循環で
表す（「特殊化」の節）。

### 型の中の置き場所

Fix の型の中で lambda set が付く場所を、置き場所（slot）と呼ぶ。`AType` の `slots` は、型を前から順に
読んで、型構築子が現れるたびにその型構築子の置き場所を並べたものである。

- 矢印 `a -> b` は置き場所を一つ持つ。
- 構造体と union は、定義のフィールドの型に直接書かれた矢印ごとに、置き場所を一つ持つ。フィールドの
  型に別の名前の付いた型が現れるときは、その型の置き場所も自分の置き場所に数える。
- 型引数の置き場所は、型引数の側が持つ。`DSegtree I64` の `_op` の矢印は `DSegtree` の置き場所で、
  `Array (I64 -> I64)` の要素の矢印は型引数 `I64 -> I64` の置き場所である。
- 互いに参照し合う型の定義の強連結成分の中では、成分の型の出現は、成分の置き場所を共有する。こうすると、
  再帰型の置き場所の数が有限になる。

```
type DSegtree m = struct { _n : I64, _unit : m, _op : (m, m) -> m, _elems : Array m };
// DSegtree は置き場所を一つ持つ。DSegtree<α> I64 の _op の型は (I64, I64) -α-> I64
```

各型構築子について、フィールドの型ごとに、その置き場所が「自分の何番目の置き場所か、型引数の何番目の
置き場所か」を表にしておく。フィールドを読む規則（構造体のパターン、構築、getter など）は、この表で
フィールドの `AType` を作る。

unwrap 済みの newtype は、外の型の置き場所に数える。型の定義のフィールドには `IO a` のような newtype が
残っており、フィールドの型を問い合わせると unwrap される（`TypeNode::unwrap_newtypes`）。`IO` の
フィールドの矢印は、`IO a` を含む型の置き場所になる。

**型引数として、引数を取らずに渡された型構築子**（`type [f : * -> *] Foo f = box struct { data : f () }`
の `Foo IO` の `IO`）の置き場所は、消去済みにする。このような置き場所に一つのラムダを入れるには、型の
写しを、引数を待つ型として作る必要がある。

### ラムダ

推論の対象のラムダは、記号の本体の中の `Expr::Lam` である。捕捉はその自由変数で、`LamId` はそれを
書いた記号と、本体の中での順番で決まる。

- 大域関数 `g = |a| |b| body` は、二つのラムダを持つ。一つ目は捕捉のない `g` 自身のラムダで、二つ目は
  `a` を捕捉するラムダである。`g(a)` は二つ目のラムダの値を作る式になり、部分適用に特別な扱いは
  要らない。
- 大域関数を呼ばずに値として使う式 `g` は、一つ目のラムダの値を作る式である。
- 大域関数の呼び出し `g(x)` も、`g` の型の lambda set を通る呼び出しとして推論する。集合が `g` の
  ラムダだけなら、下ろしの結果は今と同じ直接呼び出しになる。

### 推論

記号の呼び出しグラフ（`graph::Graph`）の強連結成分を、依存される側から順に推論する。成分の中の記号は
互いに単相で、成分の推論が終わってから全称化する。

式の形ごとの規則は次のとおり。「等しくする」は、二つの `AType` の `slots` を同じ位置どうし
union-find で一つにすることである。

- **局所変数。** 束縛したところの `AType` を使う。
- **大域の記号。** 推論の済んだ成分の記号なら、その型の全称化した変数を新しい変数に置き換え、制約も
  写す。同じ成分の記号なら、その記号の `AType` をそのまま使う。
- **`Lam`。** 型の矢印の置き場所に、そのラムダを要素として入れる（包含の制約）。引数は型の定義域、
  本体は値域と等しくする。
- **`App`。** 関数の型の定義域を引数と等しくし、値域を式の型と等しくする。
- **`Let`、`Match`。** 束縛する値をパターンと等しくする。構造体のパターンは、フィールドの表で
  フィールドの `AType` を作り、部分パターンと等しくする。腕の値は式の型と等しくする。
- **`If`。** 二つの腕を式の型と等しくする。
- **`MakeStruct`。** フィールドの表で作ったフィールドの `AType` を、それぞれの値と等しくする。
- **`ArrayLit`。** 要素を、配列の型の要素と等しくする。
- **`TyAnno`、`Eval`。** 値を式の型と等しくする。
- **`FFICall`。** 引数と結果は C の型で、置き場所を持たない。
- **組み込み関数。** `BuiltinOp` に、オペランドの `AType` と結果の `AType` のあいだの規則を述べる
  メソッドを足す。既定は、オペランドと結果のすべての置き場所を消去済みにする規則である。既定はいつでも
  健全で、規則を述べていない組み込み関数は、性能を失うだけで正しさを失わない。規則を述べるのは、値を
  形を保って運ぶ組み込み関数である。
  - 配列の操作（`ArrayUnsafeGetBoundsUncheckedOp`、`ArraySetOp`、`ArrayPunchOp` など）は、要素の型どうしを等しくする。
  - 構造体と union の操作（`StructGetOp`、`StructSetOp`、`StructPunchOp`、`StructPlugInOp`、
    `MakeUnionOp`、`UnionAsOp`、`UnionModOp`）は、フィールドの表で作ったフィールドの `AType` を、
    オペランドや結果と等しくする。
  - 値をそのまま通す組み込み関数（`MarkThreadedOp`、`IsUniqueOp` など）は、通す値と結果を等しくする。

  組み込み関数の宣言の型（`BuiltinOpExpr::generic_ty`）は結果の型だけを述べ、型検査の後は読まれない
  ので、この規則の代わりにはならない。

成分の推論が終わったら、成分の記号の型に現れる変数を全称化し、その変数の制約を記号の制約として残す。
型に現れない変数は、そこへ入るラムダの集合そのものに決める。

### 実行時のクロージャが要る場所

次の置き場所は、実行時のクロージャ（関数ポインタと、box に入った捕捉の組）を要する。推論の初めに、
これらの置き場所に要素 `Erased` を入れる。

- エントリの IO 値（`Program::entry_io_value`）と、export された値（`Program::export_statements`）の型
- `Std::FFI::Destructor` の `_dtor` のフィールド。値を解放するコードが、クロージャとして呼ぶ。
- 組み込み関数の既定の規則で消去済みにした置き場所。`Std::fix`（`FixCombinatorOp`）、関数のオペランドを
  呼ぶ組み込み関数（`WithRetainedOp`、`BorrowPtrOp`、`MutatePtrOp`）、値を `Ptr` にする組み込み関数が
  これに当たる。
- 引数を取らずに型引数として渡された型構築子の置き場所（「型の中の置き場所」の節）

`Erased` を含む集合は、ほかの要素も持っていてよい。そのような集合の値は、すべて実行時のクロージャで
表す。

### 特殊化

エントリの IO 値と export された値から、記号の参照をたどる。参照ごとに、全称化した変数の具体値が
決まり、`Instance` が一つ決まる。`Instance` ごとに記号の写しを一つ作る。

- 成分の中の再帰は単相なので、再帰の呼び出しの `Instance` は、呼び出し側と同じになる。多相再帰が
  ないので、写しの数は有限で、手続きは停止する。
- 具体値の集合は、共有した表現で持つ。素朴に書き下すと、大きさが指数的になる例がある（「付録 A」の
  実装上の注意）。
- ラムダ `ℓ` が、自分の入る集合のクロージャを捕捉するとき、集合はその要素の `owner` を通して自分自身を
  含む。これが `μ` の集合で、表現の中の循環で表す。二つの集合が等しいかは、循環をたどって比べる。

名前の付いた型の写しは、`(型構築子, 自分の置き場所の具体値)` ごとに一つ作る。写しのフィールドの型は、
置き場所の具体値で下ろした型である。

- すべての置き場所が消去済みなら、写しの代わりに元の型構築子を使う。`Destructor` はいつもこれに当たる
  ので、`is_destructor_object` のような名前で型を見分ける箇所は、そのまま動く。
- punch した型（`TyConInfo::punched_from` を持つ型）も、元の構造体と同じ具体値で写す。
- getter、setter、`mod_`、`punch`、`plug_in` は、本体が組み込み関数かパターンの、ふつうの記号である。
  ほかの記号と同じ規則で写される。

写しの名前は、元の名前と、具体値から決まる短い印で作る。コンパイルの結果をキャッシュするので、同じ
プログラムからは同じ名前ができるようにする。

### 下ろし方

型は、置き場所の具体値で次のように下ろす。

- **矢印。** 集合の要素が一つのラムダなら、そのラムダの捕捉の構造体の型になる。二つ以上のラムダなら、
  捕捉を payload に持つ unbox の union になる。`Erased` を含むなら、今のクロージャの型のまま
  （定義域と値域は下ろす）である。
- **`μ` の集合。** 捕捉が同じ集合の値を含むので、unbox では大きさが決まらない。box の union にする。
  box が要るのは、unbox のフィールドだけをたどって自分に戻る型で、`Program::validate_layouts` が
  退ける形と同じである。
- **名前の付いた型。** 写しの型構築子になる。

ラムダは、すべて大域関数に持ち上げる。捕捉の構造体は `CaptureStruct` で作り、持ち上げた関数は
`|cap| |x| body` の形にする。大域関数自身のラムダは捕捉がないので、その記号のままにする。

式は、次のように下ろす。

- **ラムダの値を作る式。** 一つのラムダの集合なら、捕捉の構造体の構築になる。二つ以上なら、それを
  union に入れる式になる。`Erased` を含むなら、持ち上げた関数を捕捉の構造体に部分適用した式
  `ℓ(cap)` になる。この形は今の `closure_specialization` が作るクロージャと同じで、
  `decapture_scope_functions` と `uncurry` はこの形を読む。
- **呼び出し `f(x)`。** 一つのラムダの集合なら、持ち上げた関数の直接呼び出し `ℓ(f)(x)` になる。
  二つ以上なら、`f` の `match` と、腕ごとの直接呼び出しになる。`Erased` を含むなら、今の間接呼び出しの
  ままである。
- **型の名前を埋め込んだ式。** `MakeStruct` と構造体のパターンの型構築子は、写しの型構築子に替える。
- **すべてのノードの型。** 式とパターンのノードの型、記号の型（`Symbol::ty`）を、下ろした型に替える。

どの表現も、今の型（構造体、union、box、クロージャ）で書ける。参照カウントは今の RC IR がそのまま
扱う。

### 前後のパス

- `closure_specialization` と `split_struct_args` を消す。`split_struct_args` の直後の `inline` と
  `collapse_constructions` は、`split_struct_args` の残した形を片付けるためにあるので、要るかを測って
  決める。
- `move_bodies_into_callers` は、新しいパスの最後で使う。持ち上げたラムダのうち、ただ一か所から呼ばれる
  ものの本体を、その呼び出しに置く。
- `decapture_scope_functions`、`uncurry` と、その後の `inline_local` と
  `replace_calls_with_funptr_versions` は、そのまま使う。

`collapse_constructions`（case-of-case を含む）は、構築とその分解を打ち消す一般の変換として残す。

## 確かめ方

- **意味が変わらないこと。** 全テスト、speedtest のコーパス、LangArena の出力が変わらない
  こと。参照カウントは、コーパスを memcheck に通して漏れと二重解放がないことを見る。
- **効くこと。** speedtest を `--langarena` で測り、全ケースを報告する。cp_dsegtree、
  cp_ldsegtree、cp_ldsegtree_fold_act、iterator の連鎖、`Calculator::Interpreter`、モナドの
  スタック（`StateT` を `IO` に重ねたもの）を、効くはずのケースとして個別に見る。
- **写しの数。** 予算がなくなるので、写しの数とコンパイル時間を LangArena で測り、今のやり方と
  比べる。LSS の論文の 6 本ではバイナリの大きさはほとんど変わっていないが、Fix の iterator は型が
  深く、同じとは限らない。

## 段取り

1. 注釈と推論だけを実装し、プログラムを変えずに、各置き場所の lambda set と、消去済みになった
   理由をダンプに出す。全テストで推論が失敗しないこと、ダンプが手で確かめた例と合うことを見る。
2. 一つのラムダの集合だけを下ろす（それ以外の集合は消去済みとして扱う）。今の
   `closure_specialization` と並べて測れる。
3. 二つ以上のラムダの集合を、union と `match` で下ろす。
4. `μ` の集合を `box union` で下ろす。
5. 置き換わるパスを消し、後段のパスを新しい形に合わせる。

各段で全テストと speedtest を通す。

## 未決の問い

- **名前の付いた型の写しを、どこまで作るか。** 型の写しは、getter や `mod_` の記号の写しを伴う。写しの
  数が増えたときにコンパイル時間がどう伸びるかは、段取りの 2 で測る。
- **二つ以上のラムダの集合を、いつ下ろすか。** 呼び出しが `match` になるので、腕が多いと命令数が
  増えうる。今のクロージャ（間接呼び出し）とどちらが速いかは、ケースによる。下ろす条件（集合の
  大きさ）を測って決める。
- **組み込み関数の規則をどこまで述べるか。** 既定の規則は消去済みにするので、規則を述べた組み込み関数の
  範囲が性能を決める。段取りの 1 のダンプで、消去済みになった置き場所とその理由を出し、効くものから
  述べる。

## 付録 A: LSS の論文の要約

William Brandon, Benjamin Driscoll, Frank Dai, Wilson Berkow, Mae Milano. *Better
Defunctionalization through Lambda Set Specialization.* Proc. ACM Program. Lang. 7, PLDI,
Article 146 (2023). https://doi.org/10.1145/3591260

- 対象の言語 L_src は、単純型付きラムダ計算に積、和、iso-recursive な `μ` 型を足したもの。
  特殊化の単位は `def` で束縛した大域定義で、相互再帰する定義は強連結成分を一つの `def` にする
  （6.3 節）。
- 注釈付きの言語 L_annot は、矢印、適用、ラムダの三か所に lambda set を付ける（4 節）。
  lambda set は具体的な集合、変数、`μa.σ` のいずれか。
- 推論（4.2 節）は、定義ごとに新しい変数を置き、型の等式から lambda set の変数の等式を取り
  出して最も一般的な単一化子を求める。ラムダの包含の制約（`ℓ ⊏ σ`）は、型に現れる変数なら
  定義の制約として残し、現れない変数なら最小の具体的な集合に決める（internalization）。
  自分を含む制約は `μ` で解く。推論が健全かつ完全であることを Isabelle/HOL で証明している。
- 特殊化（5.1 節）は、入口から依存の逆順にたどり、使われた lambda set の具体値ごとに定義を
  写す。多相再帰がないので停止する。写しへの参照の置き換えには、`μ` を展開した形でも一致を
  見る置き換え（μ-aware substitution）が要る。
- 下ろし方（5.2 節）は、関数の型を捕捉の直和に、ラムダを注入に、適用を `match` にする。
- 実装上の注意（6 節）。lambda set を素朴に表すと大きさが指数的になるので、共通の部分を名前で
  共有する（メモ化）。置き換えを即座に行うと 2 乗の時間になるので、置き換えを遅延させる。
- 評価（7 節）。Morphic で書いた 6 本（calc、parse_json、primes_sieve、primes_iter、quicksort、
  unify）を、iterator、状態モナド、パーサ combinator のライブラリの上で測った。MLton で 0.91 倍
  から 6.85 倍、OCaml で 1.08 倍から 3.45 倍、Morphic（比較対象は単相の defunctionalization）で
  最大 78.93 倍。バイナリの大きさは MLton で変わらず、Morphic で小さく、OCaml でやや大きく
  なった。

## 付録 B: 変数に付く知識で追った試作の記録

試作は、ブランチ `struct-field-closure-spec`（コミットしていない作業ツリー）にある。次の変換を
2 周回した。

- 構造体の引数の分割
- 引数をそのまま返す部分の削除（互いの結果を返し合う関数の集まりを単位に）
- case-of-case を含む構築の読み取り
- 既知の値（`g(c)` と union の variant）による関数の写し

RC IR の解放の順を名前の hash によらず固定した版どうしで、speedtest の 122 本を比べた結果（命令数）:
0.01% 以内が 93 本、動いたもの 29 本。cp_ldsegtree_fold_act -44.46%、iter_flatten -12.98%、
Calculator::Interpreter -4.49%、Etc::Words -2.27%、Json::Generate -1.62%、Json::ParseDom
-1.03% など 21 本が減り、iter_filter_map +13.56%、cp_dsegtree +2.85%、Distance::NGram
+2.25%、index_syntax +1.54%、Brainfuck::Array +0.43%、Template::Parse +0.02% が増えた。
Json::ParseMapping +17.18% と Etc::LogParser +1.17% は、`--cu-size inf` で測るとコンパイル単位の
分け方による揺れだった。

cp_dsegtree では、クロージャ `_op` が次の四か所を通ってループを回る。試作は最初の三つを通り抜けた

1. getter で 1 フィールドずつ読む構造体（全フィールドを束ねるパターンがないと分割しない）
