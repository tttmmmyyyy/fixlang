# Lambda set 特殊化

## この文書が決めること

新しい最適化パス `lambda_set` の設計を決める。このパスは、どのラムダがその値として現れうるかを関数の型に持たせて推論し直し、その結果でクロージャの呼び出しを直接呼び出しにする。決めるのは、後から変えると実装のやり直しになる次の 6 つである。

- パスの位置と、今あるクロージャ最適化のパスとの関係
- 推論が書き換えの段に渡すもの
- シンボルのコピーの作り方と名前
- 型のコピーの作り方と登録先
- ラムダをグローバル関数にリフトする単位と、値と呼び出しの書き換え
- 段階ごとに、どの集合の値の表現を書き換えるか

実装は段階 1 から 4 に分けて進める。段階 1 (推論と、その結果のダンプ) はできている。段階 2 と 3 で、書き換える値の種類を一つずつ増やし、段階 4 で今のクロージャ最適化のパスを外す。このほかの細部は、実装しながら決める。

## 背景

### 今のクロージャ最適化

Fix の関数値は、実行時にはクロージャ (関数ポインタと、box に入ったキャプチャからなる値) で、呼び出しは関数ポインタを通る間接呼び出しになる。今のパス `closure_specialization` は、ラムダを「キャプチャの構造体を受け取るグローバル関数」にリフトし、どのラムダかが分かっている引数を受け取る関数のコピーを作って、間接呼び出しを直接呼び出しにする。

どのラムダかは、変数に付く情報として追う。追えるのは、ラムダに束縛された変数、そのラムダを受け取った引数、キャプチャのフィールド (1 段まで) である。クロージャが値として運ばれる経路は、ほかにもある。

- 利用者の構造体や union のフィールド
- 関数の結果
- `if` や `match` の合流
- `Std::loop` や `fold` が運ぶループの状態

変数に付く情報でこれらを追うには、経路ごとに別の変換が要る。cp-library の `DSegtree` (演算をフィールドに持つセグメント木) では、ループの状態の `if` での合流で追えなくなる (付録「変数に付く情報で追った試作の記録」)。

もう一つの限界は停止性である。コピーを作るたびに分かっている値が育つ再帰 (毎回クロージャを包み直す関数) があるので、今のやり方は「コピーの数の予算」で止めている。どのコピーが作られるかが、予算を使う順番で決まる。

### Lambda set specialization

Brandon らの手法 (PLDI 2023、付録「LSS の論文の要約」) を、以下 LSS と呼ぶ。LSS は、型検査の済んだプログラムに対して、もう一度型推論に似た計算を行う。型推論が「この式の型は何か」を求めるのに対して、LSS は「この関数の値として、実行時にどのラムダが現れうるか」を求める。Rust や C++ はラムダごとに固有の型を与えるので、`DSegtree<F>` の `F` が何であるかを型が運ぶ。LSS は、それを言語仕様ではなく最適化として行う。

**計算の結果。** LSS が求めるのは次の二つである。

- プログラムに現れる関数型の矢印それぞれについて、その型の値になりうるラムダの集合。これを lambda set と呼ぶ。
- 各グローバル関数について、それが呼ばれるときに引数の関数がどの lambda set を持つかの組み合わせの一覧。組み合わせごとに、その関数のコピーを一つ作る。

この二つが分かると、集合が一つのラムダだけの場所では、関数の値をキャプチャの構造体で表し、呼び出しをそのラムダの直接呼び出しにできる。以下、小さなプログラムで計算を順に追う。

```
apply : (I64 -> I64) -> I64 -> I64;
apply = |f, x| f(x);

main = (
    let n = 10;
    let a = apply(|x| x + n, 1);    // このラムダを lam1 と呼ぶ。n をキャプチャする
    let b = apply(|x| x * 2, 2);    // このラムダを lam2 と呼ぶ。何もキャプチャしない
    ...
);
```

**1. 矢印に変数を置く。** プログラムに現れるすべての型の矢印の一つ一つに、lambda set の変数を置く。対象はグローバル値の型だけでなく、局所変数、ラムダの引数、式のノード一つ一つの型も含む。型の奥にある矢印 (関数を返す関数の結果の矢印、`Array (I64 -> I64)` の要素の矢印) にも、それぞれ別の変数を置く。変数は「ここに来るラムダの集合」を表し、中身はまだ分からない。この例の矢印は 3 本あるが、手順 1 から 4 では `apply` の引数 `f` の矢印に置いた変数 `s` だけを追う。残りの 2 本は、手順 4 の後の「例の矢印をすべてたどる」で同じ規則でたどる。

```
apply : (I64 -s-> I64) -> I64 -> I64
```

**2. 関数ごとに推論する。** グローバル関数を一つずつ取り、その本体の式をたどる。順番には決まりが一つある。関数を推論する前に、その関数が呼ぶ関数を先に推論しておく。この例では `main` が `apply` を呼ぶので、`apply`、`main` の順になる。呼ぶ側を推論するときには、呼ばれる側の型 (後で述べる `forall` の付いた型) がもう分かっている必要があるからである。互いに呼び合う関数 (相互再帰) は、どちらも先にできないので、まとめて推論する。まとめる単位は、呼び出しグラフ (グローバル値が別のグローバル値を参照する関係のグラフ) の強連結成分で、以下これを成分と呼ぶ。再帰しない関数も、自分を呼ぶ関数 (自己再帰) も、それだけで一つの成分である。成分の推論の手順は、後の「再帰する関数」で述べる。たどる規則は二つだけである。

- **ラムダを書いた場所では、そのラムダを集合に入れる。** `|x| x + n` という式の型の矢印の変数に、`lam1` を要素として加える。
- **値が一方から他方へ流れる場所では、両側の変数を一つにする。** 関数に引数を渡す、変数に束縛する、`if` の二つのアームが合流する、構造体のフィールドに入れる、といった場所では、両側の型の同じ位置にある変数を同じ変数にする。型推論の単一化と同じ操作で、union-find で書ける。一つにした変数は、両方の要素を持つ。

`apply` の本体をたどり終えたら、`apply` の型に現れる変数 `s` を一般化する。型推論で型変数を一般化するのと同じで、`s` は呼び出しごとに決まる変数になる。本体 `f(x)` は `f` を呼ぶだけで `s` にラムダを入れないので、`s` は、呼び出し側が渡したラムダだけを持つ。

```
apply : forall s. (I64 -s-> I64) -> I64 -> I64
```

一般化するのは、グローバル値の型に現れる変数だけである。局所変数 `f` の型の変数は `apply` の型の `s` と同じ変数なので、`s` と一緒に呼び出しごとに決まる。グローバル値の型につながらない変数 (たとえば本体の中で書いて、その場で呼ぶだけのラムダの矢印の変数) は一般化せず、その場で入るラムダの集合に確定する。

`main` では、`apply` を呼ぶたびに `s` を新しい変数に置き換える。一つ目の呼び出しの新しい変数を `s1` とすると、引数 `|x| x + n` の矢印の変数 (要素は `lam1`) と `s1` が一つになる。二つ目も同じである。

```
s1 = { lam1 }
s2 = { lam2 }
```

本体が `s` にラムダを入れる関数もある。たとえば、負の入力では `f` の代わりに自分で書いたラムダを使う関数である。

```
apply_or_zero : (I64 -> I64) -> I64 -> I64;
apply_or_zero = |f, x| (
    let g = if x < 0 { |_| 0 } else { f };   // このラムダを lam0 と呼ぶ
    g(x)
);
```

`if` の合流で `g` と `f` の矢印の変数が一つになるので、`f` の矢印の変数 `s` は `lam0` を持つ。この場合も `s` は一般化し、「`s` は `lam0` を含む」という制約を型と一緒に持ち運ぶ。呼び出しごとの集合は、呼び出し側が渡したラムダに `lam0` を加えたものになる。

```
apply_or_zero : forall s ⊇ { lam0 }. (I64 -s-> I64) -> I64 -> I64
apply_or_zero(|x| x + n, 1)    // この呼び出しの s = { lam1, lam0 }
```

制約は、呼び出し側が変数を置き換えるときに満たす。`apply_or_zero` を呼ぶたびに `s` を新しい変数 `s1` に置き換え、その場で `s1` に `lam0` を要素として加える (`instantiate`)。そこへ引数 `|x| x + n` の矢印の変数が一つになり、`s1 = { lam1, lam0 }` になる。制約は「少なくともこの要素を含む」という下限だけで、要素を加えれば必ず満たせる。そのため、推論は制約のせいで失敗することがなく、いつでも終わる。

呼び出し側に残るのは、値の表現への影響である。引数 `|x| x + n` の矢印の変数は `s1` と同じ変数なので、この値の集合も `{ lam1, lam0 }` になる。そのため呼び出し側は、この値を二つ以上のラムダの集合の形 (後で述べる unbox の union) で作る。`apply_or_zero` のコピーも `s = { lam1, lam0 }` に対して一つ作られ、その中の `g(x)` は二つのラムダを `match` で選んで直接呼ぶ。

**再帰する関数。** 成分は次の 3 つの手順で推論する。自己再帰の関数も、相互再帰の関数の集まりも、同じ手順である (`infer_component`)。

1. 成分のすべての関数の型に、先に変数を置く。
2. 成分の関数の本体を一つずつたどる。成分の中の関数を参照したら、手順 1 で置いた型の変数をそのまま使う。成分の外の関数を参照したら、上の `main` と同じく新しい変数に置き換える。置き換えられるのは、推論を終えて制約がすべて分かった型だけである。置き換えはその時点の制約を新しい変数へ写し取るので、本体をたどり終えていない関数の型を置き換えると、後でその本体から見つかる要素が写しに入らない。成分の外の関数は先に推論を終えているが、成分の中の関数は互いに相手を先に終えられない。そのため成分の中では写しを取らず、同じ変数を共有して、どの本体から加わった要素も全員が見るようにする。
3. すべての本体をたどり終えてから、一度だけ一般化する。

制約が変わらなくなるまで繰り返す処理は要らない。推論が行う操作は、「変数に要素を加える」と「二つの変数を一つにする」の二つだけである。どちらも集合を増やす向きにだけ働き、結果は行う順番によらない。要素が持つキャプチャの集合も変数として持つので、その変数に後から加わった要素も、そのまま要素の中に現れる。そのため、本体を一度たどればすべての操作を行ったことになり、その時点の結果が不動点である。

Fix の型検査に成分が要らないのは、グローバル値の型を利用者が必ず書くからである。参照先の型は本体をたどる前から確定しているので、どの参照でも写しを作れる。lambda set は利用者が書かないので、型シグネチャのない Haskell の関数と同じく、成分ごとにまとめて推論する (Haskell 2010 Report の 4.5.1「Dependency Analysis」)。

代わりに、再帰の呼び出しが渡すラムダは、外から渡されたラムダと一つの集合に入る。次の `rec` は、再帰のたびに `f` を包むラムダを渡す。

```
rec : (I64 -> I64) -> I64 -> I64;
rec = |f, n| if n == 0 { f(0) } else { rec(|x| f(x) * 2, n - 1) };   // このラムダを rec@lam2 と呼ぶ

rec(|x| x + k, 3)   // main の中。このラムダを main@lam0 と呼ぶ
```

再帰の呼び出しは同じ変数 `s` を使うので、`rec@lam2` は `s` に入る。`rec@lam2` は `f` をキャプチャし、`f` の集合は `s` 自身なので、制約は `s ⊇ { rec@lam2[f: s] }` になる。`main` の呼び出しでは `s1 = { main@lam0, rec@lam2[f: s1] }` となり、後で述べる「自分を含む集合」になる。段階 1 のダンプもこの集合を書く (`#1 = {rec@lam2[#1], main@lam0[]}`)。再帰のたびに別の集合を置くと (多相再帰)、`rec@lam2[f: { rec@lam2[f: { main@lam0 }] }]` のような入れ子が再帰の深さだけ続き、コピーが有限個に収まらない。

集合が大きくなるのは、再帰の呼び出しが新しいラムダを渡す場合だけである。Std の `loop`、`Iterator::fold`、`Iterator::fold_m`、`loop_m` は、再帰の呼び出しに受け取った関数をそのまま渡す (`loop(s, body)`)。このとき合流するのは `s` と `s` 自身なので、集合は呼び出し側が渡したラムダ一つのままである。段階 1 のダンプで、この 4 つと `map`、`filter` を `main` から使うと、渡したラムダの集合がすべて要素一つになることを確かめた。

**3. コピーを列挙する。** エントリポイント (`main`) から呼び出しをたどり、多相な関数の一般化した変数に、具体的な集合を与える。`apply` は `s = { lam1 }` と `s = { lam2 }` の二通りで呼ばれるので、コピーが二つ要る。関数の中で関数がさらに呼ばれていれば、呼び出し側のコピーが決めた集合で、呼ばれる側のコピーも決まる。この計算は、再帰の中では一般化した変数の集合を変えない (多相再帰を作らない) ので、コピーの数は有限で、必ず終わる。予算は要らない。実装 (`specialize`) は、作るべきコピーをキューに積み、新しいコピーが出なくなるまで取り出す。成分どうしの参照は循環しないので、キューは必ず空になる。自分を含む集合は、このときに分割を細かくしていく反復 (DFA の最小化と同じ手続き) で、等しい集合を一つにまとめる (`SetStore::intern`)。

**4. 書き換える。** 集合が一つのラムダだけの場所では、関数の値をそのラムダのキャプチャの構造体で表す。ラムダの本体は、キャプチャの構造体を受け取るグローバル関数になる。`apply` は `|f| |x| f(x)` の略なので、内のラムダ `|x| f(x)` も、ほかのラムダと同じくキャプチャの構造体とグローバル関数になる。このラムダの矢印のたどり方は、次の「例の矢印をすべてたどる」で述べる。

```
type Cap1 = unbox struct { n : I64 };         // lam1 のキャプチャ
type Cap2 = unbox struct { };                 // lam2 のキャプチャ (空)
lam1 : Cap1 -> I64 -> I64;  lam1 = |{ n }, x| x + n;
lam2 : Cap2 -> I64 -> I64;  lam2 = |{ }, x| x * 2;

// apply の内のラムダ |x| f(x) のキャプチャと本体
type CapA1 = unbox struct { f : Cap1 };
type CapA2 = unbox struct { f : Cap2 };
apply#ls_lam1#h1 : CapA1 -> I64 -> I64;  apply#ls_lam1#h1 = |{ f }, x| lam1(f, x);   // 直接呼び出し
apply#ls_lam1#h2 : CapA2 -> I64 -> I64;  apply#ls_lam1#h2 = |{ f }, x| lam2(f, x);

// apply のコピー: 内のラムダのキャプチャの構造体を作って返す
apply#ls1 : Cap1 -> CapA1;  apply#ls1 = |f| CapA1 { f };
apply#ls2 : Cap2 -> CapA2;  apply#ls2 = |f| CapA2 { f };

main = (
    let n = 10;
    let a = apply#ls_lam1#h1(apply#ls1(Cap1 { n }), 1);
    let b = apply#ls_lam1#h2(apply#ls2(Cap2 { }), 2);
    ...
);
// #ls1、#h1 などはハッシュを略したもの
```

書き換えの後には、クロージャの生成も間接呼び出しも残らない。`apply#ls1` はキャプチャの構造体を作るだけの小さな関数なので、後段の `inline` が呼び出し側に展開する見込みである。展開されれば、`apply(|x| x + n, 1)` は `apply#ls_lam1#h1` の直接呼び出し一つになる。

**例の矢印をすべてたどる。** `|f, x| f(x)` は `|f| |x| f(x)` の略で、`apply` は「`f` を受け取って関数を返す関数」である。そのため、`apply` の型には矢印が 3 本ある。外のラムダを `apply@lam0`、内のラムダを `apply@lam1` と呼ぶ (ダンプもこう書く)。

```
apply : (I64 -s-> I64) -p-> (I64 -q-> I64);
apply = |f| |x| f(x);
//      apply@lam0  apply@lam1 (f をキャプチャする)
```

- `s`: 引数 `f` の矢印。
- `p`: `apply` 自身の矢印。`apply` を `f` に適用するときに通る。
- `q`: `apply(f)` の結果の矢印。結果を `x` に適用するときに通る。

`apply` の本体は、手順 2 の二つの規則で次のようにたどる。

1. 外のラムダを書いた場所なので、その式の矢印の変数に `apply@lam0` を入れる。シンボル `apply` の値はこの式そのものなので、両者の型の変数を一つにする。こうして `p` は `apply@lam0` を持つ。
2. 内のラムダを書いた場所なので、その式の矢印の変数に `apply@lam1` を入れる。内のラムダは外のラムダの本体なので、その型は外のラムダの結果の型と一つになり、変数は `q` になる。内のラムダは `f` をキャプチャし、`f` の集合は `s` なので、要素は `apply@lam1[f: s]` になる。
3. `f(x)` は、局所変数 `f` の型の矢印、つまり `s` を通る呼び出しである。`x` と結果は `I64` で、矢印を持たない。

たどり終えたら、型に現れる 3 つの変数をすべて一般化する。`p` と `q` は自分で書いたラムダを持つので、`apply_or_zero` の `s` と同じく、その要素を制約として持ち運ぶ。

```
apply : forall s, p ⊇ { apply@lam0 }, q ⊇ { apply@lam1[f: s] }.
        (I64 -s-> I64) -p-> (I64 -q-> I64)
```

`main` の `apply(|x| x + n, 1)` は `apply(|x| x + n)(1)` で、二つの呼び出しからなる。

1. 参照 `apply` の型では、3 つの変数を新しい変数 `s1`、`p1`、`q1` に置き換える。制約も置き換えて、`p1 ⊇ { apply@lam0 }`、`q1 ⊇ { apply@lam1[f: s1] }` になる。
2. 一つ目の呼び出しは `p1` を通る。引数 `|x| x + n` の矢印の変数 (要素は `lam1`) と `s1` を一つにするので、`s1 = { lam1 }` になる。`p1 = { apply@lam0 }` はグローバル関数自身のラムダだけなので、この呼び出しは `apply` の直接呼び出しになる。
3. 一つ目の呼び出しの結果の型は `I64 -q1-> I64` で、`q1 = { apply@lam1[f: { lam1 }] }` である。二つ目の呼び出し `(...)(1)` は `q1` を通る。集合のラムダは一つなので、この呼び出しはリフトした `apply@lam1` の直接呼び出しになる。

二つ目の `apply(|x| x * 2, 2)` では、同じ計算で `s2 = { lam2 }`、`q2 = { apply@lam1[f: { lam2 }] }` になる。`q1` と `q2` の要素は、キャプチャの集合が違うので別の要素である。そのため、リフトした `apply@lam1` も二つできる。一つは `Cap1` を、もう一つは `Cap2` をキャプチャの構造体に持つ。

手順 4 の書き換えは、この二つの要素から作る。`apply` の外のラムダはグローバル関数自身のラムダなのでリフトせず、`apply` のコピー `apply#ls1` と `apply#ls2` になる。内のラムダは `q` の要素なので、ほかのラムダと同じくリフトする。`q1` の要素 `apply@lam1[f: { lam1 }]` から `CapA1` と `apply#ls_lam1#h1` が、`q2` の要素から `CapA2` と `apply#ls_lam1#h2` ができる。

この例のほかの矢印も、同じ規則でたどる。`n`、`a`、`b` の型は `I64` で、矢印を持たない。`main` 自身の型 (`IO ()`) の矢印には、後で述べる理由で特別な要素が入る。`println` や `to_string` の中の矢印は、Std の関数の成分ごとに同じ手順で推論され、`main` から呼ばれるコピーが列挙される。

**合流する場合。** `if` で二つのラムダが合流すると、二つのアームの変数が一つになり、集合は二つのラムダを持つ。

```
let f = if c { |x| x + n } else { |x| x * 2 };   // f の矢印の変数 = { lam1, lam2 }
apply(f, 3)                                        // この呼び出しの s = { lam1, lam2 }
```

この集合の値は「`Cap1` か `Cap2` か」を持つ unbox の union で表し、呼び出しは union の `match` と、アームごとの直接呼び出しになる。クロージャで表すのに比べて、キャプチャを box に入れる確保と解放が要らず、LLVM はアームごとにラムダの本体をインライン展開できる。二つ以上のラムダを持つ集合でも要素を区別して持つのは、この表現をするためである。アームが多いと `match` のほうが間接呼び出しより遅くなりうるので、どの大きさの集合までこう表すかは測って決める。

**構造体に入る場合。** フィールドに矢印がある型は、その矢印の変数を型の一部に含む。

```
type Seg = box struct { op : (I64, I64) -> I64, data : Array I64 };
// Seg の値の型は「op の矢印の変数」を一つ持つ。Seg<t> と書く。

let s = Seg { op : |(x, y)| max(x, y), data : ... };   // t = { lam3 }
let s = if c { s.set(0, 5) } else { s };               // アームの型 Seg<t> どうしが一つになる
s.fold                                                  // fold のコピーは t = { lam3 } で決まる
```

値がフィールドを読む関数や書き換える関数を通っても、`if` で合流しても、ループの状態に乗っても、型が `Seg<t>` である限り同じ変数 `t` が付いて回る。型の単一化だけで追えるので、経路ごとの変換は要らない。`t` の集合ごとに `Seg` のコピーを作る。

`Array (I64 -> I64)` のように型引数に現れる矢印も、変数を一つ持つ。配列のすべての要素がその変数を共有し、どこかで配列に入れられるラムダはすべてその変数に入る。集合の要素はプログラムに書かれたラムダ式なので、集合は常に有限である。実行時に同じラムダ式からキャプチャの違う値がいくつできても、それらは集合の一つの要素であり、キャプチャの構造体の中身だけが違う。

```
let fs = Array::fill(n, |x| x);                   // fs : Array<u>, u ⊇ { lam5 }
let fs = fs.set(0, |x| x + k);                      // u ⊇ { lam6 }
let fs = range(0, n).fold(fs, |i, fs| fs.push(|x| x * i));  // u ⊇ { lam7 }
// u = { lam5, lam6, lam7 }。要素は n + 1 個でも、集合の要素は 3 つ
```

**関数の形でなければならない値。** 値の中には、書き換えた後も今の関数の形 (クロージャか関数ポインタ) でなければならないものがある。その場所の集合には、どのラムダかが実行時まで決まらないことを表す特別な要素 `Dynamic` を入れ、`Dynamic` を含む集合の値は今と同じ関数の形で表す。理由は二通りある。

- **どのラムダかを知らないコードが呼ぶ。** `Destructor` の解放関数は、値を解放するランタイムのコードが関数ポインタを通して呼ぶ。
- **コンパイラが生成するコードが、関数として呼ぶ。** エントリポイントの IO 値は生成した C の `main` (`build_main_function`) が、export された値は生成した C の関数 (`ExportStatement::implement`) が、それぞれグローバルなシンボルとして読み、関数として適用する。どのシンボルかは分かっているので、たいていは `uncurry` の後に関数ポインタを通らない直接呼び出しになる。それでも値は関数の形でなければならず、キャプチャの構造体では適用できない。生成コードは値を、C の関数が受け取る引数の数だけ適用する。そのために関数の形でなければならないのは、適用の結果として次々に現れる矢印のすべてである。たとえば export された `f : I64 -> I64 -> I64` は `I64 -> (I64 -> I64)` であり、2 本の矢印のどちらにも `Dynamic` が付く。この 2 本が関数の形であるから、`uncurry` が 2 引数の `f#func2` を作れるので、生成コードはそれを 1 回だけ呼ぶ。このパスの位置では `unwrap_newtype` が済んでいて、`IO a` は `IOState -> (IOState, a)` という関数の型なので、エントリの `IO ()` ではその矢印に付く。export の型は引数と結果が C の数値型に限られるので、型に現れる矢印は生成コードが適用するものだけであり、型のすべての矢印に `Dynamic` を付ければよい。

`Dynamic` が入る場所の一覧は「推論の規則」の節にある。

**自分を含む集合。** 集合の要素はラムダだけでなく、そのラムダがキャプチャする値の型に付いた集合も合わせて持つ。キャプチャの構造体の形は、それで決まるからである。構造体の場合と違って、この集合は型には付かない。関数の型 `I64 -> I64` はキャプチャの型を書かず、キャプチャの違うラムダも同じ型になるので、キャプチャの集合は要素の側に持たせる。(実際には、ラムダの引数と本体の中の式の型に付いた集合も持つ。リフトした関数の本体の形も、それで決まるからである。) たとえば関数をキャプチャするラムダ `lam4 = |x| f(x) + 1` は、`f` の集合が `{ lam1 }` のとき `lam4[f: { lam1 }]` という要素になる。

このとき、ラムダが自分と同じ集合のクロージャをキャプチャすることがある。関数の配列を一つの関数に合成する、次のようなコードである。

```
let g = fs.to_iter.fold(|x| x, |f, acc| |x| f(acc(x)));
//                      lam8          lam9 (f と acc をキャプチャする)
```

`fold` の状態 `acc` には、初めに `lam8` が入り、その後は各回の結果の `lam9` が入る。状態の集合を `s` とし、`fs` の要素の集合を `u` とする。`lam9` がキャプチャする `acc` は状態なので、その集合は `s` 自身である。

```
s = { lam8, lam9[f: u, acc: s] }
```

右辺に `s` が現れる。これを展開して書き下しても終わらない。

```
s = { lam8, lam9[f: u, acc: { lam8, lam9[f: u, acc: { lam8, lam9[...] }] }] }
```

実行時には、`lam9` の値が `lam9` の値をキャプチャし、それがまた `lam9` の値をキャプチャする連鎖が、`fs` の長さだけ続く。連鎖の長さは値の側にあり、集合の要素はどれだけ長くても `lam8` と `lam9` の 2 つである。`List` のバリアントは `nil` と `cons` の 2 つだが、リストはいくらでも長くできるのと同じである。

集合の要素は有限だが、要素が持つ集合をたどると無限に続く木になる。実装はこの木を展開せず、`acc: s` のところを `s` 自身への参照として持つ。グラフの辺が自分に戻る形である。型理論ではこの形を mu と書き (`s = mu s. { lam8, lam9[f: u, acc: s] }`)、Fix の再帰型 `type List a = box union { nil : (), cons : (a, List a) }` が自分の名前を中に書くのと同じことである。

同じ集合が、別の書き方で現れることがある。`s` を 1 段展開した `{ lam8, lam9[f: u, acc: { lam8, lam9[f: u, acc: s] }] }` も、展開すれば同じ木になる。シンボルのコピーは集合をキーに作るので、展開した木が等しい集合は一つとして扱わなければならない。そうしなければ、同じコピーがいくつもできる。

値の表現にも影響がある。`s` の値を union で表すと、`lam9` のアームのキャプチャの構造体に、その union 自身が入る。unbox の union では大きさが無限になるので、`List` と同じくどこかに box を挟まなければならない。このような集合の値は、今のクロージャ (box に入ったキャプチャと関数ポインタ) のまま残す。連鎖の段数だけの確保はどの表現でも残り、box を挟む表現で減らせるのは間接呼び出しと一部の確保だけだからである。

### 段階 1 でできているもの

パス `src/optimization/lambda_set/` は、上の手順の 1 から 3 までを行い、プログラムを変えずに結果をダンプに書く。この文書が決めるのは、手順 4 の書き換えである。

- **注釈。** 推論の前に、型に変数を付ける段である。Fix の型の中で lambda set が付く場所を、スロット (`AType::slots`) と呼ぶ。矢印はスロットを一つ持つ。構造体、union、配列の型コンストラクタは、宣言のフィールドの型に現れるスロットを持ち、これを型コンストラクタの `own_slots` と呼ぶ。数え方は、フィールドの型を前から読み、矢印のスロットと、型引数をすべて与えて書かれた別の型コンストラクタの `own_slots` を数える。型変数は何も足さない。互いに参照し合う型のグループの中では、グループで共有するスロットを指す。たとえば `type Outer = struct { inner : Inner, fs : Array (I64 -> I64) }` の `Outer` は、`Inner` の `own_slots` と、`I64 -> I64` の矢印のスロットを持つ。型を使う側が与える型引数の中の矢印 (`Seg m` を `Seg (I64 -> I64)` として使ったときの `I64 -> I64`) は、型引数の側のスロットである。式のノードごとに、型のスロットの数だけ lambda set の変数 (`SetVar`) を置く。
- **推論。** 成分ごとに、変数を union-find で一つにし、ラムダを集合に入れる。成分のシンボルの型に現れる変数を一般化する。以下、これを成分の一般化した変数と呼ぶ。参照が受け取る形 (`Scheme`) では、展開した木が等しいクラスを一つにまとめ、一般化した変数に依存しないクラスは、写しを作らずにすべての参照で共有する。こうしないと、下のシンボルを二度参照するシンボルの鎖で、クラスの数が段ごとに倍になる (LSS の論文の 6 節が述べる指数的な大きさ)。
- **特殊化。** エントリポイントの IO 値から参照をたどり、成分のコピーを列挙する。コピー (`Instance`) は、成分の一般化した変数それぞれに具体的な集合 (`SetId`) を与えたものである。`SetStore` は、等しい具体的な集合を一つにまとめて持つ。自分を含む集合 (mu) も、展開した木が等しければ一つにまとまる。
- **Dynamic。** 関数の形でなければならない場所の集合は、要素 `Dynamic` を持つ。

全テストとコーパスがこの推論を通る。結果の数字は付録「段階 1 の結果」にある。

### 推論の規則

式の形ごとの規則は次のとおり。「一つにする」は、二つの `AType` の `slots` を同じ位置どうし union-find で一つにすることである。このパスの位置のプログラムは型検査を通っているので、注釈を付ける前の Fix の型は、一つにすべき二か所でもう等しく、スロットの並びもそろう。

- **局所変数。** 束縛したところの `AType` を使う。
- **グローバルなシンボル。** 成分の外のシンボルなら、その型の一般化した変数を新しい変数に置き換え、制約も写す。同じ成分のシンボルなら、その `AType` をそのまま使う。
- **`Lam`。** 型の矢印のスロットに、そのラムダを要素として入れる。引数は型の定義域と、本体は値域と一つにする。
- **`App`。** 関数の型の定義域を引数と、値域を式の型と一つにする。
- **`Let`、`Match`。** 束縛する値をパターンと一つにする。構造体のパターンは、型コンストラクタのフィールドの型から作ったフィールドの `AType` を、部分パターンと一つにする。アームの値は式の型と一つにする。
- **`If`。** 二つのアームを式の型と一つにする。
- **`MakeStruct`。** フィールドの `AType` を、それぞれの値と一つにする。
- **`ArrayLit`。** 要素を、配列の型の要素と一つにする。
- **`TyAnno`、`Eval`。** 値を式の型と一つにする。
- **`FFICall`。** 引数と結果は C の型で、スロットを持たない。
- **組み込み関数。** `BuiltinOp::lambda_set_flow` が、オペランドの `AType` と結果の `AType` のあいだの規則を述べる。既定は、オペランドと結果のすべてのスロットに `Dynamic` を入れる規則である。既定はいつでも正しく、規則を述べていない組み込み関数は、性能を失うだけで正しさを失わない。規則を述べるのは、値を形を保って運ぶ組み込み関数である。配列の操作は要素の型どうしを、構造体と union の操作はフィールドの `AType` をオペランドや結果と、値をそのまま通す操作は通す値と結果を、それぞれ一つにする。

`Dynamic` が入るのは次の場所である。

- エントリポイントの IO 値 (`Program::entry_io_value`) と、export された値 (`Program::export_statements`) の型
- `Std::FFI::Destructor` のフィールド。値を解放するランタイムのコードが呼ぶ。
- 規則を述べていない組み込み関数のオペランドと結果。規則が「渡された関数を呼ぶ」と述べるオペランドも含む。
- 引数を取らずに型引数として渡された型コンストラクタが、フィールドの型に持ち込むスロット (`type [f : * -> *] Foo f = box struct { data : f () }` の `Foo IO` の `IO`)。フィールド `data : f ()` を `Foo IO` で読むと `IO ()` になる。このうち `IO` の定義から来る矢印は、読むたびに新しい変数を置いて `Dynamic` を入れる。
- 本体が自分のキャプチャを丸ごと (`CAP_NAME`) 読むラムダの矢印。キャプチャを丸ごと持つのはクロージャのオブジェクトだけである。

`Dynamic` を含む集合は、ほかの要素も持っていてよい。そのような集合の値は、すべて関数の形で表す。

## 全体の流れ

新しいパスは推論の後に、プログラムを書き換える段 (以下、書き換え) を持ち、今のクロージャ最適化のパスの前で動く。

```
inline, inline_local
lambda_set                  推論 -> 特殊化 -> 書き換え -> move_bodies_into_callers
split_struct_args           (段階 4 まで残す)
inline
collapse_constructions
closure_specialization      (段階 4 まで残す)
decapture_scope_functions
uncurry ...
```

- この位置では単相化が済み、すべてのシンボル (`Program::symbols`) が具体的な型を持ち、すべての式のノードに型が付いている。式はカリー化された形で、`Lam` の引数と `App` の引数は一つずつである。`inline` がコンビネータを利用者のコードに展開した後なので、ラムダの数が少なく、集合も小さい。RC IR では、クロージャはすでに関数ポインタと `#DynamicObject` の組で、構造体の型のレイアウトも決まっているので、型のコピーを作るには遅い。
- 段階 2 と 3 の間、`split_struct_args` から `closure_specialization` までのパスは新しいパスの後ろで動き続ける。新しいパスがクロージャのまま残した値は、これらが今までどおり扱う。どの段階でも、今の `closure_specialization` が直接呼び出しにする呼び出しは、直接呼び出しのまま残る。
- 段階 4 で、これらのパスを止めた形を測り、要らないものを消す。
- `inline` は、application spine (入れ子の適用を関数の側へ根からたどった道) の根のグローバル関数を、spine 上の引数がその関数の引数をすべて渡すところでだけ展開する。一部の引数だけを渡した適用は関数のクロージャを作る式で、そこに本体を置いても呼び出しは減らず、同じクロージャをラムダとして作ることになる。後段の `inline` がリフトした関数を `lam(cap)` に置くと、リフトする前のラムダに戻ってしまう。
- 新しいパスは `Configuration::enable_closure_specialization` が真のとき (`Max` 以上) に動く。旧と新を切り替える設定は作らない。比べる相手は main のバイナリである。

## 推論が書き換えに渡すもの

書き換えは、シンボルのコピーごとに式を一度たどり、ノードの型を書き換える。そのために、推論は成分ごとにノードの記録を残し、特殊化はコピーごとに成分の変数の集合を残す。

```rust
/// 推論がノードに記録すること。
pub struct NodeType {
    pub ty: AType,             // 注釈を付けた型。スロットはどれも solver の代表
    pub names: Vec<NameRef>,   // 変数ならその名前、組み込み関数ならオペランドが指すもの
}

/// 成分のコピーの一つ。
pub struct Instance {
    pub component: usize,
    pub args: Vec<SetId>,      // 成分のパラメータ (`Component::params`) ごとの集合
    pub var_sets: Vec<SetId>,  // 成分の変数 (`Component::vars`) ごとの集合
}
```

- `Component::node_types` は、成分のシンボルの式ごとに、推論が注釈を付けた順 (式の前順) に `NodeType` を並べる。書き換えは同じ前順でたどって読み、最後に読んだ数が並べた数と等しいことを assert する。
- `Instance::var_sets` は、`specialize` がコピーごとに `CopyEquations` で集め、`SetStore::intern` で解く連立方程式の解である。変数の位置は `Component::var_index` で引く。
- `SetStore` は、同じ木に展開される集合を一つだけ持つ。自分を含む集合の連立方程式は、その強連結成分と、成分から到達できる手持ちの循環する集合をノードにして、分割を細かくする。各回の分割の番号をシグネチャの順で振るので、番号は集合の番号の付き方によらず木だけで決まる。安定した分割の表 (`CycleClasses`) と集合の番号の組が、その集合の正準形で、手持ちの循環する集合をこの正準形で引く。分割は `partition::canonical_classes` が行い、推論がスキームの等しいクラスをまとめるのも、表現のクラスを分けるのも、同じ関数で行う。

## シンボルのコピー

成分のコピーは、成分の各シンボルのコピーになる。コピーの `Symbol` は、元のシンボルと同じ `generic_name` を持ち、`ty` と `expr` は書き換えたものになる。

- コピーが一つしか要らない成分では、シンボルの名前をそのまま使う。
- コピーは、成分の一般化した変数に与えた集合の表現で区別する。クロージャで表す集合は、どのラムダを持つかによらず一つのキー「クロージャ」に置き換える。呼ばれる側のコピーにとって、クロージャの値の中のラムダは区別できず、ラムダのキャプチャの型が効くのはそのラムダを書いた側だけだからである。表現が同じになるコピーは一つにまとまる。
- コピーが二つ以上要る成分では、コピーの名前を `<シンボル>#ls<ハッシュ>` にする。ハッシュは、コピーが成分の一般化した変数に与えた集合の表現を並べた文字列から作る。クロージャで表す集合は `c` と書き、キャプチャの構造体で表す集合はそのクラスのハッシュで書く。クラスのハッシュは、クラスを書いた文字列から作る。その文字列では、ラムダを「それを書いたシンボルの名前と、その本体の中での順番」で書き、ラムダのインタフェースの集合 (「表現の決め方」の節) の表現を括弧の中に並べ、クラスの循環は後方参照で書く。`SetId` は列挙の順で決まる番号なので、ハッシュの材料には使わない。コンパイルの結果をキャッシュするので、同じプログラムからは同じ名前ができるようにする。
- エントリポイントの IO 値と export された値は、コピーせずに書き換える。

**Examples**

```
Main::apply_twice#a1b2   (成分が一通り)   -> Main::apply_twice#a1b2
Main::apply_twice#a1b2   (成分が二通り)   -> Main::apply_twice#a1b2#ls5e0c1d, Main::apply_twice#a1b2#ls93ab07
```

## 型のコピー

`own_slots` を持つ型コンストラクタ (フィールドの型にスロットが現れる構造体や union) は、`own_slots` に与えられた集合ごとにコピーする。

- コピーは、型コンストラクタと、`own_slots` の集合の表現の並びごとに一つ作る。`own_slots` の集合がどれもクロージャで表されるなら、元の型コンストラクタを使う。
- コピーは元の型変数をそのまま持つ。名前は `<型コンストラクタ>#ls<ハッシュ>` で、ハッシュはシンボルのコピーと同じ作り方をする。`TypeEnv::add_tycons` で型環境に足す。
- フィールドの型は、`own_slots` の集合で書き換える。型引数の中身は、型を適用した側で書き換えられる。
- 互いに参照し合う型コンストラクタのグループは `own_slots` を共有するので、グループの全員を同じ集合でまとめてコピーする。フィールドを一つ抜き出した構造体の型 (`TyConInfo::punched_from` を持つ型) は、元の構造体と同じ集合でコピーする。
- getter、setter、`mod_`、`punch`、`plug_in` は、本体が組み込み関数かパターンのふつうのシンボルで、ほかのシンボルと同じ規則でコピーされる。
- 名前で型を見分けている箇所 (`Std::Array`、`Std::FFI::Destructor`、タプル、func type `#Func{n}`) の型は、コピーの対象にならない。`own_slots` を持たないか、スロットの集合がいつも `Dynamic` を含むからである (付録「名前で見分ける箇所」)。

**Examples**

```
type Seg m = box struct { op : (m, m) -> m, data : Array m };   // スロットを一つ持つ

// op の値が |(x, y)| max(x, y) だけになるコピー
type Seg#ls7d21 m = box struct { op : #LsCap@main#ls_lam0, data : Array m };
```

## ラムダリフティング

ラムダは、書き換えた後にグローバル関数になる。

- リフトする単位は、要素のクラス (`LamClass`) である。要素 `Elem::Lam(lam, args)` の `args` は、ラムダの引数・本体・キャプチャの型に付いた変数に与えた具体的な集合の列で、クラスは、インタフェースの集合を同じに表す要素をまとめたものである (「表現の決め方」の節)。
- リフトした関数は `|cap| |x| body` の形で、名前は `<シンボル>#ls_lam<番号>` である。同じラムダのクラスが二つ以上あれば、シンボルのコピーと同じく、クラスのハッシュ `#<ハッシュ>` を足す。
- キャプチャの構造体は `CaptureStruct` で作る。接頭辞は新しく `#LsCap` を与える。フィールドの型は、クラスを代表する要素を作るコピー (`LamClass::instance`) の集合で書き換えたキャプチャの型である。「与えられた集合のもとで型を書き換える」処理は、型のスロットを読む順にたどる `SlotLayout::fold_slots` の上に書く。型のコピーのフィールドは、宣言された型を読む規則 (`SlotLayout::declared_own_range`) を、推論がフィールドを読む `walk_declared` と共有して書き換える。キャプチャの構造体は、「クラスごとに作る構造体の型」として、型のコピーと同じ扱いになる。
- グローバル関数自身のラムダ (`g = |a| ...` の一番外のラムダ) はキャプチャを持たないので、リフトせずにシンボル `g` をそのまま使う。グローバル関数を呼ばずに値として使う式 `g` は、このラムダの値を作る式である。
- `g = |a| |b| ...` の内側のラムダは、ほかのラムダと同じくリフトする。全部の引数を渡す呼び出し `g(a, b)` は、`g` のコピーの呼び出しで内のラムダのキャプチャの構造体を作り、それを内のラムダの直接呼び出しに渡す形になる。`g` のコピーは構造体を作るだけなので、後段の `inline` が展開する見込みである。一部の引数だけを渡した値 `g(a)` も、キャプチャの構造体になる。

## 値と呼び出しの書き換え方

集合ごとに、その集合をどう表すかを一度だけ決める。表現は三通りある。

| 集合の表現 | 値の型 | ラムダの値を作る式 | 呼び出し `f(x)` |
| --- | --- | --- | --- |
| 要素が一つの同値類にまとまる | その同値類のキャプチャの構造体 | キャプチャの構造体の構築 | 直接呼び出し `lam(f)(x)` |
| 二つ以上の同値類にまたがる | キャプチャをペイロードに持つ unbox の union | union の値の構築 | `f` の `match` と、アームごとの直接呼び出し |
| クロージャ | 今の関数の型 (引数と結果の型は書き換える) | リフトした関数をキャプチャに部分適用した `lam(cap)` | 今の間接呼び出し |

クロージャの形 `lam(cap)` は、今の `closure_specialization` が作るクロージャと同じ形で、後段の `decapture_scope_functions` と `uncurry` がそのまま読む。

- リフトした関数は、要素のクラスごとに一つ作る。クラスの決め方は次の「表現の決め方」の節にある。キャプチャの構造体で表す集合の要素と、クロージャで表す集合の要素が同じクラスに入れば、二つはリフトした関数とキャプチャの構造体を共有する。
- 本体が自分のキャプチャを丸ごと (`CAP_NAME`) 読むラムダは、リフトせずに書かれた場所に残す。キャプチャを丸ごと持つのはクロージャのオブジェクトだけだからである。このラムダの集合は `Dynamic` を含むので、クロージャで表される。

### 表現の決め方

`represent` は、集合の表現を三つの手順で決める。

1. キャプチャの構造体でも union でも表せない集合を、先にクロージャに決める。空の集合と、`Dynamic` を含む集合と、レイアウトが循環する集合である。レイアウトの循環は、ラムダだけを要素に持つ集合を、要素のキャプチャが unbox のフィールドだけをたどって持つ関数のスロット (`Lambda::held_in_place`) でつないだグラフの循環として見つける。段階 3 の unbox の union もキャプチャを box を介さずに値の中に直接持つので、二つ以上のラムダの集合もこのグラフに入れる。
2. 残りの集合と要素を、書き換えた後のコードが同じになるもの同士の同値類に分ける (`partition::canonical_classes`)。二つの要素は、同じラムダを指し、ラムダのインタフェースの集合が順に同じ同値類にあるとき、同じ同値類に入る。二つの集合は、要素が属する同値類の集まりが同じとき、同じ同値類に入る。手順 1 の集合は、何を持つかによらず互いに同じ同値類にする。クロージャの型は、中のラムダによらないからである。
3. 要素が一つの同値類にまとまる集合を、その同値類のキャプチャの構造体で表す。要素が二つ以上の同値類にまたがる集合は、同値類ごとのキャプチャの構造体を variant に持つ unbox の union で表す。手順 2 で等しい集合は、同じキャプチャの構造体か同じ union を共有する。union のタグが区別できる variant の数 (`MAX_UNION_VARIANTS`、256) より多い同値類にまたがる集合は、クロージャに決めて、手順 2 からやり直す。クロージャに決めた集合は手順 2 で一つの同値類にまとめるので、分割が変わるからである。クロージャに決める集合は増える一方なので、やり直しは終わる。

ラムダのインタフェースの集合は、ラムダの値を作る側と、リフトした関数の両方が読む集合である。ラムダの引数と結果の型の集合と、キャプチャした値の型の集合がこれにあたり、推論が `Lambda::interface` に記録する。ラムダ自身の集合は入れない。グローバル関数自身のラムダは、シンボルのコピーを決める集合 (`Component::body_params`) をインタフェースとする。インタフェースに入らない集合、つまりリフトした関数の本体の中だけで使う集合は、クラスの要素ごとに違ってもよい。本体は、クラスを代表する要素を作るコピー (`LamClass::instance`) の集合で一度だけ書き換えるので、本体の中で型がそろう。シンボルのコピーを、本体が依存する引数の表現でまとめてよいのと同じ理由である。クラスのキーは、ラムダと、インタフェースの集合の表現の並びである。

インタフェースにキャプチャの集合を入れるのは、キャプチャの集合の表現が、ラムダの引数の表現からは決まらないからである。次の `k` が返すラムダは `g` をキャプチャする。

```
k = |f1, f2| (
    let g = if c { mk(f1) } else { mk(f2) };   // mk = |f| |x| f(x) + 1
    |y| g(y)
);
```

`f1` と `f2` に同じ集合 `S` が来るコピーでは、`g` の集合は `{ mk@lam[S] }` で、要素が一つである。違う集合 `S1` と `S2` が来るコピーでは `{ mk@lam[S1], mk@lam[S2] }` で、要素が二つになる。`S1` と `S2` がどちらもクロージャで表されるなら、二つのコピーは `f1` と `f2` を同じに表すが、`g` の表現は違う。`g` の集合が自分を含むかどうかも、同じように引数の表現からは決まらない。

手順 2 で要素を同値類で数えるのは、同値類が同じ要素は、キャプチャの構造体もリフトした関数も同じだからである。上の `S1` と `S2` が同じ同値類のキャプチャの構造体で表されるとき、`mk@lam[S1]` と `mk@lam[S2]` も同じ同値類になり、`g` の集合はその組のキャプチャの構造体で表せる。

union の variant は、手順 2 の分割が同値類の要素を並べた順に置く。この順は、集合の番号の付き方によらず木だけで決まる。union の名前は `#LsUnion@<ハッシュ>` で、ハッシュは variant のクラスの文字列を順に並べた文字列から作る。クラスと union は互いを含みうるので、両方を一つのグラフのノードにして、強連結成分ごとに後方参照で書く (`name_classes_and_unions`)。

union の値の呼び出し `f(x)` は、`f` と `x` をこの順に `let` に束縛し、`f` の `match` のアームごとに、その variant のクラスの関数を直接呼ぶ。束縛するのは、`f` と `x` をそれぞれ一度だけ、呼び出しが評価する順に評価するためである。

そのほかの書き換えは次のとおり。

- `MakeStruct` と構造体のパターンが持つ型コンストラクタを、コピーの型コンストラクタに替える。
- 式とパターンのすべてのノードの型と、シンボルの型を、書き換えた型に替える。組み込み関数はオペランドの型をノードの型から読むので、式はそのままでよい。
- グローバルなシンボルの参照を、参照先のコピーの名前に替える。

どの表現も、今の型 (構造体、union、box、クロージャ) で書けるので、参照カウントは今の RC IR がそのまま扱う。

書き換えの最後に `move_bodies_into_callers` を使い、ただ一か所から呼ばれるリフトした関数の本体を、その呼び出しに置く。

## 段階ごとに書き換える集合

集合の値の表現は、要素と、書き換えた型のメモリレイアウトで決まる。キャプチャの型が unbox のフィールドだけをたどって同じ集合の値に戻る集合を、レイアウトが循環する集合と呼ぶ。`Program::validate_layouts` が退ける形と同じで、unbox のままでは大きさが決まらないので、この集合の値はクロージャのまま残す。段階が進むごとに、値をクロージャのまま残す集合が減る。

| 段階 | 値をクロージャのまま残す集合 | 値の表現を新しく書き換える集合 |
| --- | --- | --- |
| 2 | `Dynamic` を含む集合、二つ以上の同値類にまたがる集合、レイアウトが循環する集合 | 要素が一つの同値類にまとまる集合 (「表現の決め方」の手順 2 の同値類) |
| 3 | `Dynamic` を含む集合、レイアウトが循環する集合、`MAX_UNION_VARIANTS` より多い同値類にまたがる集合 | 二つ以上の同値類にまたがる集合 (unbox の union) |
| 4 | 後ろの `split_struct_args` から `closure_specialization` までを止めて測り、要らないものを消す | |

- 再帰する関数の集合は mu だが、グローバル関数のラムダはキャプチャを持たないのでレイアウトは循環しない。段階 2 で書き換えられる。
- 集合の値をクロージャのまま残しても、推論の結果は変えない。表現を決める段だけが、その集合を `Dynamic` を含む集合と同じに扱う。

## 段階 4 で行うこと

- `uncurry` を書き直し、lambda set のパスの前へ移す。書き直した `uncurry` は、何度走っても同じ結果になる。uncurried function をシンボルの同一性で追い、まだ uncurried function を持たないシンボルにだけ作る。段階 2 と 3 では、`uncurry` を今の位置 (lambda set のパスより後ろ) に置いたままにする。
- 汎用のパス (`pull_let`、`unique_local_names`、名前の付け替え、`find_usage_of_name`、`collapse_constructions`) に、複数の引数を持つ `App` と `Lam` を扱わせる。lambda set のパスにも、func type と複数の引数を扱わせる。
- `split_struct_args` から `closure_specialization` までのパスを止めた形を測り、要らないものを消す。`split_struct_args` は無くす見込みである。
- 段階 2 の計測で命令数が増えたケースを、段階 4 の形で測り直す (付録「段階 2 の LangArena の計測」)。原因の分かっているものは次のとおり。
  - random_state (+105%)。State モナドの `fold_m` のループの本体が `bind` の続きのラムダになり、「処理してから調べる」形のループになる。最初の 1 回の処理がループの外に出て、乱数を作る関数の呼び出しが 2 か所になり、LLVM がそれを展開しない。main では `uncurry` が `fold_m(s, f, it)(state)` を一つの関数にまとめ、「調べてから処理する」形になる。`uncurry` を前へ移した後に確かめる。段階 3 の後の命令数は 367,908,427 で、main (367,940,476) と同じ水準に戻った。段階 4 でも保たれるかを確かめる。
  - iter_flatten (+23%)。main では `_inner_until` が別の関数として残り、内側の配列を回すループが締まったループになる。段階 2 ではすべてが一つのループに展開され、要素ごとに `flatten` の外側の状態を調べ直す。LLVM が入れ子のループを取り戻せない形で、原因の段は特定していない。
  - Maze::BFS (+13%) と Compress::BWTEncode (+15%)。RC IR の borrow の振り分け (`borrow.rs` の `routing_is_safe`) は、末尾の位置で own の値を一つでも渡す呼び出しを borrow 版へ送らないので、borrow 版のループは 1 周目だけ回って own 版へ移る。段階 2 で直接呼び出しが増え、剥がれた 1 周目と own 版の両方が内側のループの borrow 版を呼ぶので、LLVM がそれを展開しない。main にもある振り分けの弱点で、引数の位置ごとに判定する形に直す (lambda set とは別の変更にする)。
  - CLBG::Spectralnorm (+8.8%、AVX-512 のない機械だけ) と cp_dsegtree (+9.5%)。Fix の IR は良くなっている。前者は依存を断つ `vxorps` が増えたもの (サイクルは変わらない)、後者は LLVM が `set` のループの範囲検査を一つ消せなくなったもの。
- 段階 3 の終わりで落ちているテストを通す。どちらの族も、全部の引数を渡す呼び出しが、段階 2 では内側のラムダの連鎖への呼び出しになるために起きる。`uncurry` を前へ移すと、その連鎖ができなくなる。
  - `test_a_round_of_a_specialized_combinator_builds_no_closure`。グローバル関数の先頭の連鎖 `|s| |f| let io = f(s); |st| ...` を分けてリフトすると、`loop_m` の `io` が周の終わりで作られて次の周の頭で使われ、作る場所と使う場所のあいだに再帰呼び出しが挟まる。今の位置の `uncurry` は eta 展開で `let io = f(s)` を `|st|` の内側へ移すので、main では `io` を作る式と使う式が同じ式に入る。
  - `test_evaluation_order` の 2 本。3 引数の関数を呼ぶと、3 番目の引数が先に評価される。リフトした関数を `inline` が展開した後、`let_elimination` の規則 2-c が、2 番目の引数を含む式を後ろへ動かす。評価順は未規定で、寿命は延びない。

## 各段階の終え方

1. 全テスト (`cargo test --release --no-fail-fast`) を通す。
2. speedtest のコーパスを memcheck に通し、メモリリークと二重解放がないことを見る。
3. speedtest を `--langarena` で測り、全ケースの命令数を main と比べる。段階 4 の終わりでは、命令数が main より増えていないことを全ケースで確かめる。段階 2 と 3 では、増えたケースの原因を調べて記録し、後で直すものを「段階 4 で行うこと」に足す。増えたケースは、`--cu-size inf` でコンパイル単位の分け方の影響を除いて読む。効くはずのケースとして、cp_dsegtree、cp_ldsegtree、cp_ldsegtree_fold_act、イテレータの連鎖、`Calculator::Interpreter`、モナドのスタック (`StateT` を `IO` に重ねたもの) を個別に見る。
4. `code-review` と `bug-hunt` を通し、main への PR を一つ出す。merge はユーザが行う。

段階 1 (推論とダンプ) も、この手順で一つの PR にする。段階 1 の推論は、develop mode か `--emit-symbols` のときだけ走るので、利用者のビルドのバイナリもコンパイル時間も変えない。推論が書き換えに使われる段階 2 から、PR にコンパイル時間の増分も載せる。予算がなくなるので、段階 4 ではコピーの数とコンパイル時間を LangArena で測り、今のやり方と比べる。比べるコピーの数は、「シンボルのコピー」の節の区別 (クロージャで表す集合を一つのキーにまとめる) で数えたものである。

## 実装しながら決めること

- コピーの名前に使うハッシュ関数と、その長さ
- 推論の時間の伸び方。下を二度参照するグローバル値を N 段つないだ鎖で、推論の時間は N = 200 で 0.12 秒、400 で 0.89 秒、800 で 7.2 秒と、N の 3 乗で伸びる。ほとんどは `merge_equal_classes` である。c_i の値の集合は深さ i の木なので、c_i のスキームは下の成分から受け継いだ i 個のクラスを持ち、`merge_equal_classes` はそれを成分ごとに最初から分割し直す。分割は鎖の深さの回数だけ回り、1 回に O(i) かかる。直し方は二つある。パラメータに依らないクラス (`shared`) の要素をスキームに展開しない形 (`instantiate` はこの要素を読まない) と、`SetStore` と同じく強連結成分ごとに正準形で引く形である。前者は、前の成分の変数が後の成分で変わらないことに依るので、その不変条件を確かめてから入れる。LangArena 全体の推論は 0.37 秒なので、段階 4 のコンパイル時間の作業で直す。
- コピーが多いプログラムで、後段のパスの時間が伸びる。再帰する関数 `app` を、毎回違うラムダを渡して 1200 か所で呼ぶプログラムで、最適化にかかる時間は統合ブランチで 339 秒 (`uncurry` と `inline_local` が大半)、段階 2 で 619 秒 (`inline` と `collapse_constructions` が大半) である。300 か所では両方とも 14 秒ほどで、どちらもコピーの数の 2 乗に近く伸びる。lambda set のパス自身は 1200 か所で 1.4 秒である。段階 4 で、後段のパスのどこで 2 乗になるかを測って直す。
- 2 種類のラムダを `if` で選ぶ値を K 段つないだ鎖 (`f_i = if c_i { |x| f_{i-1}(x) + i } else { |x| f_{i-1}(x) * 2 }`) で、`fix build` の命令数が、統合ブランチの 20.5G に対して段階 2 で 33.4G (K = 200)、70.5G に対して 236.5G (K = 400) になる。ほとんどは LLVM の `ScheduleDAGTopologicalSort` である。各段のラムダがリフトした関数になり、シンボルが 13 個から 408 個に、LLVM IR が 2.9MB から 8.3MB になる。段階 4 で、後段のパスのどれが鎖を一つの関数に戻さないかを調べる。
- 関数を値に持つグローバル値 (関数の配列など) をコピーすると、初期化式がコピーごとに評価される。Document の `eval` の節は、グローバル値の初期化式が何回評価されるかを保証しないので、仕様の範囲内である。それでも、初期化の仕事と記憶域はコピーの数だけ要る。段階 4 で、コピーされるグローバル値の数と初期化の重さをコーパスで数え、コピーの代わりに一つの値を共有させる必要があるかを決める。
- `NodeTypes` を作るときと読むときのたどり方を一つの関数に共有する方法
- 組み込み関数の規則をどこまで書くか。`Dynamic` が入った理由をダンプで見て、効くものから書く。`defunctionalize_fix` が残した `Std::fix` は候補の一つである。今は組み込み関数 `fix` が規則を持たず、自分のキャプチャを丸ごと読むので、渡された関数と結果の集合が `Dynamic` を含む。「`f` の引数には自分自身が入る」という規則を書き、自分のキャプチャの読みをキャプチャの構造体に書き換えれば、`Std::fix` も特殊化できる。

場当たりの対処でしか越えられない障害に当たったときは、実装の前に候補とそれぞれのコストを挙げて判断を仰ぐ。

## 付録: 退けた案

- **段階 2 で今のパスを消す。** 新しいパスが残したクロージャを扱うものがなくなり、段階 3 が終わるまで、二つ以上のラムダの集合の呼び出しが、今より遅くなりうる。
- **レイアウトが循環する集合の値を、box に入れた union で表す。** union ごと box に入れる表現と、循環を作るフィールドだけを box に入れる表現がある。前者は何もキャプチャしない要素の値でも確保が要り、後者は box を置く場所を決める規則が要る。どちらも、連鎖の段数だけの確保は残る。コーパスでこの種の集合が速さに効いていると分かったら、改めて設計する。
- **グローバル関数の先頭のラムダの連鎖 (`|f| |x| ...`) をまとめてグローバル関数自身のラムダとして扱い、リフトしない。** 全部の引数を渡す呼び出しは `uncurry` の作る `#func2` で一つの呼び出しになるが、一部の引数だけを渡した値 (`map(add(k))` の `add(k)`) がクロージャのまま残り、それを受け取る関数のコピーを特殊化できない。グローバル関数の連鎖だけを特別に扱う規則も要る。
- **旧と新を切り替える設定を作る。** 一つのバイナリに二つの実装を持たせると、比べる相手の挙動が変わりうる。main のバイナリとの比較で足りる。
- **ラムダを成分のコピーごとにリフトする。** ラムダが依存しない変数の集合の違いだけで、同じ本体のグローバル関数ができる。
- **コピーを集合そのもので区別する。** クロージャで表す集合 (`Dynamic` を含む集合と、段階 2 では二つ以上のラムダの集合) が違うだけのコピーは、名前だけが違う同じ関数になる。
- **ノードの注釈を付けた型を `Arc<ExprNode>` のポインタで引く。** 同じ部分木が二か所で共有されていると、一つのキーに二つの型が要る。
- **名前の付いた型のコピーの代わりに、型引数を足す。** `DSegtree` の定義に型引数 `f` を足して `_op : f` とし、使う場所で `f` にキャプチャの構造体などの型を渡す形 (Rust の `DSegtree<F>` と同じ形) である。型の定義は一つのままで済むが、引数を取らずに型引数として渡された型コンストラクタ (`Foo IO` の `IO`) の位置の集合を表せない。そこでは `f` に、引数を待つ型を渡す必要がある。型のコピーは、引数を待つ型のコピーも同じ仕組みで作れるので、すべての場合を一つの仕組みで扱える。
- **推論に型検査の単一化を使う。** このパスの位置のプログラムは型検査を通っているので、二つの注釈付きの型の単一化は、同じ位置にあるスロットの変数どうしを一つにすることに尽き、union-find で書ける。

## 付録: LSS の論文の要約

William Brandon, Benjamin Driscoll, Frank Dai, Wilson Berkow, Mae Milano. *Better Defunctionalization through Lambda Set Specialization.* Proc. ACM Program. Lang. 7, PLDI, Article 146 (2023). https://doi.org/10.1145/3591260

- 対象の言語 L_src は、単純型付きラムダ計算に積、和、iso-recursive な `μ` 型を足したもの。特殊化の単位は `def` で束縛したグローバルな定義で、相互再帰する定義は強連結成分を一つの `def` にする (6.3 節)。
- 注釈付きの言語 L_annot は、矢印、適用、ラムダの三か所に lambda set を付ける (4 節)。lambda set は具体的な集合、変数、`μa.σ` のいずれか。
- 推論 (4.2 節) は、定義ごとに新しい変数を置き、型の等式から lambda set の変数の等式を取り出して最も一般的な単一化子を求める。ラムダの包含の制約 (`ℓ ⊏ σ`) は、型に現れる変数なら定義の制約として残し、現れない変数なら最小の具体的な集合に決める (internalization)。自分を含む制約は `μ` で解く。推論が健全かつ完全であることを Isabelle/HOL で証明している。
- 特殊化 (5.1 節) は、入口から依存の逆順にたどり、使われた lambda set の具体的な値ごとに定義をコピーする。多相再帰がないので停止する。コピーへの参照の置き換えには、`μ` を展開した形でも一致を見る置き換え (μ-aware substitution) が要る。
- 下ろし方 (5.2 節) は、関数の型をキャプチャの直和に、ラムダを注入に、適用を `match` にする。
- 実装上の注意 (6 節)。lambda set を素朴に表すと大きさが指数的になるので、共通の部分を名前で共有する (メモ化)。置き換えを即座に行うと 2 乗の時間になるので、置き換えを遅延させる。
- 評価 (7 節)。Morphic で書いた 6 本 (calc、parse_json、primes_sieve、primes_iter、quicksort、unify) を、イテレータ、状態モナド、パーサコンビネータのライブラリの上で測った。MLton で 0.91 倍から 6.85 倍、OCaml で 1.08 倍から 3.45 倍、Morphic (比較対象は単相の defunctionalization) で最大 78.93 倍。バイナリの大きさは MLton で変わらず、Morphic で小さく、OCaml でやや大きくなった。
