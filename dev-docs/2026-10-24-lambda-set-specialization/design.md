# どのラムダかを型に持たせるクロージャ特殊化

## 目的

クロージャの呼び出しを、どのラムダを呼ぶかがコンパイル時に分かる場所では、直接呼び出しにする。
それを、クロージャが構造体のフィールドに入るときも、関数の結果として返るときも、`if` の分岐で
合流するときも、ループの状態に乗るときも、同じ一つの仕組みで行う。

仕組みは、型検査と単相化の終わったプログラムの関数の型に、「そこに届きうるラムダの集合」を
付けて推論し直すことである。Rust や C++ はラムダごとに固有の型を与えるので、`DSegtree<F>` の
`F` が何であるかを型が運ぶ。この設計は、それを言語仕様ではなく最適化として行う。手法は
Brandon らの lambda set specialization（以下 LSS。PLDI 2023、「付録 A」に要約）に拠る。

## 今のやり方と、その限界

main の `closure_specialization` は、ラムダを大域関数に持ち上げ（decapture）、既知のラムダを
受け取る関数の写しを作る（specialization）。「既知」は変数に付く知識で、ラムダに束縛された変数、
そのラムダを受け取った引数、捕捉リストのフィールド（1 段まで、narrowing）を追う。

クロージャが値として運ばれる経路は、ほかにもある。

- 利用者の構造体や union のフィールド
- 関数の結果
- `if` や `match` の合流
- `Std::loop` や `fold` が運ぶループの状態

変数に付く知識でこれらを追うには、経路ごとに変換が要る。試作（ブランチ
`struct-field-closure-spec`）は、構造体の引数の分割（`split_struct_args`）、引数をそのまま返す
部分の削除、case-of-case、合流の読み取りを足して、繰り返し回した。iterator の連鎖や遅延
セグメント木の一部では効いたが、getter と setter でクロージャを運ぶ構造体（cp-library の
`DSegtree`）では経路が 4 つ続き、4 つ目の「ループの状態の `if` での合流」で止まった。詳細は
「付録 B」にある。

もう一つの限界は停止性である。写しを作るたびに既知の値が育つ再帰（毎回クロージャを包み直す
関数）があるので、今のやり方は「写しの数の予算」で止めている。予算はテストの多くが数を固定する
ほど振る舞いに効いており、どの写しが作られるかが予算の消費順で決まる。

## 手法の要点

LSS は、関数の型の矢印ごとに lambda set を付ける。lambda set は、その型の値として実行時に
現れうるラムダの集合である。

```
twice : (I64 -α-> I64) -> I64 -> I64        // α は lambda set の変数
twice(|x| x + 2, 5)                          // α := { λ1 }
twice(if b { |x| x } else { |x| x + 2 }, 5)  // α := { λ2, λ1 }
```

- **推論。** 単相化の済んだプログラムに、矢印ごとに新しい変数を置き、型検査と同じ単一化で
  変数どうしを等しくする。部分型は使わないので、合流では二つの集合が一つになる。
- **多相性。** 大域関数の型に現れる変数は全称化する。`twice` は α について多相になり、呼び出し
  ごとに α の具体値が決まる。型に現れない変数は、そこへ流れ込むラムダの最小の集合に決める。
- **再帰。** 集合が自分を含むとき（ラムダが同じ集合のクロージャを捕捉するとき）は、再帰型と同じ
  `μ` で表す。大域関数の再帰は単相にし、多相再帰を作らない。
- **特殊化。** 大域関数を、呼び出しで決まった lambda set の具体値ごとに写す。多相再帰がない
  ので、写しの数は有限で、手続きは必ず停止する。予算は要らない。
- **下ろし方。** 関数の型は「各ラムダの捕捉の直和」になり、ラムダを作る式は直和への注入に、
  呼び出しは直和の `match` と直接呼び出しになる。集合が一つのラムダだけなら、値は捕捉そのもので、
  呼び出しは分岐のない直接呼び出しになる。

経路ごとの変換は要らない。構造体のフィールドも関数の結果も合流もループの状態も、どれも型の
単一化の中で扱われる。`DSegtree` の `set` が返す値の型は、`_op` の lambda set を含む
`DSegtree` の型なので、`if` で合流しても同じ型どうしの単一化になり、ループの次の周にも
同じ lambda set が届く。

## Fix への当てはめ

### 入力と置き場所

最適化の入口のプログラムは単相である。すべての大域値は具体的な型の instance で、すべての式が
基底の型を持つ。`unwrap_newtype` の後では `IO a` は `IOState -> (IOState, a)` という関数の型に
なっているので、IO のコードもこの最適化の対象になる。

新しいパスは、今の `closure_specialization` の位置に置く。つまり、`defunctionalize_fix`、
`inline`、`inline_local` の後、`uncurry` の前である。`inline` が combinator を利用者のコードに
展開した後のほうが、ラムダの数が少なく、集合も小さい。

### ラムダとその捕捉

推論の対象のラムダは次の二種類である。

- 式の中の `Expr::Lam`。捕捉はその自由変数である。
- 値として使われる大域関数（`f` を呼ばずに渡す）。捕捉は空である。

大域関数 `g = |a| |b| body` は、二つ目の `Lam` が `a` を捕捉するラムダで、`g(a)` はそれを作る式
である。部分適用に特別な扱いは要らない。

### 名前の付いた型

LSS の型は構造的で、構造体の中の矢印にはその場で変数が付く。Fix の構造体と union は名前の
付いた型なので、型の定義に lambda set の引数を足す。

```
type DSegtree m = struct { _n : I64, _unit : m, _op : (m, m) -> m, _elems : Array m };
// 推論の中では DSegtree⟨α⟩ m。α は _op の矢印の lambda set
```

- 定義が直接持つ矢印ごとに引数を一つ足す。型引数（`m`）に矢印が入る場合は、型引数の側の
  注釈がそのまま運ぶので、引数は要らない。
- 自分自身を含む型（`box union` で書いた連結リストの要素がクロージャ、など）は、再帰の中で同じ
  引数を共有させる。
- `Array`、`Option`、タプルも同じ扱いになる。`Array (I64 -> I64)` の要素の型の注釈は型引数が
  運ぶ。

特殊化では、型も lambda set の具体値ごとに写す。`DSegtree⟨{λmax}⟩ I64` は、`_op` のフィールドが
`λmax` の捕捉の型になった新しい構造体になる。写しには、フィールドの更新に使う punch 用の型
（`PUNCHED_TYPE_SYMBOL` の型）も要る。構築とパターンに埋め込まれた型の名前は写しの名前に
書き換え、getter や `mod_` などの instance も写しの型で作り直す。

### 推論

大域関数の呼び出しグラフの強連結成分を単位に、依存の順に推論する。

1. 型の矢印ごと、名前の付いた型の lambda set の引数ごとに、新しい変数を置く。
2. 型検査の規則（適用、`let`、`match` の腕の合流、構築とパターン、`if`）が等しいとする型を、
   単一化で等しくする。
3. 組み込み関数は、`BuiltinOpExpr` が持つ一般の型（`generic_ty`）を注釈の付いた型で
   instance にして単一化する。`array_get` の結果の型は、配列の要素の型と同じ変数を持つ。
4. 成分の型に現れる変数を全称化し、現れない変数を最小の集合に決める。自分を含む集合は `μ` で
   表す。

単一化は、変数の数にほぼ線形で済む。lambda set を書き下すと大きさが指数的になる例があるので、
集合は名前を付けて共有する（「付録 A」の実装上の注意）。

### 実行時のクロージャが要る場所

いくつかの場所は、実行時のクロージャ（関数ポインタと、box に入った捕捉の組）を要する。

- `Std::fix`（`FixCombinatorOp`）。`defunctionalize_fix` が外せなかったもの。
- `Destructor` の `_dtor`。解放の traverser から呼ばれる。
- エントリの IO 値と、`FFI_EXPORT` された値。
- `env_operand` を持つ組み込み関数（`with_retained`、`borrow_ptr`、`mutate_ptr`）は、捕捉が空の
  クロージャなら受け取れる。今の `decapture_scope_functions` がその形を作っている。

これらの位置の lambda set には、特別な要素「消去済み」を入れる。消去済みを含む集合は、今の
クロージャの表現のまま下ろす。そこへ流れ込むラムダは作るときに今のクロージャになり、そこから
呼ぶ呼び出しは今の間接呼び出しになる。消去済みの集合は、単一化で他の集合と合わさると、
合わさった先も消去済みにする。

### 下ろし方と参照カウント

- **一つのラムダの集合。** 値はそのラムダの捕捉の構造体（今の `#CapList`、unbox）で、呼び出しは
  持ち上げた大域関数の直接呼び出しになる。捕捉が空なら値の大きさは 0 になる（`#674` の扱い）。
- **二つ以上のラムダの集合。** 値は、捕捉を payload に持つ unbox の union で、呼び出しはその
  `match` と、腕ごとの直接呼び出しになる。
- **`μ` の集合。** 捕捉が同じ集合のクロージャを含むので、unbox では大きさが決まらない。
  `box union` にする。

どの表現も、今の型（構造体、union、box）で書ける。参照カウントは今の RC IR がそのまま扱う。

### 置き換わるもの

- `closure_specialization`（decapture、narrowing、予算）
- `split_struct_args`。クロージャを構造体の外へ出すためのパスで、構造体の型が lambda set を
  運ぶので要らなくなる。
- 試作で足した、引数をそのまま返す部分の削除、合流の読み取り、variant による特殊化

`collapse_constructions`（case-of-case を含む）は、構築とその分解を打ち消す一般の変換として
残す。`decapture_scope_functions`、`uncurry`、`move_bodies_into_callers` は、新しい出力の形に
合わせて見直す。

## 確かめ方

- **意味が変わらないこと。** 全テスト、speedtest のコーパス、LangArena の出力が変わらない
  こと。参照カウントは、コーパスを memcheck に通して漏れと二重解放がないことを見る。
- **効くこと。** speedtest を `--langarena` で測り、全ケースを報告する。cp_dsegtree、
  cp_ldsegtree、cp_ldsegtree_fold_act、iterator の連鎖、`Calculator::Interpreter`、モナドの
  スタック（`StateT` を `IO` に重ねたもの）を、効くはずのケースとして個別に見る。
- **写しの数。** 予算がなくなるので、写しの数とコンパイル時間を LangArena で測り、今のやり方と
  比べる。LSS の論文の 6 本ではバイナリの大きさはほとんど変わっていないが、Fix の iterator は型が
  深く、同じとは限らない。

## 段取り

1. 推論だけを実装し、プログラムを変えずに、各位置の lambda set をダンプに出す。全テストで推論が
   失敗しないこと、ダンプが手で確かめた例と合うことを見る。
2. 一つのラムダの集合だけを下ろす（それ以外の集合は消去済みとして扱う）。今の
   `closure_specialization` と並べて測れる。
3. 二つ以上のラムダの集合を、union と `match` で下ろす。
4. `μ` の集合を `box union` で下ろす。
5. 置き換わるパスを消し、後段のパスを新しい形に合わせる。

各段で全テストと speedtest を通す。

## 未決の問い

- **名前の付いた型の写しを、どこまで作るか。** 型の写しは、getter や `mod_` の instance の写しを
  伴う。写しの数が増えたときにコンパイル時間がどう伸びるかは、段取りの 2 で測る。
- **二つ以上のラムダの集合を、いつ下ろすか。** 呼び出しが `match` になるので、腕が多いと命令数が
  増えうる。今のクロージャ（間接呼び出し）とどちらが速いかは、ケースによる。下ろす条件（集合の
  大きさ）を測って決める。
- **型の名前で型を見分けている箇所。** `is_io`、`is_string`、`is_destructor_object` などは、
  写しの型を元の型と同じに扱う必要がある。写しに元の型を記録するか、写す前に答えを決めて
  おくかを決める。

## 付録 A: LSS の論文の要約

William Brandon, Benjamin Driscoll, Frank Dai, Wilson Berkow, Mae Milano. *Better
Defunctionalization through Lambda Set Specialization.* Proc. ACM Program. Lang. 7, PLDI,
Article 146 (2023). https://doi.org/10.1145/3591260

- 対象の言語 L_src は、単純型付きラムダ計算に積、和、iso-recursive な `μ` 型を足したもの。
  特殊化の単位は `def` で束縛した大域定義で、相互再帰する定義は強連結成分を一つの `def` にする
  （6.3 節）。
- 注釈付きの言語 L_annot は、矢印、適用、ラムダの三か所に lambda set を付ける（4 節）。
  lambda set は具体的な集合、変数、`μa.σ` のいずれか。
- 推論（4.2 節）は、定義ごとに新しい変数を置き、型の等式から lambda set の変数の等式を取り
  出して最も一般的な単一化子を求める。ラムダの包含の制約（`ℓ ⊏ σ`）は、型に現れる変数なら
  定義の制約として残し、現れない変数なら最小の具体的な集合に決める（internalization）。
  自分を含む制約は `μ` で解く。推論が健全かつ完全であることを Isabelle/HOL で証明している。
- 特殊化（5.1 節）は、入口から依存の逆順にたどり、使われた lambda set の具体値ごとに定義を
  写す。多相再帰がないので停止する。写しへの参照の置き換えには、`μ` を展開した形でも一致を
  見る置き換え（μ-aware substitution）が要る。
- 下ろし方（5.2 節）は、関数の型を捕捉の直和に、ラムダを注入に、適用を `match` にする。
- 実装上の注意（6 節）。lambda set を素朴に表すと大きさが指数的になるので、共通の部分を名前で
  共有する（メモ化）。置き換えを即座に行うと 2 乗の時間になるので、置き換えを遅延させる。
- 評価（7 節）。Morphic で書いた 6 本（calc、parse_json、primes_sieve、primes_iter、quicksort、
  unify）を、iterator、状態モナド、パーサ combinator のライブラリの上で測った。MLton で 0.91 倍
  から 6.85 倍、OCaml で 1.08 倍から 3.45 倍、Morphic（比較対象は単相の defunctionalization）で
  最大 78.93 倍。バイナリの大きさは MLton で変わらず、Morphic で小さく、OCaml でやや大きく
  なった。

## 付録 B: 変数に付く知識で追った試作の記録

試作は、ブランチ `struct-field-closure-spec`（コミットしていない作業ツリー）にある。次の変換を
2 周回した。

- 構造体の引数の分割
- 引数をそのまま返す部分の削除（互いの結果を返し合う関数の集まりを単位に）
- case-of-case を含む構築の読み取り
- 既知の値（`g(c)` と union の variant）による関数の写し

RC IR の解放の順を名前の hash によらず固定した版どうしで、speedtest の 122 本を比べた結果（命令数）:
0.01% 以内が 93 本、動いたもの 29 本。cp_ldsegtree_fold_act -44.46%、iter_flatten -12.98%、
Calculator::Interpreter -4.49%、Etc::Words -2.27%、Json::Generate -1.62%、Json::ParseDom
-1.03% など 21 本が減り、iter_filter_map +13.56%、cp_dsegtree +2.85%、Distance::NGram
+2.25%、index_syntax +1.54%、Brainfuck::Array +0.43%、Template::Parse +0.02% が増えた。
Json::ParseMapping +17.18% と Etc::LogParser +1.17% は、`--cu-size inf` で測るとコンパイル単位の
分け方による揺れだった。

cp_dsegtree では、クロージャ `_op` が次の四か所を通ってループを回る。試作は最初の三つを通り抜けた
が、四つ目で止まった。

1. getter で 1 フィールドずつ読む構造体（全フィールドを束ねるパターンがないと分割しない）
2. `mod__elems` による更新（`struct_punch` と `struct_plug_in` の組み込み関数）
3. `Std::loop` が返す結果
4. `range(0, q).fold` の状態 `(tree, acc)` を、`if` で `tree.set(...)` の結果と元の `tree` から
   選ぶ合流

既存の cp_ldsegtree（-0.67%）も 4 と同じ形で止まっている。`if` のない cp_ldsegtree_fold_act
（-44.46%）だけが最後まで通った。
